# Acceptance Criteria

เอกสารนี้กำหนดเกณฑ์ยอมรับ (Given-When-Then) ของทุกรหัส FR/NFR ใน [[backlog]] จัดกลุ่มตามหัวข้อฟีเจอร์เดียวกับ [[feature-list]] เพื่อให้ไล่อ่านคู่กันได้ง่าย อ้างอิงพฤติกรรมจาก [[feature-list]] และ [[user-journey]] เป็นหลัก (spec ต้นทางคือ [[20260828-01-flood-damage-survey]])

ระดับความสำคัญ (สูง/กลาง/ต่ำ) ที่กำกับท้ายรหัสแต่ละหัวข้อย่อยดึงมาจาก [[backlog]] โดยตรงเสมอ

## 1. บันทึกข้อมูลอาคารและสภาพแวดล้อม

อ้างอิง: [[feature-list#1. บันทึกข้อมูลอาคารและสภาพแวดล้อม|ฟีเจอร์ 1]] · [[user-journey#Journey: ผู้สำรวจภาคสนามลงพื้นที่สำรวจอาคาร|journey ผู้สำรวจภาคสนาม]] · บทบาท: ผู้สำรวจภาคสนาม

#### FR-01 (สูง) — [[20260828-01-flood-damage-survey#4.1 ข้อมูลอาคารและสภาพแวดล้อม|บันทึกข้อมูลทั่วไปของอาคาร]]

- AC-1: Given ผู้สำรวจภาคสนามเข้าสู่ระบบและเริ่มบันทึกแบบสำรวจอาคารใหม่ (ออนไลน์หรือออฟไลน์ก็ได้), When กรอกข้อมูลทั่วไปของอาคารครบทุกช่องบังคับ (ชื่ออาคาร เจ้าของ ที่ตั้ง การใช้สอย กรรมสิทธิ์) แล้วบันทึก, Then ระบบบันทึกข้อมูลทั่วไปไว้กับรายการสำรวจอาคารนั้นสำเร็จและอนุญาตให้ไปหมวดถัดไปได้
- AC-2: Given ผู้สำรวจกำลังกรอกข้อมูลทั่วไปของอาคาร, When เว้นว่างช่องข้อมูลบังคับข้อใดข้อหนึ่งแล้วพยายามไปหมวดถัดไป, Then ระบบแจ้งเตือนว่าต้องกรอกข้อมูลให้ครบก่อน และไม่อนุญาตให้ข้ามหมวดจนกว่าจะกรอกครบ

#### FR-02 (สูง) — [[20260828-01-flood-damage-survey#4.1 ข้อมูลอาคารและสภาพแวดล้อม|บันทึกพิกัด GPS ของอาคาร]]

- AC-1: Given ผู้สำรวจอยู่ที่หน้างานและเปิดหน้าบันทึกข้อมูลอาคาร, When ระบบขอตำแหน่งปัจจุบันจากอุปกรณ์และรับสัญญาณ GPS ได้ตามเกณฑ์ความแม่นยำ (NFR-06), Then ระบบบันทึกพิกัด GPS ผูกกับอาคารนั้นสำเร็จ
- AC-2: Given อุปกรณ์ยังไม่สามารถรับสัญญาณ GPS ที่มีความแม่นยำตามเกณฑ์ได้, When ผู้สำรวจพยายามบันทึกพิกัด, Then ระบบแจ้งสถานะว่ายังไม่สามารถระบุพิกัดที่แม่นยำเพียงพอ และไม่บันทึกพิกัดนั้นจนกว่าจะรับสัญญาณได้ตามเกณฑ์

#### FR-03 (สูง) — [[20260828-01-flood-damage-survey#4.1 ข้อมูลอาคารและสภาพแวดล้อม|บันทึกข้อมูลทางกายภาพของอาคาร]]

- AC-1: Given ผู้สำรวจกรอกข้อมูลทั่วไปของอาคารแล้ว, When กรอกข้อมูลทางกายภาพ (จำนวนชั้น พื้นที่ใช้สอย ชนิดโครงสร้าง วัสดุหลัก) ครบถ้วนแล้วบันทึก, Then ระบบบันทึกข้อมูลทางกายภาพไว้กับอาคารนั้นสำเร็จ
- AC-2: Given ผู้สำรวจกรอกจำนวนชั้นหรือพื้นที่เป็นค่าที่ไม่ใช่ตัวเลขหรือเป็นค่าติดลบ, When พยายามบันทึก, Then ระบบแจ้งเตือนว่าข้อมูลไม่ถูกต้องและไม่บันทึกค่านั้น

#### FR-04 (สูง) — [[20260828-01-flood-damage-survey#4.1 ข้อมูลอาคารและสภาพแวดล้อม|บันทึกอันตรายของสภาพแวดล้อมโดยรอบอาคาร]]

- AC-1: Given ผู้สำรวจตรวจพบอันตรายจากสภาพแวดล้อมโดยรอบ (เช่น อาคารข้างเคียง ลาดเชิงเขา ดินทรุดตัว), When เลือก/บันทึกรายการอันตรายที่พบ, Then ระบบบันทึกรายการอันตรายโดยรอบไว้กับอาคารนั้นสำเร็จ
- AC-2: Given ไม่พบอันตรายจากสภาพแวดล้อมโดยรอบเลย, When ผู้สำรวจระบุว่า "ไม่พบอันตราย" แล้วบันทึก, Then ระบบบันทึกสถานะไม่พบอันตรายและอนุญาตให้ไปหมวดถัดไปได้โดยไม่บังคับให้เลือกอันตรายใดๆ

#### NFR-06 (กลาง) — [[20260828-01-flood-damage-survey#5. Non-Functional Requirements|Accuracy (ความแม่นยำของพิกัด GPS)]]

- AC-1: Given อุปกรณ์รับสัญญาณ GPS ได้ขณะบันทึกอาคาร, When ระบบบันทึกพิกัด, Then ค่าความแม่นยำ (accuracy) ของพิกัดต้องอยู่ในเกณฑ์ที่ยอมรับได้สำหรับงานสำรวจภาคสนาม มิฉะนั้นระบบต้องแจ้งเตือนผู้สำรวจว่าความแม่นยำต่ำกว่าเกณฑ์ก่อนยืนยันบันทึก

## 2. ประเมินความเสียหายโครงสร้างและส่วนประกอบอาคารแยกตามหมวด

อ้างอิง: [[feature-list#2. ประเมินความเสียหายโครงสร้างและส่วนประกอบอาคารแยกตามหมวด|ฟีเจอร์ 2]] · บทบาท: ผู้สำรวจภาคสนาม

#### FR-05 (สูง) — [[20260828-01-flood-damage-survey#4.2 การประเมินความเสียหายโครงสร้าง|บันทึกความเสียหายที่สังเกตจากภายนอกอาคาร]]

- AC-1: Given ผู้สำรวจตรวจสอบภายนอกอาคาร, When บันทึกลักษณะ/ระดับความเสียหายที่สังเกตเห็นจากภายนอก, Then ระบบบันทึกข้อมูลความเสียหายภายนอกไว้กับอาคารนั้นสำเร็จ
- AC-2: Given ผู้สำรวจยังไม่เลือกระดับความเสียหายของหมวดภายนอกอาคาร, When พยายามไปหมวดถัดไป, Then ระบบแจ้งเตือนให้กรอกหมวดนี้ให้ครบก่อน

#### FR-06 (สูง) — [[20260828-01-flood-damage-survey#4.2 การประเมินความเสียหายโครงสร้าง|บันทึกความเสียหายของโครงสร้างอาคารแยกตามชนิดวัสดุและตำแหน่ง]]

- AC-1: Given ผู้สำรวจตรวจพบความเสียหายโครงสร้าง, When เลือกชนิดวัสดุ (ไม้/คอนกรีตเสริมเหล็ก/เหล็กรูปพรรณ) และระบุตำแหน่ง/ระดับความเสียหาย, Then ระบบบันทึกความเสียหายโครงสร้างแยกตามชนิดวัสดุและตำแหน่งสำเร็จ
- AC-2: Given อาคารมีโครงสร้างมากกว่าหนึ่งชนิดวัสดุ, When ผู้สำรวจบันทึกความเสียหายของแต่ละชนิดวัสดุแยกกัน, Then ระบบเก็บบันทึกแยกตามชนิดวัสดุโดยไม่ปะปนกัน

#### FR-07 (กลาง) — [[20260828-01-flood-damage-survey#4.2 การประเมินความเสียหายโครงสร้าง|บันทึกความเสียหายของโครงหลังคา]]

- AC-1: Given ผู้สำรวจตรวจพบความเสียหายของโครงหลังคา, When บันทึกระดับความเสียหายของโครงหลังคา, Then ระบบบันทึกข้อมูลไว้กับอาคารนั้นสำเร็จ

#### FR-08 (สูง) — [[20260828-01-flood-damage-survey#4.2 การประเมินความเสียหายโครงสร้าง|บันทึกความเสียหายของส่วนประกอบอาคาร]]

- AC-1: Given ผู้สำรวจตรวจพบความเสียหายของส่วนประกอบอาคาร (ผนัง/ฝ้าเพดาน/วัสดุมุงหลังคา), When เลือกส่วนประกอบและระบุระดับความเสียหาย, Then ระบบบันทึกความเสียหายของส่วนประกอบอาคารแยกตามชนิดสำเร็จ
- AC-2: Given ผู้สำรวจข้ามหมวดส่วนประกอบอาคารโดยไม่กรอก, When พยายามไปหมวดถัดไป, Then ระบบแจ้งเตือนให้กรอกให้ครบก่อน

#### FR-09 (กลาง) — [[20260828-01-flood-damage-survey#4.2 การประเมินความเสียหายโครงสร้าง|บันทึกความเสียหายของระบบไฟฟ้าและระบบอื่นๆ]]

- AC-1: Given ผู้สำรวจตรวจพบความเสียหายของระบบไฟฟ้า/ระบบอื่นๆ, When บันทึกระดับความเสียหายของระบบไฟฟ้า, Then ระบบบันทึกข้อมูลไว้กับอาคารนั้นสำเร็จ

## 3. สรุปผลประเมินเป็น 3 ระดับสีพร้อมเกณฑ์อ้างอิงคู่มือ

อ้างอิง: [[feature-list#3. สรุปผลประเมินเป็น 3 ระดับสีพร้อมเกณฑ์อ้างอิงคู่มือ|ฟีเจอร์ 3]] · บทบาท: ผู้สำรวจภาคสนาม

#### FR-10 (สูง) — [[20260828-01-flood-damage-survey#4.2 การประเมินความเสียหายโครงสร้าง|สรุปผลการประเมินความเสียหายเป็น 3 ระดับสี]]

- AC-1: Given ผู้สำรวจกรอกความเสียหายครบทุกหมวดที่บังคับแล้ว, When สรุปผลประเมินเป็นระดับสี, Then ระบบแสดง/บันทึกผลสรุปเป็นหนึ่งในสามระดับ (เขียว/เหลือง/แดง) พร้อมข้อแนะนำเพิ่มเติมที่สอดคล้องกับระดับนั้น
- AC-2: Given ผู้สำรวจยังกรอกความเสียหายไม่ครบทุกหมวดที่บังคับ, When พยายามสรุปผลเป็นระดับสี, Then ระบบไม่อนุญาตให้สรุปผลจนกว่าจะกรอกข้อมูลที่จำเป็นครบถ้วน และแจ้งเตือนหมวดที่ยังขาด

#### FR-11 (สูง) — [[20260828-01-flood-damage-survey#4.2 การประเมินความเสียหายโครงสร้าง|แสดงเกณฑ์อ้างอิงจากคู่มือประกอบแต่ละหมวดการประเมินในแอป]]

- AC-1: Given ผู้สำรวจกำลังกรอกหมวดการประเมินความเสียหายหมวดใดหมวดหนึ่ง, When เลือกเปิดดูเกณฑ์อ้างอิงคู่มือของหมวดนั้น, Then ระบบแสดงเนื้อหาเกณฑ์อ้างอิงคู่มือ (deep link ตามเลขหน้าที่เกี่ยวข้อง) โดยไม่ต้องออกจากหน้ากรอกข้อมูลปัจจุบัน
- AC-2: Given อุปกรณ์ไม่มีสัญญาณอินเทอร์เน็ตที่หน้างาน, When ผู้สำรวจเปิดดูเกณฑ์อ้างอิงคู่มือ, Then ระบบยังคงแสดงเนื้อหาเกณฑ์อ้างอิงได้ตามปกติ สอดคล้องกับการทำงานออฟไลน์เต็มรูปแบบ ([[acceptance-criteria#NFR-01 (สูง) — Availability Offline Support|NFR-01]])

## 4. ถ่ายภาพและประเมินรอยร้าวด้วย AI พร้อมทางเลือกกรอกเอง (Human-in-the-loop)

อ้างอิง: [[feature-list#4. ถ่ายภาพและประเมินรอยร้าวด้วย AI พร้อมทางเลือกกรอกเอง (Human-in-the-loop)|ฟีเจอร์ 4]] · บทบาท: ผู้สำรวจภาคสนาม

หมายเหตุอัปเดต (2026-09-03): ผู้ใช้ปิดข้อสมมติจำนวนภาพสูงสุดต่อบริเวณของ FR-12 = **5 ภาพ** เพิ่ม AC-3 (negative case พยายามถ่ายภาพเกิน 5 ภาพต่อบริเวณ) ให้กับ FR-12 ด้านล่าง

#### FR-12 (สูง) — [[20260828-01-flood-damage-survey#4.3 ภาพถ่ายและ AI วิเคราะห์รอยร้าว|ถ่ายภาพประกอบความเสียหายผูกกับตำแหน่ง/บริเวณ]]

- AC-1: Given ผู้สำรวจต้องการบันทึกภาพประกอบความเสียหาย ณ ตำแหน่ง/บริเวณหนึ่ง, When ถ่ายภาพและระบุตำแหน่ง/บริเวณที่ภาพนั้นเกี่ยวข้อง, Then ระบบบันทึกภาพผูกกับตำแหน่งนั้นไว้กับอาคารสำเร็จ
- AC-2: Given อุปกรณ์ไม่มีสัญญาณอินเทอร์เน็ต, When ผู้สำรวจถ่ายภาพประกอบ, Then ระบบเก็บภาพไว้ในเครื่องก่อนและรอซิงค์เมื่อมีสัญญาณ โดยไม่บล็อกการทำงานต่อ
- AC-3 (เพิ่ม 2026-09-03 — ปิดข้อสมมติจำนวนภาพสูงสุด): Given บริเวณหนึ่งมีภาพที่ผูกไว้แล้วครบ 5 ภาพ (จำนวนสูงสุดตามที่ยืนยันแล้ว), When ผู้สำรวจพยายามถ่าย/แนบภาพเพิ่มอีกสำหรับบริเวณเดียวกัน, Then ระบบปฏิเสธการเพิ่มภาพใหม่และแจ้งว่าถึงจำนวนสูงสุด 5 ภาพต่อบริเวณแล้ว โดยไม่ทำให้ภาพที่มีอยู่เดิมสูญหายหรือถูกเขียนทับ (ผู้สำรวจต้องลบภาพเดิมออกก่อนหากต้องการแทนที่ หรือระบุเป็นบริเวณอื่นแทน)

#### FR-13 (สูง) — [[20260828-01-flood-damage-survey#4.3 ภาพถ่ายและ AI วิเคราะห์รอยร้าว|วิเคราะห์ภาพถ่ายรอยร้าวด้วย AI]]

ขอบเขต: FR-13 ครอบคลุมเฉพาะกรณี AI วิเคราะห์ภาพสำเร็จเท่านั้น กรณี AI วิเคราะห์ไม่สำเร็จอยู่ในขอบเขตของ [[acceptance-criteria#FR-28 (สูง) — ตรวจจับและแจ้งกรณี AI วิเคราะห์ภาพรอยร้าวไม่สำเร็จ พร้อมทางเลือกถ่ายภาพใหม่|FR-28]] แทน (ปรับตามการแก้ไข spec ล่าสุดที่เพิ่ม FR-28/FR-29)

- AC-1: Given มีภาพถ่ายรอยร้าวที่ผูกกับตำแหน่งแล้วและผู้สำรวจเลือกให้ AI ช่วยวิเคราะห์, When ผู้สำรวจสั่งให้ AI วิเคราะห์ภาพ (ทำงานได้แม้ออฟไลน์ ตามขอบเขตฟีเจอร์ 1-6 ใน NFR-01) และ AI วิเคราะห์สำเร็จ, Then ระบบแสดงผลประมาณความกว้างรอยแตกร้าวและระดับความเสียหายที่ AI เสนอเป็นค่าตั้งต้น (draft) ให้ผู้สำรวจเห็นก่อนยืนยัน

#### FR-14 (สูง) — [[20260828-01-flood-damage-survey#4.3 ภาพถ่ายและ AI วิเคราะห์รอยร้าว|ให้ผู้สำรวจยืนยัน/แก้ไขผลวิเคราะห์ของ AI ก่อนบันทึกเป็นผลจริง]]

- AC-1: Given AI เสนอผลวิเคราะห์ความกว้างรอยร้าวและระดับความเสียหายเป็นค่าตั้งต้นแล้ว (กรณี AI วิเคราะห์สำเร็จ ตาม FR-13), When ผู้สำรวจตรวจสอบแล้วเห็นว่าถูกต้องและกดยืนยัน, Then ระบบบันทึกผลนั้นเป็นผลจริงของอาคารนั้น พร้อมบันทึกว่าเป็นผลที่ยืนยันตามที่ AI เสนอ (ไม่มีการแก้ไข)
- AC-2: Given AI เสนอผลวิเคราะห์เป็นค่าตั้งต้น, When ผู้สำรวจเห็นว่าไม่ถูกต้องและแก้ไขค่าความกว้างรอยร้าว/ระดับความเสียหายก่อนกดยืนยัน, Then ระบบบันทึกค่าที่ผู้สำรวจแก้ไขเป็นผลจริง และบันทึกประวัติว่าเดิม AI เสนอค่าใด ผู้สำรวจแก้เป็นค่าใด ([[acceptance-criteria#NFR-05 (สูง) — Auditability Accountability (ประวัติการแก้ไขผล AI)|NFR-05]])
- AC-3: Given AI ประมวลผลภาพเสร็จและเสนอผลตั้งต้นแล้ว, When ผู้สำรวจยังไม่กดยืนยัน/แก้ไข, Then ระบบต้องไม่บันทึกผลของ AI เป็นผลสรุปสุดท้ายโดยอัตโนมัติไม่ว่าจะผ่านไปนานเท่าใด

#### FR-28 (สูง) — [[20260828-01-flood-damage-survey#4.3 ภาพถ่ายและ AI วิเคราะห์รอยร้าว|ตรวจจับและแจ้งกรณี AI วิเคราะห์ภาพรอยร้าวไม่สำเร็จ พร้อมทางเลือกถ่ายภาพใหม่]]

หมายเหตุ: เกณฑ์ทางเทคนิคที่ใช้ตัดสินว่า AI "วิเคราะห์ไม่สำเร็จ" (เช่น confidence score) ยังไม่กำหนด รอขั้นตอนออกแบบเชิงเทคนิค ([[20260828-01-flood-damage-survey|spec หัวข้อ 6 ข้อ 8]]) — AC ด้านล่างเขียนเชิงพฤติกรรมที่สังเกตได้เท่านั้น ไม่อ้างตัวเลข threshold

- AC-1: Given ผู้สำรวจสั่งให้ AI วิเคราะห์ภาพถ่ายรอยร้าว, When AI ประมวลผลแล้วไม่สามารถวิเคราะห์ภาพนั้นได้สำเร็จ (เช่น ภาพเบลอ แสงไม่เพียงพอ หรือไม่พบรอยร้าวในภาพ), Then ระบบแจ้งสาเหตุที่วิเคราะห์ไม่สำเร็จให้ผู้สำรวจทราบ พร้อมเสนอทางเลือกถ่ายภาพใหม่ทันทีในหน้างานเดียวกัน โดยไม่บันทึกผลวิเคราะห์ที่ไม่สมบูรณ์เป็นผลจริง
- AC-2: Given ระบบแจ้งว่า AI วิเคราะห์ไม่สำเร็จและเสนอให้ถ่ายภาพใหม่, When ผู้สำรวจเลือกถ่ายภาพใหม่, Then ระบบพาผู้สำรวจกลับไปยังขั้นตอนถ่ายภาพประกอบความเสียหาย (FR-12) เพื่อถ่ายภาพใหม่แล้ววนกลับมาให้ AI วิเคราะห์ได้อีกครั้ง
- AC-3: Given ระบบแจ้งว่า AI วิเคราะห์ไม่สำเร็จและเสนอให้ถ่ายภาพใหม่, When ผู้สำรวจเลือกไม่ถ่ายภาพใหม่, Then ระบบพาผู้สำรวจไปยังเส้นทางกรอกระดับความเสียหายด้วยตนเอง ([[acceptance-criteria#FR-29 (สูง) — กรอกระดับความเสียหายของรอยร้าวด้วยตนเองโดยไม่ต้องพึ่ง AI|FR-29]]) แทนการบังคับให้ถ่ายภาพใหม่

#### FR-29 (สูง) — [[20260828-01-flood-damage-survey#4.3 ภาพถ่ายและ AI วิเคราะห์รอยร้าว|กรอกระดับความเสียหายของรอยร้าวด้วยตนเองโดยไม่ต้องพึ่ง AI]]

สำคัญ: เส้นทางนี้เป็น**เส้นทางใช้งานปกติ ไม่ใช่ทางออกฉุกเฉิน** ต้องใช้งานได้เสมอโดยไม่ต้องรอให้ AI วิเคราะห์ไม่สำเร็จก่อน

- AC-1: Given ผู้สำรวจถ่ายภาพประกอบความเสียหายที่มีรอยร้าวไว้แล้ว, When ผู้สำรวจเลือกไม่ให้ AI ช่วยวิเคราะห์ตั้งแต่แรก (เลือกกรอกเองทันทีโดยยังไม่เคยลองให้ AI วิเคราะห์เลย), Then ระบบอนุญาตให้ผู้สำรวจกรอกความกว้างรอยร้าว/ระดับความเสียหายด้วยตนเองได้ทันที และบันทึกเป็นผลจริงเมื่อยืนยัน
- AC-2: Given AI วิเคราะห์ภาพไม่สำเร็จและผู้สำรวจเลือกไม่ถ่ายภาพใหม่ (ตาม FR-28 AC-3), When ผู้สำรวจกรอกความกว้างรอยร้าว/ระดับความเสียหายด้วยตนเอง, Then ระบบบันทึกค่าที่กรอกเป็นผลจริงของรอยร้าวนั้นสำเร็จเช่นเดียวกับเส้นทางอื่น
- AC-3: Given ผู้สำรวจกำลังกรอกระดับความเสียหายของรอยร้าวด้วยตนเอง, When เว้นว่างค่าที่บังคับกรอก (เช่น ระดับความเสียหาย) แล้วพยายามยืนยัน, Then ระบบแจ้งเตือนว่าต้องกรอกให้ครบก่อนจึงจะบันทึกเป็นผลจริงได้

#### NFR-05 (สูง) — [[20260828-01-flood-damage-survey#5. Non-Functional Requirements|Auditability / Accountability (ประวัติการแก้ไขผล AI)]]

ขอบเขต (ปรับปรุง 2026-09-02 ตามสัญญาณ `NEEDS_TEST_PLAN_SYNC` จาก `backlog-auditor`): เดิมหัวข้อนี้ครอบคลุมเฉพาะประวัติการแก้ไขผล AI (FR-14) และเชื่อมโยงกับการแก้ไขความขัดแย้งด้วยมือ (FR-31, ดูหัวข้อ 15) — [[db-spec#7.2 AuditTrailEntry|db-spec §7.2 AuditTrailEntry]] และ operation [[api-spec#14.1 ซิงค์ข้อมูลแบบสำรวจที่ค้างจากอุปกรณ์|14.1]]/[[api-spec#14.2 ตรวจสอบ/แก้ไขความขัดแย้งของข้อมูลที่ซิงค์|14.2]] ขยายขอบเขต NFR-05 ให้ครอบคลุมผลการซิงค์ข้อมูลอัตโนมัติของฟีเจอร์ 13 ด้วย (ซิงค์สำเร็จ/ตรวจพบความขัดแย้ง) พร้อมกฎ "ผู้กระทำ" แบบมีเงื่อนไข: **บังคับต้องระบุผู้กระทำสำหรับเหตุการณ์ที่มนุษย์เป็นผู้ทำ** (ยืนยัน/แก้ไขผล AI ของ FR-14, รับรองผล/ส่งกลับแก้ไขของ FR-18/FR-19, แก้ไขความขัดแย้งด้วยมือของ FR-31, สร้าง/แก้ไข/ปิด-เปิดใช้งานบัญชีผู้ใช้ของ FR-21) **แต่ไม่บังคับสำหรับเหตุการณ์ที่ระบบเป็นผู้บันทึกเอง** (ซิงค์สำเร็จ/ตรวจพบความขัดแย้งของฟีเจอร์ 13) AC-2 ถึง AC-4 ด้านล่างครอบคลุมส่วนที่ขยายนี้

- AC-1: Given ผู้สำรวจยืนยันหรือแก้ไขผลวิเคราะห์ของ AI, When การกระทำนั้นถูกบันทึก, Then ระบบเก็บประวัติการเปลี่ยนแปลง (ค่าที่ AI เสนอเดิม ค่าที่ผู้สำรวจยืนยัน/แก้ไข ผู้ทำรายการ และเวลา) ไว้ตรวจสอบย้อนหลังได้ครบถ้วน และประวัตินี้ต้องไม่สามารถแก้ไขย้อนหลังได้
- AC-2: Given ระบบซิงค์ข้อมูลของอาคารหนึ่งจากอุปกรณ์ขึ้นเซิร์ฟเวอร์สำเร็จ (ไม่ว่าจะเป็นการซิงค์ครั้งแรกหรือ merge อัตโนมัติสำเร็จตาม [[acceptance-criteria#NFR-02 (สูง) — Performance / Reliability|NFR-02]]), When การซิงค์เสร็จสมบูรณ์, Then ระบบต้องบันทึกประวัติการซิงค์สำเร็จของอาคารนั้นไว้เสมอ (ระบุอาคารที่เกี่ยวข้องและเวลาที่ซิงค์สำเร็จ) โดยไม่บังคับต้องระบุผู้กระทำ เนื่องจากเป็นเหตุการณ์ที่ระบบเป็นผู้บันทึกเอง — ให้ระบุอุปกรณ์ต้นทางไว้ในหมายเหตุประกอบแทน
- AC-3: Given ระบบตรวจพบว่าข้อมูลของอาคารเดียวกันถูกแก้ไขจากหลายอุปกรณ์จนไม่สามารถ merge อัตโนมัติได้ ([[acceptance-criteria#NFR-03 (สูง) — Data Integrity|NFR-03]]), When ระบบตัดสินว่า merge ไม่ได้และตั้งสถานะ "รอแก้ไขความขัดแย้ง" ให้อาคารนั้น, Then ระบบต้องบันทึกประวัติว่าตรวจพบความขัดแย้งของข้อมูลไว้เสมอ (ระบุอาคารที่เกี่ยวข้องและเวลาที่ตรวจพบ) โดยไม่บังคับต้องระบุผู้กระทำเช่นเดียวกับ AC-2
- AC-4 (ป้องกัน regression ของกฎผู้กระทำแบบมีเงื่อนไข): Given เหตุการณ์ที่มนุษย์เป็นผู้กระทำจริง (เช่น ยืนยัน/แก้ไขผล AI ตาม FR-14, รับรองผล/ส่งกลับแก้ไขตาม FR-18/FR-19, แก้ไขความขัดแย้งของข้อมูลด้วยมือตาม FR-31, สร้าง/แก้ไข/ปิด-เปิดใช้งานบัญชีผู้ใช้ตาม FR-21), When ระบบพยายามบันทึกประวัติของเหตุการณ์เหล่านี้โดยไม่มีการระบุผู้กระทำ, Then ระบบต้องปฏิเสธการบันทึกนั้นเสมอ (ห้ามบันทึกประวัติการกระทำของมนุษย์แบบไม่ระบุผู้กระทำไม่ว่ากรณีใด)

## 5. วาดภาพประกอบเพิ่มเติม

อ้างอิง: [[feature-list#5. วาดภาพประกอบเพิ่มเติม|ฟีเจอร์ 5]] · บทบาท: ผู้สำรวจภาคสนาม

#### FR-15 (กลาง) — [[20260828-01-flood-damage-survey#4.3 ภาพถ่ายและ AI วิเคราะห์รอยร้าว|วาด/เขียนภาพประกอบเพิ่มเติม]]

- AC-1: Given ผู้สำรวจต้องการระบุตำแหน่งความเสียหายที่ถ่ายภาพลำบาก, When เลือกวาด/เขียนภาพประกอบเพิ่มเติมในหมวด "พื้นที่สำหรับวาดภาพประกอบที่จำเป็น", Then ระบบบันทึกภาพวาดนั้นไว้กับอาคารสำเร็จ
- AC-2: Given ผู้สำรวจไม่มีความจำเป็นต้องวาดภาพประกอบเพิ่มเติม, When ข้ามหมวดนี้ไปโดยไม่วาด, Then ระบบอนุญาตให้ข้ามได้โดยไม่บังคับ (เป็นหมวดไม่บังคับ)

## 6. บันทึกข้อมูลผู้สำรวจและระยะเวลาการสำรวจ

อ้างอิง: [[feature-list#6. บันทึกข้อมูลผู้สำรวจและระยะเวลาการสำรวจ|ฟีเจอร์ 6]] · บทบาท: ผู้สำรวจภาคสนาม

#### FR-16 (สูง) — [[20260828-01-flood-damage-survey#4.4 ผู้สำรวจ การรับรองผล และการมอบหมายงาน|บันทึกข้อมูลผู้สำรวจและหัวหน้าผู้สำรวจ]]

- AC-1: Given ผู้สำรวจเริ่มสรุปแบบสำรวจอาคาร, When กรอกรายชื่อผู้สำรวจ (สูงสุด 3 คน) และหัวหน้าผู้สำรวจพร้อมหน่วยงาน/โทรศัพท์/ตำแหน่ง, Then ระบบบันทึกข้อมูลผู้สำรวจไว้กับอาคารนั้นสำเร็จ
- AC-2: Given มีการกรอกรายชื่อผู้สำรวจแล้ว 3 คน, When ผู้สำรวจพยายามเพิ่มรายชื่อคนที่ 4, Then ระบบไม่อนุญาตให้เพิ่มเกิน 3 คน และแจ้งเตือนจำนวนสูงสุดที่กำหนด

#### FR-17 (กลาง) — [[20260828-01-flood-damage-survey#4.4 ผู้สำรวจ การรับรองผล และการมอบหมายงาน|บันทึกวันที่และเวลาเริ่ม/เวลาแล้วเสร็จของการสำรวจ]]

- AC-1: Given ผู้สำรวจเริ่มต้นสำรวจอาคารหนึ่ง, When ระบบบันทึกเวลาเริ่มสำรวจ และเมื่อผู้สำรวจกรอกข้อมูลครบและยืนยันเสร็จสิ้น ระบบบันทึกเวลาแล้วเสร็จ, Then ระบบเก็บวันที่และเวลาเริ่ม/แล้วเสร็จของการสำรวจอาคารนั้นไว้ครบถ้วน

## 7. ตรวจทานและรับรองผลสำรวจด้วยลายเซ็นดิจิทัล

อ้างอิง: [[feature-list#7. ตรวจทานและรับรองผลสำรวจด้วยลายเซ็นดิจิทัล|ฟีเจอร์ 7]] · บทบาท: หัวหน้าผู้สำรวจ

#### FR-19 (สูง) — [[20260828-01-flood-damage-survey#4.4 ผู้สำรวจ การรับรองผล และการมอบหมายงาน|หัวหน้าผู้สำรวจตรวจทานผลการสำรวจของทีมก่อนรับรอง]]

- AC-1: Given หัวหน้าผู้สำรวจตรวจทานผลการสำรวจที่ทีมกรอกครบทุกอาคาร, When เห็นว่าผลถูกต้องครบถ้วน, Then ระบบอนุญาตให้ดำเนินการต่อไปสู่ขั้นตอนลงลายมือชื่อรับรอง (FR-18)
- AC-2: Given หัวหน้าผู้สำรวจตรวจทานแล้วพบว่าข้อมูลไม่ครบถ้วน/ไม่ถูกต้อง, When เลือกส่งกลับให้ทีมแก้ไข, Then ระบบเปลี่ยนสถานะของรายการสำรวจนั้นเป็น "ส่งกลับแก้ไข" แจ้งผู้สำรวจที่เกี่ยวข้อง และไม่อนุญาตให้ลงลายมือชื่อรับรองจนกว่าจะแก้ไขและส่งกลับมาตรวจทานใหม่

#### FR-18 (สูง) — [[20260828-01-flood-damage-survey#4.4 ผู้สำรวจ การรับรองผล และการมอบหมายงาน|ลงลายมือชื่อดิจิทัลของหัวหน้าผู้สำรวจเพื่อรับรองผลสรุป]]

- AC-1: Given ผลการสำรวจอาคารถูกตรวจทานว่าครบถ้วนถูกต้องแล้ว (FR-19), When หัวหน้าผู้สำรวจลงลายมือชื่อดิจิทัล (touch signature) เพื่อรับรอง, Then ระบบบันทึกลายมือชื่อผูกกับผลสรุปของอาคารนั้นและเปลี่ยนสถานะเป็น "รับรองแล้ว" สำเร็จ
- AC-2: Given หัวหน้าผู้สำรวจยังไม่ได้ลงลายมือชื่อ, When พยายามปิดหน้าจอหรือดำเนินการอื่นโดยไม่ลงนาม, Then สถานะของผลสรุปยังคงเป็น "รอรับรอง" และไม่ถือว่าผลนั้นได้รับการรับรองอย่างเป็นทางการ

## 8. มอบหมายงานสำรวจให้ทีม

อ้างอิง: [[feature-list#8. มอบหมายงานสำรวจให้ทีม|ฟีเจอร์ 8]] · บทบาท: หัวหน้าผู้สำรวจ

#### FR-20 (กลาง) — [[20260828-01-flood-damage-survey#4.4 ผู้สำรวจ การรับรองผล และการมอบหมายงาน|หัวหน้าผู้สำรวจมอบหมายงานสำรวจอาคาร/พื้นที่ให้สมาชิกทีม]]

- AC-1: Given หัวหน้าผู้สำรวจต้องการกระจายงานให้ทีม, When สร้างรายการอาคาร/พื้นที่ที่ต้องสำรวจและมอบหมายให้สมาชิกทีมที่ระบุ, Then ระบบบันทึกการมอบหมายงานและสมาชิกทีมที่ได้รับมอบหมายเห็นรายการงานของตนเอง
- AC-2: Given ยังไม่มีบัญชีผู้ใช้บทบาทผู้สำรวจภาคสนามให้เลือกมอบหมาย, When หัวหน้าผู้สำรวจพยายามมอบหมายงาน, Then ระบบแจ้งเตือนว่าไม่มีสมาชิกให้เลือกและแนะนำให้ผู้ดูแลระบบสร้างบัญชีก่อน (เชื่อมโยงกับ [[feature-list#9. จัดการผู้ใช้และสิทธิ์การเข้าถึง|ฟีเจอร์ 9]])
- AC-3: Given หัวหน้าผู้สำรวจยังไม่ได้มอบหมายงานใดให้สมาชิกทีมคนหนึ่งเลย (เช่น ผู้สำรวจภาคสนามที่เพิ่งได้รับบัญชีใหม่), When สมาชิกทีมนั้นเปิดหน้ารายการงานของตนเอง, Then ระบบแสดงสถานะว่ายังไม่มีงานที่ได้รับมอบหมาย พร้อมอธิบายสาเหตุและสิ่งที่ควรทำต่อ (เช่น ให้ติดต่อหัวหน้าผู้สำรวจ) โดยถือเป็นสถานะปกติ ไม่ใช่ข้อผิดพลาดของระบบ (ตามเกณฑ์ empty state ของ `DESIGN.md` §3.9)

## 9. จัดการผู้ใช้และสิทธิ์การเข้าถึง

อ้างอิง: [[feature-list#9. จัดการผู้ใช้และสิทธิ์การเข้าถึง|ฟีเจอร์ 9]] · บทบาท: ผู้ดูแลระบบ

#### FR-21 (สูง) — [[20260828-01-flood-damage-survey#4.5 การจัดการผู้ใช้ สิทธิ์ และภาพรวมผลสำรวจ|จัดการผู้ใช้และสิทธิ์การเข้าถึงตามบทบาท]]

- AC-1: Given ผู้ดูแลระบบเข้าสู่ระบบ, When สร้างบัญชีผู้ใช้ใหม่พร้อมกำหนดบทบาท (ผู้สำรวจภาคสนาม/หัวหน้าผู้สำรวจ/ผู้ดูแลระบบ/หน่วยงานส่วนกลาง), Then ระบบสร้างบัญชีผู้ใช้พร้อมบทบาทที่กำหนดสำเร็จ
- AC-2: Given มีบัญชีผู้ใช้อยู่แล้ว, When ผู้ดูแลระบบแก้ไขข้อมูล/บทบาทของบัญชีนั้น, Then ระบบบันทึกการเปลี่ยนแปลงและมีผลกับสิทธิ์การเข้าถึงของผู้ใช้นั้นในการเข้าใช้งานครั้งถัดไป
- AC-3: Given บัญชีผู้ใช้ไม่ควรเข้าถึงระบบอีกต่อไป, When ผู้ดูแลระบบปิดการใช้งานบัญชีนั้น, Then ระบบปฏิเสธการเข้าสู่ระบบของบัญชีนั้นตั้งแต่ครั้งถัดไป

#### NFR-08 (สูง) — [[20260828-01-flood-damage-survey#5. Non-Functional Requirements|Security (ข้อมูลเข้าถึงได้เฉพาะผู้ใช้ที่มีสิทธิ์ตามบทบาท)]]

- AC-1: Given ผู้ใช้แต่ละบทบาทมีสิทธิ์การเข้าถึงข้อมูลตามที่กำหนดไว้ (FR-21), When ผู้ใช้พยายามเข้าถึงข้อมูล/ฟังก์ชันที่อยู่นอกเหนือบทบาทของตน, Then ระบบต้องปฏิเสธการเข้าถึงนั้นและไม่แสดงข้อมูลที่ไม่มีสิทธิ์

## 10. Dashboard ภาพรวมผลสำรวจ

อ้างอิง: [[feature-list#10. Dashboard ภาพรวมผลสำรวจ|ฟีเจอร์ 10]] · บทบาท: หน่วยงานส่วนกลาง/ผู้บริหาร

## 11. ส่งออกรายงานผลการสำรวจ

อ้างอิง: [[feature-list#11. ส่งออกรายงานผลการสำรวจ|ฟีเจอร์ 11]] · บทบาท: หน่วยงานส่วนกลาง/ผู้บริหาร

- AC-1: Given หน่วยงานส่วนกลาง/ผู้บริหารต้องการนำผลสำรวจไปใช้นอกระบบ, When เลือกส่งออกรายงานรายอาคารหรือสรุปภาพรวม, Then ระบบสร้างไฟล์รายงานที่มีข้อมูลตรงกับที่แสดงในระบบให้ดาวน์โหลดสำเร็จ (รูปแบบไฟล์เป็นไปตามที่จะตัดสินใจใน `technology-stack.md`)
- AC-2: Given เลือกส่งออกโดยไม่มีข้อมูลตรงเงื่อนไขที่กรองไว้เลย, When สั่งส่งออก, Then ระบบแจ้งเตือนว่าไม่มีข้อมูลให้ส่งออกแทนที่จะสร้างไฟล์ว่างเปล่าโดยไม่แจ้งอะไร

## 12. ค้นหา/กรองรายการอาคารที่สำรวจแล้ว

อ้างอิง: [[feature-list#12. ค้นหา/กรองรายการอาคารที่สำรวจแล้ว|ฟีเจอร์ 12]] · บทบาท: หน่วยงานส่วนกลาง/ผู้บริหาร, หัวหน้าผู้สำรวจ

#### FR-24 (กลาง) — [[20260828-01-flood-damage-survey#4.5 การจัดการผู้ใช้ สิทธิ์ และภาพรวมผลสำรวจ|ค้นหา/กรองรายการอาคารที่สำรวจแล้ว]]

- AC-1: Given มีรายการอาคารที่สำรวจแล้วในระบบ, When ผู้ใช้ (หัวหน้าผู้สำรวจ/หน่วยงานส่วนกลาง) ค้นหา/กรองตามพื้นที่ ระดับสี ช่วงวันที่ หรือผู้สำรวจ, Then ระบบแสดงเฉพาะรายการที่ตรงเงื่อนไขทั้งหมดที่เลือกถูกต้อง
- AC-2: Given เงื่อนไขที่กรองไม่ตรงกับรายการใดเลย, When ค้นหา, Then ระบบแสดงข้อความว่าไม่พบรายการที่ตรงเงื่อนไข แทนที่จะแสดงหน้าว่างเปล่าโดยไม่มีคำอธิบาย

#### NFR-01 (สูง) — [[20260828-01-flood-damage-survey#5. Non-Functional Requirements|Availability / Offline Support]]

- AC-1: Given อุปกรณ์ของผู้สำรวจไม่มีสัญญาณอินเทอร์เน็ตที่หน้างาน, When ผู้สำรวจกรอกแบบสำรวจครบทุกหมวด (ฟีเจอร์ 1-6 รวมถ่ายภาพและวิเคราะห์ด้วย AI), Then ระบบต้องให้ทำงานได้ครบทุกฟังก์ชันหลักของการสำรวจโดยไม่ต้องพึ่งพาการเชื่อมต่อเครือข่ายเลย

#### NFR-02 (สูง) — [[20260828-01-flood-damage-survey#5. Non-Functional Requirements|Performance / Reliability]]

หมายเหตุ (เพิ่ม 2026-09-03): ปริมาณภาพต่อการสำรวจที่ต้องซิงค์ถูกจำกัดด้วยจำนวนภาพสูงสุด **5 ภาพต่อบริเวณ** ตาม [[acceptance-criteria#FR-12 (สูง) — ถ่ายภาพประกอบความเสียหายผูกกับตำแหน่ง/บริเวณ|FR-12 AC-3]] (ยืนยันจากผู้ใช้แล้ว) — ใช้ประมาณปริมาณข้อมูล/จำนวนไฟล์สูงสุดต่อบริเวณเมื่อออกแบบ test data ของ AC ด้านล่าง ส่วนขนาด/ความละเอียดไฟล์ภาพยังไม่กำหนด (ข้อสมมติยังเปิดอยู่)

- AC-1: Given อุปกรณ์กลับมามีสัญญาณอินเทอร์เน็ตหลังทำงานออฟไลน์, When ระบบเริ่มกระบวนการซิงค์ข้อมูลและภาพถ่ายที่ค้างอยู่ขึ้นเซิร์ฟเวอร์, Then การซิงค์ต้องดำเนินไปสำเร็จโดยอัตโนมัติโดยผู้ใช้ไม่ต้องเข้าไปแทรกแซงเอง
- AC-2: Given การซิงค์ถูกขัดจังหวะกลางคัน (สัญญาณหลุดระหว่างซิงค์), When อุปกรณ์กลับมามีสัญญาณอีกครั้ง, Then ระบบซิงค์ต่อจากจุดที่ค้างได้โดยไม่ทำข้อมูลซ้ำซ้อนหรือสูญหาย
- AC-3: Given ไม่มีข้อมูลใดค้างรอซิงค์อยู่เลย (ซิงค์ครบถ้วนแล้วทั้งหมด), When ผู้สำรวจภาคสนามเปิดหน้าสถานะการซิงค์, Then ระบบแสดงสถานะว่าซิงค์ข้อมูลครบถ้วนแล้วอย่างชัดเจน โดยสื่อว่าเป็นสถานะปกติ/สำเร็จ ไม่ใช่ข้อผิดพลาดหรือทำให้ผู้ใช้เข้าใจผิดว่าระบบมีปัญหา (ตามเกณฑ์ empty state ของ `DESIGN.md` §3.9 และสอดคล้องกับหลักการไม่ทำให้ออฟไลน์ดูเหมือนข้อผิดพลาด)

#### NFR-03 (สูง) — [[20260828-01-flood-damage-survey#5. Non-Functional Requirements|Data Integrity]]

- AC-1: Given หลายอุปกรณ์แก้ไขข้อมูลอาคารเดียวกันขณะออฟไลน์แยกกัน, When ทั้งสองอุปกรณ์กลับมาซิงค์พร้อมกัน, Then ระบบต้องตรวจจับความขัดแย้งของข้อมูลและจัดการตามนโยบายที่กำหนดโดยไม่ทำให้ข้อมูลที่บันทึกไว้สูญหายเงียบๆ (ต้องมีร่องรอย/แจ้งเตือนความขัดแย้งให้ผู้เกี่ยวข้องทราบ)

#### NFR-04 (สูง) — [[20260828-01-flood-damage-survey#5. Non-Functional Requirements|Usability / Compatibility]]

- AC-1: Given ผู้สำรวจใช้งานแอปบนมือถือ/แท็บเล็ตกลางแจ้งภายใต้สภาพหน้างานหลังน้ำท่วม (แสงจ้า/ฝุ่น/ความชื้น), When ใช้งานฟังก์ชันบันทึกแบบสำรวจ, Then หน้าจอและการควบคุมต้องใช้งานได้จริงในสภาพแวดล้อมกลางแจ้งดังกล่าว (อ่านง่าย กดง่าย)

#### NFR-07 (กลาง) — [[20260828-01-flood-damage-survey#5. Non-Functional Requirements|Scalability]]

- AC-1: Given เกิดเหตุการณ์อุทกภัยและมีหลายทีมสำรวจจำนวนมากพร้อมกัน, When ทุกทีมกลับมามีสัญญาณและซิงค์ข้อมูลพร้อมกันในช่วงเวลาใกล้เคียงกัน, Then ระบบต้องรองรับปริมาณการซิงค์พร้อมกันจำนวนมากได้โดยไม่ล่มหรือทำข้อมูลสูญหาย

## 14. ยืนยันตัวตนและเข้าสู่ระบบ

อ้างอิง: [[feature-list#14. ยืนยันตัวตนและเข้าสู่ระบบ|ฟีเจอร์ 14]] · บทบาท: ทุกบทบาท (FR-27/NFR-09 เฉพาะผู้สำรวจภาคสนาม)

หมายเหตุอัปเดต (2026-09-03): ผู้ใช้ปิดข้อสมมติค้างในหัวข้อ 6 ข้อ 6/7 ของ spec — กลไกยืนยันตัวตนคือ "รหัสผ่านครั้งแรก + ตั้ง PIN สำหรับปลดล็อกออฟไลน์" และอายุ PIN/เซสชันที่แคชไว้ = **7 วัน** เพิ่ม AC สำหรับ: การบังคับตั้ง PIN หลังเข้าสู่ระบบด้วยรหัสผ่านสำเร็จ (FR-25 AC-4/AC-5), การกรอก PIN ผิดขณะปลดล็อกออฟไลน์ (FR-27 AC-3), กรณี PIN หมดอายุครบ 7 วันขณะยังไม่มีสัญญาณ (FR-27 AC-4 — กรณีกระทบผู้ใช้จริงมากที่สุด ดู [[test-plan#Risk Management|test-plan §Risk Management]]) และ boundary case ยังไม่ครบ 7 วัน (NFR-09 AC-2) — ดูรายการช่องว่างที่ยังไม่มี FR/NFR รองรับ (ข้อจำกัดจำนวนครั้งที่กรอก PIN ผิดได้ก่อนถูกล็อก) ที่ท้ายรายงานของ `test-writer`

#### FR-25 (สูง) — [[20260828-01-flood-damage-survey#4.6 การยืนยันตัวตนและการเข้าสู่ระบบ|ยืนยันตัวตนผู้ใช้ (เข้าสู่ระบบ/ออกจากระบบ)]]

- AC-1: Given ผู้ใช้มีบัญชีที่ถูกต้องและมีสัญญาณอินเทอร์เน็ต, When กรอกชื่อผู้ใช้/รหัสผ่านที่ถูกต้องแล้วเข้าสู่ระบบ, Then ระบบยืนยันตัวตนสำเร็จและนำผู้ใช้เข้าสู่หน้าหลักตามบทบาทของตน
- AC-2: Given ผู้ใช้กรอกชื่อผู้ใช้/รหัสผ่านไม่ถูกต้อง, When พยายามเข้าสู่ระบบ, Then ระบบปฏิเสธการเข้าสู่ระบบและแจ้งข้อความว่าข้อมูลเข้าสู่ระบบไม่ถูกต้อง โดยไม่เปิดเผยว่าผิดที่ชื่อผู้ใช้หรือรหัสผ่าน
- AC-3: Given ผู้ใช้เข้าสู่ระบบอยู่, When เลือกออกจากระบบ, Then ระบบยุติ session ปัจจุบันและต้องเข้าสู่ระบบใหม่ก่อนใช้งานฟังก์ชันใดๆ อีกครั้ง
- AC-4 (เพิ่ม 2026-09-03 — ปิดข้อสมมติกลไกยืนยันตัวตน): Given ผู้ใช้ยืนยันตัวตนด้วยชื่อผู้ใช้/รหัสผ่านสำเร็จ (เข้าสู่ระบบครั้งแรก หรือเข้าสู่ระบบใหม่หลังจาก credential/session ที่แคชไว้หมดอายุตาม [[acceptance-criteria#NFR-09 (สูง) — Security (Offline Session Expiry)|NFR-09]]), When ระบบให้ตั้งรหัส PIN สำหรับปลดล็อกออฟไลน์ครั้งถัดไป, Then ผู้ใช้ต้องตั้ง PIN สำเร็จก่อนจึงจะเข้าใช้งานฟังก์ชันหลักของบทบาทตนได้ (ห้ามข้ามขั้นตอนตั้ง PIN ไปเฉยๆ) และ PIN ที่ตั้งไว้นี้จะมีอายุการใช้งานตาม NFR-09
- AC-5 (เพิ่ม 2026-09-03): Given ผู้ใช้กำลังตั้งรหัส PIN ครั้งแรกหลังเข้าสู่ระบบด้วยรหัสผ่านสำเร็จ, When ยืนยัน PIN ซ้ำไม่ตรงกับที่กรอกครั้งแรก, Then ระบบปฏิเสธการตั้ง PIN และให้กรอกใหม่ทั้งสองช่องจนกว่าจะตรงกัน โดยยังไม่ให้ผ่านเข้าใช้งานฟังก์ชันหลักจนกว่าจะตั้ง PIN สำเร็จ

#### FR-26 (สูง) — [[20260828-01-flood-damage-survey#4.6 การยืนยันตัวตนและการเข้าสู่ระบบ|บังคับสิทธิ์การเข้าถึงฟังก์ชัน/หน้าจอตามบทบาทหลังเข้าสู่ระบบ]]

- AC-1: Given ผู้ใช้เข้าสู่ระบบสำเร็จด้วยบทบาทหนึ่ง (ตามที่ผู้ดูแลระบบกำหนดใน FR-21), When ผู้ใช้ใช้งานระบบ, Then ระบบแสดงและอนุญาตเฉพาะฟังก์ชัน/หน้าจอที่ตรงกับบทบาทนั้นเท่านั้น
- AC-2: Given ผู้ใช้พยายามเข้าถึงหน้าจอที่อยู่นอกเหนือสิทธิ์ของบทบาทตนโดยตรง, When ระบบตรวจสอบสิทธิ์, Then ระบบปฏิเสธการเข้าถึงและแจ้งว่าไม่มีสิทธิ์เข้าถึง

#### FR-27 (สูง) — [[20260828-01-flood-damage-survey#4.6 การยืนยันตัวตนและการเข้าสู่ระบบ|เข้าสู่ระบบและใช้งานแอปขณะไม่มีการเชื่อมต่ออินเทอร์เน็ต]]

- AC-1: Given ผู้สำรวจภาคสนามเคยเข้าสู่ระบบสำเร็จจากเซิร์ฟเวอร์มาก่อนและอุปกรณ์มี credential/session ที่แคชไว้ที่ยังไม่หมดอายุ, When เปิดแอปที่หน้างานโดยไม่มีสัญญาณอินเทอร์เน็ตแล้วกรอก PIN ที่ตั้งไว้ถูกต้อง (ตาม [[acceptance-criteria#FR-25 (สูง) — ยืนยันตัวตนผู้ใช้ (เข้าสู่ระบบ/ออกจากระบบ)|FR-25]]), Then ระบบอนุญาตให้ปลดล็อกและใช้งานฟังก์ชันสำรวจภาคสนามได้ตามปกติโดยไม่ต้องติดต่อเซิร์ฟเวอร์
- AC-2: Given credential/session ที่แคชไว้หมดอายุแล้วตามเกณฑ์ที่กำหนด ([[acceptance-criteria#NFR-09 (สูง) — Security (Offline Session Expiry)|NFR-09]]), When ผู้สำรวจพยายามเข้าสู่ระบบขณะไม่มีสัญญาณอินเทอร์เน็ต, Then ระบบปฏิเสธการเข้าสู่ระบบด้วย credential ที่แคชไว้ และแจ้งว่าต้องเชื่อมต่อสัญญาณเพื่อยืนยันตัวตนใหม่ก่อนใช้งานต่อ
- AC-3 (เพิ่ม 2026-09-03 — negative case กรอก PIN ผิด): Given credential/session ที่แคชไว้ยังไม่หมดอายุ, When ผู้สำรวจกรอก PIN ไม่ถูกต้องขณะปลดล็อกออฟไลน์, Then ระบบปฏิเสธการปลดล็อกและแจ้งว่า PIN ไม่ถูกต้อง โดยยังอนุญาตให้ลองกรอกใหม่ได้ทันที (ไม่ล้าง credential/session ที่แคชไว้จากการกรอก PIN ผิดเพียงครั้งเดียว)
- AC-4 (เพิ่ม 2026-09-03 — กรณีกระทบผู้ใช้จริงมากที่สุด: PIN หมดอายุครบ 7 วันขณะยังติดอยู่ในพื้นที่ไม่มีสัญญาณ): Given credential/session ที่แคชไว้หมดอายุครบ 7 วันแล้ว ([[acceptance-criteria#NFR-09 (สูง) — Security (Offline Session Expiry)|NFR-09]]) และอุปกรณ์ยังไม่มีสัญญาณอินเทอร์เน็ตเลย (ผู้สำรวจยังอยู่ในพื้นที่ปฏิบัติงาน), When ผู้สำรวจพยายามปลดล็อกแอปด้วย PIN, Then ระบบปฏิเสธการปลดล็อกและแจ้งชัดเจนว่าต้องเชื่อมต่อสัญญาณเพื่อเข้าสู่ระบบใหม่ด้วยรหัสผ่านก่อนจึงจะใช้งานต่อได้ (เป็นความเสี่ยงที่ยอมรับแล้วตามข้อสมมติที่ปิดในหัวข้อ 6 ข้อ 6 ของ spec) — แต่ระบบต้องไม่ลบหรือทำให้ข้อมูลแบบสำรวจที่บันทึกไว้แล้วในเครื่อง (ยังไม่ได้ซิงค์) สูญหายระหว่างที่ถูกล็อกอยู่ และต้องซิงค์ข้อมูลเหล่านั้นโดยอัตโนมัติทันทีที่เข้าสู่ระบบใหม่สำเร็จเมื่อกลับมามีสัญญาณ (สอดคล้องกับ [[acceptance-criteria#NFR-01 (สูง) — Availability / Offline Support|NFR-01]] และ [[acceptance-criteria#NFR-02 (สูง) — Performance / Reliability|NFR-02]])

#### NFR-09 (สูง) — [[20260828-01-flood-damage-survey#5. Non-Functional Requirements|Security (Offline Session Expiry)]]

- AC-1: Given ผู้สำรวจเข้าสู่ระบบขณะออฟไลน์ด้วย credential/session ที่แคชไว้ (FR-27), When ครบกำหนดอายุการใช้งานที่จำกัดไว้ 7 วัน หรืออุปกรณ์กลับมามีสัญญาณอินเทอร์เน็ต (แล้วแต่อย่างใดถึงก่อน), Then ระบบบังคับให้ยืนยันตัวตนใหม่กับเซิร์ฟเวอร์ก่อนอนุญาตให้ใช้งานต่อ เพื่อจำกัดความเสี่ยงจากอุปกรณ์สูญหาย/ถูกขโมย
- AC-2 (เพิ่ม 2026-09-03 — boundary case ยังไม่ครบ 7 วัน): Given ผู้สำรวจเข้าสู่ระบบด้วยรหัสผ่านครั้งล่าสุดที่เชื่อมต่อสำเร็จมาแล้วน้อยกว่า 7 วัน (เช่น วันที่ 6 นับจากวันเข้าสู่ระบบล่าสุด), When ผู้สำรวจปลดล็อกแอปด้วย PIN ขณะออฟไลน์, Then ระบบอนุญาตให้ปลดล็อกและใช้งานต่อได้ตามปกติโดยยังไม่บังคับให้เข้าสู่ระบบใหม่ (ยังไม่ครบกำหนดอายุ)

## 15. แก้ไขความขัดแย้งของข้อมูลจากการซิงค์ด้วยมือ (Manual Conflict Resolution)

อ้างอิง: [[feature-list#15. แก้ไขความขัดแย้งของข้อมูลจากการซิงค์ด้วยมือ (Manual Conflict Resolution)|ฟีเจอร์ 15]] · [[user-journey#Journey: หัวหน้าผู้สำรวจตรวจทานและรับรองผลสำรวจ|journey หัวหน้าผู้สำรวจ]] ขั้นตอน 8-10 และ [[user-journey#Journey: ผู้ดูแลระบบจัดการผู้ใช้และสิทธิ์|journey ผู้ดูแลระบบ]] ขั้นตอน 7-9 · บทบาท: หัวหน้าผู้สำรวจ, ผู้ดูแลระบบ (เฉพาะ 2 บทบาทนี้เท่านั้นที่มีสิทธิ์เข้าถึงหน้าจอนี้ตาม spec)

หมายเหตุ: ฟีเจอร์นี้เชื่อมโยงกับ NFR-03 (กลไกตรวจจับความขัดแย้งอัตโนมัติ ในฟีเจอร์ 13) เป็นขั้นตอนต่อเนื่องที่มนุษย์เข้ามาแก้ไขด้วยมือเมื่อระบบ merge เองไม่ได้ ([[acceptance-criteria#NFR-03 (สูง) — Data Integrity|NFR-03]]) และเชื่อมโยงกับ NFR-05 (Auditability — ประวัติการแก้ไขที่มีอยู่แล้วในฟีเจอร์ 4) ซึ่ง spec ระบุว่าครอบคลุมทั้งกรณีแก้ไขผล AI (FR-14) และกรณีแก้ไขความขัดแย้งของข้อมูลด้วยมือ (FR-31) ดังนั้นทุก AC ของ FR-31 ที่บันทึกผลลัพธ์สำเร็จต้องเก็บประวัติผู้แก้ไข/เวลา/เวอร์ชันที่เลือก-ละทิ้งไว้ตรวจสอบย้อนหลังตาม [[acceptance-criteria#NFR-05 (สูง) — Auditability / Accountability (ประวัติการแก้ไขผล AI)|NFR-05]] ด้วยเช่นกัน (ไม่สร้างหัวข้อ NFR-05 ซ้ำในฟีเจอร์นี้) — **ปรับปรุง 2026-09-02**: การแก้ไขความขัดแย้งด้วยมือ (FR-31) เป็นหนึ่งในเหตุการณ์ที่กฎ "ผู้กระทำแบบมีเงื่อนไข" ของ NFR-05 บังคับต้องระบุผู้กระทำเสมอ (ต่างจากเหตุการณ์ซิงค์อัตโนมัติของฟีเจอร์ 13 ที่ไม่บังคับ) — ดู [[acceptance-criteria#NFR-05 (สูง) — Auditability / Accountability (ประวัติการแก้ไขผล AI)|NFR-05 AC-4]] สำหรับ AC เชิงลบที่ทดสอบเรื่องนี้โดยตรง (ที่มาจาก regression จริงที่เคยเกิดขึ้นและถูกแก้ไขแล้ว)

#### FR-30 (สูง) — [[20260828-01-flood-damage-survey#4.7 การแก้ไขความขัดแย้งของข้อมูลจากการซิงค์ (Manual Conflict Resolution)|แสดงรายการระเบียนที่มีความขัดแย้งของข้อมูลรอการแก้ไขด้วยมือ]]

- AC-1: Given ระบบตรวจพบว่าข้อมูลชุดเดียวกัน (เช่น ผลประเมินความเสียหายของอาคารเดียวกัน) ถูกแก้ไขจากหลายอุปกรณ์จนไม่สามารถ merge อัตโนมัติได้ ([[acceptance-criteria#NFR-03 (สูง) — Data Integrity|NFR-03]]), When หัวหน้าผู้สำรวจหรือผู้ดูแลระบบเปิดหน้ารายการระเบียนที่รอแก้ไขความขัดแย้ง, Then ระบบแสดงรายการระเบียนดังกล่าวพร้อมสถานะ "รอแก้ไขความขัดแย้ง" ครบถ้วนตรงกับจำนวนจริงในระบบ
- AC-2: Given ผู้ใช้ที่ไม่ใช่หัวหน้าผู้สำรวจหรือผู้ดูแลระบบ (เช่น ผู้สำรวจภาคสนามหรือหน่วยงานส่วนกลาง/ผู้บริหาร), When พยายามเข้าถึงหน้ารายการระเบียนที่มีความขัดแย้งรอแก้ไข, Then ระบบปฏิเสธการเข้าถึงเนื่องจากไม่มีสิทธิ์ (สอดคล้องกับ [[acceptance-criteria#FR-26 (สูง) — บังคับสิทธิ์การเข้าถึงฟังก์ชัน/หน้าจอตามบทบาทหลังเข้าสู่ระบบ|FR-26]])
- AC-3: Given ไม่มีระเบียนใดค้างสถานะขัดแย้งอยู่เลยในขณะนั้น, When หัวหน้าผู้สำรวจหรือผู้ดูแลระบบเปิดหน้านี้, Then ระบบแสดงสถานะว่าไม่มีระเบียนรอแก้ไข แทนที่จะแสดงหน้าว่างเปล่าหรือข้อผิดพลาดที่สับสน

#### FR-31 (สูง) — [[20260828-01-flood-damage-survey#4.7 การแก้ไขความขัดแย้งของข้อมูลจากการซิงค์ (Manual Conflict Resolution)|เปรียบเทียบเวอร์ชันข้อมูลที่ขัดแย้งกันและเลือก/รวมค่าด้วยมือ]]

- AC-1: Given มีระเบียนหนึ่งที่มีสถานะ "รอแก้ไขความขัดแย้ง" ([[acceptance-criteria#FR-30 (สูง) — แสดงรายการระเบียนที่มีความขัดแย้งของข้อมูลรอการแก้ไขด้วยมือ|FR-30]]), When หัวหน้าผู้สำรวจหรือผู้ดูแลระบบเปิดดูรายละเอียดระเบียนนั้น, Then ระบบแสดงข้อมูลเปรียบเทียบระหว่างทุกเวอร์ชันที่ขัดแย้งกันแบบเคียงข้างกัน อย่างน้อยประกอบด้วยค่าเดิม/ค่าใหม่ของแต่ละเวอร์ชัน อุปกรณ์ที่บันทึก ผู้แก้ไข และเวลาที่บันทึก
- AC-2: Given กำลังเปรียบเทียบเวอร์ชันที่ขัดแย้งกันของระเบียนหนึ่ง, When ผู้ใช้เลือกเก็บค่าจากเวอร์ชันใดเวอร์ชันหนึ่งทั้งหมดแล้วยืนยัน, Then ระบบบันทึกค่าจากเวอร์ชันที่เลือกเป็นข้อมูลจริงชุดเดียว ปลดสถานะ "รอแก้ไขความขัดแย้ง" ของระเบียนนั้นสำเร็จ และเก็บประวัติว่าเลือกเวอร์ชันใด/ละทิ้งเวอร์ชันใดไว้ตรวจสอบย้อนหลัง
- AC-3: Given กำลังเปรียบเทียบเวอร์ชันที่ขัดแย้งกันของระเบียนหนึ่ง, When ผู้ใช้เลือกรวมค่าโดยเลือกเป็นรายฟิลด์จากคนละเวอร์ชันแล้วยืนยัน, Then ระบบบันทึกค่าที่รวมแล้วเป็นข้อมูลจริงชุดเดียว (แต่ละฟิลด์ตรงกับเวอร์ชันที่เลือกไว้จริง) ปลดสถานะขัดแย้งของระเบียนนั้นสำเร็จ และเก็บประวัติว่าแต่ละฟิลด์เลือกมาจากเวอร์ชันใดไว้ตรวจสอบย้อนหลัง
- AC-4: Given ผู้ใช้ยังไม่ได้เลือก/ยืนยันค่าใดๆ ในหน้าเปรียบเทียบเวอร์ชัน, When ปิดหน้าจอหรือออกจากหน้านี้โดยไม่ยืนยัน, Then สถานะของระเบียนนั้นยังคงเป็น "รอแก้ไขความขัดแย้ง" และระบบไม่บันทึกผลลัพธ์ใดๆ จากการเปิดดูครั้งนั้น

#### NFR-10 (สูง) — [[20260828-01-flood-damage-survey#5. Non-Functional Requirements|Data Integrity (Reporting Consistency)]]

- AC-1: Given ระเบียนหนึ่งยังมีสถานะ "รอแก้ไขความขัดแย้ง" ค้างอยู่ ([[acceptance-criteria#FR-30 (สูง) — แสดงรายการระเบียนที่มีความขัดแย้งของข้อมูลรอการแก้ไขด้วยมือ|FR-30]]), When หน่วยงานส่วนกลาง/ผู้บริหารเปิดดู dashboard ภาพรวมผลสำรวจ ([[acceptance-criteria#FR-22 (สูง) — แสดง dashboard ภาพรวมผลสำรวจ|FR-22]]), Then ระเบียนที่ยังขัดแย้งนั้นต้องไม่ถูกนับรวมในจำนวน/สัดส่วนที่แสดงบน dashboard
- AC-2: Given ระเบียนหนึ่งยังมีสถานะ "รอแก้ไขความขัดแย้ง" ค้างอยู่, When หน่วยงานส่วนกลาง/ผู้บริหารส่งออกรายงานผลการสำรวจ ([[acceptance-criteria#FR-23 (กลาง) — ส่งออกรายงานผลการสำรวจ|FR-23]]) ที่ครอบคลุมช่วงข้อมูลนั้น, Then ระเบียนที่ยังขัดแย้งต้องไม่ปรากฏอยู่ในไฟล์รายงานที่ส่งออก
- AC-3: Given ระเบียนที่เคยขัดแย้งได้รับการแก้ไขและปลดสถานะแล้ว ([[acceptance-criteria#FR-31 (สูง) — เปรียบเทียบเวอร์ชันข้อมูลที่ขัดแย้งกันและเลือก/รวมค่าด้วยมือ|FR-31]]), When หน่วยงานส่วนกลาง/ผู้บริหารเปิด dashboard หรือส่งออกรายงานหลังจากนั้น, Then ระเบียนนั้นต้องถูกนับรวมในภาพรวม/รายงานตามปกติแล้ว (ไม่ถูกกันไว้ตลอดไป)

## 16. เรียกดูประวัติการแก้ไขผลประเมินรายอาคาร (Audit Trail รายอาคาร)

อ้างอิง: [[feature-list#16. เรียกดูประวัติการแก้ไขผลประเมินรายอาคาร (Audit Trail รายอาคาร)|ฟีเจอร์ 16]] · [[user-journey#Journey: หัวหน้าผู้สำรวจตรวจทานและรับรองผลสำรวจ|journey หัวหน้าผู้สำรวจ]] ขั้นตอน 4-5 · [[user-journey#Journey: ผู้ดูแลระบบจัดการผู้ใช้และสิทธิ์|journey ผู้ดูแลระบบ]] ขั้นตอน 12-13 · [[user-journey#Journey: หน่วยงานส่วนกลาง/ผู้บริหารติดตามภาพรวมผลสำรวจ|journey หน่วยงานส่วนกลาง/ผู้บริหาร]] ขั้นตอน 4-5 · บทบาท: หัวหน้าผู้สำรวจ (เฉพาะทีม/อาคารของตน), ผู้ดูแลระบบ, หน่วยงานส่วนกลาง/ผู้บริหาร — **ไม่รวมผู้สำรวจภาคสนาม**

หมายเหตุที่มา: ฟีเจอร์นี้ (พร้อมฟีเจอร์ 17) มาจากรหัส FR-32 ที่เพิ่มใหม่ใน `backlog.md` เมื่อ 2026-09-02 หลัง `prototype-auditor` พบว่า [[acceptance-criteria#NFR-05 (สูง) — Auditability / Accountability (ประวัติการแก้ไขผล AI)|NFR-05]] กำหนดให้เก็บประวัติ "เพื่อการตรวจสอบย้อนหลัง" แต่ไม่มี FR ใดให้ผู้มีสิทธิ์เรียกดูประวัตินั้นได้จริง — ดูที่มาเต็มที่ [[20260828-01-flood-damage-survey#4.8 การตรวจสอบย้อนหลัง (Audit Trail)|spec หัวข้อ 4.8]]

หมายเหตุอัปเดต (2026-09-03): มีหน้าจอ prototype รองรับฟีเจอร์นี้แล้วตั้งแต่ 2026-09-02 — `docs/02-design/01-prototypes/20260830-01-v1/audit-trail-building.html` มีปุ่ม "มุมมองสาธิต" ให้สลับดู 5 สถานการณ์ตรงกับ AC-1..5 ด้านล่าง: หัวหน้าผู้สำรวจดูอาคารในทีมตน (มีประวัติ), หัวหน้าผู้สำรวจดูอาคารในทีมตน (ยังไม่มีประวัติ), หัวหน้าผู้สำรวจพยายามดูอาคารนอกทีม (ปฏิเสธสิทธิ์), ผู้ดูแลระบบ/ส่วนกลางดูอาคารใดก็ได้ (ไม่จำกัดทีม), ผู้สำรวจภาคสนามพยายามเข้าถึง (ไม่มีสิทธิ์) — ผู้ใช้ยืนยันแล้วว่าทดสอบในเบราว์เซอร์จริงครบทุกสถานะ ดูชื่อหน้าจอ/องค์ประกอบจริงในคอลัมน์ขั้นตอนของ `test-cases/audit-trail-building.md`

#### FR-32 (กลาง) — [[20260828-01-flood-damage-survey#4.8 การตรวจสอบย้อนหลัง (Audit Trail)|เรียกดูประวัติการแก้ไขผลประเมินรายอาคาร]]

- AC-1: Given อาคารหนึ่งมีประวัติการแก้ไขผลประเมินอย่างน้อย 1 เหตุการณ์ (แก้ไขผล AI ตาม [[acceptance-criteria#FR-14 (สูง) — ให้ผู้สำรวจยืนยัน/แก้ไขผลวิเคราะห์ของ AI ก่อนบันทึกเป็นผลจริง|FR-14]] และ/หรือแก้ไขความขัดแย้งของข้อมูลด้วยมือตาม [[acceptance-criteria#FR-31 (สูง) — เปรียบเทียบเวอร์ชันข้อมูลที่ขัดแย้งกันและเลือก/รวมค่าด้วยมือ|FR-31]]), When ผู้ใช้ที่มีสิทธิ์ (หัวหน้าผู้สำรวจ/ผู้ดูแลระบบ/หน่วยงานส่วนกลาง) เปิดหน้าประวัติการแก้ไขผลประเมินของอาคารนั้น, Then ระบบแสดงรายการประวัติทั้งหมดเรียงตามลำดับเวลา ระบุผู้แก้ไข เวลา และค่าเดิม/ค่าใหม่ของแต่ละเหตุการณ์ครบถ้วนตรงกับที่บันทึกไว้จริงตาม [[acceptance-criteria#NFR-05 (สูง) — Auditability / Accountability (ประวัติการแก้ไขผล AI)|NFR-05]]
- AC-2: Given ผู้สำรวจภาคสนามเข้าสู่ระบบ, When พยายามเข้าถึงหน้าประวัติการแก้ไขผลประเมินของอาคารใดๆ (แม้เป็นอาคารที่ตนเองเป็นผู้สำรวจ), Then ระบบปฏิเสธการเข้าถึงและไม่แสดงจุดเข้าถึง (เมนู/ปุ่ม) ไปยังหน้านี้ในส่วนต่อประสานของบทบาทนี้เลย (สอดคล้องกับ [[acceptance-criteria#FR-26 (สูง) — บังคับสิทธิ์การเข้าถึงฟังก์ชัน/หน้าจอตามบทบาทหลังเข้าสู่ระบบ|FR-26]])
- AC-3: Given หัวหน้าผู้สำรวจเข้าสู่ระบบ และมีอาคาร X ที่อยู่นอกทีม/ความรับผิดชอบของตน (มีหัวหน้าผู้สำรวจคนอื่นรับผิดชอบอยู่จริง), When พยายามเปิดดูประวัติการแก้ไขผลประเมินของอาคาร X, Then ระบบไม่แสดงอาคาร X เป็นตัวเลือกให้เข้าถึง และปฏิเสธการเข้าถึงหากพยายามเข้าถึงโดยตรง เนื่องจากอยู่นอกขอบเขตทีม/อาคารที่ตนรับผิดชอบ
- AC-4: Given ผู้ดูแลระบบหรือหน่วยงานส่วนกลาง/ผู้บริหารเข้าสู่ระบบ, When เปิดดูประวัติการแก้ไขผลประเมินของอาคารใดก็ได้ในระบบ (ไม่ว่าจะอยู่ในทีมใด), Then ระบบอนุญาตให้เข้าถึงและแสดงประวัติของอาคารนั้นได้สำเร็จ โดยไม่ถูกจำกัดขอบเขตทีมเหมือนบทบาทหัวหน้าผู้สำรวจ
- AC-5: Given อาคารหนึ่งไม่เคยมีเหตุการณ์แก้ไขผลใดๆ เกิดขึ้นเลย (ยังไม่เคยแก้ไขผล AI และไม่เคยเกิดความขัดแย้งของข้อมูล), When ผู้มีสิทธิ์เปิดดูประวัติของอาคารนั้น, Then ระบบแสดงสถานะว่าไม่มีประวัติการแก้ไขสำหรับอาคารนี้ แทนที่จะแสดงหน้าว่างเปล่าหรือข้อผิดพลาดที่สับสน (ตามเกณฑ์ empty state ของ `DESIGN.md` §3.9)

## 17. ค้นหา/กรองประวัติการแก้ไขทั่วทั้งระบบ (Audit Trail ระดับหน่วยงาน)

#### FR-33 (กลาง) — [[20260828-01-flood-damage-survey#4.8 การตรวจสอบย้อนหลัง (Audit Trail)|ค้นหา/กรองประวัติการแก้ไขทั่วทั้งระบบ]]

- AC-1: Given มีประวัติการแก้ไขหลายรายการทั่วทั้งระบบ ครอบคลุมหลายอาคาร ผู้แก้ไข ประเภทการกระทำ (แก้ไขผล AI/แก้ไขความขัดแย้ง) และพื้นที่/จังหวัดต่างกัน, When ผู้ดูแลระบบหรือหน่วยงานส่วนกลาง/ผู้บริหารค้นหา/กรองตามช่วงเวลา/ผู้แก้ไข/ประเภทการกระทำ/พื้นที่, Then ระบบแสดงเฉพาะรายการประวัติที่ตรงเงื่อนไขทั้งหมดที่เลือกถูกต้อง ไม่ปนรายการที่ไม่ตรงเงื่อนไข
- AC-2: Given หัวหน้าผู้สำรวจเข้าสู่ระบบ, When พยายามเข้าถึงหน้าค้นหา/กรองประวัติการแก้ไขทั่วทั้งระบบ, Then ระบบปฏิเสธการเข้าถึงเนื่องจากขอบเขตกว้างกว่าทีม/อาคารที่ตนรับผิดชอบ (ให้ใช้ [[acceptance-criteria#FR-32 (กลาง) — เรียกดูประวัติการแก้ไขผลประเมินรายอาคาร|FR-32]] แบบรายอาคารในขอบเขตทีมตนเองแทน)
- AC-3: Given ผู้สำรวจภาคสนามเข้าสู่ระบบ, When พยายามเข้าถึงหน้าค้นหา/กรองประวัติการแก้ไขทั่วทั้งระบบ, Then ระบบปฏิเสธการเข้าถึง (สอดคล้องกับ [[acceptance-criteria#FR-26 (สูง) — บังคับสิทธิ์การเข้าถึงฟังก์ชัน/หน้าจอตามบทบาทหลังเข้าสู่ระบบ|FR-26]])
- AC-4: Given เงื่อนไขที่กรองไม่ตรงกับประวัติรายการใดเลยในระบบ, When ผู้ดูแลระบบหรือหน่วยงานส่วนกลาง/ผู้บริหารสั่งค้นหา, Then ระบบแสดงข้อความว่าไม่พบรายการที่ตรงเงื่อนไข แทนที่จะแสดงหน้าว่างเปล่าโดยไม่มีคำอธิบาย
