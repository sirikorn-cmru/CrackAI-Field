# แผนการทดสอบ (Test Plan)

เอกสารนี้สรุปภาพรวมกลยุทธ์การทดสอบทั้งหมดของโปรเจกต์ระบบสำรวจความเสียหายขั้นต้นของโครงสร้างอาคารหลังเหตุการณ์อุทกภัย อ้างอิงขอบเขตจาก [[feature-list]], [[user-journey]] และ [[backlog]] เป็นแหล่งความจริงว่า "มีอะไรบ้างที่ต้องทดสอบ" รายละเอียดเกณฑ์ยอมรับต่อรหัส FR/NFR อยู่ใน [[acceptance-criteria]] และ test case แบบ step-by-step อยู่ใน `test-cases/{feature-slug}.md`

- การทดสอบด้านความปลอดภัยเชิงลึกระดับ penetration testing ไม่อยู่ในขอบเขตเอกสารชุดนี้ (ครอบคลุมเฉพาะ functional security testing ตาม NFR-08/NFR-09)
- กรอบเวลา (SLA) ที่ระเบียนขัดแย้งของฟีเจอร์ 15 (FR-30/FR-31) ต้องได้รับการแก้ไขให้เสร็จภายในเวลาใด — spec ระบุชัดว่ายังไม่กำหนด SLA ตายตัวในเฟสนี้ (ดูข้อสมมติ 6 ข้อ 9 ของ spec) จึงทดสอบได้เฉพาะพฤติกรรมเชิงตรรกะของการแสดงรายการ/แก้ไข/ปลดสถานะ ไม่ใช่ระยะเวลาที่ยอมรับได้เจาะจง
- ระยะเวลาที่ต้องเก็บรักษาประวัติการแก้ไข (audit trail retention) ของฟีเจอร์ 16/17 (FR-32/FR-33) — spec ระบุชัดว่ายังไม่กำหนดระยะเวลาเก็บรักษาที่แน่นอน (ดูข้อสมมติ 6 ข้อ 10 ของ spec) จึงทดสอบได้เฉพาะพฤติกรรมของการเรียกดู/ค้นหา ไม่ใช่ระยะเวลาเก็บรักษาเจาะจง
- (อัปเดต 2026-09-03) หน้าจอ prototype ของฟีเจอร์ 16/17 มีแล้วตั้งแต่ 2026-09-02 — `docs/02-design/01-prototypes/20260830-01-v1/audit-trail-building.html` และ `audit-trail-search.html` ผู้ใช้ยืนยันทดสอบในเบราว์เซอร์จริงครบทุกสถานะแล้ว จึงไม่ใช่รายการนอกขอบเขตอีกต่อไป (เดิมข้อนี้ระบุว่ายังไม่มี prototype รองรับ)

## 2. ประเภทการทดสอบ

### Functional Testing (ต่อกลุ่ม FR)
- ข้อมูลอาคารและสภาพแวดล้อม (FR-01–FR-04)
- การประเมินความเสียหาย (FR-05–FR-09)
- การสรุปผลเป็นระดับสีและเกณฑ์อ้างอิง (FR-10, FR-11)
- ภาพถ่ายและ AI ประเมินรอยร้าว รวม human-in-the-loop confirmation และเส้นทางกรอกเอง (FR-12–FR-14, FR-28, FR-29)
- ภาพวาดประกอบ (FR-15)
- ข้อมูลผู้สำรวจและระยะเวลา (FR-16, FR-17)
- การตรวจทาน/รับรองผลด้วยลายเซ็นดิจิทัล (FR-18, FR-19)
- การมอบหมายงาน (FR-20)
- การจัดการผู้ใช้และสิทธิ์ (FR-21)
- Dashboard ภาพรวม (FR-22)
- การส่งออกรายงาน (FR-23)
- การค้นหา/กรอง (FR-24)
- การยืนยันตัวตนและควบคุมสิทธิ์ (FR-25–FR-27)
- การแก้ไขความขัดแย้งของข้อมูลจากการซิงค์ด้วยมือ (FR-30, FR-31)

### Non-Functional Testing (ต่อ NFR แต่ละด้าน)
- **Availability / Offline Support Testing** — NFR-01: ทดสอบว่าฟังก์ชันหลัก (ฟีเจอร์ 1-6) ใช้งานได้ครบขณะไม่มีสัญญาณอินเทอร์เน็ต
- **Performance / Reliability Testing** — NFR-02: ทดสอบความสำเร็จและความต่อเนื่องของการซิงค์ข้อมูลอัตโนมัติ รวมกรณีซิงค์ถูกขัดจังหวะ
- **Data Integrity Testing** — NFR-03: ทดสอบการตรวจจับและจัดการความขัดแย้งของข้อมูลเมื่อหลายอุปกรณ์แก้ไขข้อมูลชุดเดียวกัน
- **Usability / Compatibility Testing** — NFR-04: ทดสอบการใช้งานจริงบนมือถือ/แท็บเล็ตในสภาพแวดล้อมกลางแจ้งหลังน้ำท่วม
- **Auditability Testing** — NFR-05: ทดสอบว่าประวัติการแก้ไขผลวิเคราะห์ของ AI (FR-14), การแก้ไขความขัดแย้งด้วยมือของฟีเจอร์ 15 (FR-31) **และผลการซิงค์ข้อมูลอัตโนมัติของฟีเจอร์ 13 (ซิงค์สำเร็จ/ตรวจพบความขัดแย้ง — ขยายขอบเขต 2026-09-02)** ถูกบันทึกครบและแก้ไขย้อนหลังไม่ได้ รวมถึงทดสอบกฎ "ผู้กระทำแบบมีเงื่อนไข" (บังคับระบุผู้กระทำเฉพาะเหตุการณ์ที่มนุษย์ทำ ไม่บังคับสำหรับเหตุการณ์ที่ระบบบันทึกเอง) เป็นการทดสอบเชิงลบเพื่อป้องกัน regression ที่เคยเกิดขึ้นจริง
- **Accuracy Testing** — NFR-06: ทดสอบความแม่นยำของพิกัด GPS เทียบกับเกณฑ์ที่กำหนด
- **Scalability Testing** — NFR-07: ทดสอบการรองรับหลายทีมซิงค์ข้อมูลพร้อมกันจำนวนมาก
- **Security Testing** — NFR-08, NFR-09, NFR-11: ทดสอบการบังคับสิทธิ์ตามบทบาท และอายุ/การหมดอายุของ credential/PIN ที่แคชไว้สำหรับการเข้าสู่ระบบออฟไลน์ (ยืนยันแล้ว = **7 วัน** นับจากการเข้าสู่ระบบด้วยรหัสผ่านครั้งล่าสุดที่เชื่อมต่อสำเร็จ) รวมถึง negative case ของกลไก PIN (กรอกผิด, การบังคับตั้ง PIN ก่อนเข้าใช้งานฟังก์ชันหลัก) ตาม FR-25/FR-27 และกลไกจำกัดจำนวนครั้งที่กรอก PIN ผิด (NFR-11 — ล้าง credential/PIN และบังคับเข้าสู่ระบบใหม่เมื่อครบ 5 ครั้ง ตามที่ผู้ใช้ยืนยันเมื่อ 2026-09-04) **โดยต้องทดสอบร่วมกับ NFR-01 เสมอว่าข้อมูลแบบสำรวจที่ยังไม่ซิงค์ไม่ถูกลบไปพร้อมการล้าง credential**
- **Data Integrity Testing (Reporting Consistency)** — NFR-10: ทดสอบว่าระเบียนที่ยังมีสถานะ "รอแก้ไขความขัดแย้ง" ไม่ถูกนับรวมใน dashboard (FR-22) หรือรายงานที่ส่งออก (FR-23) จนกว่าจะแก้ไขเสร็จ

## 3. Environment (สภาพแวดล้อมการทดสอบ)

`docs/02-design/02-technical/technology-stack.md` ยังไม่มีการตัดสินใจเรื่อง tech stack ในโปรเจกต์นี้ — **รอกำหนด tech stack ก่อน** จึงยังไม่สามารถระบุ environment เชิงเทคนิค (อุปกรณ์ทดสอบจริง, เวอร์ชันระบบปฏิบัติการ, เครื่องมือทดสอบอัตโนมัติ, ระบบจัดการ test execution) ได้ในตอนนี้ เมื่อมีการตัดสินใจ tech stack แล้วให้กลับมาเติมเนื้อหาส่วนนี้

สิ่งที่ระบุได้แล้วจาก NFR-04 (ไม่ผูก tech stack): ต้องทดสอบบนอุปกรณ์มือถือ/แท็บเล็ตภายใต้สภาพแวดล้อมกลางแจ้งจำลอง (แสงจ้า/ฝุ่น/ความชื้น) เพื่อให้ครอบคลุมสภาพการใช้งานจริงหลังเหตุอุทกภัย

สิ่งที่ระบุได้แล้วจาก NFR-03/ฟีเจอร์ 13 และฟีเจอร์ 15 (ไม่ผูก tech stack): การทดสอบตรวจจับ/แก้ไขความขัดแย้งของข้อมูลต้องมี**อุปกรณ์ภาคสนามอย่างน้อย 2 เครื่อง** ที่แก้ไขข้อมูลอาคารเดียวกันขณะออฟไลน์แยกกันแล้วซิงค์พร้อมกัน จึงจะจำลองสถานการณ์ conflict ได้จริง และต้องมีบัญชีผู้ใช้บทบาทหัวหน้าผู้สำรวจ/ผู้ดูแลระบบสำหรับทดสอบหน้าจอ back-office ของฟีเจอร์ 15 แยกจากบัญชีผู้สำรวจภาคสนามที่สร้างความขัดแย้ง

สิ่งที่ระบุได้แล้วจาก NFR-11/ฟีเจอร์ 14 (ไม่ผูก tech stack, ปิดข้อสมมติแล้ว 2026-09-04): จำนวนครั้งสูงสุดที่อนุญาตให้กรอก PIN ผิดก่อนถูกล็อกได้รับการยืนยันจากผู้ใช้แล้วเป็น **5 ครั้ง** (เดิมเสนอช่วง 5-10 ครั้ง) test data ของ TC-14-13–TC-14-15 จึงระบุตัวเลข 5 ตรงๆ ได้แล้ว สภาพแวดล้อมทดสอบยังคงต้อง**สามารถตั้งค่า/ยืนยันได้ว่าระบบจริง (เมื่อพัฒนาแล้ว) บังคับใช้ค่า 5 ครั้งตรงตามที่กำหนด** (เช่น ผ่านหน้าจอ config หรือค่าคงที่ที่ทีมพัฒนากำหนดไว้) เพื่อจับ regression หากค่าที่ implement จริงคลาดเคลื่อนจากที่ปิดไว้

## 4. Risk Management (การบริหารความเสี่ยงของการทดสอบ)

ความเสี่ยงด้านล่าง derive จาก NFR ทั้ง 10 ตัวใน [[backlog]] และบริบทจริงของระบบ (ใช้งานกลางแจ้งในพื้นที่ภัยพิบัติ, ต้องออฟไลน์เต็มรูปแบบ, ผลลัพธ์กระทบการตัดสินใจเรื่องความปลอดภัยในการเข้าใช้อาคาร, AI ช่วยวิเคราะห์แต่คนต้องยืนยันเสมอ, tech stack ยังไม่ตัดสินใจ) ไม่ใช่รายการความเสี่ยงทั่วไปที่ใช้ได้กับทุกโปรเจกต์

| ความเสี่ยง | โอกาสเกิด | ผลกระทบ | แนวทางรับมือ | รหัส FR/NFR ที่เกี่ยวข้อง |
|---|---|---|---|---|

## 5. Entry Criteria (เกณฑ์เริ่มทดสอบ)

- [[feature-list]] และ [[user-journey]] มีเนื้อหาครบและสอดคล้องกับ [[backlog]] แล้ว (ตรวจสอบแล้วในรอบนี้)
- [[acceptance-criteria]] เขียนครบทุกรหัส FR/NFR ที่เกี่ยวข้องกับฟีเจอร์ที่จะทดสอบ
- มี test case แบบ step-by-step ในไฟล์ `test-cases/{feature-slug}.md` ของฟีเจอร์นั้นแล้ว
- (เมื่อเริ่มพัฒนาจริง) มี build/environment ที่พร้อมให้ทดสอบตามที่จะระบุใน `technology-stack.md`

## 6. Exit Criteria (เกณฑ์ผ่านการทดสอบ)

- Test case ทั้งหมดของฟีเจอร์ระดับ Must have (MVP) ผ่านผลลัพธ์ตามที่คาดหวัง 100%
- Test case ของฟีเจอร์ระดับ Should have ผ่านผลลัพธ์ตามที่คาดหวังอย่างน้อย 90% หรือมีแผนแก้ไขข้อบกพร่องที่เหลือชัดเจนก่อน release
- ไม่มี defect ระดับวิกฤต (critical) ที่กระทบการทำงานออฟไลน์ (NFR-01–NFR-04), ความถูกต้องของการสรุปผล 3 ระดับสี (FR-10), กลไก human-in-the-loop ของ AI (FR-14), การปนเปื้อนของข้อมูลที่ยังขัดแย้งเข้า dashboard/รายงาน (NFR-10), กลไกปลดล็อก/หมดอายุ PIN ออฟไลน์ 7 วัน (FR-27, NFR-09 — รวมถึงการรักษาข้อมูลที่ยังไม่ได้ซิงค์ไม่ให้สูญหายขณะถูกล็อก), หรือกลไกล้าง credential/PIN เมื่อกรอก PIN ผิดครบจำนวนครั้งสูงสุด (NFR-11 — โดยเฉพาะการรักษาข้อมูลแบบสำรวจที่ยังไม่ซิงค์ไม่ให้ถูกลบไปพร้อมกัน) ค้างอยู่
- ผลการรันทดสอบถูกบันทึกไว้ใน `docs/03-testing/02-test-result/` (เมื่อมีซอร์สโค้ดให้ทดสอบจริง — ปัจจุบันโฟลเดอร์นี้ยังไม่มีเนื้อหาเพราะยังไม่มีการพัฒนา)
