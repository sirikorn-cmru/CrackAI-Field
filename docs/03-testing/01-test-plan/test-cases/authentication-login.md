# Test Case: ยืนยันตัวตนและเข้าสู่ระบบ

อ้างอิง: [[feature-list#14. ยืนยันตัวตนและเข้าสู่ระบบ|ฟีเจอร์ 14]] · ปรากฏเป็นขั้นตอนแรกของทุก journey ใน [[user-journey]] (journey ผู้สำรวจภาคสนามแยกขั้นตอนนี้เป็น 8 ขั้นตอนย่อย: ตรวจสัญญาณ → ล็อกอิน+ตั้ง PIN → ตรวจอายุ PIN → ปลดล็อกด้วย PIN → ตรวจจำนวนครั้งที่กรอก PIN ผิด (NFR-11) → ล้าง credential เมื่อครบจำนวน หรือรอสัญญาณเพื่อล็อกอินใหม่เมื่อ PIN หมดอายุ → บังคับสิทธิ์) · [[acceptance-criteria#14. ยืนยันตัวตนและเข้าสู่ระบบ|acceptance-criteria]]

หมายเหตุอัปเดต (2026-09-03): ผู้ใช้ปิดข้อสมมติค้าง — กลไกยืนยันตัวตนคือ "รหัสผ่านครั้งแรก + ตั้ง PIN สำหรับปลดล็อกออฟไลน์" และอายุ PIN/เซสชันที่แคชไว้ = **7 วัน** นับจากการเข้าสู่ระบบด้วยรหัสผ่านครั้งล่าสุดที่เชื่อมต่อสำเร็จ ปรับปรุงตารางนี้ให้ตรงกับค่าที่ปิดแล้ว เพิ่ม TC-14-04, TC-14-05, TC-14-09, TC-14-12 ใหม่ และแก้ไข TC-14-08/TC-14-10/TC-14-11 (เดิม TC-14-06/07/08) ให้อ้างอิง PIN + 7 วันแทนข้อความ "รอ spec กำหนด"

หมายเหตุอัปเดตเพิ่มเติม (2026-09-03 — เพิ่ม NFR-11): backlog เพิ่มรหัสใหม่ **NFR-11 (Security — PIN Attempt Lockout, ระดับความสำคัญสูง)** หลังพบระหว่างเขียน test case ของ FR-27 ว่าไม่มีกลไกจำกัดจำนวนครั้งที่กรอก PIN ผิด เพิ่ม TC-14-13, TC-14-14, TC-14-15 ใหม่ครอบคลุม happy path (ล้าง credential แล้วบังคับล็อกอินใหม่), เงื่อนไขที่ห้ามพลาดที่สุด (ข้อมูลแบบสำรวจที่ยังไม่ซิงค์ต้องไม่ถูกลบ) และ boundary (กรอกผิดยังไม่ครบจำนวนครั้งสูงสุด) — **จำนวนครั้งสูงสุดที่แน่นอนยังไม่ยืนยันจากผู้ใช้** (spec เสนอช่วง 5-10 ครั้ง) ทุก TC ด้านล่างจึงอ้างอิงเป็น "จำนวนครั้งสูงสุดที่ตั้งไว้จริงในระบบ" แทนตัวเลขตายตัว
