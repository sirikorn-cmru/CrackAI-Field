## 1. Brand Identity & CI

### 1.1 ผลิตภัณฑ์นี้คืออะไร

**CrackAI-Field** คือเครื่องมือสำรวจความเสียหายขั้นต้นของโครงสร้างอาคารหลังเหตุการณ์อุทกภัย อิงแบบฟอร์มของกรมโยธาธิการและผังเมือง (DPT) ผู้ใช้หลักคือผู้สำรวจภาคสนามที่ทำงาน **กลางแจ้ง ในพื้นที่ประสบภัย ไม่มีสัญญาณอินเทอร์เน็ต และมักอยู่ภายใต้ความกดดันด้านเวลา**

ผลลัพธ์ของการสำรวจคือการตัดสินว่าอาคารหลังหนึ่ง **เข้าใช้งานได้ / ใช้ได้แต่ต้องระวัง / ห้ามเข้า** ซึ่งเป็นข้อมูลที่กระทบความปลอดภัยของชีวิตคนโดยตรง

### 1.2 หลักการออกแบบ (Design Principles)

หลักการเรียงตามลำดับความสำคัญ — เมื่อขัดแย้งกัน ข้อที่อยู่บนกว่าชนะเสมอ

| # | หลักการ | ความหมายในทางปฏิบัติ |
|---|---|---|
| 1 | **อ่านผิดไม่ได้ (Unmistakable)** | ระดับความเสียหายและสถานะข้อมูลต้องตีความผิดไม่ได้ แม้อยู่กลางแดด สวมถุงมือ หรือรีบ — ความชัดเจนสำคัญกว่าความสวยงามเสมอ |
| 2 | **เงียบและไม่รบกวน (Quiet)** | อินเทอร์เฟซไม่แย่งความสนใจจากเนื้อหา ไม่มีการตกแต่งที่ไม่ได้ทำหน้าที่ ไม่มีสีสันเพื่อความสนุก |
| 3 | **ซื่อตรง (Honest)** | ระบบต้องบอกความจริงเสมอว่าข้อมูลอยู่สถานะใด — ยังไม่ซิงค์, AI เป็นคนเสนอ, ข้อมูลขัดแย้งอยู่ ห้ามซ่อนความไม่แน่นอนเพื่อให้หน้าจอดูสะอาด |
| 4 | **ให้อภัย (Forgiving)** | งานภาคสนามเกิดอุบัติเหตุเสมอ — กดพลาด แอปถูกปิด แบตหมด ระบบต้องกู้คืนงานได้และย้อนกลับได้ |
| 5 | **เรียบง่ายอย่างตั้งใจ (Considered Simplicity)** | ลดทุกอย่างจนเหลือเท่าที่จำเป็น แต่ไม่ตัดสิ่งที่ผู้ใช้ต้องการจริง |

### 1.3 ภาษาทางสายตา (Visual Language)

ได้แรงบันดาลใจจากแนวทาง **Muji / earth tone / minimalist**:

- **วัสดุคือพื้นหลัง** — พื้นผิวเป็นโทนกระดาษและผ้าลินินอุ่น ไม่ใช่ขาวจ้าหรือเทาเย็น
- **เส้นแทนเงา** — ใช้เส้นขอบบางแบ่งพื้นที่ ไม่ใช้เงาลอยเพื่อสร้างมิติ (ยกเว้น overlay ที่ต้องบอกลำดับชั้นจริงๆ)
- **มุมเกือบตรง** — รัศมีมุมเล็กมาก ไม่ใช้ปุ่มทรงแคปซูล
- **ไม่มีไล่ระดับสี ไม่มีความมันวาว** — สีทึบเรียบเท่านั้น
- **ที่ว่างคือองค์ประกอบ** — ใช้ระยะห่างจัดลำดับความสำคัญแทนการใช้กรอบ สี หรือขนาดที่ฉูดฉาด
- **สีคือสัญญาณ ไม่ใช่การตกแต่ง** — สีสดปรากฏได้เฉพาะเมื่อสื่อสถานะเท่านั้น

### 1.4 ข้อยกเว้นสำคัญที่ต้องเข้าใจก่อนใช้เอกสารนี้

> **สีสถานะความเสียหายไม่อยู่ภายใต้สุนทรียะ Muji**
>
> โทน earth tone ต้องการสีที่ลดความอิ่มตัวและกลมกลืน แต่สีเขียว/เหลือง/แดง ที่บอกว่าอาคารเข้าได้หรือไม่เป็น **ข้อมูลความปลอดภัยต่อชีวิต** การทำให้จางลงเพื่อความสวยงามคือการออกแบบที่ผิด
>
> ทางออกของระบบนี้: ใช้สีสถานะที่ **ลดความอิ่มตัวลงพอให้เข้ากับ earth tone แต่ยังเข้มและต่างเฉดกันชัดเจน** แล้ว **บังคับให้ทุกจุดที่ใช้สีสถานะต้องมีไอคอนและข้อความไทยกำกับเสมอ** (ดู [กติกา UX-02](#ux-02-ห้ามใช้สีสื่อความหมายเพียงลำพัง)) ความชัดเจนจึงไม่ได้พึ่งสีเพียงอย่างเดียว

## 2. Design Tokens

Token คือชื่อที่ใช้อ้างอิงค่าจริง **โค้ดทุกที่ต้องอ้าง token ห้ามเขียนค่าดิบ (hard-coded) ลงไปตรงๆ**

### 2.1 สี — พื้นผิวและตัวอักษร (Neutral / Earth Base)

โทนกลางทั้งหมดมี hue อุ่น (เอนไปทางเบจ/ดินเผา) ไม่มีเทาเย็นในระบบนี้

| Token | ค่า | ใช้เมื่อ |
|---|---|---|
| `--surface-page` | `#FAF8F5` | พื้นหลังหน้าจอหลัก (โทนกระดาษ ไม่ใช่ขาวบริสุทธิ์) |
| `--surface-raised` | `#FFFFFF` | การ์ด แผงเนื้อหา ที่ต้องยกจากพื้นหลัง |
| `--surface-sunken` | `#F2EEE9` | พื้นที่ยุบ เช่น หัวตาราง แถบเครื่องมือ ช่องกรอกที่ยังไม่โฟกัส |
| `--surface-muted` | `#E8E2DA` | พื้นที่ปิดใช้งาน แถบคั่นหมวด |
| `--border-subtle` | `#E0D9CF` | เส้นแบ่งภายในการ์ด แถวตาราง |
| `--border-default` | `#CFC6B8` | ขอบการ์ด ขอบช่องกรอก |
| `--border-strong` | `#948770` | ขอบที่ต้องเห็นชัด เช่น ช่องกรอกที่โฟกัส |
| `--text-primary` | `#2B2620` | ข้อความหลัก หัวข้อ (คำนวณแล้ว 14.14:1 บน `--surface-page`) |
| `--text-secondary` | `#57503F` | ข้อความรอง คำอธิบาย (คำนวณแล้ว 7.55:1 ผ่าน AAA) |
| `--text-tertiary` | `#736B5A` | ข้อความประกอบ ป้ายกำกับ (คำนวณแล้ว 4.98:1 ผ่าน AA) |
| `--text-disabled` | `#A69C8B` | ข้อความที่ปิดใช้งาน — **ห้ามใช้กับข้อมูลที่ผู้ใช้ต้องอ่าน** |
| `--text-on-dark` | `#FAF8F5` | ข้อความบนพื้นเข้ม |

### 2.2 สี — แบรนด์และการกระทำ (Brand / Action)

> **เหตุผลที่สีหลักของแบรนด์เป็นสีน้ำตาลเข้ม ไม่ใช่เขียว/เหลือง/แดง**: สามสีนั้นถูกจองไว้สื่อระดับความเสียหายทั้งหมดแล้ว ถ้าปุ่มหลักเป็นสีเขียว ผู้ใช้จะสับสนระหว่าง "ปุ่มที่กดได้" กับ "อาคารปลอดภัย" สีน้ำตาลอมเทาเข้มจึงเป็นทางเลือกที่ทั้งเข้ากับ earth tone และไม่มีวันถูกเข้าใจผิดเป็นสถานะ

| Token | ค่า | ใช้เมื่อ |
|---|---|---|
| `--brand-primary` | `#4A4139` | ปุ่มหลัก องค์ประกอบที่แทนแบรนด์ |
| `--brand-primary-hover` | `#3A322B` | สถานะ hover/pressed ของปุ่มหลัก |
| `--brand-primary-subtle` | `#EDE8E1` | พื้นหลังอ่อนของสถานะเลือกอยู่ |
| `--accent-info` | `#39495B` | ลิงก์ ข้อความระบบ ไอคอนให้ข้อมูล (คราม-เทา ไม่ใช่สถานะความเสียหาย) |
| `--accent-info-subtle` | `#E7EBF0` | พื้นหลังของกล่องข้อความให้ข้อมูล |
| `--focus-ring` | `#39495B` | เส้นขอบตอนโฟกัสด้วยคีย์บอร์ด (หนา 2px + เว้น 2px) |

### 2.3 สี — ระดับความเสียหาย (Damage Severity) 🔴 สำคัญที่สุด

สามระดับนี้มาจากแบบฟอร์ม DPT โดยตรง ([[feature-list|ฟีเจอร์ 3]], FR-10) **ห้ามเปลี่ยนความหมาย ห้ามเพิ่มระดับ ห้ามใช้สีเหล่านี้กับเรื่องอื่นเด็ดขาด**

| ระดับ | Token ข้อความ/ไอคอน | Token พื้นหลัง | Token ขอบ | ความหมาย |
|---|---|---|---|---|
| **เขียว** | `--severity-safe-fg` `#1B5136` | `--severity-safe-bg` `#E4EDE6` | `--severity-safe-border` `#7FA893` | เสียหายเล็กน้อยหรือไม่เสียหาย ใช้งานได้ปกติ |
| **เหลือง** | `--severity-caution-fg` `#66440C` | `--severity-caution-bg` `#F7EDD8` | `--severity-caution-border` `#C9A253` | เสียหายปานกลาง ใช้งานได้แต่ต้องระวัง |
| **แดง** | `--severity-danger-fg` `#82261D` | `--severity-danger-bg` `#F5E3E0` | `--severity-danger-border` `#BF7A72` | เสียหายหนัก อาจพังถล่ม ห้ามใช้งาน |

**กติกาการใช้:**
- โทน `-fg` ผ่านคอนทราสต์ **≥ 7:1 (WCAG AAA)** ทั้งบนพื้น `--surface-page` (8.26–8.83:1) และบนพื้น `-bg` ของตัวเอง (7.53–7.71:1) — คำนวณยืนยันแล้วทุกค่า เข้มกว่ามาตรฐานทั่วไปเพราะต้องอ่านกลางแดด
- สีเหลืองใช้เฉด **ออกน้ำตาลทอง (ochre)** ไม่ใช่เหลืองสด เพราะเหลืองสดบนพื้นสว่างไม่มีทางผ่านคอนทราสต์ได้
- **ทุกครั้งที่ใช้สีเหล่านี้ ต้องมีไอคอนรูปทรงต่างกันและข้อความไทยกำกับ** (ดู [UX-02](#ux-02-ห้ามใช้สีสื่อความหมายเพียงลำพัง))
- ไอคอนประจำระดับ: เขียว = วงกลม · เหลือง = สามเหลี่ยม · แดง = แปดเหลี่ยม (รูปทรงต่างกันเพื่อให้แยกได้แม้มองเห็นสีผิดปกติ)

### 2.4 สี — สถานะระบบ (System State)

แยกจากสีความเสียหายโดยสิ้นเชิง ห้ามใช้ปนกัน **และแยกจากสถานะความคืบหน้าของงานด้านล่างโดยสิ้นเชิงเช่นกัน** — กลุ่มนี้สื่อ **สถานะการซิงค์ข้อมูลระหว่างอุปกรณ์กับเซิร์ฟเวอร์เท่านั้น** (NFR-01/02) ห้ามนำ `--state-pending-*` / `--state-synced-*` ไปใช้สื่อความหมายอื่นใดเด็ดขาด แม้จะรู้สึกว่าคำว่า "pending/synced" ฟังดูใช้ได้กับสถานะอื่นก็ตาม — ดูเหตุผลที่ [UX-14](#ux-14-แยก-token-ตามความหมาย-ห้ามข้ามกลุ่มความหมาย)

| Token | ค่า | ใช้เมื่อ |
|---|---|---|
| `--state-offline-fg` / `-bg` | `#6B5B45` / `#F0EBE1` | ทำงานออฟไลน์อยู่ (NFR-01) |
| `--state-pending-fg` / `-bg` | `#5C5346` / `#EFEBE4` | รอซิงค์ ยังไม่ส่งขึ้นเซิร์ฟเวอร์ (เฉพาะการซิงค์เท่านั้น) |
| `--state-synced-fg` / `-bg` | `#41564A` / `#E9EEEA` | ซิงค์แล้ว (เฉพาะการซิงค์เท่านั้น) |
| `--state-conflict-fg` / `-bg` | `#6F3860` / `#F1E7EF` | ข้อมูลขัดแย้งรอแก้ไขด้วยมือ (FR-30/31) |
| `--state-ai-fg` / `-bg` | `#39495B` / `#E7EBF0` | ค่าที่ AI เสนอ ยังไม่ได้ยืนยัน (FR-13/14) |

> **สีม่วงอมน้ำตาลของ conflict เป็นสีเดียวในระบบที่ไม่ใช่ earth tone แท้** — จงใจ เพราะข้อมูลขัดแย้งต้องสะดุดตาในตารางที่เต็มไปด้วยโทนดิน และต้องไม่ถูกสับสนกับสถานะความเสียหายทั้งสามสี

**สถานะความคืบหน้าของงาน/การตรวจทาน (Task & Review Progress — คนละเรื่องกับสถานะซิงค์ด้านบน)**

ใช้กับความคืบหน้าเชิงงาน (FR-19/20): สถานะงานที่หัวหน้าทีมมอบหมาย, สถานะงานที่ผู้สำรวจภาคสนามได้รับ, สถานะแถวในคิวตรวจทาน, และขั้นตอนที่ทำแล้วในวิซาร์ดสำรวจ — เพิ่มขึ้นเพราะพบว่า Prototype เคยนำ token สถานะซิงค์ไปใช้กับความหมายนี้โดยไม่ตั้งใจ (semantic drift) จึงต้องมี token ของตัวเองแยกออกมาชัดเจน เพื่อไม่ให้การเปลี่ยนสีสถานะซิงค์ในอนาคตกระทบสถานะงานโดยไม่ได้ตั้งใจ และไม่ให้คนอ่านโค้ดเข้าใจผิดว่าเกี่ยวกับการซิงค์

| Token | ค่า | ใช้เมื่อ |
|---|---|---|
| `--state-progress-todo-fg` / `-bg` | `#5C5346` / `#EFEBE4` | งาน/รายการที่ยังไม่เริ่มหรือยังไม่ดำเนินการ (งานที่มอบหมายแล้วแต่ยังไม่ทำ, รายการที่ยังไม่ถูกตรวจทาน, ขั้นตอนวิซาร์ดที่ยังไม่ถึง) — FR-19/20 |
| `--state-progress-done-fg` / `-bg` | `#41564A` / `#E9EEEA` | งาน/รายการที่เสร็จสิ้นแล้ว (งานที่ทำเสร็จแล้ว, รายการที่ตรวจทานแล้ว, ขั้นตอนวิซาร์ดที่ผ่านแล้ว) — FR-19/20 |

> **ทำไมค่าสีจึงซ้ำกับ `--state-pending-*` / `--state-synced-*` ทุกตัวอักษร**: จงใจใช้ค่าเดียวกันเพื่อไม่ต้องคำนวณคอนทราสต์ใหม่ (ค่านี้ผ่าน AAA ≥7:1 ทั้งบนพื้น `--surface-page` และบนพื้น `-bg` ของตัวเองแล้วตามหัวข้อ 2.3) แต่ตั้งใจแยกเป็นคนละชื่อ token เพื่อ **ตัดการเชื่อมโยงเชิงความหมาย** — วันไหนที่อยากเปลี่ยนสีสถานะซิงค์ (เช่น เปลี่ยนเพราะทดสอบผู้ใช้แล้วสับสน) จะไม่กระทบสีสถานะความคืบหน้าของงานโดยอัตโนมัติ และในทางกลับกัน หากพบว่าสีทั้งสองกลุ่มดูเหมือนกันเกินไปจนผู้ใช้สับสนเมื่อขึ้นพร้อมกันในหน้าเดียว (เช่นแถบซิงค์ + ป้ายสถานะงานในหน้าเดียวกัน) ให้ปรับสีกลุ่มใดกลุ่มหนึ่งให้ต่างออกไปในรอบถัดไป — ยังไม่พบเคสจริงที่ขึ้นพร้อมกันจนกระทบการอ่าน จึงยังไม่ปรับตอนนี้ (ดู [สิ่งที่ยังไม่ตัดสินใจ](#5-สิ่งที่ยังไม่ตัดสินใจ))

**สถานะบัญชีผู้ใช้ (Account Status — คนละเรื่องกับสถานะซิงค์และความคืบหน้าของงานด้านบน)**

ใช้กับการเปิด/ปิดใช้งานบัญชีผู้ใช้ในหน้าจอผู้ดูแลระบบ (FR-21, NFR-08) — เพิ่มขึ้นเพราะพบว่า Prototype เคยยืม `--state-synced-*`/`--state-offline-*` ไปสื่อความหมายนี้โดยไม่ตั้งใจ เป็น semantic drift โดเมนที่สามที่พบต่อจากกรณีสถานะความคืบหน้าของงานด้านบน จึงต้องมี token ของตัวเองแยกออกมาชัดเจนเช่นกัน

| Token | ค่า | ใช้เมื่อ |
|---|---|---|
| `--state-account-active-fg` / `-bg` | `#41564A` / `#E9EEEA` | บัญชีใช้งานได้ตามปกติ (FR-21) |
| `--state-account-inactive-fg` / `-bg` | `#5C5346` / `#EFEBE4` | บัญชีถูกปิดใช้งานแล้ว เข้าสู่ระบบไม่ได้ (FR-21, NFR-08) |

> **ทำไมไม่ใช้ `--text-disabled`/`--surface-muted` กับ "ปิดใช้งานแล้ว"**: สอง token นั้นออกแบบมาสำหรับองค์ประกอบ UI ที่ถูกปิดใช้งานเชิงโต้ตอบ (เช่นปุ่มกดไม่ได้ชั่วคราว) และมีคอนทราสต์ต่ำโดยตั้งใจ ตามกติกาในหัวข้อ 2.1 ที่ห้ามใช้ `--text-disabled` กับ "ข้อมูลที่ผู้ใช้ต้องอ่าน" — แต่สถานะบัญชีในหน้าผู้ดูแลระบบเป็นข้อมูลที่ผู้ดูแลต้องอ่านและตัดสินใจต่อจากมันจริง (เช่น จะเปิดบัญชีคืนหรือไม่) จึงต้องผ่านเกณฑ์คอนทราสต์เดียวกับข้อความสำคัญอื่น ไม่ใช่ค่าที่จงใจจางกว่าปกติ
>
> **ทำไมไม่ใช้ `--state-offline-*`**: "ปิดใช้งานแล้ว" ไม่เกี่ยวกับการเชื่อมต่อเครือข่ายเลย การยืมสีออฟไลน์มาใช้จะทำให้ผู้ดูแลระบบสับสนว่าบัญชีนี้ "ยังไม่ได้ซิงค์" หรือ "อุปกรณ์ออฟไลน์อยู่" ซึ่งเป็นคนละเรื่องกันโดยสิ้นเชิง
>
> **ทำไมค่าสีจึงซ้ำกับ `--state-progress-done-*`/`--state-progress-todo-*` ทุกตัวอักษร**: ใช้แนวทางเดียวกับที่ตัดสินใจไว้กับกลุ่มความคืบหน้าของงานด้านบน — ไม่ต้องคำนวณคอนทราสต์ใหม่ (ค่านี้ผ่าน AAA ≥7:1 ตามที่ยืนยันไว้แล้วในหัวข้อ 2.3) และเลือกจับคู่ความหมายที่ใกล้เคียงกัน ("ใช้งานอยู่" ≈ สถานะปกติ/บวก เหมือน "เสร็จแล้ว", "ปิดใช้งานแล้ว" ≈ สถานะเป็นกลาง-ลบเล็กน้อย เหมือน "ยังไม่เริ่ม") แต่แยกชื่อ token เพื่อตัดการเชื่อมโยงเชิงความหมายระหว่างสามโดเมนนี้อย่างเด็ดขาด — ถ้าพบเคสจริงที่สถานะบัญชีต้องแสดงพร้อมกับสถานะซิงค์หรือสถานะความคืบหน้าของงานในหน้าจอเดียวกันจนผู้ใช้แยกไม่ออก ต้องกลับมาแยกค่าสีให้ต่างกันจริงในรอบถัดไป (ยังไม่พบเคสจริงในขณะนี้ — ดู [สิ่งที่ยังไม่ตัดสินใจ](#5-สิ่งที่ยังไม่ตัดสินใจ))

### 2.5 ตัวอักษร (Typography)

**ฟอนต์**: เลือกฟอนต์ที่รองรับภาษาไทยครบทั้งวรรณยุกต์และสระซ้อน มีน้ำหนักหลายระดับ และมีรูปทรงเรียบแบบ neutral grotesque

```
--font-sans: "IBM Plex Sans Thai", "Noto Sans Thai", "Sarabun",
             -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif;
--font-mono: "IBM Plex Mono", ui-monospace, "Courier New", monospace;
```

`--font-mono` ใช้เฉพาะ **ตัวเลขที่ต้องเทียบกันเป็นคอลัมน์** เช่น พิกัด GPS ค่า `data_version` และหน้าจอเปรียบเทียบเวอร์ชันที่ขัดแย้ง

**สเกลขนาด** — ระบบมีสองบริบทที่ต้องการขนาดต่างกัน

| Token | ภาคสนาม (มือถือ/แท็บเล็ต) | Back-office (เดสก์ท็อป) | ใช้กับ |
|---|---|---|---|
| `--text-xs` | 13px | 12px | ป้ายกำกับเล็ก คำอธิบายใต้ช่องกรอก |
| `--text-sm` | 15px | 14px | ข้อความรอง ป้ายสถานะ |
| `--text-base` | **17px** | 15px | ข้อความเนื้อหาหลัก |
| `--text-lg` | 20px | 18px | หัวข้อย่อย ชื่อหมวดในแบบฟอร์ม |
| `--text-xl` | 24px | 22px | หัวข้อหน้าจอ |
| `--text-2xl` | 30px | 28px | ตัวเลขสรุปใน dashboard |
| `--text-3xl` | 38px | 34px | ผลสรุประดับความเสียหายบนหน้าจอสรุป |

> **เหตุผลที่ภาคสนามใช้ 17px เป็นขนาดฐาน ไม่ใช่ 16px**: ผู้สำรวจอ่านหน้าจอกลางแดด ระยะห่างมือไม่คงที่ และอาจสวมแว่นกันแดด ขนาดที่เล็กกว่านี้ทำให้ต้องยกจอเข้าใกล้ตาซึ่งทำไม่ได้ขณะถือเครื่องมือหรือสวมถุงมือ

**น้ำหนัก**: `--weight-regular: 400` · `--weight-medium: 500` · `--weight-semibold: 600`
ห้ามใช้ 700 ขึ้นไป — หนาเกินไปสำหรับตัวอักษรไทยที่มีวรรณยุกต์ ทำให้สระและวรรณยุกต์ติดกันจนอ่านยาก

**ความสูงบรรทัด** — จุดนี้สำคัญเป็นพิเศษสำหรับภาษาไทย

| Token | ค่า | ใช้กับ |
|---|---|---|
| `--leading-tight` | 1.45 | หัวข้อขนาดใหญ่ (`--text-xl` ขึ้นไป) |
| `--leading-normal` | **1.70** | ข้อความเนื้อหาทั่วไป |
| `--leading-relaxed` | 1.85 | ย่อหน้ายาว คำอธิบายเชิงเกณฑ์จากคู่มือ |

> ภาษาไทยมีสระบนและวรรณยุกต์ซ้อนได้ถึงสองชั้น (เช่น "เขื่อน" "ตื้น") ความสูงบรรทัด 1.5 แบบที่ใช้กับภาษาอังกฤษทำให้วรรณยุกต์ของบรรทัดล่างชนสระของบรรทัดบน จึงกำหนดขั้นต่ำที่ **1.70** สำหรับเนื้อหา ห้ามลดต่ำกว่านี้เพื่อประหยัดพื้นที่

### 2.6 ระยะห่าง (Spacing)

ฐาน 4px ทุกค่าเป็นพหุคูณของ 4 เสมอ

| Token | ค่า | ใช้กับ |
|---|---|---|
| `--space-1` | 4px | ระยะระหว่างไอคอนกับข้อความ |
| `--space-2` | 8px | ระยะภายในองค์ประกอบเล็ก |
| `--space-3` | 12px | ระยะระหว่างช่องกรอกในกลุ่มเดียวกัน |
| `--space-4` | 16px | ระยะขอบมาตรฐานภายในการ์ด |
| `--space-6` | 24px | ระยะระหว่างกลุ่มช่องกรอก |
| `--space-8` | 32px | ระยะระหว่างหมวดในแบบฟอร์ม |
| `--space-12` | 48px | ระยะระหว่างส่วนหลักของหน้า |
| `--space-16` | 64px | ระยะขอบบน-ล่างของหน้า |

**ระยะขอบหน้าจอ**: มือถือ `--space-4` · แท็บเล็ต `--space-6` · เดสก์ท็อป `--space-8`
**ความกว้างเนื้อหาสูงสุด**: 720px สำหรับแบบฟอร์ม · 1280px สำหรับตาราง/dashboard

### 2.7 รัศมีมุม เส้นขอบ และเงา

```
--radius-sm: 2px;    /* ป้ายสถานะ ช่องติ๊ก */
--radius-md: 4px;    /* ปุ่ม ช่องกรอก — ค่าเริ่มต้นของระบบ */
--radius-lg: 8px;    /* การ์ด แผงเนื้อหา */
--radius-full: 999px; /* ใช้ได้เฉพาะรูปโปรไฟล์เท่านั้น */

--border-width: 1px;
--border-width-strong: 2px;  /* ช่องกรอกที่โฟกัส องค์ประกอบที่เลือกอยู่ */

--shadow-overlay: 0 4px 16px rgba(43, 38, 32, 0.12);
```

> **ระบบนี้ใช้เงาได้เพียงจุดเดียวคือ overlay** (modal, dropdown, sheet) ที่ต้องบอกว่าลอยอยู่เหนือเนื้อหาจริงๆ การ์ดและปุ่มทั้งหมดแยกตัวจากพื้นหลังด้วย **เส้นขอบและสีพื้นผิว** เท่านั้น เพราะเงาบนหน้าจอที่อ่านกลางแดดแทบมองไม่เห็น และเป็นการตกแต่งที่ไม่ทำหน้าที่

### 2.8 ขนาดพื้นที่กด (Touch Target) 🔴 สำคัญ

| Token | ค่า | ใช้กับ |
|---|---|---|
| `--touch-min` | 44px | ขั้นต่ำสัมบูรณ์ ทุกองค์ประกอบที่กดได้บนทุกอุปกรณ์ |
| `--touch-field` | **56px** | **ทุกองค์ประกอบที่กดได้บนหน้าจอภาคสนาม** |
| `--touch-critical` | 64px | ปุ่มเลือกระดับความเสียหาย ปุ่มยืนยันผล AI ปุ่มถ่ายภาพ |
| `--touch-gap` | 8px | ระยะห่างขั้นต่ำระหว่างสองพื้นที่กดที่อยู่ติดกัน |

> **เหตุผลที่ภาคสนามใช้ 56px ไม่ใช่ 44px**: 44px คือมาตรฐานสำหรับนิ้วเปล่าในสภาวะปกติ ผู้สำรวจในพื้นที่อุทกภัยสวมถุงมือยาง มือเปียก และอาจยืนบนพื้นไม่มั่นคง พื้นที่สัมผัสจริงของนิ้วจึงกว้างและแม่นยำน้อยกว่ามาก — ดู edge case ใน [[detailed-design/building-environment-info]]

### 2.9 การเคลื่อนไหว (Motion)

```
--duration-fast: 120ms;   /* ตอบสนองการกด เปลี่ยนสถานะ */
--duration-base: 200ms;   /* เปิด/ปิด panel */
--duration-slow: 320ms;   /* เปลี่ยนหน้าจอ */
--easing-standard: cubic-bezier(0.2, 0, 0.2, 1);
```

การเคลื่อนไหวมีไว้เพื่อ**อธิบายว่าอะไรเปลี่ยนไป**เท่านั้น ห้ามใช้เพื่อความบันเทิง ห้ามมีอนิเมชันวนซ้ำนอกจากตัวบ่งชี้ว่ากำลังประมวลผล และต้องเคารพ `prefers-reduced-motion: reduce` โดยลดเหลือการเปลี่ยนแบบทันที

## 3. UI Components & Patterns

ทุกองค์ประกอบต้องมีสถานะครบ: ปกติ (default), ชี้ (hover), กด (pressed), โฟกัสด้วยคีย์บอร์ด (focus-visible), ปิดใช้งาน (disabled), ผิดพลาด (error) และ **กำลังโหลด (loading)** ตามที่เกี่ยวข้อง

### 3.1 ปุ่ม (Button)

| ชนิด | รูปลักษณ์ | ใช้เมื่อ |
|---|---|---|
| **Primary** | พื้น `--brand-primary` ตัวอักษร `--text-on-dark` | การกระทำหลัก 1 ปุ่มต่อหน้าจอเท่านั้น |
| **Secondary** | พื้นโปร่ง ขอบ `--border-default` ตัวอักษร `--text-primary` | การกระทำรอง |
| **Ghost** | ไม่มีพื้นไม่มีขอบ ตัวอักษร `--accent-info` | การกระทำเสริม ลิงก์ในตาราง |
| **Destructive** | ขอบและตัวอักษร `--severity-danger-fg` พื้นโปร่ง | ลบ ยกเลิก ปฏิเสธ — **ต้องมีขั้นตอนยืนยันเสมอ** |

ความสูง: `--touch-field` (ภาคสนาม) / 40px (back-office) · รัศมี `--radius-md` · น้ำหนักตัวอักษร `--weight-medium`
**ปุ่ม Destructive ห้ามใช้พื้นสีแดงทึบ** เพราะจะแย่งความเด่นกับป้ายระดับความเสียหายสีแดงบนหน้าจอเดียวกัน

### 3.2 ช่องกรอกข้อมูล (Input, Textarea, Select)

- ความสูง `--touch-field` · ขอบ `--border-default` · พื้น `--surface-raised` · รัศมี `--radius-md`
- โฟกัส: ขอบเป็น `--border-strong` หนา `--border-width-strong` + `--focus-ring`
- **ป้ายกำกับอยู่เหนือช่องกรอกเสมอ ห้ามใช้ placeholder แทนป้ายกำกับ** เพราะ placeholder หายไปเมื่อเริ่มพิมพ์ ทำให้ผู้ใช้ลืมว่ากรอกอะไรอยู่ในฟอร์มที่ยาว 10 หมวด
- ข้อความผิดพลาดอยู่ใต้ช่องกรอก มีไอคอนกำกับ ใช้ `--severity-danger-fg`
- ช่องที่บังคับกรอกทำเครื่องหมายด้วยคำว่า "จำเป็น" ไม่ใช่เครื่องหมายดอกจัน

### 3.3 ช่องติ๊กและตัวเลือก (Checkbox / Radio)

แบบฟอร์ม DPT มีช่องติ๊กจำนวนมากมาก (การใช้สอยอาคาร 13 ประเภท, ชนิดโครงสร้าง 6 แบบ, วัสดุผนัง ฯลฯ) องค์ประกอบนี้จึงถูกใช้หนักที่สุดในระบบ

- **พื้นที่กดครอบคลุมทั้งแถวรวมข้อความ** ไม่ใช่เฉพาะกล่องสี่เหลี่ยม — สูงอย่างน้อย `--touch-field`
- ตัวกล่อง 24px ขอบ `--border-strong` เมื่อเลือกแล้วพื้นเป็น `--brand-primary`
- แถวที่เลือกอยู่มีพื้นหลัง `--brand-primary-subtle` เพื่อให้กวาดตาเห็นได้เร็วว่าติ๊กอะไรไปแล้ว
- Checkbox = รัศมี `--radius-sm` (เลือกได้หลายข้อ) · Radio = วงกลม (เลือกได้ข้อเดียว) — **รูปทรงต้องต่างกันเสมอ** เพื่อสื่อกฎการเลือกโดยไม่ต้องอ่านคำอธิบาย

### 3.4 ตัวเลือกระดับความเสียหาย (Severity Selector) 🔴

องค์ประกอบที่สำคัญที่สุดของผลิตภัณฑ์ ใช้ทั้งในหมวดโครงสร้างและหน้าสรุปผล

- ปุ่มสามช่องเรียงกัน ความสูง `--touch-critical`
- แต่ละช่องประกอบด้วย **ไอคอนรูปทรงเฉพาะ + ชื่อระดับเป็นภาษาไทย + คำอธิบายสั้น** ครบทั้งสามอย่าง
- สถานะยังไม่เลือก: พื้น `--surface-raised` ขอบ `--border-default` ตัวอักษร `--text-secondary` — **สีของระดับยังไม่ปรากฏ**
- สถานะเลือกแล้ว: พื้น `--severity-*-bg` ขอบ `--severity-*-border` หนา 2px ตัวอักษรและไอคอน `--severity-*-fg`
- **ห้ามเลือกค่าเริ่มต้นให้อัตโนมัติ** ต้องเป็นการตัดสินใจของผู้สำรวจเสมอ — ค่าเริ่มต้นจะทำให้เกิดการกดผ่านโดยไม่ได้ประเมินจริง

### 3.5 การ์ดผลวิเคราะห์จาก AI (AI Suggestion Card) 🔴

รองรับ FR-13/FR-14 (human-in-the-loop) และ FR-28/FR-29 — ดู [[detailed-design/ai-crack-photo-analysis]]

- ใช้พื้น `--state-ai-bg` และ **ขอบประ (dashed)** `--state-ai-fg` เพื่อสื่อว่า "ยังไม่ใช่ข้อมูลจริง"
- มีป้ายข้อความชัดเจนว่า **"AI เสนอ — รอการยืนยัน"** ห้ามละ
- ต้องมีปุ่มสามทางเสมอ: **ยืนยันตามที่เสนอ** · **แก้ไขค่า** · **กรอกเอง**
- เมื่อยืนยันแล้ว การ์ดเปลี่ยนเป็นขอบทึบและแสดงที่มาของค่า (ยืนยันตาม AI / แก้ไขจาก AI / กรอกเอง) ตาม `source_of_value` ใน [[db-spec]]
- กรณี AI วิเคราะห์ไม่สำเร็จ (FR-28): แสดงสาเหตุเป็นภาษาที่คนทั่วไปเข้าใจ พร้อมปุ่ม **ถ่ายภาพใหม่** และ **กรอกเอง** โดยสองปุ่มมีน้ำหนักทางสายตาเท่ากัน

> **ห้ามออกแบบให้ "กรอกเอง" ดูเป็นทางเลือกสำรอง** — FR-29 กำหนดว่าการกรอกเองเป็นเส้นทางปกติที่ใช้ได้ตั้งแต่ต้น ถ้าปุ่มกรอกเองเล็กกว่าหรือจางกว่าปุ่มใช้ AI แปลว่าออกแบบผิดข้อกำหนด

### 3.6 ตัวบ่งชี้สถานะการซิงค์ (Sync Status Indicator)

- อยู่ตำแหน่งคงที่บนหน้าจอภาคสนาม **มองเห็นได้ตลอดเวลา** ไม่ใช่ซ่อนในเมนู
- สี่สถานะ ใช้ token จาก [2.4](#24-สี--สถานะระบบ-system-state): ออฟไลน์ · รอซิงค์ (พร้อมจำนวนรายการ) · กำลังซิงค์ · ซิงค์แล้ว
- **สถานะออฟไลน์ต้องไม่ใช้สีแดงหรือไอคอนเตือนภัย** — การทำงานออฟไลน์คือพฤติกรรมปกติของระบบนี้ตาม NFR-01 ไม่ใช่ความผิดพลาด การทำให้ดูเหมือนข้อผิดพลาดจะสร้างความกังวลที่ไม่จำเป็นตลอดวันทำงาน

### 3.7 มุมมองเปรียบเทียบเวอร์ชันที่ขัดแย้ง (Conflict Comparison)

รองรับ FR-30/FR-31 — ดู [[detailed-design/manual-conflict-resolution]]

- แสดงสองคอลัมน์เคียงกัน แต่ละคอลัมน์ระบุ **ใครแก้ · อุปกรณ์ใด · เมื่อใด** อยู่ด้านบนเสมอ
- ไฮไลต์เฉพาะ field ที่ค่าต่างกันด้วยพื้น `--state-conflict-bg` ส่วน field ที่เหมือนกันแสดงแบบปกติ เพื่อให้สายตาไปที่จุดที่ต้องตัดสินทันที
- ใช้ `--font-mono` กับค่าที่ต้องเทียบตัวต่อตัว
- ปุ่มตัดสินอยู่ใต้แต่ละคอลัมน์ ไม่ใช่รวมไว้ที่เดียว เพื่อลดโอกาสเลือกผิดคอลัมน์

### 3.8 ป้ายสถานะ (Badge / Chip)

รัศมี `--radius-sm` · ตัวอักษร `--text-sm` น้ำหนัก `--weight-medium` · ระยะใน `--space-1` `--space-2` · มีไอคอนนำหน้าเสมอ · **ห้ามใช้ป้ายที่มีแต่สีไม่มีข้อความ**

**ก่อนเลือกสีป้าย ต้องเลือกกลุ่ม token ให้ตรงความหมายก่อนเสมอ** ห้ามเลือกจาก "สีที่ดูเข้ากับความหมายที่ต้องการสื่อ" — ให้ไล่ตามตารางนี้ว่าป้ายกำลังสื่อเรื่องอะไร:

| ป้ายนี้สื่อเรื่อง... | ใช้กลุ่ม token | ตัวอย่าง |
|---|---|---|
| ระดับความเสียหายของโครงสร้าง | `--severity-*` (2.3) | เขียว/เหลือง/แดง บนแบบฟอร์มสำรวจ |
| การซิงค์ข้อมูลกับเซิร์ฟเวอร์ | `--state-offline-*` / `--state-pending-*` / `--state-synced-*` (2.4) | แถบสถานะออฟไลน์, ไอคอนซิงค์ |
| ข้อมูลขัดแย้งรอแก้ไข | `--state-conflict-*` (2.4) | แถวในคิว conflict |
| ค่าที่ AI เสนอ ยังไม่ยืนยัน | `--state-ai-*` (2.4) | ค่าที่กรอกอัตโนมัติจาก AI |
| ความคืบหน้าของงาน/การตรวจทาน (มอบหมาย, งานของฉัน, คิวตรวจทาน, ขั้นตอนวิซาร์ด) | `--state-progress-todo-*` / `--state-progress-done-*` (2.4) | ป้ายสถานะงานใน `lead-assign`, `field-my-tasks`, `lead-review-list`, `lead-review-detail` (badge "รอตรวจทาน" คือระเบียนเดียวกับคอลัมน์สถานะใน `lead-review-list` แค่มุมมองรายละเอียด), จุดบอกขั้นตอนในวิซาร์ดสำรวจ |
| สถานะบัญชีผู้ใช้ (เปิด/ปิดใช้งาน) | `--state-account-active-*` / `--state-account-inactive-*` (2.4) | badge "ใช้งานอยู่"/"ปิดใช้งานแล้ว" ใน `admin-users.html` |

**รายชื่อไฟล์ในคอลัมน์ "ตัวอย่าง" เป็นเพียงตัวอย่างประกอบ ไม่ใช่รายการปิด (non-exhaustive)** — ตารางนี้จะล้าสมัยทุกครั้งที่ Prototype เพิ่มหน้าจอใหม่โดยธรรมชาติ **เกณฑ์ตัดสินที่แท้จริงคือความหมายที่ป้ายนั้นสื่อ ไม่ใช่ว่าไฟล์ถูกระบุไว้ในตารางหรือไม่** หากพบป้ายในไฟล์ที่ไม่ถูกระบุแต่สื่อความหมายเดียวกันกับแถวใดในตารางนี้ (เช่น เป็นระเบียน/สถานะเดียวกันที่แสดงต่างมุมมอง — รายการ vs. รายละเอียด) ให้จัดเข้ากลุ่ม token เดิมของแถวนั้นได้ทันทีโดยไม่ต้องรอแก้ตารางนี้ก่อน แล้วค่อยเพิ่มชื่อไฟล์เข้ามาเป็นตัวอย่างเพิ่มเติมภายหลังเพื่อความครบถ้วนของเอกสาร

ถ้าความหมายที่ต้องการสื่อไม่ตรงกับแถวใดในตารางนี้ **ห้ามหยิบยืม token กลุ่มใกล้เคียงมาใช้ก่อน** ให้ส่งกลับมาที่ `DESIGN.md` เพื่อพิจารณาเพิ่มกลุ่ม token ใหม่

### 3.9 ตารางข้อมูล (Data Table)

ใช้ใน back-office (dashboard, ค้นหา, รายการ conflict)

- หัวตารางพื้น `--surface-sunken` ตรึงไว้เมื่อเลื่อน
- เส้นแบ่งแถวแนวนอน `--border-subtle` เท่านั้น **ไม่มีเส้นแนวตั้ง** ไม่มีแถบสีสลับ
- ความสูงแถวขั้นต่ำ 48px · ตัวเลขจัดชิดขวาและใช้ `--font-mono`
- แถวที่มีข้อมูลขัดแย้งมีแถบสีซ้าย 3px สี `--state-conflict-fg`
- ต้องมีสถานะว่าง (empty state) ที่อธิบายว่าทำไมถึงว่างและควรทำอะไรต่อ ไม่ใช่แค่คำว่า "ไม่มีข้อมูล"

### 3.10 กล่องข้อความระบบ (Banner / Toast / Dialog)

- **Banner** อยู่กับที่ในหน้า ใช้กับสถานะที่คงอยู่ (ออฟไลน์, มีข้อมูลขัดแย้งรอแก้ไข)
- **Toast** ปรากฏชั่วคราวมุมล่าง ใช้กับผลลัพธ์ของการกระทำ ต้องอยู่อย่างน้อย 4 วินาที และ **ห้ามใช้กับข้อความผิดพลาดที่ผู้ใช้ต้องลงมือแก้**
- **Dialog** ใช้เมื่อต้องการการตัดสินใจก่อนไปต่อเท่านั้น มี `--shadow-overlay` · ปุ่มยืนยันอยู่ขวา · กด Esc หรือคลิกนอกกล่องเพื่อยกเลิกได้ **ยกเว้น** กล่องยืนยันการกระทำที่ทำลายข้อมูล

### 3.11 ตัวตนผู้กระทำ (Actor Identity) 🔴

รองรับ FR-32/FR-33 (ตารางประวัติการแก้ไข ฟีเจอร์ 16/17) — ดู [[detailed-design/audit-trail-building]] คอลัมน์ "ผู้กระทำ" ในตารางประวัติต้องแยกให้ชัดว่าเหตุการณ์นั้น**มนุษย์เป็นคนทำ**หรือ**ระบบบันทึกเอง** (เมื่อ `action_type` เป็น "ซิงค์ข้อมูลสำเร็จ" หรือ "ตรวจพบความขัดแย้งของข้อมูล" ค่า `performed_by_user_id` จะว่างโดยตั้งใจตาม [[db-spec#7.2 AuditTrailEntry]])

- **กรณีมนุษย์**: ไอคอนรูปคน (outline) นำหน้าเสมอ + ชื่อ-นามสกุลเต็ม ตัวอักษร `--text-primary` น้ำหนัก `--weight-medium`
- **กรณีระบบ**: ไอคอนรูปเฟือง/สัญลักษณ์อัตโนมัติ (outline รูปทรงต่างจากไอคอนคนอย่างชัดเจน) นำหน้า + คำว่า **"ระบบ"** ตัวอักษร `--text-secondary` น้ำหนัก `--weight-medium` ตามด้วยบรรทัดรองขนาด `--text-xs` สี `--text-tertiary` ระบุอุปกรณ์ต้นทาง เช่น "อุปกรณ์: {device_id}" (ค่าดึงจากฟิลด์ `note` ของระเบียน `AuditTrailEntry` ตามที่ edge case ใน [[detailed-design/audit-trail-building#4. Edge Case และวิธีจัดการ]] กำหนด)
- **ห้ามปล่อยช่องผู้กระทำว่างเปล่าเด็ดขาดไม่ว่ากรณีใด** — ดู [UX-15](#ux-15-ผู้กระทำต้องไม่ว่างเปล่าเมื่อเป็นระบบ)
- **ไม่ใช้ token สีสถานะใดๆ กับ pattern นี้** (ไม่ใช่กลุ่ม `--state-*` ใดตาม [2.4](#24-สี--สถานะระบบ-system-state)) เพราะ "ผู้กระทำ" คือตัวตน ไม่ใช่สถานะ — ใช้เฉพาะ token ตัวอักษรที่มีอยู่แล้ว (`--text-primary` / `--text-secondary` / `--text-tertiary`) ทั้งสามค่านี้ผ่านคอนทราสต์ AAA/AA บน `--surface-page` และพื้นตารางแล้วตาม [2.1](#21-สี--พื้นผิวและตัวอักษร-neutral--earth-base) จึง**ไม่มี token สีใหม่และไม่มีคู่สีใหม่ที่ต้องตรวจคอนทราสต์เพิ่ม**
- ไอคอนคนและไอคอนระบบต้องมาจากชุดไอคอนเดียวกับที่ใช้ทั่วระบบ (รอเลือกจริงตาม [หัวข้อ 5](#5-สิ่งที่ยังไม่ตัดสินใจ)) รูปทรงต้องต่างกันมากพอที่จะแยกออกได้แม้ในภาพขนาดเล็กหรือพิมพ์ขาวดำ เทียบแนวทางเดียวกับไอคอนประจำระดับความเสียหายใน [2.3](#23-สี--ระดับความเสียหาย-damage-severity--สำคัญที่สุด)
- ใช้รูปแบบเดียวกันไม่เปลี่ยนตามหน้าจอ ทั้งตารางประวัติรายอาคาร (ฟีเจอร์ 16) และตารางค้นหาประวัติทั่วระบบ (ฟีเจอร์ 17)

> **ทำไมไม่ใช้ Avatar วงกลม (initials)**: พิจารณาแล้วแต่เลือกไม่ใช้ เพราะชื่อไทยไม่มีธรรมเนียมย่อด้วยอักษรแรกแบบอังกฤษที่ให้ผลลัพธ์ชัดเจน และองค์ประกอบวงกลมตกแต่งเพิ่มเติมขัดกับหลักการ "เงียบและไม่รบกวน" และ "เรียบง่ายอย่างตั้งใจ" ใน [1.2](#12-หลักการออกแบบ-design-principles) — ไอคอน+ข้อความล้วนตอบโจทย์ความชัดเจนได้เพียงพอโดยไม่เพิ่มความซับซ้อน

## 4. UX Guidelines & Rules

กติกาในหัวข้อนี้เป็น **ข้อบังคับ** ทุก Prototype และการออกแบบหน้าจอต้องผ่านทุกข้อ

### UX-01 ความชัดเจนชนะความสวยงามเสมอ
เมื่อทางเลือกที่สวยกว่าทำให้อ่านยากขึ้นแม้เพียงเล็กน้อย ให้เลือกทางที่อ่านง่ายกว่า โดยเฉพาะทุกอย่างที่เกี่ยวกับระดับความเสียหายและสถานะข้อมูล

### UX-02 ห้ามใช้สีสื่อความหมายเพียงลำพัง
ทุกจุดที่ใช้สีสื่อสถานะ **ต้องมีไอคอนรูปทรงเฉพาะและข้อความภาษาไทยกำกับด้วยเสมอ** ผู้ใช้ที่มองเห็นสีผิดปกติ ผู้ใช้ที่อ่านหน้าจอกลางแดดจ้า และเอกสารที่ถูกพิมพ์เป็นขาวดำ ต้องเข้าใจความหมายได้เท่ากัน

### UX-03 คอนทราสต์ขั้นต่ำสูงกว่ามาตรฐานทั่วไป
- ข้อความเนื้อหาและข้อความที่เกี่ยวกับความปลอดภัย: **≥ 7:1 (AAA)**
- ข้อความประกอบและไอคอน: **≥ 4.5:1 (AA)**
- ขอบขององค์ประกอบที่ใช้งานได้: **≥ 3:1**
- เหตุผล: หน้าจอกลางแดดสูญเสียคอนทราสต์ที่รับรู้ได้จริงไปมาก การออกแบบให้ผ่านเกณฑ์ขั้นต่ำในห้องแอร์จึงไม่เพียงพอ

### UX-04 ออกแบบสำหรับมือที่ไม่แม่นยำ
พื้นที่กดบนหน้าจอภาคสนามต้องไม่เล็กกว่า `--touch-field` (56px) และเว้นระยะกันอย่างน้อย `--touch-gap` การกระทำที่ย้อนกลับไม่ได้ต้องไม่อยู่ติดกับปุ่มที่ใช้บ่อย

### UX-05 งานต้องไม่หาย
แบบฟอร์มมี 10 หมวด ใช้เวลากรอกนาน ระบบต้องบันทึกร่างอัตโนมัติทุกครั้งที่ค่าเปลี่ยน และเมื่อเปิดแอปใหม่หลังถูกปิดกลางคัน ต้องกลับมาที่หมวดเดิมพร้อมข้อมูลครบ **ห้ามมีหน้าจอใดที่ปิดแล้วข้อมูลหายโดยไม่เตือน**

### UX-06 บอกความจริงเรื่องสถานะข้อมูลเสมอ
ผู้ใช้ต้องรู้ได้ตลอดเวลาว่าข้อมูลตรงหน้า **ซิงค์แล้วหรือยัง · เป็นค่าที่ AI เสนอหรือคนยืนยันแล้ว · ขัดแย้งอยู่หรือไม่** ห้ามซ่อนสถานะเหล่านี้เพื่อให้หน้าจอดูเรียบร้อยขึ้น

### UX-07 ออฟไลน์คือสภาวะปกติ ไม่ใช่ข้อผิดพลาด
ห้ามใช้ภาษาหรือสีที่สื่อว่าการทำงานออฟไลน์คือความล้มเหลว ห้ามบล็อกการทำงานใดๆ ที่ทำได้โดยไม่ต้องต่อเน็ต และห้ามแสดงกล่องเตือนซ้ำๆ เมื่อไม่มีสัญญาณ

### UX-08 AI เป็นผู้ช่วย ไม่ใช่ผู้ตัดสิน
ค่าที่ AI เสนอต้องแยกจากค่าที่ยืนยันแล้วด้วยรูปลักษณ์ที่ต่างกันชัดเจน และต้องไม่ถูกบันทึกเป็นข้อมูลจริงจนกว่าคนจะยืนยัน เส้นทางกรอกเองต้องมีน้ำหนักทางสายตาเท่ากับเส้นทางใช้ AI เสมอ

### UX-09 การกระทำที่ย้อนกลับไม่ได้ต้องยืนยันเสมอ
การส่งผลสำรวจเข้าคิวตรวจทาน การรับรองด้วยลายมือชื่อ การตัดสินความขัดแย้ง และการลบข้อมูล ต้องมีขั้นยืนยันที่ **สรุปผลลัพธ์ของการกระทำเป็นข้อความ** ไม่ใช่แค่ถามว่า "แน่ใจหรือไม่"

### UX-10 ข้อความผิดพลาดต้องบอกทางออก
ทุกข้อความผิดพลาดต้องบอกว่า **เกิดอะไรขึ้น · เพราะอะไร · ผู้ใช้ทำอะไรได้ต่อ** ห้ามแสดงรหัสข้อผิดพลาดเพียงลำพัง และห้ามใช้ภาษาที่โทษผู้ใช้

### UX-11 ใช้ภาษาไทยที่ตรงกับแบบฟอร์มราชการ
คำเรียกหมวด ระดับความเสียหาย และชิ้นส่วนโครงสร้าง ต้องใช้คำเดียวกับแบบฟอร์ม DPT ต้นฉบับใน [[00-source]] เพื่อให้ผู้สำรวจที่คุ้นแบบฟอร์มกระดาษใช้งานได้ทันที **ห้ามคิดคำใหม่ให้ฟังทันสมัยขึ้น**

### UX-12 รองรับการใช้งานด้วยคีย์บอร์ดและโปรแกรมอ่านหน้าจอ
ทุกองค์ประกอบที่ใช้งานได้ต้องเข้าถึงด้วย Tab ตามลำดับที่สมเหตุสมผล มีสถานะโฟกัสที่เห็นชัดด้วย `--focus-ring` และมีป้ายกำกับที่โปรแกรมอ่านหน้าจอเข้าใจ — สำคัญเป็นพิเศษกับหน้าจอ back-office ที่ผู้ใช้ทำงานกับข้อมูลจำนวนมากต่อเนื่อง

### UX-13 ลำดับชั้นด้วยที่ว่างก่อนเสมอ
ใช้ระยะห่างและขนาดตัวอักษรจัดลำดับความสำคัญเป็นอันดับแรก ใช้เส้นขอบเป็นอันดับสอง ใช้พื้นหลังเป็นอันดับสาม **ห้ามใช้สีสดหรือเงาเพื่อสร้างลำดับชั้น**

### UX-14 แยก token ตามความหมาย ห้ามข้ามกลุ่มความหมาย
ระบบนี้มี "สถานะ" หลายชนิดที่ต้องไม่ปนกันเด็ดขาด: ระดับความเสียหาย (2.3) · สถานะการซิงค์ (2.4) · สถานะข้อมูลขัดแย้ง (2.4) · สถานะค่าที่ AI เสนอ (2.4) · สถานะความคืบหน้าของงาน/การตรวจทาน (2.4) · สถานะบัญชีผู้ใช้ (2.4) แต่ละกลุ่มมีเจ้าของความหมายของตัวเอง **ห้ามหยิบยืม token จากกลุ่มหนึ่งไปสื่อความหมายของอีกกลุ่มหนึ่ง แม้สีจะดูเข้ากันดีก็ตาม**

**เมื่อพบสถานะชนิดใหม่ที่ยังไม่มีกลุ่ม token รองรับ**: ห้ามหยิบยืมกลุ่มที่มีอยู่แล้วไปใช้ชั่วคราวโดยเด็ดขาด แม้ชื่อ token จะฟังดูใช้ได้กับความหมายใหม่นั้นก็ตาม (เช่น "synced" ฟังดูใช้ได้กับ "ใช้งานอยู่" แต่คนละโดเมนกันโดยสิ้นเชิง) ให้หยุดจุดนั้นไว้ก่อน แล้วส่งสัญญาณกลับมาที่ `DESIGN.md` (ผ่าน `/sync-design-system`) เพื่อพิจารณาเพิ่มกลุ่ม token ใหม่ก่อนใช้งานจริงเสมอ — รูปแบบนี้เกิดซ้ำมาแล้ว 3 ครั้ง (สถานะซิงค์ → สถานะความคืบหน้าของงาน → สถานะบัญชีผู้ใช้) ล้วนเป็นการหยิบ token ที่ "ชื่อฟังดูใช้ได้" มาใช้กับโดเมนใหม่โดยไม่ตั้งใจ ทุกครั้งที่เกิดต้องรอรอบ audit ถัดไปจึงจะจับได้ ซึ่งช้ากว่าการเช็กจากรายการโดเมนที่ประกาศไว้ในย่อหน้านี้ก่อนใช้งานจริง (ดูตัวอย่างจริงที่เคยเกิดขึ้นใน [3.8](#38-ป้ายสถานะ-badge--chip))

### UX-15 ผู้กระทำต้องไม่ว่างเปล่าเมื่อเป็นระบบ
ทุกตารางประวัติการแก้ไข (audit trail) ที่มีบางเหตุการณ์เกิดจากระบบเอง ไม่ใช่มนุษย์ (`performed_by_user_id` ว่างโดยตั้งใจตาม [[db-spec#7.2 AuditTrailEntry]]) **ห้ามแสดงช่องผู้กระทำเป็นค่าว่างหรือ "ไม่ระบุ"** ต้องแสดงเป็น "ระบบ" พร้อมไอคอนกำกับและอุปกรณ์ต้นทางเสมอตาม [3.11](#311-ตัวตนผู้กระทำ-actor-identity) — เหตุผล: ตารางนี้ถูกใช้เป็นหลักฐานยืนยันเมื่อมีข้อโต้แย้งเรื่องผลสำรวจ ช่องว่างในเอกสารหลักฐานอ่านได้เป็น "ข้อมูลขาดหายหรือบันทึกไม่สมบูรณ์" ซึ่งบั่นทอนความน่าเชื่อถือของทั้งระเบียน แม้ความว่างของ `performed_by_user_id` จะถูกต้องตามการออกแบบฐานข้อมูลก็ตาม กติกานี้คือการแปลความว่างที่ถูกต้องเชิงข้อมูลให้เป็นข้อความที่ถูกต้องเชิงความหมายบนหน้าจอเสมอ

## 5. สิ่งที่ยังไม่ตัดสินใจ

- **ไอคอนชุดใด** — ยังไม่เลือก กำหนดไว้เพียงว่าต้องเป็นเส้น (outline) ความหนาสม่ำเสมอ มีรูปทรงประจำระดับความเสียหายตาม [2.3](#23-สี--ระดับความเสียหาย-damage-severity--สำคัญที่สุด) และมีไอคอนรูปคน + ไอคอนเฟือง/ระบบอัตโนมัติสำหรับ pattern ตัวตนผู้กระทำตาม [3.11](#311-ตัวตนผู้กระทำ-actor-identity) — ทั้งหมดรอเลือกชุดไอคอนจริงพร้อมกันในรอบเดียว
- **โหมดกลางแดด (high-visibility mode)** — เป็นชุด token ทางเลือกที่เพิ่มคอนทราสต์และขนาดตัวอักษร ยังไม่ออกแบบค่าจริง รอผลทดสอบภาคสนาม
- **โหมดมืด** — ยังไม่จำเป็นในเฟสนี้ เพราะงานสำรวจทำกลางวัน
- **โลโก้และเครื่องหมายทางการ** — รอการตัดสินใจร่วมกับหน่วยงานเจ้าของระบบ
- ค่าเชิงเทคนิคของการนำไปใช้จริง (หน่วยที่ใช้ ระบบ CSS ฯลฯ) รอ [[technology-stack]]
- **สีของ `--state-progress-*` ใช้ค่าเดียวกับ `--state-pending-*`/`--state-synced-*` โดยตั้งใจ (ดู 2.4)** — ถ้าพบว่าหน้าจอใดต้องแสดงสถานะซิงค์และสถานะความคืบหน้าของงานพร้อมกันจนผู้ใช้แยกไม่ออกว่าอันไหนคืออันไหน ต้องกลับมาแยกค่าสีของสองกลุ่มนี้ให้ต่างกันจริง (ไม่ใช่แค่ต่างชื่อ token) — ยังไม่มีเคสยืนยันจาก Prototype จริง จึงยังไม่ปรับตอนนี้
