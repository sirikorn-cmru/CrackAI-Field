# ตรวจสอบความสอดคล้องของ NFR กับการออกแบบเชิงเทคนิค (NFR Review)

เอกสารนี้ตรวจสอบว่า NFR ทั้ง 10 ตัวใน [[backlog]] ถูกออกแบบรองรับจริงหรือไม่ในเอกสารเชิงเทคนิคทั้งหมด ([[architecture]], [[api-spec]], [[db-spec]], และไฟล์ใน `detailed-design/`) **เป็นการตรวจสอบและรายงานเท่านั้น ไม่มีการแก้ไขเอกสารเชิงเทคนิคใดๆ ในกระบวนการนี้**

อัปเดตล่าสุด: 2026-09-01 (**รอบตรวจที่ 4 — ตรวจซ้ำเฉพาะจุด NFR-05**) — รอบตรวจที่ 3 (ก่อนหน้ารอบนี้ในวันเดียวกัน) ลดระดับ NFR-05 เป็น "รองรับบางส่วน" เพราะพบว่า `db-spec.md#7.2 AuditTrailEntry` เขียน `performed_by_user_id` เป็น "ไม่" (ไม่บังคับ) **แบบไม่มีเงื่อนไข** ต่างจากรูปแบบมีเงื่อนไขที่เอกสารเดียวกันใช้กับฟิลด์อื่น — รอบนี้ (รอบที่ 4) ตรวจซ้ำ**เฉพาะ NFR-05 จุดเดียว** หลัง `api-db-writer` แก้ไขตามคำแนะนำ ไม่ได้ตรวจ NFR ข้ออื่นซ้ำใหม่ (9 ตัวที่เหลือคงผลจากรอบที่ 3 ไว้ทั้งหมด ไม่มีการเปลี่ยนแปลง) ผลตรวจซ้ำ: **ช่องว่างถูกปิดจริง NFR-05 กลับเป็น "รองรับแล้ว"** (รายละเอียดในหัวข้อ "ผลตรวจรอบที่ 4 (2026-09-01) — ตรวจซ้ำเฉพาะ NFR-05" ด้านล่าง)

> **หมายเหตุสำคัญเกี่ยวกับวิธีตรวจ**: ไม่ได้เชื่อหัวข้อ "Mapping NFR ไปยัง Component" ใน [[architecture#5. Mapping NFR ไปยัง Component|architecture หัวข้อ 5]] เพียงอย่างเดียว — การ map ไว้ในตารางไม่ได้แปลว่ามีกลไกออกแบบจริง จึงตรวจไล่ลงไปถึง [[api-spec]]/[[db-spec]] และไฟล์ `detailed-design/` ที่เกี่ยวข้องของแต่ละ NFR ก่อนสรุปสถานะ (วิธีนี้เองที่จับ NFR-04/NFR-07 ได้ในรอบก่อน จึงใช้วิธีเดียวกันตรวจซ้ำการซ่อมในรอบนี้ ไม่เชื่อคำอธิบายการซ่อมเฉยๆ)

## ประวัติการแก้ไขจากรอบตรวจก่อนหน้า (ตรวจซ้ำแล้ว ยืนยันว่าปิดจริง)

### NFR-03 — Data Integrity (เดิม: รองรับบางส่วน → ตอนนี้: รองรับแล้ว)

- **ช่องว่าง (1) กลไกแก้ไขความขัดแย้งด้วยมือ — ปิดแล้ว**: เพิ่ม FR-30/FR-31 ([[feature-list#15. แก้ไขความขัดแย้งของข้อมูลจากการซิงค์ด้วยมือ (Manual Conflict Resolution)|ฟีเจอร์ 15]]) + entity [[db-spec#8.1 SyncConflict|SyncConflict]]/[[db-spec#8.2 SyncConflictVersion|SyncConflictVersion]] (เก็บทุกเวอร์ชันที่ขัดแย้งไว้เปรียบเทียบ) + operation [[api-spec#15.1 แสดงรายการระเบียนที่มีความขัดแย้งของข้อมูลรอการแก้ไขด้วยมือ|15.1]]/[[api-spec#15.2 เปรียบเทียบเวอร์ชันข้อมูลที่ขัดแย้งกันและเลือก/รวมค่าด้วยมือ|15.2]] + ไฟล์ [[detailed-design/manual-conflict-resolution|manual-conflict-resolution.md]] ที่มี sequence diagram, state diagram (`SyncConflict.status`), ตาราง edge case ครบ — ตรวจแล้วว่าไม่ใช่แค่ประกาศแนวคิดแต่มีกลไกจริงครบทั้ง 3 ชั้นเอกสาร ยืนยันปิดช่องว่างนี้จริง
- **ช่องว่าง (2) `client_generated_id` ของ entity ย่อย — ปิดแล้ว พร้อมประเมินขอบเขตที่จำกัดไว้ว่าเพียงพอ**: [[db-spec]] เพิ่ม `client_generated_id` ให้ entity ย่อย 6 ตัว (`SurveyParticipant`, `SurroundingHazard`, `ExternalDamage`, `StructuralDamage`, `ComponentDamage`, `ElectricalSystemDamage`) แต่จงใจจำกัดขอบเขตไว้ว่าใช้เพื่อ **idempotent upsert + referential stability เท่านั้น** ส่วนการตรวจจับความขัดแย้ง (conflict detection) ยังอยู่ที่ระดับ `SurveyedBuilding` (aggregate) จุดเดียวตามเดิม ([[api-spec#14.1 ซิงค์ข้อมูลแบบสำรวจที่ค้างจากอุปกรณ์|api-spec 14.1]], [[db-spec#10. กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล|db-spec หัวข้อ 10 ข้อ 2-3]])
  - **ประเมินว่าเหตุผลนี้เพียงพอหรือไม่**: **เพียงพอ** เพราะ (ก) ตาม [[user-journey]] ทีมสำรวจกรอกฟอร์มทั้งชุดของอาคารหนึ่งบนอุปกรณ์เดียวในช่วงเวลาเดียวกันเสมอ ความขัดแย้งที่เกิดขึ้นจริงในทางปฏิบัติจึงมักเป็นระดับ "อาคารทั้งอาคารถูกสำรวจซ้ำจากคนละอุปกรณ์" ไม่ใช่ "field ย่อยของอาคารเดียวกันถูกแก้จากอุปกรณ์ต่างกันในช่วงเวลาต่างกัน", (ข) การแก้ไข entity ย่อยใดๆ ต้องกระทบ `SurveyedBuilding.data_version`/`last_modified_at` ของอาคารแม่เสมอ (เป็น aggregate) ทำให้ความขัดแย้งระดับ field ย่อยจะถูกยกระดับเป็นความขัดแย้งของอาคารแม่โดยอัตโนมัติอยู่แล้ว ไม่มีทางหลุดรอดไปไม่ถูกตรวจจับ, (ค) `SyncConflictVersion.snapshot_content` เก็บค่าทั้งอาคารรวม entity ย่อย ณ เวลานั้นไว้เปรียบเทียบครบอยู่แล้ว จึงไม่จำเป็นต้องมี conflict detection แยกระดับ field — สรุป: การจำกัดขอบเขตนี้เป็นการออกแบบที่สมเหตุสมผล ไม่ใช่ช่องว่างที่หลงเหลือ

### NFR-04 — Usability / Compatibility (เดิม: รองรับบางส่วน → ตอนนี้: รองรับแล้ว)

รอบก่อนพบว่า "map ไว้ในตารางแต่ไม่มีการออกแบบจริงรองรับ" — รอบนี้เพิ่มตาราง Edge Case เชิง logical ใน 3 ไฟล์: [[detailed-design/building-environment-info#5. Edge Case เพิ่มเติมสำหรับการใช้งานกลางแจ้งในพื้นที่ภัยพิบัติ (NFR-04)|building-environment-info หัวข้อ 5]] (ข้อมูลหายเมื่อแอปปิดกลางฟอร์มยาว → ต้องบันทึกทันทีที่กรอกเสร็จแต่ละ field/หมวดย่อย, สวมถุงมือ/มือเปียกกดพลาด → ตัวเลือกต้องมีขนาดสัมผัสใหญ่พอ, อ่านหน้าจอกลางแดดจ้า → ข้อความแจ้งเตือนต้องคมชัด/คอนทราสต์สูงไม่พึ่งสีอย่างเดียว, ขนาดหน้าจอต่างกัน → ฟอร์มต้องแสดงผล/เลื่อนดูได้ครบ), [[detailed-design/ai-crack-photo-analysis#5. Edge Case เพิ่มเติมสำหรับการใช้งานกลางแจ้งในพื้นที่ภัยพิบัติ (NFR-04)|ai-crack-photo-analysis หัวข้อ 5]], [[detailed-design/offline-sync#5. Edge Case และวิธีจัดการ|offline-sync หัวข้อ 5]] (แอปดับกลางคันระหว่างมีระเบียนค้างในคิว → ระเบียนต้องไม่หาย คิวต้องทำต่อได้) (หมายเหตุ: anchor นี้แก้จาก `#6` เป็น `#5` ในรอบตรวจที่ 3 เพื่อให้ตรงเลขหัวข้อจริงในไฟล์)
- **ประเมินว่าครอบคลุมพอหรือยัง**: **พอแล้วสำหรับสถานะ "รองรับแล้ว"** เหตุผล: 3 ไฟล์นี้ครอบคลุมหมวดปัญหาหลักของ NFR-04 ครบ (การสูญเสียข้อมูล, การโต้ตอบด้วยถุงมือ/แสงจ้า, ความทนทานต่อการขัดจังหวะของการซิงค์) และ [[detailed-design/offline-sync|offline-sync.md]] ถูกออกแบบไว้แต่แรกให้เป็น "แหล่งอ้างอิงหลัก (single source) ของ lifecycle `sync_status`" ที่ใช้ร่วมกันทุกฟีเจอร์ที่สร้างข้อมูลออฟไลน์อยู่แล้ว เอดจ์เคสเรื่อง crash-resilience จึงมีผลครอบคลุมฟีเจอร์อื่นโดยอ้อมโดยไม่ต้องเขียนซ้ำทุกไฟล์ — ไม่ถือเป็นช่องว่างที่บล็อกสถานะ "รองรับแล้ว" แต่การขยายชุด edge case เดียวกัน (โดยเฉพาะเรื่องถุงมือ/แสงจ้าที่เฉพาะเจาะจงกับแต่ละหน้าจอ) ไปยังไฟล์ field-facing ที่เหลือ (`structural-damage-assessment.md`, `surveyor-info-duration.md`, `additional-sketch.md`) จะทำให้เอกสารสม่ำเสมอมากขึ้น — เป็นข้อเสนอแนะเสริมไม่บังคับ

### NFR-07 — Scalability (เดิม: รองรับบางส่วน → ตอนนี้: รองรับแล้ว)

รอบก่อนพบว่าไม่มี component/กลไกคิวฝั่งเซิร์ฟเวอร์เลย มีแต่ "คิวรอซิงค์ในเครื่อง" ฝั่ง Field Client ซึ่งแก้คนละปัญหา — รอบนี้ [[architecture]] เพิ่ม sub-component ใหม่ **"คิวรับคำขอซิงค์ฝั่งเซิร์ฟเวอร์ (Server-side Sync Intake Queue)"** เป็น node `INTAKE` แยกต่างหากภายใน Sync & Conflict Resolution Service ปรากฏจริงทั้งใน component diagram ([[architecture#3. Component Diagram|architecture หัวข้อ 3]]: `FCQueue -->|ซิงค์เมื่อมีสัญญาณ| INTAKE` และ `INTAKE -->|จัดคิว/จำกัดอัตราตามโหลด (NFR-07)| SYNC`), data flow diagram 4.1 ("ส่งข้อมูล/ไฟล์ภาพที่ค้างอยู่ ผ่านคิวรับคำขอฝั่งเซิร์ฟเวอร์"), ตาราง NFR mapping (ขยายเป็นคำอธิบายเต็มย่อหน้าอธิบายรูปแบบโหลดที่กระจุกตัวเป็นช่วง), และ [[api-spec#14.1 ซิงค์ข้อมูลแบบสำรวจที่ค้างจากอุปกรณ์|api-spec 14.1]] ผูก business rule กับ component นี้ตรงๆ
- **ประเมินว่าขยับขึ้นครบหรือไม่**: **ครบ** — ตอนนี้มีกลไกระดับ logical (component แยกต่างหากที่ทำหน้าที่จัดคิว/จำกัดอัตรา) ไม่ใช่แค่ประโยคลอยๆ อีกต่อไป ส่วนอัลกอริทึม/ตัวเลข rate-limit ที่เป็นรูปธรรมยังคงเป็นประเด็นรอ `technology-stack.md` เหมือนกับ NFR-06 ที่เกณฑ์ตัวเลขรอตัดสินใจแต่กลไกออกแบบไว้ครบแล้ว — จัดอยู่ในหมวดเดียวกัน ไม่ใช่ช่องว่างของการออกแบบอีกต่อไป

## NFR-10 — Data Integrity (Reporting Consistency) — ตัวใหม่ของรอบนี้

ตรวจสอบแล้วว่ามีการออกแบบรองรับครบทั้ง 3 ชั้น ไม่ใช่แค่ map ไว้ลอยๆ: [[architecture]] มีทั้ง edge ใน component diagram และคำอธิบายเต็มในตาราง NFR mapping, [[db-spec#8.2 SyncConflictVersion|db-spec]] มีกฎทางธุรกิจระบุชัดว่าการปลดสถานะขัดแย้งกับการเปลี่ยน `sync_status` เป็น "ซิงค์สำเร็จ" ต้องเกิดในธุรกรรมเดียวกัน, [[api-spec]] มี 3 operation ที่เกี่ยวข้องกับการอ่านข้อมูลสรุป (11.1 Dashboard, 12.1 ส่งออกรายงาน, 13.1 ค้นหา/กรอง) ทุกตัวมีกฎกรอง `sync_status = มีความขัดแย้งรอแก้ไข` ออกชัดเจนเป็นรายบรรทัด ไม่ใช่แปะรหัสลอยๆ แบบที่เคยพบใน NFR-04/07 รอบก่อน และ detailed-design ทั้ง 4 ไฟล์ที่เกี่ยวข้อง ([[detailed-design/dashboard-overview|dashboard-overview]], [[detailed-design/export-report|export-report]], [[detailed-design/search-filter-buildings|search-filter-buildings]], [[detailed-design/manual-conflict-resolution|manual-conflict-resolution]]) มีตาราง edge case ระบุการกรองออก/จุดปลดเงื่อนไขตรงกันสอดคล้องกันทั้งหมด — **ไม่พบช่องว่าง**

### NFR-05 — Auditability (เดิม: รองรับแล้ว → ตอนนี้: รองรับบางส่วน) — **ช่องว่างใหม่ที่พบรอบนี้**

การเปลี่ยนแปลงที่ตั้งใจ (ขยาย `AuditTrailEntry.action_type` ครอบคลุมผลการซิงค์ + สร้าง audit entry ใน operation 14.1/14.2 + sequence diagram ของ [[detailed-design/offline-sync|offline-sync]] ครบ 3 จุด) **ทำสำเร็จจริง** ไม่ใช่แค่ประกาศลอยๆ — ตรวจสอบแล้วพบทั้ง 3 ชั้นเอกสารสอดคล้องกัน แต่ผลข้างเคียงของการทำให้ `performed_by_user_id` "ไม่บังคับ" เพื่อรองรับกรณีระบบเป็นผู้บันทึกเอง (audit entry ที่เกิดจาก sync event ไม่มีผู้ใช้เป็นผู้กระทำโดยตรง) **ถูกเขียนแบบไม่มีเงื่อนไขในคอลัมน์ "จำเป็น"** ของ [[db-spec#7.2 AuditTrailEntry|db-spec 7.2]] แทนที่จะเขียนแบบมีเงื่อนไขตามรูปแบบที่เอกสารเดียวกันใช้กับฟิลด์อื่นอยู่แล้ว (เช่น `CertificationRecord.digital_signature_file` = "ไม่ (จำเป็นเมื่อ `review_result = รับรอง`)", `SyncConflict.resolution_type` = "ไม่ (จำเป็นเมื่อ `status = แก้ไขแล้ว`)")

**ผลกระทบจริง**: ที่ระดับเอกสาร logical นี้ ไม่มีกฎบังคับใดกันไม่ให้ `AuditTrailEntry` ที่เกิดจาก action ซึ่งมนุษย์เป็นผู้กระทำจริง (เช่น `action_type = รับรองผล`, `แก้ไขบัญชีผู้ใช้`, `แก้ไขความขัดแย้งของข้อมูล`) ถูกบันทึกโดยไม่ระบุ `performed_by_user_id` — เหตุผลที่ให้ไว้ ("ไม่บังคับเมื่อผู้กระทำคือระบบภายในเอง") ปรากฏเฉพาะในคอลัมน์คำอธิบายซึ่งเป็นข้อความบรรยาย ไม่ใช่ constraint ที่บังคับใช้จริง เทียบกับก่อนหน้านี้ที่ฟิลด์นี้เคย "บังคับ" (ใช่) แบบไม่มีเงื่อนไขมาก่อน การเปลี่ยนเป็น "ไม่บังคับแบบไม่มีเงื่อนไข" จึงเป็นการ**ลดความเข้มงวดของ accountability ลงกว้างกว่าที่จำเป็น** (ควรลดเฉพาะกรณีระบบเป็นผู้บันทึกเองเท่านั้น ไม่ใช่ลดทั้งหมด)

**สรุป**: กลไก auditability โดยรวมยังทำงานได้ (audit entry ถูกสร้างครบทุก flow ที่ตรวจสอบ) จึงไม่ใช่ "ยังไม่รองรับ" แต่การบังคับใช้ระดับ schema มีช่องโหว่จริงที่ควรปิด จึงจัดเป็น **รองรับบางส่วน**

**แนะนำให้รันต่อ**: `sync-api-db` — แก้เฉพาะคำอธิบาย/เงื่อนไขของ `performed_by_user_id` ใน [[db-spec#7.2 AuditTrailEntry|db-spec 7.2]] ให้เป็น "ไม่ (จำเป็นเมื่อ `action_type` ไม่ใช่ `ซิงค์ข้อมูลสำเร็จ`/`ตรวจพบความขัดแย้งของข้อมูล`)" ไม่ต้องแตะ `architecture.md` หรือ `detailed-design/` เพราะช่องว่างอยู่ที่การเขียนกฎในระดับ entity attribute ของ db-spec เท่านั้น

### NFR-08 — Security/RBAC (ตรวจเป็นพิเศษตามที่ผู้เรียกกังวล — ไม่พบผลกระทบ)

ตรวจสอบแล้วว่าการเปลี่ยน `performed_by_user_id` เป็นไม่บังคับ **ไม่กระทบ NFR-08** เพราะ RBAC ("ใครมีสิทธิ์ทำอะไรได้บ้าง") เป็นการตรวจสอบ ณ เวลาเรียก request ที่ Backend Service ตาม [[architecture#4. Data Flow Diagram ต่อ Journey หลัก|architecture 4.3]] และ [[architecture#5.5 Cross-cutting concerns|architecture §5.5]] ซึ่งเป็นกลไกคนละจุด คนละเวลากับการเขียน audit log ("ใครทำอะไรไปแล้ว") — ต่อให้ `performed_by_user_id` ว่าง ก็ไม่ทำให้ผู้ไม่มีสิทธิ์เข้าถึงข้อมูลได้เพิ่มขึ้น ความกังวลของผู้เรียกเรื่อง "ตรวจสอบย้อนหลังว่าใครทำอะไรอ่อนลง" จึงตรงกับขอบเขตของ **NFR-05 (Auditability)** มากกว่า ไม่ใช่ NFR-08 — ได้ย้ายรายละเอียดทั้งหมดไปไว้ที่ผลตรวจ NFR-05 ด้านบนแล้ว NFR-08 คงสถานะ **รองรับแล้ว** ไม่เปลี่ยนแปลง

### NFR-10 — Data Integrity/Reporting Consistency (ตรวจเป็นพิเศษตามที่ผู้เรียกกังวล — ยืนยันครอบคลุมครบ)

ไล่ตรวจทุก operation ในเอกสารทั้งหมดที่มีลักษณะ "อ่าน/แสดงรายการ/สรุปผล" เทียบกับคำกล่าวของ [[architecture#5.5 Cross-cutting concerns|architecture §5.5]] ที่ระบุว่า Backend Service ต้องกรองสถานะขัดแย้งออกจาก**ทุกช่องทางอ่านข้อมูล** พบว่าครอบคลุมจริง 4 ช่องทาง ไม่ใช่ 3 ช่องทางที่รายงานไว้เดิม:

1. [[api-spec#10.1 ส่งแบบสำรวจเข้าสู่คิวตรวจทาน|10.1 ส่งแบบสำรวจเข้าสู่คิวตรวจทาน]] — **ช่องทางที่ยังไม่เคยถูกกล่าวถึงในรอบก่อน** ("ต้องมี `sync_status = ซิงค์สำเร็จ` ก่อนจึงจะปรากฏในคิวตรวจทานของหัวหน้าผู้สำรวจได้")
2. [[api-spec#11.1 ดู Dashboard ภาพรวมผลสำรวจ|11.1 Dashboard]]
3. [[api-spec#12.1 ส่งออกรายงานผลการสำรวจ|12.1 ส่งออกรายงาน]]
4. [[api-spec#13.1 ค้นหา/กรองรายการอาคารที่สำรวจแล้ว|13.1 ค้นหา/กรอง]]

ทั้ง 4 ช่องทางมีกฎกรองเขียนไว้เป็นรายบรรทัดตรงๆ ไม่ใช่แปะรหัส NFR ลอยๆ และ [[db-spec#10. กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล|db-spec หัวข้อ 10 ข้อ 4]] ระบุกฎเดียวกันซ้ำไว้ระดับโมเดลข้อมูลด้วย ไม่พบ operation อ่านข้อมูลสรุปใดตกหล่น NFR-10 คงสถานะ **รองรับแล้ว** และหลักฐานยิ่งแน่นขึ้นกว่ารอบก่อน

## ผลตรวจรอบที่ 4 (2026-09-01) — ตรวจซ้ำเฉพาะ NFR-05

**ขอบเขตรอบนี้แคบมาก ตามคำขอ**: ตรวจซ้ำเฉพาะช่องว่างเดียวที่รอบที่ 3 รายงานไว้ที่ NFR-05 (ไม่ตรวจ NFR ข้ออื่นซ้ำ — 9 ตัวที่เหลือคงผลจากรอบที่ 3 ไว้ทั้งหมดโดยไม่มีการเปลี่ยนแปลงใดๆ)

### สิ่งที่ตรวจ (1): `db-spec.md#7.2 AuditTrailEntry` แก้ไขตรงตามคำแนะนำหรือไม่

อ่านไฟล์จริงบรรทัด `performed_by_user_id` ใน [[db-spec#7.2 AuditTrailEntry|db-spec 7.2]] พบว่าถูกแก้เป็น:

> `ไม่ (จำเป็นเมื่อ \`action_type\` ไม่ใช่ \`ซิงค์ข้อมูลสำเร็จ\` หรือ \`ตรวจพบความขัดแย้งของข้อมูล\`)`

ตรงกับคำแนะนำที่รอบที่ 3 ให้ไว้เป๊ะ ทั้งเนื้อหาเงื่อนไขและรูปแบบการเขียน (เทียบกับฟิลด์เงื่อนไขอื่นในไฟล์เดียวกัน เช่น `CertificationRecord.digital_signature_file` = "ไม่ (จำเป็นเมื่อ `review_result = รับรอง`)" ที่ [[db-spec#7.1 CertificationRecord|db-spec 7.1]], `SyncConflict.resolution_type` = "ไม่ (จำเป็นเมื่อ `status = แก้ไขแล้ว`)" — รูปแบบสอดคล้องกันแล้ว) คอลัมน์ "คำอธิบาย" ของฟิลด์เดียวกันยังคงข้อความเดิม ("ผู้กระทำ (ไม่บังคับเมื่อผู้กระทำคือระบบภายในเอง...)") ไม่ถูกแก้เพิ่มเติม ตรวจสอบว่าไม่มีบรรทัด/ไฟล์อื่นถูกแตะพร้อมกัน — ยืนยันว่าเป็นการแก้บรรทัดเดียวจริงตามที่ผู้เรียกแจ้ง

**สรุป**: ช่องว่างนี้ **ปิดแล้วจริง** — ตอนนี้มีกฎบังคับระดับ logical (ไม่ใช่แค่คำอธิบายบรรยาย) ว่า action_type ใดๆ ที่ไม่ใช่ 2 ค่าที่ระบบเป็นผู้บันทึกเอง (`ซิงค์ข้อมูลสำเร็จ`, `ตรวจพบความขัดแย้งของข้อมูล`) ต้องมี `performed_by_user_id` เสมอ

**สรุป**: ข้ออ้างของ `api-db-writer` **ถูกต้อง** — ไม่จำเป็นต้องแก้ `api-spec.md` ไม่พบช่องโหว่เพิ่มเติม

### สรุปรวมรอบที่ 4

NFR-05 กลับเป็น **รองรับแล้ว** เต็มรูปแบบ — ทั้ง 3 ชั้นเอกสาร (db-spec, api-spec, detailed-design/offline-sync) สอดคล้องกัน กฎบังคับระดับ schema ปิดช่องโหว่ accountability ที่รอบที่ 3 พบได้จริงตามคำแนะนำเป๊ะ ไม่มีการเปลี่ยนแปลงไฟล์อื่นนอกเหนือจาก `db-spec.md#7.2` บรรทัดเดียว (ตรวจสอบยืนยันแล้วว่า `architecture.md` และไฟล์ `detailed-design/*` ไม่ถูกแตะในการแก้ไขรอบนี้ ตรงตามที่คำแนะนำระบุไว้ว่าไม่จำเป็นต้องแก้)

**บันทึกไว้เพื่อผู้อ่านย้อนหลัง**: NFR-05 ผ่านการปรับสถานะ 3 ครั้งในวันเดียว — รอบที่ 2 (ก่อนหน้า 2026-09-01): รองรับแล้ว → รอบที่ 3 (2026-09-01): ลดเป็นรองรับบางส่วน (พบช่องว่างเรื่อง `performed_by_user_id` ไม่มีเงื่อนไข) → รอบที่ 4 (2026-09-01 เช่นกัน): กลับเป็นรองรับแล้ว (ช่องว่างถูกปิดด้วยการแก้เงื่อนไขในบรรทัดเดียว) การขึ้น-ลงนี้ไม่ใช่ความผิดพลาดของการตรวจ แต่สะท้อนว่ากระบวนการตรวจ-แก้-ตรวจซ้ำทำงานตามที่ออกแบบไว้จริง
