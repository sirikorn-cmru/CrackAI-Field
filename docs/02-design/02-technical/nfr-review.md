# ตรวจสอบความสอดคล้องของ NFR กับการออกแบบเชิงเทคนิค (NFR Review)

เอกสารนี้ตรวจสอบว่า NFR ทั้ง 11 ตัวใน [[backlog]] ถูกออกแบบรองรับจริงหรือไม่ในเอกสารเชิงเทคนิคทั้งหมด ([[architecture]], [[api-spec]], [[db-spec]], และไฟล์ใน `detailed-design/`) **เป็นการตรวจสอบและรายงานเท่านั้น ไม่มีการแก้ไขเอกสารเชิงเทคนิคใดๆ ในกระบวนการนี้**

อัปเดตล่าสุด: 2026-09-04 (**รอบตรวจที่ 11 — ตรวจซ้ำเฉพาะ NFR-02, NFR-03, NFR-05, NFR-07 หลังผู้ใช้ยืนยันการตัดสินใจใหม่เพิ่มอีก 3 ข้อ (รอบสอง วันเดียวกัน): Hosting/Deployment target = คลาวด์กลางภาครัฐ (GDCC) พร้อมข้อจำกัดขยายกำลังเครื่องช้ากว่า cloud เอกชน, กลไกจัดคิว/จำกัดอัตราคำขอซิงค์ = token bucket ต่อ `device_id` + จำกัดจำนวน worker + ตอบ "ขอมากเกินไป" พร้อมเวลาแนะนำให้ลองใหม่ (ตัวเลขจริงยังไม่ปิด), นโยบายเก็บรักษา audit trail = เก็บถาวรไม่ลบอัตโนมัติ + เตรียม `archive_status`/index 3 ชุด (ระยะเวลาจริงยังไม่ปิด) — พบว่า**ต้องลดระดับ NFR-03 เป็น "รองรับบางส่วน"** เพราะการปิด `snapshot_content` format (JSON, ใช้เพื่อมนุษย์เปรียบเทียบเท่านั้น ไม่เคย query รายฟิลด์) เผยให้เห็นว่าไม่มีเอกสารใดระบุกลไก field-level comparison ที่ใช้แยก "แก้ไขคนละฟิลด์" ออกจาก "ฟิลด์เดียวกันขัดแย้งจริง" จริงๆ — ส่วน NFR-02/NFR-05/NFR-07 ยังคงรองรับแล้ว ดูรายละเอียดที่หัวข้อ "ผลตรวจรอบที่ 11" ด้านล่าง) — รอบตรวจที่ 10 (2026-09-04 ก่อนหน้า) ตรวจซ้ำเฉพาะ NFR-02, NFR-03, NFR-07, NFR-08, NFR-09 หลังผู้ใช้ยืนยันการตัดสินใจใหม่ 6 ข้อในรอบเดียวกัน: Protocol/Web Framework = REST over HTTP + Fastify, authentication token = opaque token + Session ในฐานข้อมูล (ไม่ใช่ JWT), CORS = allowlist origin จาก environment variable, chunk ของ resumable upload = 256 KB, stale ของรอบอัปโหลด = 72 ชั่วโมง, auto-merge = ส่งมนุษย์ตัดสินใจทุกครั้งที่พบความขัดแย้งจริง (ไม่ทำ auto-merge ระดับฟิลด์) — ไม่ตรวจ NFR ข้ออื่นซ้ำในรอบนั้น (คงผลจากรอบที่ 9) ดูรายละเอียดที่หัวข้อ "ผลตรวจรอบที่ 10" ด้านล่าง) — รอบตรวจที่ 9 (2026-09-04) ตรวจซ้ำเฉพาะ NFR-11 หลังผู้ใช้ปิดข้อสมมติหมวด 6 ข้อ 11 ของ spec ต้นทาง (จำนวนครั้งสูงสุดที่ยอมให้กรอก PIN ผิดติดต่อกัน = 5 ครั้ง) ยืนยันคงรองรับแล้ว — รอบตรวจที่ 6 (2026-09-03) ตรวจเทียบ `technology-stack.md` ที่เพิ่งมีเนื้อหาเป็นครั้งแรก พบว่า **NFR-02 ต้องลดระดับเป็นรองรับบางส่วน** เพราะเลือก local filesystem แทน object storage ทำให้สมมติฐานเดิมที่เคยใช้ปัดช่องว่าง resumable upload ไม่เป็นจริงอีกต่อไป และโมเดลข้อมูล/state diagram ขัดกันเอง (ข้อความบอกว่า "ทำต่อได้" แต่ state กลับไป "ยังไม่ซิงค์") — รอบตรวจที่ 7 (2026-09-03 วันเดียวกัน) ตรวจซ้ำเฉพาะ NFR-02 หลัง `api-db-writer`/`detailed-design-writer` แก้ไขตามคำแนะนำ ยืนยันว่าช่องว่างปิดจริงและกลับเป็นรองรับแล้ว 10/10 — **รอบตรวจที่ 8 (2026-09-03 วันเดียวกัน)** ตรวจ NFR-11 ใหม่ทั้งหมด (พบว่ารองรับแล้วครบทั้ง 3 ชั้นเอกสารตั้งแต่รอบแรกที่ตรวจ) และตรวจซ้ำ NFR-01/NFR-02/NFR-04/NFR-09 เทียบกับ `technology-stack.md` ที่เพิ่งเจาะจงขึ้น (bare React Native แทนที่จะเป็น React Native เฉยๆ, `op-sqlite` เป็น library ของ Local Persistent Store) **ยืนยันว่าไม่มีตัวใดถูกลดระดับ — คงรองรับแล้ว 11/11** พบเพียงจุดอ้างอิงเลขข้อสมมติผิดพลาดเล็กน้อยใน `architecture.md` §5 (ไม่กระทบสถานะ) ดูรายละเอียดที่หัวข้อ "ผลตรวจรอบที่ 8"

> **หมายเหตุสำคัญเกี่ยวกับวิธีตรวจ**: ไม่ได้เชื่อหัวข้อ "Mapping NFR ไปยัง Component" ใน [[architecture#5. Mapping NFR ไปยัง Component|architecture หัวข้อ 5]] เพียงอย่างเดียว — การ map ไว้ในตารางไม่ได้แปลว่ามีกลไกออกแบบจริง จึงตรวจไล่ลงไปถึง [[api-spec]]/[[db-spec]] และไฟล์ `detailed-design/` ที่เกี่ยวข้องของแต่ละ NFR ก่อนสรุปสถานะ (วิธีนี้เองที่จับ NFR-04/NFR-07 ได้ในรอบก่อน จึงใช้วิธีเดียวกันตรวจซ้ำการซ่อมในรอบนี้ ไม่เชื่อคำอธิบายการซ่อมเฉยๆ)

"ผลตรวจรอบที่ 4" — รอบตรวจที่ 5 (2026-09-02) ตรวจซ้ำครบทั้ง 10 ตัวหลังเพิ่ม FR-32/FR-33 เข้า backlog ยืนยันว่า **ไม่มีตัวใดถูกลดระดับ** (คงรองรับแล้ว 10/10 เท่าเดิม) — รอบตรวจที่ 6 (2026-09-03) ตรวจเทียบ `technology-stack.md` ที่เพิ่งมีเนื้อหาเป็นครั้งแรก พบว่า **NFR-02 ต้องลดระดับเป็น "รองรับบางส่วน"** เพราะการเลือก local filesystem (แทน object storage) ทำให้ช่องว่างเรื่อง resumable upload ที่เคยถูกปัดเป็น "ประเด็นรอ tech stack" กลายเป็นช่องว่างเชิง logical จริงที่ยังไม่มีกลไกรองรับใน api-spec/db-spec — **รอบตรวจที่ 7 (2026-09-03 วันเดียวกัน) ตรวจซ้ำเฉพาะ NFR-02 หลังปิดช่องว่างแล้ว ยืนยันว่ากลับเป็น "รองรับแล้ว"** ทั้งโมเดลข้อมูล (byte offset tracking) และ state diagram/ข้อความในเอกสารสอดคล้องกันแล้วจริง ไม่ใช่แค่เพิ่ม attribute ลอยๆ — ดูหัวข้อ "ผลตรวจรอบที่ 7" — **รอบตรวจที่ 8 (2026-09-03 วันเดียวกัน) ตรวจ NFR-11 ที่เพิ่งเข้า backlog เป็นครั้งแรก** พบว่ารองรับแล้วครบทั้ง 3 ชั้นเอกสารตั้งแต่การออกแบบรอบแรก (ไม่ต้องผ่านรอบลด-เพิ่มสถานะเหมือน NFR-02/NFR-05) และตรวจซ้ำ NFR-01/NFR-02/NFR-04/NFR-09 เทียบ tech stack ที่เจาะจงขึ้น (bare React Native + `op-sqlite`) **ยืนยันไม่มีตัวใดถูกลดระดับ — คงรองรับแล้ว 11/11** — ดูหัวข้อ "ผลตรวจรอบที่ 8" — รอบตรวจที่ 9 (2026-09-04) ตรวจซ้ำเฉพาะ NFR-11 หลังปิดตัวเลข PIN lockout เป็น 5 ครั้ง ยืนยันคงรองรับแล้ว — **รอบตรวจที่ 10 (2026-09-04 วันเดียวกัน) ตรวจซ้ำเฉพาะ NFR-02, NFR-03, NFR-07, NFR-08, NFR-09 หลังปิด 6 การตัดสินใจใหม่ (REST+Fastify, opaque token+Session, CORS allowlist, chunk 256 KB, stale 72 ชม., auto-merge = ส่งมนุษย์ทุกครั้ง) ยืนยันว่าทั้ง 5 ตัวยังคงรองรับแล้ว ไม่มีตัวใดถูกลดระดับ — คงรองรับแล้ว 11/11 เท่าเดิม แต่พบ 1 ความเสี่ยงที่ต้องติดตามเพิ่มใน NFR-03 (ไม่ใช่ช่องว่างบล็อกสถานะ) — ดูหัวข้อ "ผลตรวจรอบที่ 10"** — **รอบตรวจที่ 11 (2026-09-04 วันเดียวกัน) ตรวจซ้ำเฉพาะ NFR-02, NFR-03, NFR-05, NFR-07 หลังปิดการตัดสินใจใหม่เพิ่มอีก 3 ข้อ (Hosting = GDCC, กลไก rate limit ของ Sync Intake Queue, นโยบาย retention/archive ของ audit trail)**: NFR-02/NFR-05/NFR-07 ยืนยันคงรองรับแล้ว แต่ **NFR-03 ถูกลดระดับกลับเป็น "รองรับบางส่วน"** เพราะเมื่อไล่ตรวจตามที่นัดไว้ในรอบที่ 10 (ตรวจซ้ำตอนปิด `snapshot_content` format) พบว่าการปิด format เป็น JSON พร้อมระบุชัดว่า "ไม่เคย query รายฟิลด์ มีไว้ให้มนุษย์เปรียบเทียบเท่านั้น" กลับ**ตัดความเป็นไปได้ที่ snapshot_content จะเป็นกลไกเปรียบเทียบระดับฟิลด์**ทิ้งไปเลย แทนที่จะปิดความเสี่ยง — ไม่มีเอกสารใด (api-spec 14.2/db-spec หัวข้อ 10 ข้อ 3) ระบุกลไกอื่นที่ใช้แยก "แก้ไขคนละฟิลด์" ออกจาก "ฟิลด์เดียวกันขัดแย้งจริง" เลย มีเพียงการเทียบ `data_version`/`last_modified_at` ระดับ aggregate ซึ่งไม่พอแยกแยะทั้งสองกรณีนี้ได้ในทางเทคนิค — คงรองรับแล้วเพียง 10/11 — ดูหัวข้อ "ผลตรวจรอบที่ 11"

### NFR-03 — Data Integrity (เดิม: รองรับบางส่วน → ตอนนี้: รองรับแล้ว)

- **ช่องว่าง (1) กลไกแก้ไขความขัดแย้งด้วยมือ — ปิดแล้ว**: เพิ่ม FR-30/FR-31 ([[feature-list#15. แก้ไขความขัดแย้งของข้อมูลจากการซิงค์ด้วยมือ (Manual Conflict Resolution)|ฟีเจอร์ 15]]) + entity [[db-spec#8.1 SyncConflict|SyncConflict]]/[[db-spec#8.2 SyncConflictVersion|SyncConflictVersion]] (เก็บทุกเวอร์ชันที่ขัดแย้งไว้เปรียบเทียบ) + operation [[api-spec#15.1 แสดงรายการระเบียนที่มีความขัดแย้งของข้อมูลรอการแก้ไขด้วยมือ|15.1]]/[[api-spec#15.2 เปรียบเทียบเวอร์ชันข้อมูลที่ขัดแย้งกันและเลือก/รวมค่าด้วยมือ|15.2]] + ไฟล์ [[detailed-design/manual-conflict-resolution|manual-conflict-resolution.md]] ที่มี sequence diagram, state diagram (`SyncConflict.status`), ตาราง edge case ครบ — ตรวจแล้วว่าไม่ใช่แค่ประกาศแนวคิดแต่มีกลไกจริงครบทั้ง 3 ชั้นเอกสาร ยืนยันปิดช่องว่างนี้จริง
- **ช่องว่าง (2) `client_generated_id` ของ entity ย่อย — ปิดแล้ว พร้อมประเมินขอบเขตที่จำกัดไว้ว่าเพียงพอ**: [[db-spec]] เพิ่ม `client_generated_id` ให้ entity ย่อย 6 ตัว (`SurveyParticipant`, `SurroundingHazard`, `ExternalDamage`, `StructuralDamage`, `ComponentDamage`, `ElectricalSystemDamage`) แต่จงใจจำกัดขอบเขตไว้ว่าใช้เพื่อ **idempotent upsert + referential stability เท่านั้น** ส่วนการตรวจจับความขัดแย้ง (conflict detection) ยังอยู่ที่ระดับ `SurveyedBuilding` (aggregate) จุดเดียวตามเดิม ([[api-spec#14.1 ซิงค์ข้อมูลแบบสำรวจที่ค้างจากอุปกรณ์|api-spec 14.1]], [[db-spec#10. กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล|db-spec หัวข้อ 10 ข้อ 2-3]])
  - **ประเมินว่าเหตุผลนี้เพียงพอหรือไม่**: **เพียงพอ** เพราะ (ก) ตาม [[user-journey]] ทีมสำรวจกรอกฟอร์มทั้งชุดของอาคารหนึ่งบนอุปกรณ์เดียวในช่วงเวลาเดียวกันเสมอ ความขัดแย้งที่เกิดขึ้นจริงในทางปฏิบัติจึงมักเป็นระดับ "อาคารทั้งอาคารถูกสำรวจซ้ำจากคนละอุปกรณ์" ไม่ใช่ "field ย่อยของอาคารเดียวกันถูกแก้จากอุปกรณ์ต่างกันในช่วงเวลาต่างกัน", (ข) การแก้ไข entity ย่อยใดๆ ต้องกระทบ `SurveyedBuilding.data_version`/`last_modified_at` ของอาคารแม่เสมอ (เป็น aggregate) ทำให้ความขัดแย้งระดับ field ย่อยจะถูกยกระดับเป็นความขัดแย้งของอาคารแม่โดยอัตโนมัติอยู่แล้ว ไม่มีทางหลุดรอดไปไม่ถูกตรวจจับ, (ค) `SyncConflictVersion.snapshot_content` เก็บค่าทั้งอาคารรวม entity ย่อย ณ เวลานั้นไว้เปรียบเทียบครบอยู่แล้ว จึงไม่จำเป็นต้องมี conflict detection แยกระดับ field — สรุป: การจำกัดขอบเขตนี้เป็นการออกแบบที่สมเหตุสมผล ไม่ใช่ช่องว่างที่หลงเหลือ

### NFR-04 — Usability / Compatibility (เดิม: รองรับบางส่วน → ตอนนี้: รองรับแล้ว)

รอบก่อนพบว่า "map ไว้ในตารางแต่ไม่มีการออกแบบจริงรองรับ" — รอบนี้เพิ่มตาราง Edge Case เชิง logical ใน 3 ไฟล์: [[detailed-design/building-environment-info#5. Edge Case เพิ่มเติมสำหรับการใช้งานกลางแจ้งในพื้นที่ภัยพิบัติ (NFR-04)|building-environment-info หัวข้อ 5]] (ข้อมูลหายเมื่อแอปปิดกลางฟอร์มยาว → ต้องบันทึกทันทีที่กรอกเสร็จแต่ละ field/หมวดย่อย, สวมถุงมือ/มือเปียกกดพลาด → ตัวเลือกต้องมีขนาดสัมผัสใหญ่พอ, อ่านหน้าจอกลางแดดจ้า → ข้อความแจ้งเตือนต้องคมชัด/คอนทราสต์สูงไม่พึ่งสีอย่างเดียว, ขนาดหน้าจอต่างกัน → ฟอร์มต้องแสดงผล/เลื่อนดูได้ครบ), [[detailed-design/ai-crack-photo-analysis#5. Edge Case เพิ่มเติมสำหรับการใช้งานกลางแจ้งในพื้นที่ภัยพิบัติ (NFR-04)|ai-crack-photo-analysis หัวข้อ 5]], [[detailed-design/offline-sync#5. Edge Case และวิธีจัดการ|offline-sync หัวข้อ 5]] (แอปดับกลางคันระหว่างมีระเบียนค้างในคิว → ระเบียนต้องไม่หาย คิวต้องทำต่อได้) (หมายเหตุ: anchor นี้แก้จาก `#6` เป็น `#5` ในรอบตรวจที่ 3 เพื่อให้ตรงเลขหัวข้อจริงในไฟล์)
- **ประเมินว่าครอบคลุมพอหรือยัง**: **พอแล้วสำหรับสถานะ "รองรับแล้ว"** เหตุผล: 3 ไฟล์นี้ครอบคลุมหมวดปัญหาหลักของ NFR-04 ครบ (การสูญเสียข้อมูล, การโต้ตอบด้วยถุงมือ/แสงจ้า, ความทนทานต่อการขัดจังหวะของการซิงค์) และ [[detailed-design/offline-sync|offline-sync.md]] ถูกออกแบบไว้แต่แรกให้เป็น "แหล่งอ้างอิงหลัก (single source) ของ lifecycle `sync_status`" ที่ใช้ร่วมกันทุกฟีเจอร์ที่สร้างข้อมูลออฟไลน์อยู่แล้ว เอดจ์เคสเรื่อง crash-resilience จึงมีผลครอบคลุมฟีเจอร์อื่นโดยอ้อมโดยไม่ต้องเขียนซ้ำทุกไฟล์ — ไม่ถือเป็นช่องว่างที่บล็อกสถานะ "รองรับแล้ว" แต่การขยายชุด edge case เดียวกัน (โดยเฉพาะเรื่องถุงมือ/แสงจ้าที่เฉพาะเจาะจงกับแต่ละหน้าจอ) ไปยังไฟล์ field-facing ที่เหลือ (`structural-damage-assessment.md`, `surveyor-info-duration.md`, `additional-sketch.md`) จะทำให้เอกสารสม่ำเสมอมากขึ้น — เป็นข้อเสนอแนะเสริมไม่บังคับ

### NFR-05 — Auditability (เดิม: รองรับแล้ว → ตอนนี้: รองรับบางส่วน) — **ช่องว่างใหม่ที่พบรอบนี้**

การเปลี่ยนแปลงที่ตั้งใจ (ขยาย `AuditTrailEntry.action_type` ครอบคลุมผลการซิงค์ + สร้าง audit entry ใน operation 14.1/14.2 + sequence diagram ของ [[detailed-design/offline-sync|offline-sync]] ครบ 3 จุด) **ทำสำเร็จจริง** ไม่ใช่แค่ประกาศลอยๆ — ตรวจสอบแล้วพบทั้ง 3 ชั้นเอกสารสอดคล้องกัน แต่ผลข้างเคียงของการทำให้ `performed_by_user_id` "ไม่บังคับ" เพื่อรองรับกรณีระบบเป็นผู้บันทึกเอง (audit entry ที่เกิดจาก sync event ไม่มีผู้ใช้เป็นผู้กระทำโดยตรง) **ถูกเขียนแบบไม่มีเงื่อนไขในคอลัมน์ "จำเป็น"** ของ [[db-spec#7.2 AuditTrailEntry|db-spec 7.2]] แทนที่จะเขียนแบบมีเงื่อนไขตามรูปแบบที่เอกสารเดียวกันใช้กับฟิลด์อื่นอยู่แล้ว (เช่น `CertificationRecord.digital_signature_file` = "ไม่ (จำเป็นเมื่อ `review_result = รับรอง`)", `SyncConflict.resolution_type` = "ไม่ (จำเป็นเมื่อ `status = แก้ไขแล้ว`)")

**ผลกระทบจริง**: ที่ระดับเอกสาร logical นี้ ไม่มีกฎบังคับใดกันไม่ให้ `AuditTrailEntry` ที่เกิดจาก action ซึ่งมนุษย์เป็นผู้กระทำจริง (เช่น `action_type = รับรองผล`, `แก้ไขบัญชีผู้ใช้`, `แก้ไขความขัดแย้งของข้อมูล`) ถูกบันทึกโดยไม่ระบุ `performed_by_user_id` — เหตุผลที่ให้ไว้ ("ไม่บังคับเมื่อผู้กระทำคือระบบภายในเอง") ปรากฏเฉพาะในคอลัมน์คำอธิบายซึ่งเป็นข้อความบรรยาย ไม่ใช่ constraint ที่บังคับใช้จริง เทียบกับก่อนหน้านี้ที่ฟิลด์นี้เคย "บังคับ" (ใช่) แบบไม่มีเงื่อนไขมาก่อน การเปลี่ยนเป็น "ไม่บังคับแบบไม่มีเงื่อนไข" จึงเป็นการ**ลดความเข้มงวดของ accountability ลงกว้างกว่าที่จำเป็น** (ควรลดเฉพาะกรณีระบบเป็นผู้บันทึกเองเท่านั้น ไม่ใช่ลดทั้งหมด)

**สรุป**: กลไก auditability โดยรวมยังทำงานได้ (audit entry ถูกสร้างครบทุก flow ที่ตรวจสอบ) จึงไม่ใช่ "ยังไม่รองรับ" แต่การบังคับใช้ระดับ schema มีช่องโหว่จริงที่ควรปิด จึงจัดเป็น **รองรับบางส่วน**

**แนะนำให้รันต่อ**: `sync-api-db` — แก้เฉพาะคำอธิบาย/เงื่อนไขของ `performed_by_user_id` ใน [[db-spec#7.2 AuditTrailEntry|db-spec 7.2]] ให้เป็น "ไม่ (จำเป็นเมื่อ `action_type` ไม่ใช่ `ซิงค์ข้อมูลสำเร็จ`/`ตรวจพบความขัดแย้งของข้อมูล`)" ไม่ต้องแตะ `architecture.md` หรือ `detailed-design/` เพราะช่องว่างอยู่ที่การเขียนกฎในระดับ entity attribute ของ db-spec เท่านั้น

### NFR-08 — Security/RBAC (ตรวจเป็นพิเศษตามที่ผู้เรียกกังวล — ไม่พบผลกระทบ)

ตรวจสอบแล้วว่าการเปลี่ยน `performed_by_user_id` เป็นไม่บังคับ **ไม่กระทบ NFR-08** เพราะ RBAC ("ใครมีสิทธิ์ทำอะไรได้บ้าง") เป็นการตรวจสอบ ณ เวลาเรียก request ที่ Backend Service ตาม [[architecture#4. Data Flow Diagram ต่อ Journey หลัก|architecture 4.3]] และ [[architecture#5.5 Cross-cutting concerns|architecture §5.5]] ซึ่งเป็นกลไกคนละจุด คนละเวลากับการเขียน audit log ("ใครทำอะไรไปแล้ว") — ต่อให้ `performed_by_user_id` ว่าง ก็ไม่ทำให้ผู้ไม่มีสิทธิ์เข้าถึงข้อมูลได้เพิ่มขึ้น ความกังวลของผู้เรียกเรื่อง "ตรวจสอบย้อนหลังว่าใครทำอะไรอ่อนลง" จึงตรงกับขอบเขตของ **NFR-05 (Auditability)** มากกว่า ไม่ใช่ NFR-08 — ได้ย้ายรายละเอียดทั้งหมดไปไว้ที่ผลตรวจ NFR-05 ด้านบนแล้ว NFR-08 คงสถานะ **รองรับแล้ว** ไม่เปลี่ยนแปลง

### NFR-10 — Data Integrity/Reporting Consistency (ตรวจเป็นพิเศษตามที่ผู้เรียกกังวล — ยืนยันครอบคลุมครบ)

ไล่ตรวจทุก operation ในเอกสารทั้งหมดที่มีลักษณะ "อ่าน/แสดงรายการ/สรุปผล" เทียบกับคำกล่าวของ [[architecture#5.5 Cross-cutting concerns|architecture §5.5]] ที่ระบุว่า Backend Service ต้องกรองสถานะขัดแย้งออกจาก**ทุกช่องทางอ่านข้อมูล** พบว่าครอบคลุมจริง 4 ช่องทาง ไม่ใช่ 3 ช่องทางที่รายงานไว้เดิม:

1. [[api-spec#10.1 ส่งแบบสำรวจเข้าสู่คิวตรวจทาน|10.1 ส่งแบบสำรวจเข้าสู่คิวตรวจทาน]] — **ช่องทางที่ยังไม่เคยถูกกล่าวถึงในรอบก่อน** ("ต้องมี `sync_status = ซิงค์สำเร็จ` ก่อนจึงจะปรากฏในคิวตรวจทานของหัวหน้าผู้สำรวจได้")
2. [[api-spec#11.1 ดู Dashboard ภาพรวมผลสำรวจ|11.1 Dashboard]]
3. [[api-spec#12.1 ส่งออกรายงานผลการสำรวจ|12.1 ส่งออกรายงาน]]
4. [[api-spec#13.1 ค้นหา/กรองรายการอาคารที่สำรวจแล้ว|13.1 ค้นหา/กรอง]]

ทั้ง 4 ช่องทางมีกฎกรองเขียนไว้เป็นรายบรรทัดตรงๆ ไม่ใช่แปะรหัส NFR ลอยๆ และ [[db-spec#10. กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล|db-spec หัวข้อ 10 ข้อ 4]] ระบุกฎเดียวกันซ้ำไว้ระดับโมเดลข้อมูลด้วย ไม่พบ operation อ่านข้อมูลสรุปใดตกหล่น NFR-10 คงสถานะ **รองรับแล้ว** และหลักฐานยิ่งแน่นขึ้นกว่ารอบก่อน

ตรงกับคำแนะนำที่รอบที่ 3 ให้ไว้เป๊ะ ทั้งเนื้อหาเงื่อนไขและรูปแบบการเขียน (เทียบกับฟิลด์เงื่อนไขอื่นในไฟล์เดียวกัน เช่น `CertificationRecord.digital_signature_file` = "ไม่ (จำเป็นเมื่อ `review_result = รับรอง`)" ที่ [[db-spec#7.1 CertificationRecord|db-spec 7.1]], `SyncConflict.resolution_type` = "ไม่ (จำเป็นเมื่อ `status = แก้ไขแล้ว`)" — รูปแบบสอดคล้องกันแล้ว) คอลัมน์ "คำอธิบาย" ของฟิลด์เดียวกันยังคงข้อความเดิม ("ผู้กระทำ (ไม่บังคับเมื่อผู้กระทำคือระบบภายในเอง...)") ไม่ถูกแก้เพิ่มเติม ตรวจสอบว่าไม่มีบรรทัด/ไฟล์อื่นถูกแตะพร้อมกัน — ยืนยันว่าเป็นการแก้บรรทัดเดียวจริงตามที่ผู้เรียกแจ้ง

**สรุป**: ช่องว่างนี้ **ปิดแล้วจริง** — ตอนนี้มีกฎบังคับระดับ logical (ไม่ใช่แค่คำอธิบายบรรยาย) ว่า action_type ใดๆ ที่ไม่ใช่ 2 ค่าที่ระบบเป็นผู้บันทึกเอง (`ซิงค์ข้อมูลสำเร็จ`, `ตรวจพบความขัดแย้งของข้อมูล`) ต้องมี `performed_by_user_id` เสมอ

### สรุปรวมรอบที่ 4

NFR-05 กลับเป็น **รองรับแล้ว** เต็มรูปแบบ — ทั้ง 3 ชั้นเอกสาร (db-spec, api-spec, detailed-design/offline-sync) สอดคล้องกัน กฎบังคับระดับ schema ปิดช่องโหว่ accountability ที่รอบที่ 3 พบได้จริงตามคำแนะนำเป๊ะ ไม่มีการเปลี่ยนแปลงไฟล์อื่นนอกเหนือจาก `db-spec.md#7.2` บรรทัดเดียว (ตรวจสอบยืนยันแล้วว่า `architecture.md` และไฟล์ `detailed-design/*` ไม่ถูกแตะในการแก้ไขรอบนี้ ตรงตามที่คำแนะนำระบุไว้ว่าไม่จำเป็นต้องแก้)

**บันทึกไว้เพื่อผู้อ่านย้อนหลัง**: NFR-05 ผ่านการปรับสถานะ 3 ครั้งในวันเดียว — รอบที่ 2 (ก่อนหน้า 2026-09-01): รองรับแล้ว → รอบที่ 3 (2026-09-01): ลดเป็นรองรับบางส่วน (พบช่องว่างเรื่อง `performed_by_user_id` ไม่มีเงื่อนไข) → รอบที่ 4 (2026-09-01 เช่นกัน): กลับเป็นรองรับแล้ว (ช่องว่างถูกปิดด้วยการแก้เงื่อนไขในบรรทัดเดียว) การขึ้น-ลงนี้ไม่ใช่ความผิดพลาดของการตรวจ แต่สะท้อนว่ากระบวนการตรวจ-แก้-ตรวจซ้ำทำงานตามที่ออกแบบไว้จริง

**บริบท**: `prototype-auditor` พบว่า NFR-05 กำหนดให้เก็บประวัติ "เพื่อการตรวจสอบย้อนหลัง" แต่ทั้งระบบไม่เคยมีช่องทางอ่านประวัตินั้นจริง ผู้ใช้จึงเพิ่ม FR-32 (เรียกดูประวัติรายอาคาร — หัวหน้าผู้สำรวจเฉพาะทีมตน/ผู้ดูแลระบบ/หน่วยงานส่วนกลาง) และ FR-33 (ค้นหาประวัติทั่วทั้งระบบ — เฉพาะผู้ดูแลระบบ/หน่วยงานส่วนกลาง) เข้า backlog ระดับกลาง กระทบทั้ง 3 ชั้นเอกสาร รอบนี้ตรวจครบทั้ง 10 NFR ไม่ใช่แค่จุดที่เปลี่ยน

### สรุปผลต่อ NFR แต่ละตัว

- **NFR-01, NFR-02, NFR-03, NFR-04, NFR-06, NFR-07, NFR-09**: ไม่มี layer ที่เกี่ยวข้องถูกแก้ไขในรอบนี้ (การเปลี่ยนแปลงทั้งหมดกระจุกอยู่ที่ audit trail read-path) ตรวจสอบ anchor ที่อ้างอิงในแถวของ NFR เหล่านี้แล้วว่ายัง valid ตรง heading จริง — **คงสถานะรองรับแล้วเดิมทุกตัว ไม่มีการเปลี่ยนแปลง**
- **NFR-05 (Auditability)**: ตรวจเจาะลึกตามที่ผู้เรียกกังวลเป็นพิเศษ — **ยังคงรองรับแล้ว และแข็งแรงขึ้น** เพราะช่องว่าง "เก็บไว้แต่ไม่มีช่องทางอ่าน" ที่เป็นต้นเหตุของ FR-32/FR-33 ถูกปิดแล้วจริงทั้ง 3 ชั้น (ดูรายละเอียดในแถวตารางด้านบน) พบเพียงข้อสังเกตย่อยไม่บังคับ 1 จุด (ความเป็นนัยของ `related_entity_name` ใน operation 10.2/10.3)
- **NFR-08 (Security/ownership-based scoping)**: ตรวจเจาะลึกตามที่ผู้เรียกกังวล — **ยังคงรองรับแล้ว** ออกแบบรัดกุมทั้งฝั่งจำกัดขอบเขตหัวหน้าผู้สำรวจ (ตรวจที่ backend ก่อนคืนผลเสมอ ไม่ใช่กรองทีหลัง/ไม่ใช่ UI-only) และฝั่งปฏิเสธผู้สำรวจภาคสนามแบบไม่มีเงื่อนไขทั้ง 2 ฟีเจอร์ พบความไม่ตรงกันเชิงเอกสารระหว่าง `architecture.md` กับ 3 ชั้นที่เหลือ (ดูหัวข้อถัดไป) แต่ไม่กระทบพฤติกรรมจริงของระบบ
- **NFR-10 (Reporting Consistency)**: ตรวจยืนยันว่า operation ใหม่ 15.5.1/15.5.2 ไม่ใช่ "ช่องทางอ่านข้อมูลสรุป" ที่ NFR-10 ต้องการกรองระเบียนขัดแย้งออก (มันคือกลไกแสดง**ประวัติ**ซึ่งต้องรวมเหตุการณ์ "ตรวจพบความขัดแย้ง" ไว้โดยเจตนา) — คงสถานะรองรับแล้ว ไม่มีช่องทางที่ 5 ตกหล่น

### ประเด็นความไม่ตรงกันระหว่างชั้น: `Assignment`/FR-20 (architecture) vs `SurveyParticipant` (api-spec/db-spec/detailed-design)

ผู้เรียกตั้งข้อสังเกตว่า [[architecture#7. ข้อสมมติ|architecture §7 ข้อสมมติข้อ 7]] เขียนไว้ว่าขอบเขต "ทีม/อาคารที่หัวหน้าผู้สำรวจรับผิดชอบ" สำหรับ FR-32 จะ "ต่อยอดจากข้อมูลการมอบหมายงานของฟีเจอร์ 8/FR-20" (นั่นคือ entity `Assignment`/`AssignmentMember`) แต่เมื่อไล่ตรวจการออกแบบจริงพบว่า:

- [[api-spec#15.5.1 เรียกดูประวัติการแก้ไขผลประเมินรายอาคาร|api-spec 15.5.1]] ระบุตรงๆ ว่าใช้ `SurveyParticipant.role_in_team = หัวหน้าผู้สำรวจ` เป็นเกณฑ์ตรวจสอบขอบเขต ไม่ใช่ `Assignment`
- [[db-spec#4.2 SurveyParticipant|db-spec 4.2]] คือ entity ที่ถูกออกแบบมาตั้งแต่ก่อนหน้า FR-32/33 เพื่อรองรับ FR-16 (รายชื่อทีมสำรวจ 1-3 คน) และถูกใช้เป็น scoping pattern ซ้ำมาแล้ว **2 ครั้งก่อนหน้านี้**ใน [[api-spec#13.1 ค้นหา/กรองรายการอาคารที่สำรวจแล้ว|13.1]] และ [[api-spec#15.1 แสดงรายการระเบียนที่มีความขัดแย้งของข้อมูลรอการแก้ไขด้วยมือ|15.1]] — การเลือกใช้ pattern เดิมซ้ำสำหรับ FR-32 (ครั้งที่ 3) จึงสอดคล้องกับแนวทางที่มีอยู่แล้วในเอกสาร ไม่ใช่การเบี่ยงเบนใหม่
- [[detailed-design/audit-trail-building|audit-trail-building.md]] บันทึกความคลาดเคลื่อนนี้ไว้เองอย่างชัดเจนแล้ว (บรรทัดที่ 7 ของไฟล์) พร้อมเหตุผลที่เลือกยึดตาม `api-spec`/`db-spec` แทน — เป็นสัญญาณที่ดีว่าเจ้าของไฟล์ตรวจพบและตัดสินใจอย่างมีเหตุผล ไม่ใช่ความผิดพลาดที่ไม่มีใครรู้ตัว

**ประเมิน: เป็นปัญหาจริงหรือไม่** — เป็น**ปัญหาเชิงเอกสารจริง** (ข้อความสมมติใน `architecture.md` ไม่ตรงกับสิ่งที่ถูกออกแบบจริงในอีก 2 ชั้น) แต่**ไม่ใช่ปัญหาเชิงฟังก์ชัน** เพราะ (ก) ทั้ง 3 operation ที่ต้องการ ownership scoping (13.1, 15.1, 15.5.1) สอดคล้องกันเองว่าใช้ `SurveyParticipant` ทั้งหมด ไม่มี operation ใดหลงไปใช้ `Assignment` จริง (ข) `SurveyParticipant` เป็นตัวเลือกที่ตรงเจตนาของ NFR-08/FR-32 มากกว่าด้วยซ้ำ เพราะสะท้อน "ทีมที่ลงมือสำรวจอาคารนั้นจริง" (บันทึกตอนกรอกแบบฟอร์ม ณ เวลาสำรวจจริง) ในขณะที่ `Assignment` สะท้อนเพียง "งานที่วางแผนจะมอบหมายไว้ก่อนลงพื้นที่" ซึ่งอาจไม่ตรงกับทีมที่ไปสำรวจจริงเสมอไป (เช่น เปลี่ยนทีมกะทันหันหน้างาน)

**ควรแก้ที่ชั้นไหน**: **`architecture.md`** เท่านั้น — แก้ [[architecture#7. ข้อสมมติ|§7 ข้อสมมติข้อ 7]] ให้อ้างอิง `SurveyParticipant` แทน `Assignment`/FR-20 ให้ตรงกับสิ่งที่ `api-spec`/`db-spec`/`detailed-design` ยึดถือจริงอยู่แล้ว **ไม่ต้องแก้ 3 ชั้นที่เหลือ** เพราะทั้ง 3 ชั้นนั้นสอดคล้องกันเองอยู่แล้วและเป็นตัวเลือกที่ถูกต้องกว่า — สั่ง `sync-architecture` ได้โดยไม่กระทบ NFR-08 ที่ยังคงสถานะรองรับแล้วต่อไประหว่างรอแก้ (นี่เป็นการแก้เพื่อความถูกต้อง/สม่ำเสมอของเอกสาร ไม่ใช่การปิดช่องว่างเชิงฟังก์ชัน)

### หมายเหตุอื่นที่พบระหว่างตรวจ (ไม่บล็อกสถานะใดๆ)

- [[detailed-design/audit-trail-building|audit-trail-building.md]] บรรทัดที่ 7 อ้าง wikilink ไปยัง `[[architecture#5.5 Cross-cutting concerns]]` เพื่ออธิบายความคลาดเคลื่อนเรื่อง `Assignment` แต่ข้อความสมมติเรื่อง FR-20 จริงๆ อยู่ที่ [[architecture#7. ข้อสมมติ|§7 ข้อสมมติข้อ 7]] ไม่ใช่ §5.5 (§5.5 พูดเรื่อง ownership-based scoping เชิงหลักการเท่านั้น ไม่ได้เอ่ยถึง FR-20/`Assignment` ตรงๆ) — anchor ที่อ้างยังคง valid ทางเทคนิค (heading มีอยู่จริง) จึงไม่ใช่ลิงก์เสีย แต่เป็นการอ้างอิงผิดหัวข้อของเนื้อหาที่ต้องการชี้ถึง เป็นเรื่องเล็กน้อยที่ไม่กระทบสถานะ NFR ใด — เสนอให้ `sync-detailed-design` แก้ไขเป็น `[[architecture#7. ข้อสมมติ]]` เมื่อสะดวก (ไม่บังคับ)

## ผลตรวจรอบที่ 6 (2026-09-03) — ตรวจเทียบ stack จริงเป็นครั้งแรก หลัง `technology-stack.md` มีเนื้อหา

**บริบท**: ก่อนรอบนี้ `technology-stack.md` ว่างเปล่า ทุกรอบที่ผ่านมาตรวจได้แค่ว่า "การออกแบบเชิงตรรกะ" รองรับ NFR หรือไม่ (component รับผิดชอบถูกระบุหรือยัง, มีกลไก/state model รองรับหรือยัง) วันนี้ผู้ใช้ตัดสินใจ stack จริงแล้ว 5 ชั้น (ยังไม่กำหนดเวอร์ชันของทุกชั้น):

| ชั้น | เลือก |
|---|---|
| Field Client Framework | React Native |
| Local Persistent Store | SQLite (ผ่าน library ของ RN — ยังไม่เลือกตัวใด) |
| Server-side Runtime | Node.js / TypeScript |
| Primary Data Store | MySQL / MariaDB |
| Media/Object Storage | Local filesystem บนเซิร์ฟเวอร์ |

รอบนี้จึงเป็นรอบแรกที่ประเมินได้ว่า **สิ่งที่เลือกจริงทำให้ NFR บรรลุได้หรือไม่ ในระดับที่เป็นรูปธรรมขึ้น** ไม่ใช่แค่ระดับตรรกะเหมือนเดิม ตรวจครบทั้ง 10 ตัวตามที่ผู้เรียกกำชับ ไม่ใช่แค่ 5 ตัวที่ถูกชี้เป็นพิเศษ

### สรุปผลต่อ NFR แต่ละตัว

- **NFR-01 (Availability/Offline)** — **คงรองรับแล้ว**. React Native + SQLite คือสิ่งที่ [[technology-stack#2. ข้อจำกัดที่บีบตัวเลือก|technology-stack หัวข้อ 2]] ระบุว่าถูกเลือกเพราะ "ต้องรองรับ full local persistence ของข้อมูลสำรวจครบ 10 หมวดโดยไม่พึ่งเครือข่ายเลย" ตรงกับเจตนาของ NFR-01 ทุกประการ ไม่มีช่องว่างใหม่
- **NFR-02 (Performance/Reliability — sync ไฟล์ภาพใหญ่)** — **ลดระดับเป็นรองรับบางส่วน** (รายละเอียดเต็มในหัวข้อถัดไป) เพราะเลือก local filesystem แทน object storage ทำให้กลไก resumable/chunked upload ต้องออกแบบเอง แต่ปัจจุบันยังไม่มีการออกแบบกลไกติดตามความคืบหน้าของไฟล์ที่ส่งค้างบางส่วนเลยแม้แต่ระดับ logical
- **NFR-03 (Data Integrity — conflict detection)** — **คงรองรับแล้ว**. MySQL/MariaDB (relational) รองรับการเปรียบเทียบ `data_version`/`last_modified_at` และความสัมพันธ์ที่ [[db-spec#8.1 SyncConflict|SyncConflict]]/[[db-spec#8.2 SyncConflictVersion|SyncConflictVersion]] ต้องการได้ตรงไปตรงมา ไม่มีช่องว่างใหม่
- **NFR-04 (Usability/Compatibility — อุปกรณ์หลากรุ่น)** — **คงรองรับแล้ว แต่มีความเสี่ยง implementation ที่ต้องจับตา** (รายละเอียดในหัวข้อถัดไป) — ไม่ใช่ช่องว่างเอกสาร เพราะ `technology-stack.md` บันทึกความเสี่ยงนี้ไว้เองแล้วพร้อมเกณฑ์ทบทวน
- **NFR-05 (Auditability)** — **คงรองรับแล้ว**. Auditability เป็น business logic (สร้าง/เก็บ/อ่าน audit entry) ที่ไม่ผูกกับ stack เฉพาะเจาะจง Node.js/TypeScript + MySQL/MariaDB ทำได้ตรงไปตรงมา ไม่มีช่องว่างใหม่
- **NFR-06 (Accuracy — GPS/คุณภาพภาพ)** — **คงรองรับแล้ว**. เกณฑ์ตัวเลขที่ยอมรับได้ยังไม่กำหนด แต่เป็นประเด็นโดเมน (ต้องอิงความรู้ด้านวิศวกรรม/สนาม) ไม่ใช่ประเด็น tech stack — stack ที่เลือกไม่ปิดกั้นการกำหนดเกณฑ์นี้ในอนาคตแต่อย่างใด
- **NFR-07 (Scalability — โหลดกระจุกตัว)** — **คงรองรับแล้ว พร้อมข้อสังเกตความเสี่ยง** (รายละเอียดในหัวข้อถัดไป) — ความเสี่ยงถูกบันทึกไว้แล้วใน `technology-stack.md` พร้อมเกณฑ์ทบทวน ไม่ใช่ช่องว่างเอกสารใหม่
- **NFR-08 (Security/RBAC)** — **คงรองรับแล้ว**. `technology-stack.md` เองระบุว่า NFR-08 บีบ Server-side Runtime "น้อย" เพราะ RBAC เป็น business logic ทำได้แทบทุก stack — Node.js/TypeScript ไม่มีข้อจำกัดใดที่ขัดกับ RBAC ที่ออกแบบไว้
- **NFR-09 (Security — อายุ session ที่แคชไว้)** — **คงรองรับแล้ว** (รายละเอียดในหัวข้อถัดไป) — React Native เข้าถึง secure storage ระดับ OS ได้จริงผ่าน native module ที่มีอยู่แล้วในระบบนิเวศ
- **NFR-10 (Reporting Consistency)** — **คงรองรับแล้ว**. กฎกรองสถานะ `sync_status` เป็น query-level business logic ที่ MySQL/MariaDB รองรับได้มาตรฐาน ไม่ผูกกับ stack เฉพาะเจาะจง

### NFR-02 — ทำไมต้องลดระดับ (รายละเอียดเต็ม)

**หลักการที่ใช้ตัดสิน**: คำสั่งงานกำชับว่า "ห้ามลดระดับเพียงเพราะ stack ต่างจากที่เคยแนะนำ ต้องมีเหตุผลเชิงเทคนิคที่ยืนได้" — การลดระดับนี้ไม่ได้มาจากการที่ผู้ใช้เลือก local filesystem แทน object storage ที่เคยถูกแนะนำ (นั่นเป็นทางเลือกที่ผู้ใช้รับทราบข้อแลกเปลี่ยนแล้วเองตาม [[technology-stack#3. การตัดสินใจรายชั้น|technology-stack หัวข้อ 3]]) แต่มาจากการที่**สมมติฐานเดิมที่ใช้ปัดช่องว่างนี้ในรอบตรวจก่อนหน้าพังลง**:

1. รอบตรวจก่อนหน้า (รอบที่ 1-5) บันทึกไว้ว่า "รูปแบบ chunk/resume จริงยังไม่ตัดสินใจ (รอ `technology-stack.md` — ระบุไว้แล้วเป็นประเด็นรอตัดสินใจ ไม่ใช่ช่องว่างเชิง logical)" — เหตุผลเบื้องหลังคือสมมติว่า **ถ้าเลือก object storage** (เช่น S3-compatible) ความสามารถ resumable/multipart upload จะได้มาโดยอัตโนมัติจากตัว storage เอง ไม่ต้องออกแบบ protocol เองที่ระดับ logical
2. รอบนี้พบว่าสมมตินั้น**ไม่เป็นจริง** เพราะผู้ใช้เลือก **local filesystem บนเซิร์ฟเวอร์** และ [[technology-stack#3. การตัดสินใจรายชั้น|technology-stack หัวข้อ 3]] บันทึกไว้เองตรงๆ ว่า "**ผู้ใช้เลือก local filesystem โดยรับทราบข้อเสียนี้แล้วว่า resumable upload ตาม NFR-02 ต้องเขียนเอง ไม่ได้มาฟรีเหมือน object storage**"
3. เมื่อไล่ตรวจโมเดลข้อมูลจริงพบว่า **ไม่มีกลไกใดรองรับ "เขียนเอง" นั้นเลยแม้แต่ระดับ logical**: [[db-spec#6.1 DamagePhoto|db-spec 6.1 DamagePhoto]] และ [[db-spec#6.3 Sketch|6.3 Sketch]] มี `sync_status` เพียง 4 ค่า (ยังไม่ซิงค์/กำลังซิงค์/ซิงค์สำเร็จ/มีความขัดแย้งรอแก้ไข) — ไม่มี attribute ใดเก็บ byte offset/chunk index ที่ส่งสำเร็จไปแล้ว และ [[detailed-design/offline-sync#3. State Diagram: sync_status|offline-sync §3 state diagram]] ระบุ transition `กำลังซิงค์ → ยังไม่ซิงค์` เมื่อ "ไฟล์ภาพส่งไม่สำเร็จบางส่วน/สัญญาณขาดหาย" พร้อมหมายเหตุ "(ทำต่อได้ภายหลัง ไม่ต้องเริ่มใหม่ทั้งหมด)" — **ข้อความนี้กับโมเดลข้อมูลจริงขัดกันเอง**: ถ้าสถานะกลับไปเป็น "ยังไม่ซิงค์" (สถานะเดียวกับไฟล์ที่ยังไม่เคยส่งเลย) โดยไม่มี field ใดจำความคืบหน้าไว้ ก็ไม่มีทางที่การซิงค์ครั้งถัดไปจะ "ทำต่อจากจุดที่ค้าง" ได้จริงในทางเทคนิค จะต้องเริ่มส่งไฟล์นั้นใหม่ทั้งหมดเสมอ

**สรุป**: กลไกระดับ component (Sync & Conflict Resolution Service + Media/Object Storage รับผิดชอบ) ยังคงถูก map ไว้ถูกต้อง และเจตนาของ NFR-02 ("ต้องส่งต่อได้โดยไม่ต้องเริ่มใหม่ทั้งหมด") ถูกเขียนไว้ชัดเจนใน [[api-spec#14.1 ซิงค์ข้อมูลแบบสำรวจที่ค้างจากอุปกรณ์|api-spec 14.1]] แต่**ไม่มีกลไกรองรับเจตนานั้นจริงในโมเดลข้อมูล** — เป็นช่องว่างแบบเดียวกับที่เคยพบใน NFR-04/NFR-07 ในรอบตรวจก่อนหน้า ("map ไว้ในตารางแต่ไม่มีกลไกออกแบบจริงรองรับ") จึงจัดเป็น **รองรับบางส่วน** ไม่ใช่ "ยังไม่รองรับ" เพราะยังมีการ retry ทั้งไฟล์ได้อยู่ (แค่ไม่ resume จากจุดค้างจริง)

**สิ่งที่ต้องทำเพิ่มเพื่อให้บรรลุ NFR-02**: เพิ่มกลไก logical ในระดับ api-spec/db-spec (ไม่ต้องรอเลือก library SQLite หรือ framework อัปโหลดใดๆ ก่อน เพราะเป็น contract ระดับ logical ล้วนๆ):
- เพิ่ม attribute เก็บความคืบหน้าการอัปโหลดต่อไฟล์ (เช่น byte offset หรือ chunk index ล่าสุดที่ส่งสำเร็จ) ใน [[db-spec#6.1 DamagePhoto|DamagePhoto]]/[[db-spec#6.3 Sketch|Sketch]]
- ปรับ [[api-spec#14.1 ซิงค์ข้อมูลแบบสำรวจที่ค้างจากอุปกรณ์|api-spec 14.1]] ให้ input/output ระบุการ resume ได้ตรงๆ (เช่น client ส่ง offset ที่จะเริ่มต่อ, server ตอบกลับ offset ที่รับล่าสุด)
- **แนะนำให้รันต่อ**: `sync-api-db`

### NFR-04 — ความเสี่ยงจาก React Native (ไม่ใช่ช่องว่างเอกสาร)

React Native ถูกเลือกทั้งที่ [[technology-stack#3. การตัดสินใจรายชั้น|technology-stack หัวข้อ 3]] บันทึกไว้เองว่า Flutter "ตอบ NFR-04 ได้ตรงกว่า" (คอมไพล์เป็น native ARM ไม่ผ่าน JS bridge) แต่ผู้ใช้เลือก React Native เพราะเป็นทีมคนเดียวที่ถนัด JS/TS — เป็นข้อแลกเปลี่ยนที่รู้ตัวและบันทึกไว้ครบแล้ว ไม่ใช่การมองข้าม จุดที่ต้องจับตา 2 จุดตามที่ผู้เรียกกังวล:

1. **ประสิทธิภาพบนแท็บเล็ต Android สเปกต่ำ** — `technology-stack.md` เองบันทึกไว้แล้วว่าต้องทดสอบบนอุปกรณ์จริง (ไม่ใช่ emulator) พร้อมเกณฑ์ทบทวนที่ชัดเจนถ้าพบปัญหา ([[technology-stack#6. เกณฑ์ที่จะทำให้ต้องทบทวนการตัดสินใจนี้ใหม่|technology-stack §6 ข้อ 1]]) — ตรวจสอบแล้วว่า [[detailed-design/building-environment-info#5. Edge Case เพิ่มเติมสำหรับการใช้งานกลางแจ้งในพื้นที่ภัยพิบัติ (NFR-04)|building-environment-info §5]] ครอบคลุม edge case เชิง logical ที่ไม่ขึ้นกับ framework อยู่แล้ว (ถุงมือ/แสงจ้า/ขนาดหน้าจอ) ส่วนประสิทธิภาพจริงเป็นเรื่องที่ต้องทดสอบตอน implementation ไม่ใช่สิ่งที่เอกสารระดับ logical แก้ให้ได้ล่วงหน้า
2. **background upload อาจต้องพึ่ง native module เพิ่ม** — ตรวจสอบ [[detailed-design/offline-sync#5. Edge Case และวิธีจัดการ|offline-sync §5]] แล้วพบว่าการออกแบบปัจจุบัน**ไม่ได้อ้างอิงถึงการอัปโหลดแบบพื้นหลังขณะแอปถูกปิด** จริงๆ — สิ่งที่ออกแบบไว้คือ "ระเบียนต้องไม่หายและคิวต้องทำงานต่อได้เองเมื่อ**เปิดแอปใหม่**" ซึ่งเป็นข้อกำหนดที่อ่อนกว่า "อัปโหลดต่อได้แม้แอปถูกปิดอยู่เบื้องหลัง" — ถ้าเจตนาจริงของ NFR-02/NFR-04 ต้องการ true background upload (ไม่ใช่แค่ resume เมื่อเปิดแอปใหม่) จะต้องมี native module เพิ่มเติมตามที่ [[technology-stack#6. เกณฑ์ที่จะทำให้ต้องทบทวนการตัดสินใจนี้ใหม่|technology-stack §6 ข้อ 2]] เตือนไว้แล้ว — **ประเมินว่าเป็นข้อสังเกตไม่บล็อกสถานะ** เพราะข้อกำหนดปัจจุบันในเอกสาร ("ทำงานต่อได้เมื่อเปิดแอปใหม่") เป็นสิ่งที่ระบุไว้ชัดเจนแล้วและไม่ขัดแย้งกับตัวมันเอง เพียงแต่ควรตรวจสอบกับผู้ใช้ว่าเจตนาจริงต้องการ true background upload หรือไม่ — ไม่ใช่สิ่งที่ nfr-reviewer ตัดสินใจแทนได้
- **แนะนำให้รันต่อ (ไม่บังคับ)**: ถ้ายืนยันว่าต้องการ true background upload ให้ `sync-detailed-design` ปรับ [[detailed-design/offline-sync|offline-sync.md]] ให้ระบุข้อกำหนดนี้ตรงๆ

### NFR-07 — ข้อสังเกตเรื่อง single-server local filesystem (ไม่ใช่ช่องว่างเอกสาร)

`technology-stack.md` เลือก Node.js (เหมาะกับงาน I/O-bound ที่มี concurrent connection จำนวนมาก ตรงกับเหตุผลที่ระบุไว้ใน [[technology-stack#3. การตัดสินใจรายชั้น|technology-stack หัวข้อ 3]] — "ecosystem queue/background job รองรับโหลดกระจุกตัว") ร่วมกับ **local filesystem บนเซิร์ฟเวอร์เดียว** สำหรับเก็บไฟล์ภาพ กลไก logical ที่ [[architecture#2. Logical Component|architecture หัวข้อ 2]] ออกแบบไว้ (Server-side Sync Intake Queue จัดคิว/จำกัดอัตรา) ยังคงตอบโจทย์ NFR-07 ที่ระดับตรรกะ แต่**เซิร์ฟเวอร์เดียว + local filesystem หมายความว่าไม่มีทางขยายกำลังรับไฟล์ในแนวนอน (horizontal scaling) ได้โดยไม่รื้อสถาปัตยกรรมการเก็บไฟล์** ถ้าปริมาณทีม/ไฟล์ในอนาคตเกินกำลังเซิร์ฟเวอร์เดียวรองรับไหว — ความเสี่ยงนี้**ถูกบันทึกไว้แล้วเองใน [[technology-stack#6. เกณฑ์ที่จะทำให้ต้องทบทวนการตัดสินใจนี้ใหม่|technology-stack §6 ข้อ 5]]** พร้อมคำแนะนำเชิงปฏิบัติ (เขียน abstraction layer แยกไว้ตั้งแต่ต้นเพื่อลดต้นทุนการย้ายในอนาคต) จึงไม่ใช่ช่องว่างเอกสารที่ nfr-review ต้องรายงานใหม่ ยืนยันคงสถานะ **รองรับแล้ว**

### NFR-09 — ยืนยัน React Native เข้าถึง secure storage ระดับ OS ได้จริง

[[technology-stack#3. การตัดสินใจรายชั้น|technology-stack หัวข้อ 3]] ระบุเหตุผลเลือก SQLite ไว้ตรงๆ ว่าต้องตอบ NFR-09 ("แยกเก็บ credential ผ่าน secure storage ของ OS ได้") และ [[technology-stack#2. ข้อจำกัดที่บีบตัวเลือก|technology-stack หัวข้อ 2]] ยืนยันว่า Field Client Framework ถูกเลือกโดยพิจารณาแล้วว่า "framework ต้องมี API เข้าถึงที่เก็บข้อมูลปลอดภัยระดับ OS (Keystore บน Android) ได้" — React Native มี ecosystem library ที่ทำสิ่งนี้ได้จริงอยู่แล้ว (เข้าถึง Android Keystore ผ่าน native module) ตรวจสอบ [[detailed-design/authentication-login|authentication-login.md]] แล้วพบว่า sequence diagram/state diagram ไม่ขึ้นกับ library เฉพาะเจาะจง (อ้างอิงแค่ "Session ที่แคชไว้" เชิง logical) — library ตัวใดที่จะใช้จริงยังเป็นประเด็นเปิดใน [[architecture#8. ประเด็นรอตัดสินใจ|architecture §8]] ("กลไกยืนยันตัวตน/ออก session ที่เป็นรูปธรรม") อยู่แล้วตั้งแต่ก่อนรอบนี้ ไม่ใช่ช่องว่างใหม่ที่ต้องเพิ่ม ยืนยันคงสถานะ **รองรับแล้ว**

### NFR-01/NFR-03 — ยืนยัน SQLite + MySQL/MariaDB ตอบโจทย์ offline-first และ versioning

ทั้งสองประเด็นได้รับการยืนยันแล้วในหัวข้อ "สรุปผลต่อ NFR แต่ละตัว" ด้านบน — ไม่มีรายละเอียดเพิ่มเติมนอกเหนือจากนั้น เพราะทั้ง SQLite (รองรับ relationship ของข้อมูล 10 หมวด + เก็บ version/timestamp) และ MySQL/MariaDB (relational, รองรับ concurrent write + comparison) ถูกเลือกโดยอ้างอิง NFR-01/NFR-03 ตรงๆ ใน [[technology-stack#3. การตัดสินใจรายชั้น|technology-stack หัวข้อ 3]] อยู่แล้ว ไม่พบความขัดแย้งใดระหว่างเหตุผลที่ให้ไว้กับสิ่งที่ [[db-spec]] ออกแบบไว้จริง

### สรุปรวมรอบที่ 6

**เปลี่ยนจากรอบที่ 5**: มีเพียง **NFR-02 ตัวเดียว** ที่เปลี่ยนสถานะ (รองรับแล้ว → รองรับบางส่วน) ส่วนอีก 9 ตัวคงสถานะรองรับแล้วเช่นเดิม — **สาเหตุของการเปลี่ยนแปลงคือการมี stack จริงให้เทียบเป็นครั้งแรก** ทำให้สมมติฐานที่เคยใช้ปัดช่องว่าง NFR-02 ("รอ tech stack ตัดสินใจ") พังลงเมื่อพบว่าตัวเลือกที่ถูกเลือกจริง (local filesystem) ไม่ได้ให้ resumable upload มาฟรีเหมือนที่สมมติไว้ ไม่ใช่เพราะ stack ที่เลือกด้อยกว่าที่เคยแนะนำ — ผู้ใช้เลือกโดยรู้ข้อแลกเปลี่ยนแล้วตาม `technology-stack.md`

**ควรรันชั้นไหนซ้ำ**: `sync-api-db` เพื่อปิดช่องว่าง NFR-02 (เพิ่มกลไก resume/chunk tracking ระดับ logical ใน [[db-spec#6.1 DamagePhoto|db-spec 6.1]]/[[db-spec#6.3 Sketch|6.3]] และ [[api-spec#14.1 ซิงค์ข้อมูลแบบสำรวจที่ค้างจากอุปกรณ์|api-spec 14.1]]) — ไม่จำเป็นต้องรัน `sync-architecture` หรือ `sync-detailed-design` สำหรับ NFR-02 เพราะ component ที่รับผิดชอบและ state model ระดับสูงยังถูกต้องอยู่แล้ว ช่องว่างอยู่ที่ระดับ attribute/operation contract เท่านั้น ส่วน `sync-detailed-design` สำหรับ [[detailed-design/offline-sync|offline-sync.md]] เป็นทางเลือกเสริมไม่บังคับถ้าต้องการชี้แจงเรื่อง true background upload ของ NFR-04 (ดูหัวข้อ NFR-04 ด้านบน)

## ผลตรวจรอบที่ 7 (2026-09-03) — ตรวจซ้ำเฉพาะ NFR-02 หลังปิดช่องว่างที่รอบที่ 6 พบ

**ขอบเขตรอบนี้แคบมาก ตามคำขอ**: ตรวจซ้ำเฉพาะ NFR-02 (ไม่ตรวจ NFR ข้ออื่นซ้ำ — 9 ตัวที่เหลือคงผลจากรอบที่ 6 ไว้ทั้งหมดโดยไม่มีการเปลี่ยนแปลงใดๆ) โดยเฉพาะตรวจว่า **ข้อความในเอกสารกับโมเดลข้อมูลสอดคล้องกันแล้วจริงหรือไม่** ไม่ใช่แค่ตรวจว่ามีการเพิ่ม attribute เกิดขึ้น

### สิ่งที่ตรวจ (1): `db-spec.md` เพิ่ม attribute ตามคำแนะนำหรือไม่

อ่านไฟล์จริงพบว่า [[db-spec#6.1 DamagePhoto|db-spec 6.1 DamagePhoto]] และ [[db-spec#6.3 Sketch|6.3 Sketch]] เพิ่มครบ 4 attribute ตรงตามคำแนะนำ: `upload_session_id` (ตัวระบุเฉพาะ, ไม่บังคับเว้นแต่ `sync_status = กำลังซิงค์`), `total_file_size_bytes` (ตัวเลข, บังคับเสมอ — สมเหตุสมผลเพราะต้องทราบขนาดไฟล์ก่อนเริ่มอัปโหลดเสมอไม่ว่าจะ resume หรือไม่), `uploaded_bytes` และ `last_chunk_received_at` (ทั้งคู่มีเงื่อนไข "ไม่ (จำเป็นเมื่อ sync_status = กำลังซิงค์)" ตรงรูปแบบเดียวกับที่บังคับใช้หลัง regression ของ NFR-05 ในรอบที่ 3/4) — [[db-spec#10. กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล|db-spec หัวข้อ 10 ข้อ 8]] เพิ่มกฎระบุเงื่อนไขชัดเจนว่าเมื่อไรส่งต่อจากจุดค้าง (session ตรงกัน + ไม่ stale) เมื่อไรต้องล้างแล้วเริ่มรอบใหม่ (session ไม่ตรง หรือ stale เกินเกณฑ์) พร้อมระบุว่า `sync_status = ซิงค์สำเร็จ` ได้ก็ต่อเมื่อ `uploaded_bytes = total_file_size_bytes` เท่านั้น — ตรงตามคำแนะนำที่รอบที่ 6 ให้ไว้ครบทุกจุด

### สิ่งที่ตรวจ (2): ข้อความในเอกสารกับ state machine สอดคล้องกันแล้วจริงหรือไม่ — จุดที่ต้องตรวจเข้มที่สุด

นี่คือจุดที่รอบที่ 6 เตือนไว้ตรงๆ ว่า "แค่เพิ่ม attribute ไม่พอ ถ้า state ยังถอยกลับ `ยังไม่ซิงค์` ก็ยังขัดกันเองอยู่ดี" — อ่าน [[detailed-design/offline-sync#3. State Diagram: sync_status|offline-sync §3 state diagram]] ไฟล์จริงพบว่า:

- **Transition `กำลังซิงค์ --> ยังไม่ซิงค์` ที่เคยมีถูกลบออกแล้วจริง** — ไม่ปรากฏในไดอะแกรมอีกต่อไป
- แทนที่ด้วย **self-loop 2 เส้นบนสถานะ `กำลังซิงค์` เอง**: (ก) กรณี `upload_session_id` ตรงกันและไม่ stale → ส่งต่อจาก `uploaded_bytes` เดิม คงสถานะ `กำลังซิงค์` ไว้ไม่ถอยกลับ (ข) กรณี `upload_session_id` ไม่ตรง/รอบเดิม stale → ออก session ใหม่ เริ่มนับ `uploaded_bytes` จาก 0 แต่**ยังคงสถานะ `กำลังซิงค์` เดิม ไม่ถอยกลับ `ยังไม่ซิงค์`**
- ตาราง edge case ใน [[detailed-design/offline-sync#5. Edge Case และวิธีจัดการ|offline-sync §5]] แยกเป็น 2 แถวตามเงื่อนไขเดียวกัน ระบุชัดเจนว่า "`sync_status` คงสถานะ 'กำลังซิงค์' ไว้ ไม่ถอยกลับ 'ยังไม่ซิงค์' เพราะตำแหน่งที่ส่งสำเร็จถูกเก็บไว้ในระเบียนแล้ว" — ข้อความนี้ตรงกับสิ่งที่โมเดลข้อมูลรองรับได้จริงแล้ว (มี `uploaded_bytes` เก็บตำแหน่งไว้จริง) ไม่ใช่คำกล่าวอ้างลอยๆ เหมือนรอบก่อน
- Sequence diagram ที่ [[detailed-design/offline-sync#1. Sequence Diagram|offline-sync §1]] และตาราง operation↔entity ที่ [[detailed-design/offline-sync#2. Operation ↔ Entity ที่กระทบ|offline-sync §2]] ก็ระบุกลไกจริงตรงกัน (อ้างอิง `uploaded_bytes`/`upload_session_id`/กฎข้อ 8 ตรงๆ ไม่ใช่ประโยคลอย)
- ตรวจไขว้กับ [[api-spec#14.1 ซิงค์ข้อมูลแบบสำรวจที่ค้างจากอุปกรณ์|api-spec 14.1]] แล้วพบว่า Input/Output/กฎทางธุรกิจ/กรณี error ทั้ง 4 ส่วนพูดเรื่องเดียวกันสอดคล้องกันหมด (server ต้องรายงาน `upload_session_id`/`uploaded_bytes` กลับเสมอ, client ส่งเฉพาะส่วนที่ยังไม่ถึงเซิร์ฟเวอร์)

**สรุปข้อ (2)**: ข้อขัดแย้งเดิมที่รอบที่ 6 พบ ("ข้อความบอกว่าทำต่อได้ แต่ state กลับไปยังไม่ซิงค์") **ปิดจริงแล้ว** ไม่ใช่การซ่อมแค่ผิวเผิน — ทั้ง state diagram, edge case table, sequence diagram, และ api-spec สอดคล้องกันครบทุกจุดที่ตรวจ

### สิ่งที่ตรวจ (3): ตัวเลข chunk size/stale threshold ที่ยังไม่กำหนด — ทำให้ NFR-02 ยังต้อง "รองรับบางส่วน" หรือไม่

ประเมินตามหลักการเดียวกับที่ nfr-review ใช้กับ NFR-06 (เกณฑ์ตัวเลข GPS/คุณภาพภาพ) และ NFR-07 (ตัวเลข rate-limit) ในรอบก่อนหน้า: **กลไกระดับ logical ต้องครบก่อน ตัวเลขพารามิเตอร์ที่ไม่กระทบโครงสร้าง/พฤติกรรมของกลไกจึงจะนับเป็นประเด็น implementation ได้** ตรวจสอบแล้วว่า:

- กลไกครบจริง: มี attribute เก็บ progress ครบ, มีกฎชัดเจนว่าเมื่อไร resume/เมื่อไรต้องเริ่มใหม่, state diagram ไม่ขัดแย้งกับกฎ, operation contract ระบุ input/output สำหรับ resume ตรงๆ — ไม่มีจุดใดที่ "รอตัวเลข" ก่อนจึงจะออกแบบกลไกต่อได้
- ขนาด chunk ที่แบ่งส่งจริง และเกณฑ์เวลา stale เป็นค่าที่ **ไม่กระทบทิศทางของกลไก** ไม่ว่าจะกำหนดเป็นเท่าใด กลไก "เทียบ session + ส่งต่อจาก offset / เริ่มใหม่เมื่อ session ไม่ตรงหรือ stale" ยังทำงานแบบเดียวกันเป๊ะ ต่างกันแค่ granularity/ความไวในการตัดสินใจ stale เท่านั้น
- ทั้งสองค่าถูกบันทึกไว้ถูกที่แล้วใน [[db-spec#11. ประเด็นรอตัดสินใจ|db-spec หัวข้อ 11]] และ [[api-spec#16. ประเด็นรอตัดสินใจ|api-spec หัวข้อ 16]] พร้อมกำกับ "ห้ามเดาค่าตัวเลข" ตรงตามกติกาของโปรเจกต์

**สรุปข้อ (3)**: ตัวเลขที่ยังไม่กำหนดเป็นประเด็นระดับ implementation จริง ไม่ใช่ช่องว่างเชิง logical ที่ยังค้างอยู่ — **ไม่ทำให้ NFR-02 ต้องคงสถานะ "รองรับบางส่วน" ต่อไป**

### สรุปรวมรอบที่ 7

NFR-02 กลับเป็น **รองรับแล้ว** เต็มรูปแบบ — ทั้ง 3 ชั้นเอกสาร ([[db-spec]], [[api-spec]], [[detailed-design/offline-sync]]) สอดคล้องกันจริง ไม่ใช่แค่เพิ่ม attribute ผิวเผินแล้วปล่อย state machine ขัดแย้งไว้เหมือนเดิม การตรวจซ้ำนี้ยืนยันว่าคำแนะนำของรอบที่ 6 ถูกทำตามครบทั้ง 2 จุด (attribute ใน db-spec + แก้ state diagram ใน detailed-design) ไม่มีการเปลี่ยนแปลงใดๆ นอกเหนือจาก 3 ไฟล์ที่ระบุไว้ (`db-spec.md`, `api-spec.md`, `detailed-design/offline-sync.md`) และไม่มีตัวเลขพารามิเตอร์ใดถูกเดาหรือกำหนดขึ้นเองระหว่างการแก้ไข

**บันทึกไว้เพื่อผู้อ่านย้อนหลัง**: NFR-02 ผ่านการปรับสถานะ 2 ครั้งในวันเดียว (2026-09-03) — รอบที่ 5 (ก่อนหน้า): รองรับแล้ว → รอบที่ 6: ลดเป็นรองรับบางส่วน (พบว่าเลือก local filesystem ทำให้สมมติฐานเดิม "รอ tech stack" ไม่เป็นจริง และโมเดลข้อมูล/state diagram ขัดกันเอง) → รอบที่ 7: กลับเป็นรองรับแล้ว (ช่องว่างถูกปิดด้วยการเพิ่ม 4 attribute + กฎทางธุรกิจข้อ 8 ใน db-spec, ปรับ input/output ของ api-spec 14.1, และแก้ state diagram ของ offline-sync ให้ self-loop แทนการถอยกลับ) — เช่นเดียวกับ NFR-05 ในรอบที่ 3-4 การขึ้น-ลงนี้ไม่ใช่ความผิดพลาดของการตรวจ แต่สะท้อนว่ากระบวนการตรวจ-แก้-ตรวจซ้ำทำงานตามที่ออกแบบไว้จริง

## ผลตรวจรอบที่ 8 (2026-09-03) — NFR-11 ใหม่ (11 ตัวใน backlog) + tech stack เจาะจงขึ้น (bare React Native + `op-sqlite`)

**บริบท**: `test-writer` พบระหว่างเขียน test case ของ FR-27 ว่า NFR-09 (อายุ session ที่แคชไว้ขณะออฟไลน์มีจำกัด) ไม่บรรลุเจตนารมณ์จริง ถ้าไม่มีกลไกจำกัดจำนวนครั้งที่กรอก PIN ผิด (ผู้โจมตีที่ถือครองอุปกรณ์ไว้ในกรอบเวลา session ยังไม่หมดอายุ สามารถไล่เดา PIN ได้ไม่จำกัดจำนวนครั้ง) ผู้ใช้จึงเพิ่ม **NFR-11 (Security — PIN Attempt Lockout, ระดับสูง)** เข้า [[backlog]] เมื่อ 2026-09-03 — รวมเป็น **11 ตัว** ในรอบนี้ ระหว่างเดียวกัน `technology-stack.md` ก็ถูกปรับให้เจาะจงขึ้นอีกขั้น: **Field Client Framework = bare React Native** (ไม่ใช่ Expo managed workflow) และ **Local Persistent Store library = `op-sqlite`** (เดิมรอบที่ 6/7 รู้เพียงว่าเป็น "React Native + SQLite" ยังไม่เลือก library เฉพาะ) — รอบนี้จึงตรวจ 2 เรื่องคู่ขนาน: (ก) NFR-11 ทั้งตัวเป็นครั้งแรก และ (ข) ตรวจซ้ำ NFR-01/NFR-02/NFR-04/NFR-09 ว่า stack ที่เจาะจงขึ้นเปลี่ยนข้อสรุปเดิมหรือไม่ ตรวจครบทั้ง 11 ตัว ไม่ใช่แค่ตัวที่เปลี่ยน

### NFR-11 — ตรวจครั้งแรก: รองรับครบทั้ง 3 ชั้นเอกสารตั้งแต่การออกแบบรอบแรก

ไล่ตรวจทั้ง 4 ชั้นเอกสาร (ไม่ใช่แค่ดูตาราง NFR mapping ของ architecture เฉยๆ ตามหลักการที่ nfr-review ใช้มาตั้งแต่รอบแรก):

1. **[[architecture]]**: มีทั้ง (ก) แถวใน [[architecture#5. Mapping NFR ไปยัง Component|§5 Mapping NFR]] ระบุ Field Client App (รวม Local Persistent Store) เป็นผู้รับผิดชอบ พร้อมอธิบายกลไกเต็มย่อหน้า ไม่ใช่ระบุ component ลอยๆ (ข) `opt` block ใน [[architecture#4.1 ผู้สำรวจภาคสนามลงพื้นที่สำรวจอาคาร (ออฟไลน์ + AI + ซิงค์)|§4.1]] แทรกเป็นกิ่งย่อยของ flow เข้าสู่ระบบเดิม (ค) 2 bullet ใหม่ใน [[architecture#5.5 Cross-cutting concerns|§5.5]] (การยืนยันตัวตน + ความทนทานของข้อมูลขณะออฟไลน์ — ครอบคลุมทั้งมุมของ NFR-11 เองและผลกระทบต่อ NFR-01) และ (ง) หัวข้อเหตุผลการตัดสินใจเต็มรูปแบบที่ [[architecture#6.8 แยกพื้นที่จัดเก็บ credential/PIN ออกจากข้อมูลแบบสำรวจในเครื่อง (NFR-11)|§6.8]] ที่พิจารณา 3 ทางเลือกจริง (แยกพื้นที่จัดเก็บระดับโครงสร้าง / เก็บปนกันแล้วคัดกรองด้วย logic / ล้างข้อมูลทั้งหมดเมื่อ lockout) พร้อมเหตุผลตัดทิ้ง 2 ทางเลือกหลังอย่างมีน้ำหนัก — ไม่ใช่การ map แบบผิวเผิน
2. **[[db-spec]]**: `Session` เพิ่ม `cached_pin_secret`/`failed_pin_attempt_count` ทั้งคู่มีเงื่อนไข "จำเป็นเมื่อ `is_offline_cached = true`" (รูปแบบเดียวกับฟิลด์เงื่อนไขอื่นในไฟล์ ไม่ใช่ข้อความบรรยายลอยๆ) และ**ไม่ sync ขึ้นเซิร์ฟเวอร์** (ปิดช่องทางที่ตัวนับจะรั่วไหล/ถูกปลอมจากฝั่งเซิร์ฟเวอร์) — [[db-spec#10. กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล|db-spec หัวข้อ 10 ข้อ 10]] เขียนกฎครบ: เมื่อไรเพิ่มค่า/เมื่อไรรีเซ็ต/เมื่อไรล้าง พร้อมย้ำชัดเจนว่า **"ห้ามการล้างนี้กระทบ `SurveyedBuilding`/entity ย่อยของแบบสำรวจหรือคิวรอซิงค์บนอุปกรณ์เดียวกันเด็ดขาด"**
3. **[[api-spec]]**: [[api-spec#1.1 เข้าสู่ระบบ|1.1]] เพิ่ม input ตั้ง/เปลี่ยน PIN + รีเซ็ตตัวนับเสมอเมื่อเข้าสู่ระบบสำเร็จ, [[api-spec#1.3 เข้าสู่ระบบด้วย credential ที่แคชไว้ขณะออฟไลน์|1.3]] แตก output เป็น 3 กรณีผลลัพธ์ชัดเจน (ถูก/ผิดยังไม่ครบ/ผิดครบจำนวน) พร้อมกฎทางธุรกิจและกรณี error ระบุ NFR-11 ตรงๆ, [[api-spec#1.4 ต่ออายุ/ยืนยันตัวตนใหม่เมื่อกลับมามีสัญญาณ|1.4]] ปฏิเสธการต่ออายุ session ที่ถูกเพิกถอนจาก lockout — ไม่มี server-side operation ใหม่เพราะเหตุการณ์นี้เกิดขึ้นทั้งหมดบนอุปกรณ์ขณะออฟไลน์ (สมเหตุสมผล)
4. **[[detailed-design/authentication-login]]**: sequence diagram ครบ 3 เส้นทาง (ถูก/ผิดยังไม่ครบ/ผิดครบจำนวน) พร้อม note กำกับผลกระทบต่อ `SurveyedBuilding`/entity ย่อยตรงจุดที่อันตรายที่สุด, state diagram เพิ่ม transition `ใช้งานอยู่ → ถูกเพิกถอน` จาก lockout แยกจาก transition เดิมของการปิดบัญชี, ตาราง edge case 5 แถวครอบคลุมทั้งกรณีปกติและกรณีที่ซับซ้อนกว่า (เช่น ครบจำนวนขณะยังไม่มีสัญญาณ — ผู้ใช้ดูข้อมูลเดิมได้แต่แก้ไข/กรอกใหม่ไม่ได้จนกว่าจะกลับมามีสัญญาณ)

**สรุป**: NFR-11 **รองรับแล้ว** ตั้งแต่การตรวจครั้งแรก ไม่มีช่องว่างใดที่ต้องรายงาน — จุดที่น่าสังเกตคือเอกสารทั้ง 4 ชั้นถูกออกแบบให้ "การล้าง credential" เป็นจริงได้**โดยโครงสร้างของโมเดลข้อมูล** (entity `Session` แยกจาก `SurveyedBuilding`/entity ย่อยของแบบสำรวจอยู่แล้วโดยธรรมชาติ การอัปเดต/ล้างค่าใน `Session` จึงไม่มีทางแตะ entity อื่นได้เลยแม้ในระดับ query) ไม่ใช่แค่พึ่งพาคำสัญญาเป็นข้อความ ตรงตามที่ผู้เรียกกำชับให้ตรวจเป็นพิเศษ

### ประเด็นที่ผู้เรียกกังวลเป็นพิเศษ (1): NFR-11 ล้าง credential โดยไม่กระทบข้อมูลสำรวจที่ยังไม่ซิงค์ — ตรวจระดับ schema จริง ไม่ใช่แค่ข้อความ

ตรวจสอบว่า "การแยกพื้นที่จัดเก็บ" ที่ [[architecture#6.8 แยกพื้นที่จัดเก็บ credential/PIN ออกจากข้อมูลแบบสำรวจในเครื่อง (NFR-11)|architecture §6.8]] อ้างว่าเป็นการแยก "ตั้งแต่ระดับโครงสร้าง" นั้นเป็นจริงที่ระดับ entity/schema หรือไม่ พบว่า **เป็นจริง**: `Session` ([[db-spec#2.2 Session|db-spec 2.2]]) เป็น entity คนละตัวกับ `SurveyedBuilding`/`SurveyParticipant`/`SurroundingHazard`/`ExternalDamage`/`StructuralDamage`/`ComponentDamage`/`ElectricalSystemDamage`/`DamagePhoto`/`AIAnalysisResult`/`Sketch`/คิวรอซิงค์ ตั้งแต่แรกอยู่แล้ว (ไม่เคยมีการออกแบบให้ credential ฝังรวมอยู่ใน entity ของแบบสำรวจ) การล้างค่าตาม NFR-11 เป็นเพียงการอัปเดต 2 attribute ภายใน entity `Session` เดียว (`cached_pin_secret`, `failed_pin_attempt_count`) — ไม่มี foreign key หรือ cascade ใดๆ ที่โยงจาก `Session` ไปยัง entity ของแบบสำรวจในทิศทางที่การลบ/ล้างค่าใน `Session` จะกระทบข้อมูลแบบสำรวจได้ จึงเป็นการรับประกันที่ระดับโครงสร้างข้อมูลจริง ไม่ใช่แค่คำสัญญาเป็นข้อความในคอลัมน์คำอธิบายเหมือนกับที่เคยพบเป็นปัญหาใน NFR-05 รอบที่ 3 (`performed_by_user_id` ที่เขียนกฎไว้แค่ในคำอธิบายไม่ใช่ constraint จริง) — สถานการณ์ต่างกัน **ไม่มีช่องว่างแบบเดียวกันเกิดซ้ำที่นี่**

### ประเด็นที่ผู้เรียกกังวลเป็นพิเศษ (2): NFR-09 กับ NFR-11 ทำงานร่วมกันครบวงจรหรือไม่

ไล่ตรวจ 2 เส้นทางที่อาจทำให้เจตนารมณ์ของ NFR-09 (จำกัดอายุ session ที่แคชไว้) ยังไม่บรรลุผลถ้า NFR-11 อุดไม่ครบ:

1. **เส้นทางเวลา (NFR-09)**: `Session.expires_at` จำกัดว่า credential ที่แคชไว้ใช้ได้กี่วัน (7 วันตามข้อสมมติที่ปิดแล้ว) — ครบกำหนดต้องเชื่อมต่อเซิร์ฟเวอร์ผ่าน [[api-spec#1.4 ต่ออายุ/ยืนยันตัวตนใหม่เมื่อกลับมามีสัญญาณ|1.4]]/[[api-spec#1.1 เข้าสู่ระบบ|1.1]] เท่านั้น — ตรวจ [[detailed-design/authentication-login#4. Edge Case และวิธีจัดการ|authentication-login §4]] แล้วพบแถว "credential ที่แคชไว้หมดอายุแล้ว" แยกต่างหากจากแถวของ NFR-11 อย่างชัดเจน แปลว่าการตรวจสอบวันหมดอายุเป็นอิสระจากการนับ PIN ผิด (ทำงานคู่ขนาน ไม่ใช่แทนที่กัน)
2. **เส้นทางจำนวนครั้ง (NFR-11)**: ภายในกรอบเวลา 7 วันที่ session ยังไม่หมดอายุ ผู้ถือครองอุปกรณ์ (ไม่ว่าเจ้าของจริงหรือผู้ไม่ประสงค์ดี) ไล่เดา PIN ได้จำกัดจำนวนครั้งเท่านั้นก่อนถูกล็อก — ตรวจสอบว่าตัวนับ `failed_pin_attempt_count` **รีเซ็ตได้เฉพาะ 2 ทางเท่านั้น** (ปลดล็อก PIN ถูกต้อง หรือเข้าสู่ระบบด้วยรหัสผ่านใหม่สำเร็จ — [[db-spec#10. กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล|db-spec หัวข้อ 10 ข้อ 10]]) ไม่มีกลไกรีเซ็ตด้วยเวลา/การเปิดแอปใหม่/วิธีอื่นใด จึงไม่มีช่องให้ผู้โจมตีไล่เดา PIN แบบ "เว้นจังหวะให้ตัวนับรีเซ็ตเอง" ได้

**ผลตรวจ**: ทั้งสองเส้นทางปิดช่องโหว่กันคนละมิติและไม่ทับซ้อนกันจนเปิดช่องให้อีกฝ่ายหลุดรอด (มิติเวลา ↔ มิติจำนวนครั้ง) — เมื่อรวมกันแล้ว **ปิดช่องว่างที่ `test-writer` พบได้จริงครบวงจร**: ต่อให้ session ยังไม่หมดอายุ (ยังอยู่ในกรอบ 7 วัน) การไล่เดา PIN ก็ถูกจำกัดจำนวนครั้งไว้แล้ว และต่อให้ไล่เดาสำเร็จในบางครั้ง (PIN ถูกในที่สุด) ตัวนับก็รีเซ็ตแบบเดียวกับผู้ใช้ตัวจริงเข้าใช้งานปกติ ไม่ใช่ช่องโหว่ที่ผู้โจมตีใช้ประโยชน์ได้ต่างจากผู้ใช้จริง — **ไม่พบช่องว่างที่ยังเปิดอยู่ระหว่าง NFR-09 กับ NFR-11**

### ประเด็นที่ผู้เรียกกังวลเป็นพิเศษ (3): กลไกล้าง credential กระทบ NFR-01 หรือไม่

ดูรายละเอียดที่หัวข้อ "ประเด็น (1)" ด้านบนแล้ว — สรุปสั้น: **ไม่กระทบ ยืนยันคงรองรับแล้ว และแข็งแรงขึ้นด้วยซ้ำ** เพราะรอบนี้เป็นครั้งแรกที่ [[architecture]] มีหัวข้อเหตุผลการตัดสินใจ (§6.8) อธิบายตรงๆ ว่าทำไมการแยกพื้นที่จัดเก็บระดับโครงสร้างจึงจำเป็นต่อการปกป้อง NFR-01 จากความเสี่ยงของกลไกใหม่ (NFR-11) — เป็นตัวอย่างที่ดีของการที่ NFR ตัวใหม่ถูกออกแบบให้ "ไม่แลกด้วย" NFR ตัวเดิม แทนที่จะปล่อยให้ขัดแย้งกันแล้วค่อยแก้ภายหลัง

### ประเด็นที่ผู้เรียกกังวลเป็นพิเศษ (4): NFR-02/NFR-04 กับ stack ที่เจาะจงขึ้น (bare React Native + `op-sqlite`)

ตรวจตามที่ [[technology-stack#5. ผลกระทบต่อเอกสารชั้นอื่น|technology-stack §5]] ระบุไว้เองว่าควรกลับมาตรวจ `nfr-review.md` ซ้ำ:

- **NFR-02 (resumable upload)**: กลไก resume ที่ [[db-spec#10. กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล|db-spec หัวข้อ 10 ข้อ 8]] ออกแบบไว้ (เทียบ `upload_session_id` + ส่งต่อจาก `uploaded_bytes`) ทำงานที่ระดับ**โปรโตคอลเครือข่าย/แถวข้อมูลในตาราง** ไม่ได้ผูกกับ SQLite library ตัวใดตัวหนึ่ง — `op-sqlite` ทำหน้าที่เพียงเก็บ/อ่านค่า `upload_session_id`/`uploaded_bytes`/`total_file_size_bytes`/`last_chunk_received_at` ที่เป็นคอลัมน์ธรรมดา ไม่ต่างจาก SQLite binding ตัวอื่น จึงไม่มีช่องว่างใหม่จากการเจาะจง library — ส่วนความเสี่ยงเรื่อง "background upload ต้องเขียน native module เอง" ที่ผู้เรียกยกมานั้น เป็นคนละเรื่องกับ resumable-from-offset upload ที่ออกแบบไว้แล้ว (resume เมื่อ**เปิดแอปใหม่**เป็นข้อกำหนดปัจจุบันที่เอกสารเขียนไว้ชัดเจน ซึ่งไม่ต้องพึ่ง native module) — ประเด็น true background upload ถูกบันทึกไว้แล้วเป็นความเสี่ยงที่ต้องจับตาใน [[technology-stack#6. เกณฑ์ที่จะทำให้ต้องทบทวนการตัดสินใจนี้ใหม่|technology-stack §6 ข้อ 2]] ตั้งแต่รอบที่ 6 (ไม่ใช่ช่องว่างใหม่ของรอบนี้) — การเลือก **bare** React Native (แทน Expo) จริงๆ แล้วเป็นทางเลือกที่เปิดช่องให้เขียน native module ได้ง่ายกว่า ถ้าในอนาคตต้องทบทวนตามเกณฑ์ข้อ 2 จริง จึงไม่ใช่ปัจจัยลบต่อ NFR-02 — **ยืนยันคงรองรับแล้ว**
- **NFR-04 (ใช้งานได้ดีกลางแจ้ง)**: edge case เชิง logical (ถุงมือ/แสงจ้า/ขนาดหน้าจอ/crash-resilience) ที่ออกแบบไว้ใน [[detailed-design/building-environment-info#5. Edge Case เพิ่มเติมสำหรับการใช้งานกลางแจ้งในพื้นที่ภัยพิบัติ (NFR-04)|building-environment-info §5]] และไฟล์อื่นไม่ขึ้นกับว่าเป็น bare workflow หรือ Expo managed workflow หรือใช้ SQLite library ตัวใด — ความเสี่ยงเรื่องประสิทธิภาพบนอุปกรณ์สเปกต่ำที่แท้จริงยังคงเป็นเรื่องที่ต้องทดสอบบนอุปกรณ์จริงตามที่ [[technology-stack#6. เกณฑ์ที่จะทำให้ต้องทบทวนการตัดสินใจนี้ใหม่|technology-stack §6 ข้อ 1]] บันทึกไว้ตั้งแต่รอบที่ 6 — **ยืนยันคงรองรับแล้ว ไม่มีช่องว่างเอกสารใหม่**

**สรุปประเด็น (4)**: ความเจาะจงของ stack ที่เพิ่มขึ้น (bare RN + `op-sqlite`) เป็นการตัดสินใจระดับ implementation ที่ **ไม่กระทบกลไกระดับ logical** ที่ทั้ง NFR-02 และ NFR-04 พึ่งพาอยู่ ความเสี่ยงเชิง implementation ที่แท้จริง (native module เสถียรหรือไม่, ประสิทธิภาพบนอุปกรณ์จริง) ถูกบันทึกไว้แล้วเองใน [[technology-stack#6. เกณฑ์ที่จะทำให้ต้องทบทวนการตัดสินใจนี้ใหม่|technology-stack §6]] พร้อมเกณฑ์ทบทวนที่ชัดเจน (ข้อ 1, 2, 8, 9) จึงไม่ใช่ช่องว่างเอกสารที่ nfr-review ต้องรายงานใหม่

### ข้อสังเกตเล็กน้อยที่พบระหว่างตรวจ (ไม่กระทบสถานะใดๆ)

ระหว่างตรวจ [[architecture#5. Mapping NFR ไปยัง Component|architecture §5 แถว NFR-11]] พบว่าข้อความอ้างอิง **"ดูข้อสมมติที่ 8 ใน [[#7. ข้อสมมติ|§7]]"** แต่เมื่อไล่นับลำดับจริงใน [[architecture#7. ข้อสมมติ|§7 ข้อสมมติ]] พบว่าข้อสมมติเรื่องจำนวนครั้ง PIN ผิดของ NFR-11 คือ**ข้อ 7** ไม่ใช่ข้อ 8 (ข้อ 8 ใน §7 จริงๆ คือเรื่องขอบเขต `SurveyParticipant` ของ FR-32 ซึ่งไม่เกี่ยวกับ NFR-11 เลย) — เป็นเลขอ้างอิงที่พิมพ์ผิด ไม่ใช่ wikilink เสีย (ตัว anchor ที่ลิงก์ไปยัง `#7. ข้อสมมติ` ยังคง valid ใช้งานได้จริง เพียงแต่ตัวเลขข้อที่กำกับไว้ในข้อความไม่ตรงกับลำดับจริงในหัวข้อนั้น) — ลักษณะเดียวกับที่เคยพบใน NFR-08 รอบที่ 5 (ข้อความสมมติอ้าง `Assignment`/FR-20 ผิดจากที่ออกแบบจริง) **ไม่กระทบสถานะ NFR-11** เพราะเนื้อหาของกลไกเองถูกต้องครบถ้วน เป็นเพียงเลขอ้างอิงในประโยคเดียวที่คลาดเคลื่อน

**แนะนำให้รันต่อ (ไม่บังคับ ไม่กระทบสถานะ)**: `sync-architecture` — แก้ [[architecture#5. Mapping NFR ไปยัง Component|architecture §5 แถว NFR-11]] จาก "ข้อสมมติที่ 8" เป็น "ข้อสมมติที่ 7" ให้ตรงกับลำดับจริงใน §7

### สรุปรวมรอบที่ 8

**เปลี่ยนจากรอบที่ 7**: NFR-11 เข้ามาใหม่และรองรับแล้วตั้งแต่ตรวจครั้งแรก (11/11) ส่วน NFR-01/NFR-02/NFR-04/NFR-09 ที่ตรวจซ้ำเทียบ stack ที่เจาะจงขึ้น (bare React Native + `op-sqlite`) **ไม่มีตัวใดถูกลดระดับ** — อีก 6 ตัวที่เหลือ (NFR-03, NFR-05, NFR-06, NFR-07, NFR-08, NFR-10) ไม่มี layer ที่เกี่ยวข้องถูกแก้ไขในรอบนี้เลย จึงคงสถานะรองรับแล้วเดิมจากรอบที่ 6/7 ไว้ทั้งหมดโดยไม่ตรวจซ้ำละเอียด (ยืนยันเฉพาะว่า anchor ที่อ้างอิงในแถวของ NFR เหล่านี้ยังไม่ถูกแตะต้องจากการแก้ไขรอบนี้)

**ควรรันชั้นไหนซ้ำ**: ไม่มีข้อบังคับ — พบเพียงข้อเสนอแนะไม่บังคับ 1 จุด: `sync-architecture` เพื่อแก้เลขอ้างอิงข้อสมมติผิดพลาด ("ข้อสมมติที่ 8" → "ข้อสมมติที่ 7") ใน [[architecture#5. Mapping NFR ไปยัง Component|architecture §5 แถว NFR-11]] — ไม่กระทบสถานะ NFR ใดในปัจจุบัน

### สิ่งที่ตรวจ (1): ตรวจ `nfr-review.md` เอง — มีข้อความค้างที่ยังบอกว่าตัวเลขยังไม่ยืนยันหรือไม่

ไล่ตรวจทั้งไฟล์ (317 บรรทัดก่อนรอบนี้) ด้วยการค้นหาคำว่า "PIN", "จำนวนครั้ง", "ข้อสมมติ", "ครั้ง" ทุกจุด พบว่า **ไม่มีข้อความใดในไฟล์นี้ที่เคยระบุตัวเลขจำนวนครั้ง PIN ผิดไว้ตรงๆ มาก่อน** (ทั้งแถวตาราง NFR-11 เดิมและหัวข้อ "ผลตรวจรอบที่ 8" อธิบายกลไกเชิง logical ล้วนๆ โดยไม่เคยเอ่ยตัวเลขที่ยังไม่ปิดในตอนนั้นเลย จึงไม่มีข้อความ "ยังไม่ยืนยัน"/"รอตัดสินใจ" ค้างอยู่ที่ต้องลบทิ้ง) — จุดเดียวที่ไฟล์นี้เคยพูดถึงตัวเลขที่ "ยังไม่ปิด" คือแถว NFR-02 (บรรทัด ~24 หลังแก้ไขรอบนี้) และหัวข้อ "ผลตรวจรอบที่ 7 สิ่งที่ตรวจ (3)" (บรรทัด ~241-249, ตำแหน่งเดิมก่อนรอบนี้ใกล้เคียงกับที่ `detailed-design-writer` รายงานว่า "~247") ซึ่ง**เป็นเรื่องคนละประเด็นกับ NFR-11 โดยสิ้นเชิง** — พูดถึงขนาด chunk ที่แบ่งส่งไฟล์ภาพและเกณฑ์เวลา stale ของ resumable upload (NFR-02) ไม่ได้ปะปนกับเรื่องจำนวนครั้ง PIN ผิด (NFR-11) แต่อย่างใด **ตรวจสอบแล้วว่าไม่ต้องแก้ไขจุดใดในสองตำแหน่งนี้** เพราะเป็นเนื้อหาที่ถูกต้องอยู่แล้วสำหรับ NFR-02 ที่ยังเปิดอยู่จริง (ขนาด chunk/stale threshold) — **ไม่แตะทั้งสองจุดตามกฎห้ามยุ่งกับ NFR อื่น**

**สรุปข้อ (1)**: `nfr-review.md` ไม่มีข้อความค้างเกี่ยวกับตัวเลข PIN ที่ต้องลบ/แก้ — สิ่งที่ทำในรอบนี้คือ**เพิ่ม**ข้อความยืนยันตัวเลข 5 ครั้งเข้าไปในแถว NFR-11 และหัวข้อนี้ (ของใหม่ ไม่ใช่การแก้ข้อความเดิมที่ผิด)

### สิ่งที่ตรวจ (2): ตรวจว่าทั้ง 3 ชั้นเอกสารสอดคล้องกันจริงหลังแก้ 11 จุด

ไล่ตรวจจุดที่ผู้เรียกระบุไว้ครบทั้ง 11 จุดโดยอ่านไฟล์จริง (ไม่เชื่อคำอธิบายการแก้ไขเฉยๆ):

1. **[[architecture#5. Mapping NFR ไปยัง Component|architecture §5 แถว NFR-11]]**: ระบุ "ยืนยันแล้วเป็น **5 ครั้ง** ติดต่อกัน — ปิดข้อสมมติที่ 7 ใน §7 เมื่อ 2026-09-04" ตรงตามที่แจ้ง
2. **[[architecture#7. ข้อสมมติ|architecture §7 ข้อสมมติข้อ 7]]**: เขียนใหม่เป็น "ปิดแล้วเมื่อ 2026-09-04: ผู้ใช้ยืนยันตัวเลขเป็น **5 ครั้ง** ติดต่อกัน" **คงเลขข้อเดิม (ข้อ 7)** และ**คงข้อสมมติย่อยไว้จริง**ว่าค่านี้ "ยังคงเป็นค่าที่ตั้งค่าได้ (configurable) เช่นเดียวกับอายุ session ของ NFR-09" — ไม่ได้ลบทิ้งประวัติว่าเคยเป็นข้อสมมติเปิดอยู่ ตรงตามข้อกำหนด "เก็บประวัติไม่ใช่ลบทิ้ง"
3. **`api-spec.md` operation 1.3 กฎทางธุรกิจ**: ระบุ "จำนวนครั้งสูงสุดที่กำหนดคือ **5 ครั้งติดต่อกัน** (ยืนยันแล้วเมื่อ 2026-09-04 — ปิดประเด็นนี้ ดูหัวข้อ 16)"
4. **`api-spec.md` §16 รายการ PIN**: ปิดแล้วพร้อมระบุประวัติ "เดิม spec เสนอไว้เป็นช่วง 5-10 ครั้ง" — **แยกเป็นบรรทัดของตัวเองชัดเจน คนละบรรทัดกับประเด็น chunk/stale ของ NFR-02** (บรรทัดถัดไปในหัวข้อเดียวกันซึ่งยังคง "ยังไม่ปิด" ไว้ตามเดิม ไม่ถูกแตะ) — ไม่มีการปะปนสองประเด็นเข้าด้วยกันแบบที่ `requirement-writer` เคยกังวลไว้
5. **`db-spec.md` §10 ข้อ 10**: ระบุ "เมื่อค่าครบ **5 ครั้งติดต่อกัน** (ยืนยันแล้ว ดูหัวข้อ 11)" พร้อมกฎห้ามกระทบข้อมูลแบบสำรวจคงเดิมครบ
6. **`db-spec.md` §11 รายการ PIN**: ปิดแล้วพร้อมประวัติช่วง 5-10 ครั้งเช่นเดียวกับ api-spec — สอดคล้องกัน
7. **`db-spec.md` §2 attribute `Session.failed_pin_attempt_count`**: คำอธิบายระบุ "เมื่อครบ **5 ครั้งติดต่อกัน** (ยืนยันแล้ว ดูหัวข้อ 11)"
8. **`detailed-design/authentication-login.md` บรรทัด 7**: ระบุ "ครบ **5 ครั้ง** (ยืนยันแล้ว 2026-09-04 — ปิดข้อสมมติหมวด 6 ข้อ 11 ดู api-spec หัวข้อ 16)"

### สิ่งที่ตรวจ (3): ยืนยันว่าไม่มี operation/entity/attribute/component ใดถูกเพิ่ม-ลบ-เปลี่ยนนอกเหนือจากค่าตัวเลข

เทียบโครงสร้างของทั้ง 4 ชั้นเอกสารกับผลตรวจรอบที่ 8 (ก่อนรอบนี้) พบว่า attribute/entity/operation/component ที่เกี่ยวข้องกับ NFR-11 (`Session.cached_pin_secret`, `Session.failed_pin_attempt_count`, `Session.status`, operation 1.1/1.3/1.4, component Field Client App/Local Persistent Store, sequence diagram 3 เส้นทาง, state diagram, ตาราง edge case 5 แถว) **เหมือนเดิมทุกประการ** เปลี่ยนเฉพาะข้อความตัวเลข/สถานะการปิดประเด็นเท่านั้น ตรงตามที่ผู้เรียกยืนยันไว้ว่า "เป็นการปรับข้อความให้ตรงกับค่าที่ปิดแล้วล้วนๆ"

### สรุปรวมรอบที่ 9

**NFR-11 ยังคงสถานะ "รองรับแล้ว"** ไม่เปลี่ยนแปลงจากรอบที่ 8 — การปิดตัวเลขจำนวนครั้งจาก "ช่วง 5-10 ครั้ง" เป็น "5 ครั้งติดต่อกัน" ไม่ได้เปลี่ยนกลไกระดับ logical ที่ NFR-11 พึ่งพาอยู่แต่แรก (นับ/ล้าง/แยกพื้นที่จัดเก็บ) เพียงแต่ทำให้ตัวเลขที่เคยเป็นค่าเปิดกลายเป็นค่าปิดที่ระบุตรงกันครบทั้ง 4 ชั้นเอกสาร ไม่มีจุดใดขัดแย้งกันเอง (ไม่มีที่ใดยังบอก "ยังไม่ยืนยัน" ในขณะที่ที่อื่นบอก "5 ครั้ง") — **ไม่มีช่องว่างเหลือให้รายงาน**

**ไม่ถูกครอบคลุมในรอบนี้ (ตามขอบเขตที่ผู้เรียกจำกัดไว้)**: NFR ข้ออื่นทั้ง 10 ตัวไม่ถูกตรวจซ้ำ (คงผลจากรอบที่ 8), ประเด็นค้างของ NFR-02 (ขนาด chunk/เกณฑ์ stale ของการอัปโหลดไฟล์), NFR-03 (กลยุทธ์ auto-merge), ขนาด/ความละเอียดภาพ, protocol/web framework, AI model runtime, hosting — ทั้งหมดนี้**ยังไม่ปิด**และไม่ได้ถูกแตะต้องในรอบนี้ตามคำสั่งที่ได้รับ; ข้อเสนอแนะไม่บังคับที่ค้างจากรอบก่อน (เช่น เลขอ้างอิงข้อสมมติผิดพลาดที่เคยพบใน architecture §5 — ปัจจุบันแก้เป็น "ข้อสมมติที่ 7" ถูกต้องแล้วในรอบนี้พร้อมกับการปิดตัวเลข NFR-11 เอง จึงถือว่าปิดไปโดยอัตโนมัติ) ก็ไม่ได้ตรวจซ้ำเพิ่มเติมนอกเหนือจากที่สังเกตเห็นระหว่างตรวจ NFR-11

**ควรรันชั้นไหนซ้ำ**: ไม่มี — ทั้ง 3 ชั้นเอกสารเชิงเทคนิค (`architecture.md`, `api-spec.md`/`db-spec.md`, `detailed-design/authentication-login.md`) ถูกแก้ตรงจุดและสอดคล้องกันครบแล้ว ไม่พบช่องว่างใดที่ต้องส่งต่อให้ agent เจ้าของไฟล์แก้ไขเพิ่มเติม

## ผลตรวจรอบที่ 10 (2026-09-04) — ตรวจซ้ำเฉพาะ NFR-02, NFR-03, NFR-07, NFR-08, NFR-09 หลังปิดการตัดสินใจใหม่ 6 ข้อผ่าน `/sync-technical-spec`

**บริบท**: ผู้ใช้ยืนยันการตัดสินใจเชิงเทคนิค/สถาปัตยกรรมใหม่ 6 ข้อในรอบเดียวกัน: (1) Protocol/Web Framework = REST over HTTP + Fastify, (2) authentication token = opaque token + Session ในฐานข้อมูล (ไม่ใช่ JWT stateless — เพราะ api-spec 2.3 สั่งเพิกถอน session ที่ใช้งานอยู่ทั้งหมดทันทีตอนปิดบัญชี ซึ่ง JWT stateless ทำไม่ได้), (3) CORS = allowlist origin จาก environment variable, (4) chunk ของ resumable upload = 256 KB, (5) stale ของรอบอัปโหลด = 72 ชั่วโมง (สั้นกว่าอายุ session ออฟไลน์ 7 วันโดยเจตนา), (6) auto-merge = ส่งมนุษย์ตัดสินใจทุกครั้งที่พบความขัดแย้ง ไม่ทำ auto-merge ระดับฟิลด์ใน Phase นี้ — ทั้ง 3 ชั้นเอกสาร (`architecture.md` §6.9/§6.10/§6.11, `api-spec.md`/`db-spec.md`, `detailed-design/offline-sync.md`+`manual-conflict-resolution.md`+`authentication-login.md`) ถูกปรับให้สะท้อนการตัดสินใจนี้แล้วก่อนรอบตรวจนี้เริ่ม — **ขอบเขตรอบนี้แคบตามคำขอ**: ตรวจซ้ำเฉพาะ NFR-02, NFR-03, NFR-07, NFR-08, NFR-09 (6 ตัวที่เหลือคงผลจากรอบที่ 9 ไว้ทั้งหมดโดยไม่มีการเปลี่ยนแปลง)

### NFR-02 — ตรวจตัวเลข chunk/stale จริงกับความขัดแย้งกันเอง

อ่าน [[architecture#6.10 ขนาด chunk และเกณฑ์เวลา stale ของรอบอัปโหลดแบบ resumable (NFR-02)|architecture §6.10]], [[api-spec#14.1 ซิงค์ข้อมูลแบบสำรวจที่ค้างจากอุปกรณ์|api-spec 14.1]], [[api-spec#16. ประเด็นรอตัดสินใจ|api-spec §16]], [[db-spec#10. กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล|db-spec หัวข้อ 10 ข้อ 8]], [[db-spec#11. ประเด็นรอตัดสินใจ|db-spec §11]], [[detailed-design/offline-sync#1. Sequence Diagram|offline-sync §1]], [[detailed-design/offline-sync#3. State Diagram: sync_status|offline-sync §3]], [[detailed-design/offline-sync#5. Edge Case และวิธีจัดการ|offline-sync §5]] ทั้งหมดพร้อมกัน — พบว่าตัวเลข **256 KB** (ขนาด chunk) และ **72 ชั่วโมง** (เกณฑ์ stale) ถูกระบุตรงกันคำต่อคำในทุกจุดที่กล่าวถึง ไม่มีจุดใดเหลือข้อความ "ยังไม่กำหนด"/"รอตัวเลข" ค้างอยู่ขณะที่จุดอื่นระบุตัวเลขแล้ว (ต่างจากรูปแบบความขัดแย้งที่เคยพบใน NFR-02 รอบที่ 6) — ตรวจเพิ่มว่าเหตุผลเลือกเบื้องหลัง (chunk เล็กเพื่อทนสัญญาณขาดหาย, stale สั้นกว่า session 7 วันเพื่อไม่ให้รอบอัปโหลดอยู่ยืนกว่าเจ้าของ) สอดคล้องกับ NFR-01 (ห้ามข้อมูลภาคสนามหาย) และ NFR-09 (อายุ session 7 วัน) จริง ไม่ใช่ตัวเลขที่เดาขึ้นมาลอยๆ — **สรุป: NFR-02 คงรองรับแล้ว ไม่มีช่องว่างเหลือ**

### NFR-03 — วิเคราะห์ตรงไปตรงมาว่ากลยุทธ์ "ส่งมนุษย์ทุกครั้ง" ยังตอบ NFR-03 ครบหรือกลายเป็นรองรับบางส่วน

นี่คือประเด็นที่ต้องพิจารณาจริงจังที่สุดของรอบนี้ ตามที่ผู้เรียกกำชับไว้ — วิเคราะห์โดยไม่เข้าข้างการตัดสินใจที่เพิ่งเกิด:

1. **ข้อความ NFR-03 ที่แท้จริง** (จาก [[backlog#Non-Functional Requirements|backlog]]): "ระบบต้องมีกลไกตรวจจับความขัดแย้งของข้อมูล ... พร้อมกฎการ merge/แจ้งเตือนที่ชัดเจนก่อนบันทึกเป็นข้อมูลจริง — **ขอบเขตของ NFR นี้ครอบคลุมกลไกตรวจจับ/merge อัตโนมัติเท่านั้น กรณีระบบตัดสินใจ merge เองไม่ได้และต้องให้มนุษย์แก้ไขด้วยมือ ดู FR-30/FR-31**" — ข้อสังเกตสำคัญ: **ตัว NFR-03 เองประกาศไว้ล่วงหน้าแล้วว่ากรณี auto-merge ไม่ได้จะถูกส่งไปให้ FR-30/FR-31 จัดการ** ไม่ได้เรียกร้องให้ระบบต้อง auto-merge ทุกกรณี
2. **การตัดสินใจใหม่คือ**: "merge อัตโนมัติสำเร็จ" ใช้ได้เฉพาะกรณีไม่มีความขัดแย้งจริง (แก้ไขคนละฟิลด์/ค่าตรงกัน) — กรณีขัดแย้งจริง (ฟิลด์เดียวกัน ค่าต่างกัน) ส่งมนุษย์เสมอ ไม่มีข้อยกเว้น (ตัดตัวเลือก field-level partial auto-merge/last-write-wins ทิ้งทั้งคู่ — ดู [[architecture#6.9 กลยุทธ์การจัดการความขัดแย้งของข้อมูล เมื่อ merge อัตโนมัติไม่ได้ (NFR-03)|architecture §6.9]])
3. **เทียบกับข้อความ NFR-03 ทีละวลี**: "ตรวจจับความขัดแย้ง" — มี (เทียบ `data_version`/`last_modified_at`/`last_modified_by_device_id` ระดับ aggregate); "กฎการ merge ... เมื่อไม่ขัดแย้งกัน" — มี (merge อัตโนมัติสำเร็จกรณีคนละฟิลด์/ค่าตรงกัน); "กฎการแจ้งเตือนที่ชัดเจนก่อนบันทึกเป็นข้อมูลจริง" — มี (สร้าง `SyncConflict`+`AuditTrailEntry` ทันทีที่ตรวจพบ ไม่มีการบันทึกเป็นข้อมูลจริงจนกว่าจะแก้ไขผ่าน FR-30/31) — **ครบทั้ง 3 วลีตามตัวอักษรของ NFR-03**
4. **แต่พบความเสี่ยงเชิงกลไกที่ต้องซื่อสัตย์รายงาน**: การจะรู้ว่าการแก้ไขสองฝั่ง "เป็นคนละฟิลด์" (ไม่ขัดแย้ง → auto-merge) หรือ "ฟิลด์เดียวกันค่าต่างกัน" (ขัดแย้งจริง → ส่งมนุษย์) จำเป็นต้องเปรียบเทียบเนื้อหาระดับฟิลด์จริงอยู่ดี ไม่ใช่แค่เทียบ `data_version`/timestamp ของอาคารแม่เท่านั้น (ซึ่งบอกได้แค่ "มีการแก้ไขซ้อนกันหรือไม่" ไม่ได้บอกว่า "ทับซ้อนกันที่ฟิลด์ไหน") — กลไกเปรียบเทียบระดับฟิลด์นี้จะต้องพึ่งพา `SyncConflictVersion.snapshot_content` ที่เก็บค่าทั้งอาคาร ณ เวลานั้นไว้ แต่รูปแบบ/format จริงของ `snapshot_content` **ยังไม่ปิด** (เป็นประเด็นเปิดเดิมจาก [[db-spec#11. ประเด็นรอตัดสินใจ|db-spec §11]] ก่อนรอบนี้อยู่แล้ว ไม่ใช่ช่องว่างใหม่ที่เกิดจากการตัดสินใจรอบนี้) — ตามกฎที่ผู้เรียกกำหนดไว้ (ห้ามรายงาน `snapshot_content` เป็นช่องว่างใหม่) จึงจัดเป็น **"ความเสี่ยงที่ต้องติดตาม"** แทน: เมื่อปิด `snapshot_content` format ในรอบถัดไป ต้องตรวจสอบว่ารูปแบบที่เลือกยังรองรับการแยกแยะ "คนละฟิลด์" ออกจาก "ฟิลด์เดียวกันขัดแย้งจริง" ได้จริง เพราะการตัดสินใจ "ส่งมนุษย์ทุกครั้งที่ขัดแย้งจริง" ของรอบนี้พึ่งพาการแยกแยะนี้อยู่ (แม้จะไม่ทำ auto-merge ระดับฟิลด์ที่ทับซ้อนกันเอง แต่ยังต้อง**ตรวจจับ**ว่าทับซ้อนหรือไม่ ซึ่งเป็นงานที่ต่างจาก "merge" — เป็น field-level comparison for detection ไม่ใช่ field-level merge for resolution)
5. **สรุปการวิเคราะห์**: **NFR-03 ยังคงรองรับแล้ว ไม่ลดระดับเป็นรองรับบางส่วน** เพราะ (ก) NFR-03 เองจำกัดขอบเขตไว้แต่ต้นว่ากรณี merge ไม่ได้ให้ส่งต่อ FR-30/31 ซึ่งเป็นสิ่งที่การตัดสินใจนี้ทำอยู่พอดี ไม่ใช่การลดทอนขอบเขตของ NFR-03 แต่อย่างใด (ข) คำนิยาม "merge อัตโนมัติสำเร็จ" ที่ปิดแล้วยังครอบคลุมกรณี "ไม่ขัดแย้งกัน" ตรงตามตัวอักษรของ NFR-03 (ค) กฎ "แจ้งเตือนชัดเจนก่อนบันทึกเป็นข้อมูลจริง" ทำได้ครบผ่าน `SyncConflict`/`AuditTrailEntry` — แต่**บันทึกความเสี่ยงที่ต้องติดตามไว้ 1 จุด** (ด้านบน) เพื่อไม่ให้การปิด `snapshot_content` format ในอนาคตทำให้กลไกแยกแยะนี้พังโดยไม่มีใครสังเกต — นี่คือความแตกต่างสำคัญที่ต้องเน้นย้ำ: **การตัดสินใจนี้ไม่ได้ตัด "field-level comparison" ทิ้งทั้งหมด เพียงแต่ตัด "field-level merge/resolution" ที่เป็น auto ทิ้ง** ทั้งสองคำนี้มักถูกปนกันได้ง่ายถ้าอ่านผิวเผิน

### NFR-07 — chunk เล็กลงเพิ่มจำนวนคำขอ กระทบคิวรับคำขอซิงค์หรือไม่

ตรวจแล้วว่า [[architecture#6.10 ขนาด chunk และเกณฑ์เวลา stale ของรอบอัปโหลดแบบ resumable (NFR-02)|architecture §6.10]] พิจารณา NFR-07 ไว้ตรงๆ ตอนตัดสินใจเลือก chunk เล็ก (256 KB) แทน chunk ใหญ่: "ตัดตัวเลือก (2) [chunk ใหญ่] ทิ้ง เพราะแม้ประสิทธิภาพต่อคำขอจะดีกว่า แต่ภาระคำขอที่เพิ่มขึ้นจาก chunk เล็กมีคิวรับคำขอฝั่งเซิร์ฟเวอร์ (Server-side Sync Intake Queue) ที่ NFR-07 บังคับให้มีอยู่แล้วรองรับอยู่แล้ว จึงไม่ใช่ข้อเสียที่มีน้ำหนักพอจะเปลี่ยนใจ" — component `INTAKE` (Server-side Sync Intake Queue) ที่ออกแบบไว้ตั้งแต่รอบที่ 6/7 ยังคงเป็น component เดิมที่ไม่เปลี่ยนแปลงเชิงโครงสร้างจากการตัดสินใจ chunk รอบนี้ ([[architecture#5. Mapping NFR ไปยัง Component|architecture หัวข้อ 5 แถว NFR-07]], [[api-spec#14.1 ซิงค์ข้อมูลแบบสำรวจที่ค้างจากอุปกรณ์|api-spec 14.1]] ผูก business rule กับ component นี้ตรงๆ) ส่วนอัลกอริทึม/ตัวเลข rate-limiting ที่แท้จริงของ Server-side Sync Intake Queue ยังคงเปิดอยู่เหมือนเดิม (ประเด็นเปิดเดิมตามรายการที่ผู้เรียกระบุไว้ว่าไม่ให้รายงานเป็นช่องว่างใหม่) — **สรุป: NFR-07 คงรองรับแล้ว การตัดสิน chunk เล็กลงไม่ได้เพิ่มความเสี่ยงใหม่ต่อ NFR-07 เพราะ §6.10 พิจารณาประเด็นนี้ไว้แล้วตรงๆ ก่อนตัดสินใจ**

### NFR-08 / NFR-09 — opaque token + Session ในฐานข้อมูล

ตรวจ 3 จุดพร้อมกัน: (1) [[architecture#6.11 รูปแบบ token/session ยืนยันตัวตน — opaque token แบบมีสถานะ ไม่ใช่ JWT แบบไร้สถานะ (NFR-08, NFR-09)|architecture §6.11]] ระบุเหตุผลเลือกชัดเจนว่าผูกกับ NFR-08 (บังคับสิทธิ์ทุก request) โดยตรง เพราะ JWT stateless ทำ "เพิกถอนทันที" ไม่ได้ในตัวเอง (2) [[api-spec#2.3 ปิดการใช้งานบัญชีผู้ใช้|api-spec 2.3]] ("ต้องเพิกถอน Session ที่ยัง 'ใช้งานอยู่' ของผู้ใช้นี้ทั้งหมดทันที") และ [[api-spec#1.2 ออกจากระบบ|api-spec 1.2]] ("เพิกถอน session ทันที ไม่สามารถใช้ต่อได้แม้ยังไม่ครบ expires_at") สอดคล้องกับเหตุผลที่ §6.11 อ้างไว้ (3) [[db-spec#2.2 Session|db-spec 2.2 Session]] มี `status` ค่า "ถูกเพิกถอน" ที่ครอบคลุมทั้งกรณีปิดบัญชีและกรณี lockout จาก NFR-11 อยู่แล้ว — ไม่พบข้อขัดแย้งใดๆ ระหว่าง §6.11 กับ operation/entity ที่มีอยู่ก่อนหน้า (เพราะ Session แบบมีสถานะถูกออกแบบไว้ตั้งแต่ต้นอยู่แล้วก่อนที่ §6.11 จะมาปิดว่าเป็น "opaque" อย่างเป็นทางการ — เป็นการปิดชื่อ/ประเภทของกลไกที่มีอยู่แล้ว ไม่ใช่กลไกใหม่)

ตรวจ [[detailed-design/authentication-login]] ทั้งไฟล์ด้วย `grep` หาคำว่า "JWT"/"stateless"/"opaque" — **ไม่พบคำเหล่านี้แม้แต่คำเดียว** ยืนยันว่าไฟล์นี้ออกแบบด้วย Session-based (sequence diagram ใช้ `Session` entity ตรงๆ, state diagram คือ `Session.status`) มาแต่ต้นโดยไม่เคยระบุประเภท token เจาะจง จึงสอดคล้องกับการปิดเป็น opaque+stateful โดยอัตโนมัติ ไม่ต้องแก้ไขไฟล์นี้เพิ่ม

สำหรับ NFR-09 โดยเฉพาะ ตรวจเพิ่มว่ากรอบเวลา stale ของรอบอัปโหลด (72 ชั่วโมง, NFR-02) กับอายุ session ออฟไลน์ (7 วัน, NFR-09) ไม่ขัดแย้งกันเอง — ยืนยันว่า [[architecture#6.10 ขนาด chunk และเกณฑ์เวลา stale ของรอบอัปโหลดแบบ resumable (NFR-02)|architecture §6.10]] ระบุเหตุผลจับคู่ 2 ตัวเลขนี้ไว้ตรงๆ (72 ชม. < 7 วัน โดยเจตนา เพื่อไม่ให้รอบอัปโหลดมีอายุยืนกว่า session เจ้าของ) และไม่มีจุดใดในเอกสารทั้ง 4 ชั้นที่ระบุตัวเลขทั้งสองนี้ขัดกันเอง (ทุกจุดพูดตรงกันว่า 72 ชม./7 วัน) — **สรุป: ทั้ง NFR-08 และ NFR-09 คงรองรับแล้ว ไม่มีช่องว่างเหลือ**

### สรุปรวมรอบที่ 10

ทั้ง 5 ตัว (NFR-02, NFR-03, NFR-07, NFR-08, NFR-09) **ยังคงสถานะ "รองรับแล้ว"** ไม่มีตัวใดถูกลดระดับ — คงรองรับแล้ว 11/11 เท่าเดิมทั้ง backlog การตัดสินใจใหม่ 6 ข้อของรอบนี้เป็นการ "ปิดตัวเลข/กลยุทธ์ที่เคยเปิดอยู่" ไม่ใช่การเปลี่ยนทิศทางเชิง logical ที่เคยออกแบบไว้ จึงไม่สร้างช่องว่างใหม่ในภาพรวม — พบเพียง **1 ความเสี่ยงที่ต้องติดตาม** (ไม่ใช่ช่องว่างบล็อกสถานะ): NFR-03 พึ่งพา `SyncConflictVersion.snapshot_content` format (ที่ยังไม่ปิด — เป็นประเด็นเปิดเดิม) ให้รองรับการแยกแยะ "คนละฟิลด์" ออกจาก "ฟิลด์เดียวกันขัดแย้งจริง" ได้ ต้องตรวจซ้ำตอนปิด `snapshot_content` format ในรอบถัดไป

**ไม่ถูกครอบคลุมในรอบนี้ (ตามขอบเขตที่ผู้เรียกจำกัดไว้)**: NFR-01, NFR-04, NFR-05, NFR-06, NFR-10, NFR-11 ไม่ถูกตรวจซ้ำ (คงผลจากรอบที่ 8/9) — ประเด็นที่ตั้งใจเปิดค้างไว้เดิมทั้งหมดตามที่ผู้เรียกระบุไว้ (AI model runtime, hosting/deployment, ขนาด/ความละเอียดภาพ, `client_generated_id` การสร้างจริง, `credential_secret` encoding, `SyncConflictVersion.snapshot_content` format, retention policy + index ของ audit trail, rate limiting ของ Sync Intake Queue, HTTP method/path ต่อ operation) **ยังไม่ปิดและไม่ได้ถูกแตะต้องในรอบนี้** ตามคำสั่งที่ได้รับ — ไม่มีข้อใดถูกรายงานเป็นช่องว่างใหม่ตามกติกาที่กำหนดไว้

**ควรรันชั้นไหนซ้ำ**: ไม่มีชั้นใดต้องแก้ไขเพิ่มเติมในตอนนี้ — ทั้ง 3 ชั้นเอกสารเชิงเทคนิค (`architecture.md` §6.9/§6.10/§6.11, `api-spec.md`/`db-spec.md`, `detailed-design/offline-sync.md`+`manual-conflict-resolution.md`+`authentication-login.md`) สอดคล้องกันครบและไม่พบข้อขัดแย้งใดๆ ระหว่างกัน — มีเพียงคำแนะนำ**ติดตามล่วงหน้า (ไม่บังคับตอนนี้)**: เมื่อ `api-db-writer` ปิด `SyncConflictVersion.snapshot_content` format ในรอบถัดไป ให้ `nfr-reviewer` ตรวจซ้ำ NFR-03 อีกครั้งว่ารูปแบบที่เลือกยังรองรับการแยกแยะ "คนละฟิลด์" ออกจาก "ฟิลด์เดียวกันขัดแย้งจริง" ได้จริงหรือไม่

## ผลตรวจรอบที่ 11 (2026-09-04) — ตรวจซ้ำเฉพาะ NFR-02, NFR-03, NFR-05, NFR-07 หลังปิดการตัดสินใจใหม่เพิ่มอีก 3 ข้อ (รอบสอง วันเดียวกัน)

### NFR-07 — คำถามที่สำคัญที่สุดของรอบนี้: hosting ขยายกำลังช้ากว่า cloud เอกชน ยังรองรับอยู่หรือไม่

วิเคราะห์แบบไม่เข้าข้างการตัดสินใจที่เพิ่งเกิด:

1. **ข้อความ NFR-07**: "ระบบต้องรองรับผู้สำรวจหลายทีมบันทึกและซิงค์ข้อมูลพร้อมกันจำนวนมากในช่วงเวลาสั้นหลังเกิดเหตุอุทกภัยในพื้นที่กว้าง" — เจตนาคือรองรับโหลดกระจุกตัว ไม่ใช่รับประกันเวลาตอบสนองที่แน่นอน (ไม่มี SLA/throughput ตัวเลขกำกับใน backlog)
2. **กลไกที่มีอยู่**: token bucket ต่ออุปกรณ์ + จำกัดจำนวน worker พร้อมกัน + ปฏิเสธพร้อมเวลาแนะนำให้ลองใหม่เมื่อเกินโควตา — เป็นรูปแบบ **backpressure/graceful degradation** มาตรฐาน ไม่ใช่การพึ่งพา auto-scaling เพื่อดูดซับโหลดทั้งหมดทันที
3. **ตรวจว่า design เคยพึ่ง auto-scaling มาก่อนหรือไม่**: ไม่เคย — [[architecture#5.5 Cross-cutting concerns|architecture §5.5]] ระบุตรงๆ ว่า "สถาปัตยกรรมนี้ไม่เคยตั้งสมมติฐานว่าจะมี auto-scaling แบบทันทีมาก่อน (การออกแบบ Server-side Sync Intake Queue เป็นกลไก backpressure/คิวรอมาตั้งแต่ §6.3 อยู่แล้ว)" — สอดคล้องกับที่ตรวจพบจริงใน §6.3 (เหตุผลแยก Sync Service ออกมาตั้งแต่ต้นคือ NFR-07 ต้องการรองรับโหลดกระจุกตัว ไม่ใช่ auto-scaling) และ [[architecture#6.12 กลไกจัดคิว/จำกัดอัตราคำขอซิงค์ต่ออุปกรณ์ (NFR-07)|architecture §6.12]] เลือกจำกัดจำนวน worker "เพราะจำเป็นเมื่อ hosting ไม่รองรับ auto-scaling แบบทันที" — แสดงว่าการตัดสินใจ GDCC ถูกพิจารณาไว้ตรงๆ ตอนออกแบบกลไกนี้ ไม่ใช่ช่องว่างที่เพิ่งถูกเปิดขึ้นมาโดยไม่มีทางออก
4. **แต่ต้องตรวจให้ถี่ถ้วนกว่านั้น**: rate limiter/worker limit ปกป้องเซิร์ฟเวอร์จากการล่ม (ตอบโจทย์ "ไม่ทำให้ระบบล่ม/ข้อมูลเสียหาย" ตามที่ [[architecture#1. ภาพรวมและข้อจำกัดเชิงสถาปัตยกรรมที่สำคัญ|architecture §1 ข้อ 2]] ตีความ NFR-07 ไว้) แต่ไม่ได้ "เพิ่ม" ความสามารถในการประมวลผลพร้อมกันจริง — ถ้ากำลังที่เผื่อไว้ล่วงหน้า (capacity provisioning) ประเมินต่ำกว่าโหลดจริงที่เกิดขึ้นหลังภัยพิบัติ อุปกรณ์จำนวนมากจะเจอ "ขอมากเกินไป" ต่อเนื่องเป็นเวลานาน — GDCC ที่ขยายกำลังช้ากว่า cloud เอกชนทำให้ความเสี่ยงจากการประเมินกำลังผิดพลาดนี้**คงอยู่นานกว่า**เดิม (แก้ไขกลางคันไม่ได้เร็วเหมือน cloud เอกชน)
5. **สรุป**: **ไม่ลดระดับ** — กลไกเชิง logical (คิว + backpressure + rate limit) เป็นคำตอบที่ถูกต้องสำหรับข้อจำกัดของ hosting ที่ไม่รองรับ auto-scaling แบบทันที และสถาปัตยกรรมนี้ออกแบบด้วยแนวคิดนี้มาตั้งแต่ต้นอยู่แล้วไม่ใช่เพิ่งปะติดปะต่อ — "ยังไม่มีตัวเลขกำลังที่ต้องเผื่อ" เป็นประเด็นเชิง capacity planning/operations ระดับ deployment ไม่ใช่ช่องว่างของการออกแบบสถาปัตยกรรมระดับ logical (เทียบเคียงกับตัวเลข rate-limit ที่ยังไม่ปิดเช่นกัน ซึ่งเป็นประเด็นเปิดโดยเจตนาที่ผู้เรียกกำหนดห้ามรายงานเป็นช่องว่างใหม่) — แต่บันทึกเป็น**ความเสี่ยงที่ต้องติดตาม**ว่าการเผื่อกำลังนี้ควรมีตัวเลขปริมาณโหลดที่คาดไว้ (จำนวนทีม/อุปกรณ์สูงสุด) มาประกอบการทำ load test ก่อนขึ้นระบบจริง เพราะผลกระทบของการประเมินผิดจะรุนแรง/ยาวนานกว่าปกติจากข้อจำกัดของ GDCC

### NFR-03 — ตรวจซ้ำตามนัดจากรอบที่ 10: ปิด `snapshot_content` format แล้ว ความเสี่ยงปิดตามหรือไม่

**คำตอบ: ไม่ปิด — กลับแหลมคมขึ้นจนต้องยกระดับเป็นช่องว่างจริง ลดสถานะเป็น "รองรับบางส่วน"**

1. รอบที่ 10 ตั้งสมมติฐานไว้ว่า กลไกแยก "merge อัตโนมัติสำเร็จ (แก้ไขคนละฟิลด์/ค่าตรงกัน)" ออกจาก "ขัดแย้งจริงต้องส่งมนุษย์" ต้องอาศัยการเปรียบเทียบเนื้อหาระดับฟิลด์ ซึ่ง**น่าจะ**ใช้ `SyncConflictVersion.snapshot_content` เป็นแหล่งข้อมูล จึงรอดูตอนปิด format
2. เมื่อปิดจริง ([[db-spec#8.2 SyncConflictVersion|db-spec §8.2]]/[[db-spec#11. ประเด็นรอตัดสินใจ|db-spec §11]]) ผู้ใช้ระบุเหตุผลไว้ตรงๆ ว่า: "เก็บเป็นข้อความรูปแบบ JSON ... **เพราะเนื้อหานี้มีไว้ให้มนุษย์เปรียบเทียบเทียบเท่านั้น ไม่เคยถูก query รายฟิลด์**" — ข้อความนี้ตัดความเป็นไปได้ที่ `snapshot_content` จะเป็นกลไกตรวจจับอัตโนมัติทิ้งไปเลย เพราะมันถูกออกแบบมาเพื่อการแสดงผลให้มนุษย์ดู**หลังจาก**มีการสร้าง `SyncConflict` แล้วเท่านั้น (ดู [[db-spec#8.2 SyncConflictVersion|db-spec §8.2]]: "เก็บทุกเวอร์ชันที่ส่งเข้ามา**จนเกิดความขัดแย้ง**") ไม่ใช่ข้อมูลที่มีอยู่ก่อนขั้นตอนตัดสินใจว่าจะ auto-merge หรือส่งมนุษย์
3. ไล่ตรวจ [[api-spec#14.2 ตรวจสอบ/แก้ไขความขัดแย้งของข้อมูลที่ซิงค์|api-spec 14.2]] และ [[db-spec#10. กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล|db-spec หัวข้อ 10 ข้อ 3]] อีกครั้งอย่างละเอียด — ทั้งสองจุดระบุกลไกตรวจจับความขัดแย้งไว้เพียงแบบเดียว: เทียบ `SurveyedBuilding.data_version`/`last_modified_at`/`last_modified_by_device_id` ที่ระดับ **aggregate** (ตัวเลข/เวลา/อุปกรณ์ 1 ชุดต่ออาคาร ไม่ใช่ต่อฟิลด์) — ในทางเทคนิค ตัวเลขเวอร์ชันที่ไม่ตรงกันบอกได้เพียง "มีการแก้ไขซ้อนทับกันหรือไม่" เท่านั้น **ไม่สามารถบอกได้ว่าซ้อนทับกันที่ฟิลด์ใด** สองอุปกรณ์ที่แก้ไขกันคนละฟิลด์ล้วนๆ (ไม่ขัดแย้งกันจริง) กับสองอุปกรณ์ที่แก้ไขฟิลด์เดียวกันเป็นค่าต่างกัน (ขัดแย้งจริง) จะมี `data_version` mismatch แบบเดียวกันทุกประการภายใต้กลไกนี้
4. ดังนั้นข้อความ "merge อัตโนมัติสำเร็จเมื่อแก้ไขคนละฟิลด์" ที่ [[architecture#6.9 กลยุทธ์การจัดการความขัดแย้งของข้อมูล เมื่อ merge อัตโนมัติไม่ได้ (NFR-03)|architecture §6.9]] และ [[api-spec#14.2 ตรวจสอบ/แก้ไขความขัดแย้งของข้อมูลที่ซิงค์|api-spec 14.2]] อธิบายไว้ ยังเป็นเพียง**เจตนา/ผลลัพธ์ที่ต้องการ** ไม่ใช่กลไกที่มีข้อมูล/ขั้นตอนรองรับจริงในเอกสารชั้นใดเลย — เป็นช่องว่างที่ยืนยันได้แล้ว ไม่ใช่ความเสี่ยงเชิงทฤษฎีที่ยังไม่แน่ชัดอีกต่อไปตามที่รอบที่ 10 บันทึกไว้
5. **พบเพิ่มเติมระหว่างตรวจ (ไม่ใช่ประเด็นหลักแต่ควรบันทึกไว้)**: [[api-spec#16. ประเด็นรอตัดสินใจ|api-spec หัวข้อ 16]] ยังคงข้อความเดิมว่า "รูปแบบ/format จริงของ `SyncConflictVersion.snapshot_content` ใน 15.2 — ยังไม่ปิด" ทั้งที่ [[db-spec#8.2 SyncConflictVersion|db-spec §8.2]]/[[db-spec#11. ประเด็นรอตัดสินใจ|db-spec §11]] ปิดแล้วเป็น JSON เมื่อ 2026-09-04 — **เอกสารสองไฟล์ไม่ตรงกัน (api-spec ยังไม่อัปเดตตาม db-spec)** เป็นช่องว่างเชิงความสอดคล้องของเอกสารที่ควรแก้ควบคู่กับข้อ 4 ข้างต้น
6. **สรุป: ลดระดับ NFR-03 จาก "รองรับแล้ว" เป็น "รองรับบางส่วน"** เพราะวลี "กฎการ merge ... เมื่อไม่ขัดแย้งกัน" ของ NFR-03 ที่รอบที่ 10 เคยตรวจว่า "มี" ตามตัวอักษร ไม่มีกลไกรองรับจริงในเอกสารเมื่อตรวจลึกลงไปถึงระดับ "ใช้ข้อมูลอะไรเปรียบเทียบ" — ส่วนอีก 2 วลีของ NFR-03 ("ตรวจจับความขัดแย้ง" และ "แจ้งเตือนชัดเจนก่อนบันทึกจริง") ยังคงมีกลไกรองรับครบเหมือนเดิม ไม่ได้รับผลกระทบ

### NFR-02 — ตรวจว่ากรณี error "เกินโควตา" ใหม่ขัดกับกลไก resumable upload เดิมหรือไม่

ไล่ตรวจ [[api-spec#14.1 ซิงค์ข้อมูลแบบสำรวจที่ค้างจากอุปกรณ์|api-spec 14.1]] กรณี error ใหม่ ("อุปกรณ์ส่งคำขอซิงค์เกินโควตาที่กำหนด → ตอบ 'ขอมากเกินไป' พร้อมเวลาแนะนำให้ลองใหม่") เทียบกับกลไก chunk/stale เดิม และแถวใหม่ใน [[detailed-design/offline-sync#5. Edge Case และวิธีจัดการ|offline-sync §5]] — พบว่าการปฏิเสธคำขอเกินโควตาเกิด**ก่อน**การรับ/ประมวลผล chunk ใดๆ เสมอ (เป็นการปฏิเสธที่ชั้นคิวรับคำขอ ก่อนถึงขั้นตอนอ่าน/เขียน `uploaded_bytes`) จึงไม่กระทบ `upload_session_id`/`uploaded_bytes`/ตัวนับเวลา stale ที่มีอยู่แล้วเลย — อุปกรณ์เพียงลองส่ง chunk เดิมซ้ำตามเวลาที่แนะนำ ไม่ถือเป็นการเริ่มรอบอัปโหลดใหม่ (ต่างจากกรณี `upload_session_id` ไม่ตรงกัน/stale ที่ต้องเริ่มนับ `uploaded_bytes` จาก 0) — **สรุป: ไม่พบจุดขัดแย้งกันเอง NFR-02 คงรองรับแล้ว**

### NFR-05 — ตรวจซ้ำครั้งแรกนับจากรอบที่ 6 หลังเพิ่ม `archive_status` + index 3 ชุด

ไล่ตรวจ [[db-spec#7.2 AuditTrailEntry|db-spec §7.2]] (attribute `archive_status` ใหม่ + หมายเหตุ index 3 ชุด), [[db-spec#11. ประเด็นรอตัดสินใจ|db-spec §11]], [[architecture#6.13 นโยบายเก็บรักษาและเตรียมกลไก archive ของ audit trail (NFR-05)|architecture §6.13]], [[detailed-design/audit-trail-building#5. ประเด็นที่ยังไม่ตัดสินใจ (ส่งต่อจาก db-spec/architecture)|audit-trail-building §5]], [[detailed-design/audit-trail-search#5. ประเด็นที่ยังไม่ตัดสินใจ (ส่งต่อจาก db-spec/architecture)|audit-trail-search §5]] พร้อมกัน — ทั้ง `archive_status` (ค่าเริ่มต้น "ปกติ" เสมอ ไม่มี operation ใดอ่าน/เขียนค่านี้ในเฟสนี้) และ index 3 ชุด (`(related_surveyedbuilding_id, performed_at)`, `(action_type, performed_at)`, `(performed_by_user_id, performed_at)`) เป็นการ**เสริม**ความสามารถของโมเดลข้อมูลเดิมที่รองรับ NFR-05/FR-32/FR-33 อยู่แล้ว ไม่ใช่การเปลี่ยนแปลงที่ลดทอน — ทุกจุดที่แก้ไขสอดคล้องกันครบทั้ง 3 ชั้นเอกสาร (architecture/db-spec/detailed-design 2 ไฟล์) ไม่พบข้อขัดแย้ง — **สรุป: NFR-05 คงรองรับแล้ว** ระยะเวลาเก็บรักษาก่อนเปิดใช้ archive จริงยังไม่ปิด (รอหน่วยงานกำหนด) เป็นประเด็นเปิดโดยเจตนาตามที่ผู้เรียกระบุไว้ ไม่รายงานเป็นช่องว่างใหม่ แต่บันทึกเป็นความเสี่ยงที่ต้องติดตามต่อไปเรื่องปริมาณข้อมูลสะสมกระทบประสิทธิภาพการค้นหาของ FR-33 (ประเด็นเดิมที่เปิดไว้ตั้งแต่รอบที่ 5)

### สรุปรวมรอบที่ 11

3 ใน 4 ตัวที่ตรวจ (NFR-02, NFR-05, NFR-07) **ยังคงสถานะ "รองรับแล้ว"** — มีเพียง **NFR-03 ถูกลดระดับเป็น "รองรับบางส่วน"** (คงรองรับแล้ว 10/11 ในภาพรวม) เพราะการปิด `snapshot_content` format เผยให้เห็นว่าไม่มีกลไก field-level comparison รองรับการแยก "merge อัตโนมัติสำเร็จ" ออกจาก "ขัดแย้งจริง" จริงในเอกสารชั้นใดเลย — เป็นตัวอย่างที่ตรงกับคำเตือนของผู้เรียกพอดี ("อย่าเข้าข้างการตัดสินใจที่เพิ่งเกิด") เพราะการปิดตัวเลข/format ของรอบก่อนหน้าดูผิวเผินเหมือนทำให้ทุกอย่างสมบูรณ์ขึ้น แต่กลับเผยช่องว่างที่ซ่อนอยู่แทน

พบ **2 ความเสี่ยงที่ต้องติดตาม** เพิ่มเติม (ไม่บล็อกสถานะ): (1) NFR-07 — ยังไม่มีตัวเลขปริมาณโหลดที่คาดไว้มาประกอบการเผื่อกำลัง (capacity provisioning) บน GDCC ก่อน load test (2) NFR-05 — ปริมาณ `AuditTrailEntry` สะสมไม่มีขีดจำกัดจนกว่าจะปิดระยะเวลา retention จริง อาจกระทบประสิทธิภาพค้นหาของ FR-33 ในระยะยาว (ประเด็นเดิม ไม่ใช่ใหม่)

พบ **1 ความไม่สอดคล้องเชิงเอกสาร** ระหว่าง `api-spec.md` §16 (ยังบอกว่า `snapshot_content` format "ยังไม่ปิด") กับ `db-spec.md` §8.2/§11 (ปิดแล้วเป็น JSON) — ควรแก้ควบคู่กับช่องว่างของ NFR-03

**ไม่ถูกครอบคลุมในรอบนี้ (ตามขอบเขตที่ผู้เรียกจำกัดไว้)**: NFR-01, NFR-04, NFR-06, NFR-08, NFR-09, NFR-10, NFR-11 ไม่ถูกตรวจซ้ำ (คงผลจากรอบที่ 8/9/10) — ประเด็นที่ตั้งใจเปิดค้างไว้เดิมทั้งหมด (AI model runtime, ขนาด/ความละเอียดภาพ, `client_generated_id` การสร้างจริง, `credential_secret` encoding, ตัวเลข rate limit ที่แท้จริงของ Sync Intake Queue, ระยะเวลา retention ของ audit trail, HTTP method/path ต่อ operation) **ยังไม่ปิดและไม่ได้ถูกแตะต้องในรอบนี้** ไม่มีข้อใดถูกรายงานเป็นช่องว่างใหม่

**ควรรันชั้นไหนต่อ**:
- `sync-api-db` — ปิดช่องว่างหลักของ NFR-03: เพิ่มกฎทางธุรกิจใน [[api-spec#14.2 ตรวจสอบ/แก้ไขความขัดแย้งของข้อมูลที่ซิงค์|api-spec 14.2]]/[[db-spec#10. กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล|db-spec หัวข้อ 10]] ระบุกลไก/แหล่งข้อมูลจริงที่ใช้เปรียบเทียบค่าระดับฟิลด์ก่อนตัดสิน "merge อัตโนมัติสำเร็จ" vs "ขัดแย้งจริง" และแก้ [[api-spec#16. ประเด็นรอตัดสินใจ|api-spec หัวข้อ 16]] ให้ตรงกับ db-spec ว่า `snapshot_content` format ปิดแล้ว
- `sync-detailed-design` — หลัง `sync-api-db` ปิดกลไกข้างต้นแล้ว ปรับ [[detailed-design/offline-sync#4. ขอบเขตของ conflict detection (ปิดช่องว่างเดิมแล้ว)|offline-sync §4]] ให้สะท้อนกลไกที่ปิดจริง
- ไม่จำเป็นต้องแตะ `architecture.md` เพิ่มเติม — ช่องว่างอยู่ที่ระดับ operation contract/business rule ไม่ใช่ระดับ component/data flow
