# Technology Stack

เอกสารนี้บันทึกว่า **เลือกอะไร เพราะอะไร ไม่เลือกอะไรเพราะอะไร และอะไรยังไม่ตัดสินใจ** สำหรับ tech stack ของระบบ อ้างอิง [[backlog]] (FR/NFR ต้นทาง) และ [[architecture]] (ข้อจำกัดเชิงสถาปัตยกรรมที่ตัดสินไปแล้ว) เอกสารนี้**ไม่ derive จาก FR/NFR แบบ mechanical** — ทุกแถวในหัวข้อ 3 คือสิ่งที่ผู้ใช้เลือกเองจริงหลังผ่านการสัมภาษณ์ ไม่ใช่ผลคำนวณอัตโนมัติ

## 1. สถานะการตัดสินใจ

**อัปเดตล่าสุด: 2026-09-04**

- **ตัดสินใจแล้ว 6 ชั้น** (ครอบคลุมทุกชั้นที่ [[release-plan|Phase 1]] ต้องใช้): Field Client Framework (**bare React Native** — ระบุชัดเจนแล้วว่าไม่ใช่ Expo), Local Persistent Store (SQLite ผ่าน **`op-sqlite`** — ตัดสินใจ library แล้ว), Server-side Runtime, Primary Data Store, Media/Object Storage, **Protocol/Web Framework (REST over HTTP + Fastify — ปิดเพิ่มเมื่อ 2026-09-04)**
- **ยังไม่ตัดสินใจเหลือ 2 รายการ** (จำนวนเท่าเดิมกับรอบก่อน — Protocol/Web Framework ที่เพิ่งปิดในรอบนี้ไม่เคยถูกนับอยู่ใน 2 รายการนี้มาก่อน เป็นชั้นใหม่ที่เพิ่งถูกบันทึกเข้าหัวข้อ 3 ไม่ใช่การลดออกจากหัวข้อ 4):
  1. Runtime ของโมเดล AI วิเคราะห์รอยร้าว (บล็อกเฉพาะ Phase 3 ไม่บล็อก Phase 1-2 — ดูหัวข้อ 4.1)
  2. Hosting/deployment target — ประเด็นคร่อมชั้น (ดูหัวข้อ 4.2)
- **ประเด็นคร่อมชั้นที่ยังไม่มีคำตอบ**: hosting/deployment target (on-premise ของหน่วยงาน หรือ cloud) — **กระทบวิธี deploy ของ 3 ใน 6 ชั้นที่ตัดสินแล้ว** (Server-side Runtime, Primary Data Store, Media/Object Storage) แม้ชื่อเทคโนโลยีที่เลือกจะไม่เปลี่ยน แต่วิธี deploy/ดูแลรักษาอาจเปลี่ยนมากถ้าหน่วยงานบังคับ on-prem
- **ผู้อ่านที่ต้องการอ้างอิง**: ใช้เอกสารนี้ได้เต็มที่สำหรับงาน Phase 1-2 ทุกชั้น รวมถึงเริ่มเขียนโค้ด Local Persistent Store และชั้นขนส่ง API (REST over HTTP + Fastify) ได้แล้ว (ตัดสินใจแล้วทั้งคู่) ยกเว้นสิ่งที่เกี่ยวกับ AI model ให้รอจนกว่าหัวข้อ 4.1 จะปิด และสิ่งที่เกี่ยวกับ infrastructure/hosting จริงให้รอจนกว่าจะคุยกับหน่วยงานเสร็จ (หัวข้อ 4.2)
- **ข้อควรระวังเรื่องความรู้ล้าสมัย**: ข้อมูลเปรียบเทียบ library SQLite สำหรับ React Native ในหัวข้อ 3 (op-sqlite, react-native-sqlite-storage, expo-sqlite, WatermelonDB) อ้างอิงความรู้ถึงกลางปี 2026 สถานะการดูแล (maintenance), issue ที่ค้าง และความเข้ากันได้กับเวอร์ชัน React Native ที่จะใช้จริงเปลี่ยนแปลงเร็ว **ควรตรวจสอบ commit ล่าสุด, issue tracker, และความเข้ากันได้กับเวอร์ชัน React Native ที่เลือกจริง ก่อนติดตั้งใช้งานจริง** ไม่ควรถือเป็นข้อเท็จจริงตายตัว
- **บริบทของผู้ใช้ที่ใช้ประกอบการตัดสินใจรอบนี้** (บันทึกไว้เพื่อความโปร่งใส ไม่ใช่ข้อจำกัดของ session งาน): ทีมพัฒนาคือ**ผู้ใช้คนเดียว** ถนัด **JavaScript/TypeScript และ Python** อุปกรณ์ภาคสนามเป้าหมายคือ **Android เป็นหลัก** (ยังไม่ยืนยันรุ่น) ยังไม่ได้คุยกับหน่วยงาน (กรมโยธาธิการและผังเมือง) เรื่องข้อกำหนด hosting/data residency

## 2. ข้อจำกัดที่บีบตัวเลือก

| รหัส | บีบชั้น | บีบแค่ไหน | เหตุผล |
|---|---|---|---|
| NFR-01 (Availability/Offline) | Field Client Framework, Local Persistent Store | **มาก** | ต้องรองรับ full local persistence ของข้อมูลสำรวจครบ 10 หมวดโดยไม่พึ่งเครือข่ายเลย (ตัด framework ที่พึ่งพา network เป็นหลักทิ้งไปแล้วตั้งแต่ขั้นเลือกรูปแบบแอปภาคสนามเป็น cross-platform native) |
| FR-27 (เข้าสู่ระบบขณะออฟไลน์) | Field Client Framework, Local Persistent Store | มาก | ต้องเก็บ credential/session ที่แคชไว้ในเครื่องและเรียกใช้ได้โดยไม่มีสัญญาณ |
| NFR-02 (Performance/Reliability — sync ไฟล์ใหญ่) | Media/Object Storage, Local Persistent Store (queue), Server-side Runtime (background job), Protocol/Web Framework (เพิ่มเข้ามา 2026-09-04 เมื่อชั้นนี้ถูกตัดสินใจ) | **มาก** | ต้องรองรับอัปโหลด/ทำต่อจากจุดค้างของไฟล์ภาพขนาดใหญ่แบบพื้นหลัง ตัดตัวเลือกที่ไม่รองรับ resumable upload ทิ้ง — รวมถึงบีบให้เลือก web framework ที่จัดการ multipart/stream ได้ดี (ดูแถว Protocol/Web Framework ในหัวข้อ 3) |
| NFR-04 (Usability/Compatibility — อุปกรณ์หลากรุ่นราคาประหยัด) | Field Client Framework | **มาก** | ตัด framework ที่กินทรัพยากรหนัก/ประสิทธิภาพแย่บนแท็บเล็ตสเปกต่ำของหน่วยงานราชการ |
| NFR-09 (Security — อายุ session ที่แคชไว้) | Field Client Framework, Local Persistent Store | ปานกลาง | framework ต้องมี API เข้าถึงที่เก็บข้อมูลปลอดภัยระดับ OS (Keystore บน Android) ได้ |
| NFR-03 (Data Integrity — ตรวจจับความขัดแย้ง) | Primary Data Store | ปานกลาง | ต้องเปรียบเทียบ version/เวลาแก้ไขล่าสุดได้ เอียงไปทาง store ที่จัดการ relationship ชัดเจน |
| NFR-07 (Scalability — โหลดกระจุกตัวหลังกลับจากพื้นที่) | Server-side Runtime, Primary Data Store | ปานกลาง | ต้องมี queue/worker รองรับ burst และ DB รองรับ concurrent write โดยไม่เสียหาย |
| NFR-08 (Security — RBAC) | Server-side Runtime | **น้อย** | ทำได้แทบทุก stack — เป็น business logic ไม่ใช่ข้อจำกัดเทคโนโลยี |
| FR-21, FR-25, FR-26 (จัดการสิทธิ์/ยืนยันตัวตน/บังคับสิทธิ์) | Server-side Runtime | น้อย | ไม่บีบเทคโนโลยีเฉพาะเจาะจง เป็น business logic เช่นเดียวกับ NFR-08 |
| architecture.md [[architecture#6.4 แยก Primary Data Store และ Media/Object Storage เป็นคนละที่เก็บข้อมูล\|§6.4]] | Primary Data Store, Media/Object Storage | มาก (ตัดสินแล้วในชั้นสถาปัตยกรรม) | บังคับให้สองที่เก็บนี้เป็นคนละระบบ — ไม่ใช่ NFR โดยตรงแต่เป็นข้อจำกัดที่สืบทอดมาจาก architecture ที่ตัดสินไปก่อนชั้นนี้แล้ว |

**สรุป**: ชั้นที่ถูกบีบมากที่สุดคือ **Field Client Framework** (ถูกบีบพร้อมกันจาก NFR-01/02/04/09) รองลงมาคือ **Primary Data Store** (NFR-03/07 + ข้อจำกัดจาก §6.4) ส่วน **Server-side Runtime ถูกบีบน้อยที่สุด** — ไม่มี NFR ใดบังคับภาษา/runtime เฉพาะเจาะจง จึงเปิดให้เลือกตามความถนัดทีมได้อิสระที่สุดในบรรดา 6 ชั้น

## 3. การตัดสินใจรายชั้น

| ชั้น | สิ่งที่เลือก | เหตุผล (อ้างรหัส NFR/FR) | ทางเลือกที่พิจารณาแล้วไม่เลือกและเพราะอะไร |
|---|---|---|---|
| **Field Client Framework** (แอปภาคสนาม) | **bare React Native** (ยังไม่กำหนดเวอร์ชัน) — ระบุชัดเจนแล้วว่าเป็น bare workflow ไม่ใช่ Expo managed workflow | ผู้ใช้ถนัด JavaScript/TypeScript อยู่แล้ว (ทีมคนเดียว) ทำให้พัฒนา/ดูแลได้เร็วกว่าเรียนภาษาใหม่ — ตอบโจทย์ NFR-01/FR-27 (offline เต็มรูปแบบ) ได้ผ่าน ecosystem local-first ที่มีอยู่ **เพิ่มเติมจากรอบก่อน**: เลือกระบุเป็น bare workflow (ไม่ใช่ Expo) เพราะ NFR-02 (อัปโหลดพื้นหลังต่อจากจุดค้าง) และการเลือก library เก็บข้อมูลบนอุปกรณ์ (`op-sqlite` ที่ใช้ JSI) ต้องการความสามารถผูก native module เองได้เต็มที่ ซึ่ง Expo managed workflow จำกัดความสามารถนี้ไว้ | **Flutter** — เคยเสนอเป็นตัวแนะนำหลักเพราะคอมไพล์เป็น native ARM ไม่ผ่าน JS bridge (ตอบ NFR-04 ได้ตรงกว่า) แต่ผู้ใช้เลือก React Native เพราะทีมไม่ถนัด Dart และเป็นทีมคนเดียว การเรียนภาษาใหม่มีต้นทุนสูงกว่าประโยชน์ด้านประสิทธิภาพที่ยังไม่มีปัญหาจริง ณ ตอนนี้ · **.NET MAUI** — ตัดเพราะ ecosystem ปลั๊กอิน offline-first/กล้อง/AI on-device เล็กกว่ามาก และทีมไม่ได้ถนัด C#/.NET · **Native แยก Kotlin+Swift** — ตัดเพราะทีมคนเดียวไม่สามารถดูแล 2 โค้ดเบสคู่ขนานได้ ไม่มี NFR ใดบังคับว่าต้องแยก · **Expo (managed workflow)** — พิจารณาแล้วไม่เลือก แม้ตั้งค่าง่ายกว่า bare RN มาก เพราะเสี่ยงกับ NFR-02 ที่การอัปโหลดเบื้องหลังต่อจากจุดค้างมักต้องพึ่ง native module ที่ managed workflow เข้าถึงได้จำกัดกว่า และขัดกับการเลือก `op-sqlite` ที่ต้องการ bare workflow (ดูแถว Local Persistent Store) |
| **Local Persistent Store** (ที่เก็บข้อมูลบนอุปกรณ์) | **SQLite ผ่าน `op-sqlite`** (ยังไม่กำหนดเวอร์ชัน) | ตอบ NFR-01 (เก็บข้อมูลแบบสำรวจครบ 10 หมวดแบบมี relationship ได้), NFR-03 (เก็บ version/timestamp เปรียบเทียบได้สำหรับตรวจจับความขัดแย้งภายหลัง), NFR-09 (แยกเก็บ credential ผ่าน secure storage ของ OS ได้) — เป็นทางเลือกที่ผูกกับ ecosystem ของ bare React Native ที่เลือกไปแล้ว **library ที่เลือก**: `op-sqlite` เพราะใช้ JSI ทำให้เร็วที่สุดในกลุ่มที่เปรียบเทียบ, มีการพัฒนาต่อเนื่อง, API ทันสมัย — ตอบ NFR-02 (ต้องจัดการคิวซิงค์และไฟล์ภาพจำนวนมากบนอุปกรณ์ Android ราคาประหยัดตาม NFR-04 ให้เร็วพอ) และเปิดทางให้เขียน native module เพิ่มเองสำหรับ resumable upload ที่ NFR-02 ต้องการ | **Embedded NoSQL/document store** (เช่น Realm, ObjectBox) — พิจารณาแล้วไม่เลือกเพราะบาง engine ผูกกับ sync engine/vendor เฉพาะที่อาจขัดกับข้อจำกัดจัดซื้อ/data residency ของหน่วยงานราชการที่ยังไม่ทราบคำตอบ (ดูหัวข้อ 4.2) · **จัดการไฟล์ดิบเอง (JSON+filesystem)** — ตัดเพราะไม่รองรับ query/index/versioning ที่โดเมนข้อมูล 10 หมวดต้องการ เสี่ยง data integrity สูงกว่า · **`react-native-sqlite-storage`** — พิจารณาแล้วไม่เลือก แม้มีตัวอย่าง/community เยอะที่สุดในกลุ่ม SQLite library แต่ API เก่ากว่าและการดูแลรักษาเคยช้าเป็นช่วงๆ ไม่ใช้ JSI จึงช้ากว่า `op-sqlite` · **`expo-sqlite`** — ตัดเพราะต้องพึ่ง Expo managed workflow ที่ไม่ได้เลือกไว้ (ดูแถว Field Client Framework) และเสี่ยงกับ NFR-02 เรื่องอัปโหลดเบื้องหลังต่อจากจุดค้างที่มักต้องพึ่ง native module ที่ managed workflow เข้าถึงได้จำกัดกว่า · **WatermelonDB** — ตัดเพราะมีชั้น sync/conflict resolution มาให้ในตัว ซึ่งชนกับกลไก sync/conflict ที่โปรเจกต์ออกแบบเองไว้แล้วอย่างละเอียดใน [[offline-sync]] การใช้ทั้งสองระบบพร้อมกันจะซ้ำซ้อนและเสี่ยงขัดแย้งกันเอง — **ข้อควรระวัง**: การเปรียบเทียบ library ทั้ง 4 ตัวนี้อ้างอิงความรู้ถึงกลางปี 2026 ควรตรวจสอบสถานะการดูแลรักษาจริง (commit ล่าสุด, issue ที่ค้าง, ความเข้ากันได้กับเวอร์ชัน React Native ที่จะใช้) ก่อนติดตั้งจริง เพราะสถานะเปลี่ยนเร็ว |
| **Server-side Runtime** | **Node.js / TypeScript** (ยังไม่กำหนดเวอร์ชัน) | ผู้ใช้ถนัด JavaScript/TypeScript อยู่แล้ว ทำให้ใช้ภาษาเดียวกันได้ทั้งฝั่ง client (React Native) และฝั่งเซิร์ฟเวอร์ ลดภาระสลับบริบทสำหรับทีมคนเดียว — ตอบ NFR-07 (ecosystem queue/background job รองรับโหลดกระจุกตัว) และ NFR-02 (รองรับ resumable upload แบบพื้นหลัง) ได้ | **Python** — พิจารณาแล้วไม่เลือกแม้ทีมถนัดเช่นกัน เพราะ Node.js ทำให้ใช้ภาษาเดียวกับฝั่ง client ได้ (Python จะต้องสลับ 2 ภาษาคู่กับ frontend/React Native) จุดแข็งของ Python ด้าน ML ecosystem ยังไม่มีผลตอนนี้เพราะ Phase 1 ไม่มีรหัสเกี่ยวกับ AI เลย และ runtime ของโมเดล AI ยังไม่ตัดสินใจ (ดูหัวข้อ 4) — หากถึงเวลาตัดสิน Server-side AI Analysis ในอนาคตและพบว่าจำเป็นต้องใช้ Python ecosystem ให้ทบทวนใหม่ (ดูหัวข้อ 6) · **Java/Kotlin (Spring Boot) หรือ .NET (ASP.NET Core)** — ตัดเพราะทีมไม่ถนัด และ boilerplate/เวลาเรียนรู้ไม่เหมาะกับทีมคนเดียว แม้บางหน่วยงานราชการจะคุ้นเคยกับ stack นี้มากกว่า |
| **Primary Data Store** | **MySQL / MariaDB** (ยังไม่กำหนดเวอร์ชัน) | เป็น relational DB ตอบ NFR-03 (versioning/comparison), NFR-07 (concurrent write ที่ยังคง integrity), NFR-08 (โครงสร้างสิทธิ์แบบ role/ownership) ได้ — เข้ากับ ecosystem ของ Node.js/TypeScript ที่เลือกไปแล้ว | **PostgreSQL** — เคยเสนอเป็นตัวแนะนำหลักเพราะรองรับ JSON column/indexing ขั้นสูงกว่าและตรงกับโครงสร้าง entity-relationship ที่ [[db-spec]] ออกแบบไว้อย่างตรงไปตรงมาที่สุด แต่ผู้ใช้เลือก MySQL/MariaDB โดยรับทราบข้อเสียนี้แล้ว (ฟีเจอร์ขั้นสูงบางอย่าง เช่น extension สำหรับพิกัด GPS อาจด้อยกว่า Postgres เล็กน้อย) — บันทึกไว้เป็นข้อแลกเปลี่ยนที่รู้ตัว ไม่ใช่การมองข้าม · **MongoDB (NoSQL)** — ตัดเพราะ ownership-based scoping ที่ต้อง join อาคาร↔ทีม↔ผู้ใช้ตาม [[architecture#7. ข้อสมมติ\|architecture §7 ข้อ 7]] เขียน/ดูแลยากกว่า relational DB โดยทั่วไป เสี่ยงต่อ data integrity ที่ NFR-03 ต้องการมากกว่า |
| **Media/Object Storage** | **Local filesystem บนเซิร์ฟเวอร์** | ยังคงแยกเป็นคนละที่เก็บข้อมูลจาก Primary Data Store ตามที่ [[architecture#6.4 แยก Primary Data Store และ Media/Object Storage เป็นคนละที่เก็บข้อมูล\|architecture §6.4]] ตัดสินไปแล้ว (ไม่ขัดกัน) — เลือกเป็นทางเริ่มต้นที่ต้นทุน/ความซับซ้อนต่ำสุดสำหรับทีมคนเดียวที่ยังไม่ทราบข้อจำกัด hosting ของหน่วยงาน | **S3-compatible object storage** (AWS S3 หรือ self-host เช่น MinIO) — เคยเสนอเป็นตัวแนะนำหลักเพราะรองรับ multipart/resumable upload มาให้พร้อมใช้ตรงกับ NFR-02 โดยไม่ต้องเขียนเอง แต่ผู้ใช้เลือก local filesystem โดยรับทราบข้อเสียนี้แล้วว่า **resumable upload ตาม NFR-02 ต้องเขียนเอง** ไม่ได้มาฟรีเหมือน object storage — บันทึกไว้เป็นข้อแลกเปลี่ยนที่รู้ตัว (ดูเกณฑ์ทบทวนในหัวข้อ 6) · **Managed cloud storage อื่น** (Azure Blob/GCS) — ตัดเพราะไม่มีเหตุผลผูกกับ cloud provider ใดโดยเฉพาะ ณ ตอนนี้ |
| **Protocol/Web Framework** (ชั้นขนส่งของ [[api-spec]] — ปิดเพิ่มเมื่อ 2026-09-04) | **REST over HTTP + Fastify** (ยังไม่กำหนดเวอร์ชัน) | [[api-spec]] เขียนสัญญาการทำงานเป็น operation contract ต่อ resource ไว้แล้ว (ดู [[api-spec#16. ประเด็นรอตัดสินใจ\|api-spec §16]] ที่เคยเปิดประเด็นนี้ไว้) ซึ่งแมปเป็น REST ได้ตรงไปตรงมา ชั้นขนส่งจึงบางมาก ไม่ต้องออกแบบสัญญาใหม่ — Fastify รองรับ TypeScript ดี (สอดคล้องกับ Server-side Runtime ที่เลือกไว้แล้วคือ Node.js/TypeScript), มี schema validation ในตัว, และจัดการ multipart/stream ได้ดีซึ่งจำเป็นสำหรับ resumable upload ตาม NFR-02 ที่ต้องเขียนกลไก chunking เอง (เพราะเลือก local filesystem ไม่ใช่ object storage — ดูแถว Media/Object Storage) REST ยังเปิดทางให้หน่วยงานอื่นต่อเชื่อมภายหลังได้ง่ายกว่าถ้าเกิดความต้องการเชื่อมระบบภายนอกตามที่ [[architecture#2.1 ระบบภายนอกและจุดเชื่อมต่อ\|architecture §2.1]] เปิดไว้เป็นไปได้ในอนาคต | **REST + Express** — พิจารณาแล้วไม่เลือก แม้เป็นเฟรมเวิร์กที่ทีมคุ้นเคยที่สุด (ทีมถนัด JS/TS อยู่แล้ว) แต่ช้ากว่า Fastify และ TypeScript support อ่อนกว่า ต้องพึ่ง `@types/express` แยกต่างหากแทนที่จะมี type inference ในตัว ผู้ใช้ยอมรับต้นทุนการเรียนรู้ pattern plugin/hook ของ Fastify เพื่อแลกกับความเร็วและ NFR-02 · **เก็บงาน domain ต่อไปก่อน ยังไม่เลือก protocol** — ตัดเพราะทำให้โค้ดที่เขียนไปแล้ว (ชั้น `domain/`) ยังรันจริงเป็นระบบที่เรียกผ่านเครือข่ายไม่ได้ ผู้ใช้ต้องการปิดประเด็นนี้เพื่อเริ่มต่อชั้นขนส่งจริงได้ |

## 4. สิ่งที่ยังไม่ตัดสินใจ

### 4.1 Runtime ของโมเดล AI วิเคราะห์รอยร้าว + รูปแบบไฟล์โมเดล

**เงื่อนไขที่ต้องมีก่อนถึงจะตัดสินได้**:
- ต้องมีโมเดล AI จริง (หรืออย่างน้อยรู้ขนาด/สถาปัตยกรรมโมเดลที่จะใช้) — ปัจจุบันยังไม่มี
- ต้องมีชุดข้อมูลสำหรับฝึก/ทดสอบ — ปัจจุบันยังไม่มี
- ต้องแก้ข้อสมมติข้อ 2 และ 8 ในหมวด 6 ของ [[20260828-01-flood-damage-survey#6. ข้อสมมติ / ประเด็นค้างพิจารณา|spec]] ก่อน (เกณฑ์ความกว้างรอยร้าวยังยืมจากคู่มือแผ่นดินไหวโดยไม่ยืนยันว่าใช้กับอุทกภัยได้ และยังไม่มีเกณฑ์ตัดสินว่า "วิเคราะห์ไม่สำเร็จ")

**ผลกระทบถ้าเลื่อนต่อ**: บล็อกเฉพาะ Phase 3 (ฟีเจอร์ที่เกี่ยวกับ FR-13/FR-14/FR-28/FR-29) **ไม่บล็อก Phase 1-2** เพราะ Phase 1 ไม่มีรหัสเกี่ยวกับ AI เลย (ยืนยันจาก [[release-plan]])

**ข้อควรระวังล่วงหน้าที่บันทึกไว้แล้ว**: [[architecture#6.1 ตำแหน่งการทำงานของ AI วิเคราะห์รอยร้าว|architecture §6.1]] ตัดสินไปแล้วว่า AI ต้องรันบนอุปกรณ์เป็นเส้นทางหลัก (ไม่ใช่ทางเลือก) — React Native ที่เลือกไว้สำหรับ Field Client Framework เป็น cross-platform framework ที่การรัน on-device AI inference (เช่นผ่าน TensorFlow Lite/ONNX Runtime) ทำได้ยากกว่าทางเลือกที่คอมไพล์เป็น native โดยตรง (เช่น Flutter หรือ native แยก platform) — **ยังไม่ใช่ปัญหาตอนนี้เพราะยังไม่มีโมเดลและยังไม่ใช่ Phase 1** แต่ต้องนำมาพิจารณาอีกครั้งเมื่อถึงเวลาตัดสินใจจริง (ดูเกณฑ์ทบทวนในหัวข้อ 6)

### 4.2 Hosting/Deployment target

**เงื่อนไขที่ต้องมีก่อนถึงจะตัดสินได้**: ต้องคุยกับหน่วยงาน (กรมโยธาธิการและผังเมือง) ว่ามีข้อกำหนดเรื่อง data residency / ห้ามใช้ cloud สาธารณะ / ต้องเป็น on-premise หรือไม่ และงบประมาณ hosting เป็นอย่างไร — ปัจจุบันผู้ใช้ยังไม่ได้คุยกับหน่วยงานเรื่องนี้

**ผลกระทบถ้าเลื่อนต่อ**: ไม่บล็อกการเริ่มพัฒนา Phase 1 (พัฒนา/ทดสอบในเครื่อง dev ได้ก่อน) แต่ **กระทบวิธี deploy จริงของ Server-side Runtime, Primary Data Store, และ Media/Object Storage** ทั้งสามชั้นที่ตัดสินชื่อเทคโนโลยีไปแล้วในหัวข้อ 3 — ถ้าหน่วยงานบังคับ on-prem อาจต้องเปลี่ยนจากการใช้ managed service (ถ้าเคยวางแผนไว้) มาเป็น self-host ทั้งหมด แต่**ชื่อเทคโนโลยีที่เลือก (Node.js, MySQL/MariaDB, local filesystem) ไม่จำเป็นต้องเปลี่ยนเพราะเลือกได้ทั้ง on-prem และ cloud อยู่แล้ว**

> **หมายเหตุ (2026-09-04)**: หัวข้อ "4.3 Library เฉพาะตัวสำหรับ SQLite บน React Native" ที่เคยอยู่ตรงนี้ **ตัดสินใจแล้ว** — ผู้ใช้เลือก `op-sqlite` บน bare React Native ย้ายรายละเอียดไปบันทึกไว้ในหัวข้อ 3 (แถว Field Client Framework และ Local Persistent Store) แล้ว รวมถึงทางเลือกที่พิจารณาแล้วไม่เลือก (react-native-sqlite-storage, expo-sqlite, WatermelonDB)

> **หมายเหตุ (2026-09-04)**: ประเด็น "protocol/รูปแบบการสื่อสาร หรือ web framework" ที่ [[architecture#8. ประเด็นรอตัดสินใจ|architecture §8]] และ [[api-spec#16. ประเด็นรอตัดสินใจ|api-spec §16]] เคยระบุไว้ว่ายังไม่ปิด (เดิมเขียนไว้ว่า "การเลือก Node.js/TypeScript เป็น runtime ไม่ใช่การเลือก REST/GraphQL/gRPC") **ตัดสินใจแล้ว** — ผู้ใช้เลือก **REST over HTTP + Fastify** รายละเอียดเหตุผลและทางเลือกที่ไม่เลือกอยู่ในหัวข้อ 3 (แถว Protocol/Web Framework) เอกสารทั้งสองฉบับที่กล่าวถึงข้างต้นควรกลับไปปรับปรุงส่วนที่ระบุว่า "ยังไม่ปิด" ให้ตรงกับสถานะใหม่นี้ (ดูหัวข้อ 5)

## 5. ผลกระทบต่อเอกสารชั้นอื่น

- **[[architecture]]** — ปัจจุบันจงใจไม่ระบุชื่อเทคโนโลยีใดๆ ตามที่ระบุไว้ในหมายเหตุต้นเอกสาร ตอนนี้ `technology-stack.md` มีเนื้อหาแล้ว **ควรกลับไปทบทวนเพื่ออ้างอิงชื่อ stack จริงในจุดที่เหมาะสม** โดยเฉพาะ:
  - หัวข้อ 2 (Logical Component) — Field Client App, Backend Service, Sync & Conflict Resolution Service, Primary Data Store, Media/Object Storage อาจเพิ่มหมายเหตุอ้างอิงชื่อ stack จริงประกอบ (ไม่จำเป็นต้องเปลี่ยนชื่อ component)
  - §8 (ประเด็นรอตัดสินใจ) — ลบ/ปรับรายการที่ตอนนี้ตัดสินใจแล้ว (เทคโนโลยี Field Client App, Backend Service, Primary Data Store, Media/Object Storage) ให้เหลือเฉพาะที่ยังไม่ตัดสิน (runtime โมเดล AI, รูปแบบไฟล์รายงาน FR-23, กลไก auth/session ที่เป็นรูปธรรม, กลยุทธ์ค้นหา FR-33)
  - **(เพิ่มเข้ามา 2026-09-04)** §8 บรรทัดแรก (ที่สรุปว่า "ทั้ง framework ระดับ workflow ... และ library เฉพาะตัวของ Local Persistent Store ถูกตัดสินใจครบแล้ว") **ควรปรับปรุงเพิ่มว่า Protocol/Web Framework ก็ปิดแล้วเช่นกัน** (REST over HTTP + Fastify — ดูหัวข้อ 3 ของเอกสารนี้) และ**รายการย่อยที่ระบุว่า "รูปแบบการเรียก operation จริง (function call ภายใน monolith / message queue / API แบบใดก็ตาม) และ protocol การสื่อสาร — ยังไม่ปิด" ควรลบออกหรือปรับเป็นปิดแล้ว**
- **[[api-spec]]** — §16 (ประเด็นรอตัดสินใจ) ปัจจุบันเขียนไว้ชัดว่า "ยังไม่ได้ตัดสินใจเรื่อง protocol/รูปแบบการสื่อสารหรือ web framework ใดๆ" **ตอนนี้ปิดแล้ว (REST over HTTP + Fastify)** — ควรกลับไปปรับ §16 ให้ตัดรายการนี้ออกหรือทำเครื่องหมายว่าปิดแล้ว และ**ควรพิจารณา (ไม่บังคับ) ว่าจะเพิ่ม HTTP method/path ต่อ operation ในหัวข้อ 1-15 หรือไม่** เนื่องจากตอนนี้รู้แล้วว่าเป็น REST — การตัดสินใจนี้เป็นของ `api-db-writer` ไม่ใช่ `tech-stack-writer`
- **[[db-spec]]** — ยังคง logical ต่อไปได้ตามเดิม แต่**ประเด็นรอตัดสินใจ**ของไฟล์นี้ (ถ้ามีข้อที่ผูกกับชนิด database เช่น relational vs document) ควรกลับไปตรวจว่าปิดได้แล้วหรือไม่ เนื่องจาก Primary Data Store ถูกตัดสินเป็น relational (MySQL/MariaDB) แล้ว
- **[[release-plan]] / `03-task/`** — งานย่อยระดับ implementation เขียนไว้แบบไม่ผูก tech stack ตามกติกาเดิม ตอนนี้เมื่อ tech stack Phase 1 ตัดสินแล้ว (รวม library `op-sqlite` และ bare workflow) **ควรพิจารณาเพิ่มรายละเอียดระดับ implementation ที่อ้างอิง stack จริงได้ในรอบถัดไป** (ไม่บังคับ แต่เป็นโอกาส)
- **[[offline-sync]]** (ใน `detailed-design/`) — ออกแบบกลไก sync/conflict resolution ไว้เองแล้วโดยไม่ผูก library เฉพาะ ตอนนี้ทราบแล้วว่าใช้ `op-sqlite` (ไม่ใช่ WatermelonDB ที่มีชั้น sync มาให้ในตัว) **ควรกลับไปตรวจว่าการออกแบบ queue/conflict resolution ที่มีอยู่ยัง implement ได้จริงบน `op-sqlite` ล้วนๆ โดยไม่พึ่งชั้น sync สำเร็จรูปหรือไม่**
- **`nfr-review.md`** — ควรกลับไปตรวจว่าการเลือก bare React Native + `op-sqlite` + MySQL/MariaDB + local filesystem + **REST over HTTP + Fastify (เพิ่มเข้ามา 2026-09-04)** ยังคงตอบ NFR-01/02/04/07/09 ได้ตามที่ architecture ออกแบบไว้หรือไม่ในระดับ implementation จริง โดยเฉพาะ NFR-02 (resumable upload ต้องเขียน native module เองบน bare RN โดยอาศัยความสามารถของ `op-sqlite`/JSI ฝั่ง client และอาศัยความสามารถ multipart/stream ของ Fastify ฝั่งเซิร์ฟเวอร์) และ NFR-04 (ต้องทดสอบบนอุปกรณ์จริง)

## 6. เกณฑ์ที่จะทำให้ต้องทบทวนการตัดสินใจนี้ใหม่

1. **bare React Native + NFR-04** — ถ้าทดสอบบนแท็บเล็ต Android สเปกต่ำจริง (ไม่ใช่ emulator) แล้วพบปัญหาประสิทธิภาพที่แก้ไม่ได้ ต้องทบทวน Field Client Framework ใหม่ (Flutter เป็นตัวเลือกที่เคยพิจารณาไว้)
2. **bare React Native + `op-sqlite` + NFR-02 (background upload)** — ถ้า background upload ไฟล์ภาพขนาดใหญ่ผ่าน native module ที่ต้องเพิ่มเข้ามาบน `op-sqlite`/JSI ไม่เสถียรพอ ต้องทบทวนทั้ง Field Client Framework และวิธี implement Local Sync Queue ใน [[offline-sync]]
3. **bare React Native + AI on-device (architecture §6.1)** — เมื่อถึงเวลาตัดสิน runtime ของโมเดล AI จริง (Phase 3) ถ้าพบว่า React Native รองรับ on-device inference ได้ไม่ดีพอ (เทียบกับ NFR-01 ที่บังคับให้ AI ทำงานได้ขณะออฟไลน์) **ต้องทบทวน Field Client Framework ทั้งชั้น** ไม่ใช่แค่เพิ่ม runtime AI เข้ามา
4. **Android เป็นหลักแต่เลือก cross-platform** — ถ้าหน่วยงานยืนยันในภายหลังว่าไม่ต้องรองรับ iOS เลย ควรทบทวนว่า bare React Native (cross-platform) ยังคุ้มค่ากับความซับซ้อนที่แลกมาหรือไม่ เทียบกับ native Android เดี่ยว (Kotlin)
5. **Local filesystem + hosting ที่ยังไม่ทราบ (ข้อ 4.2)** — ถ้าหน่วยงานตอบมาว่าต้องใช้โครงสร้างพื้นฐานของเขาเอง หรือถ้าปริมาณผู้ใช้/ไฟล์โตเกินเซิร์ฟเวอร์เดียวจะรองรับไหว โค้ดส่วนที่ผูกกับ local filesystem โดยตรงอาจต้องรื้อเพื่อย้ายไป object storage — เขียน abstraction layer แยกไว้ตั้งแต่ต้นจะช่วยลดต้นทุนการย้ายในอนาคต (คำแนะนำเชิงปฏิบัติ ไม่ใช่การตัดสินใจใหม่)
6. **MySQL/MariaDB + FR-33 (ค้นหา audit trail ปริมาณมาก)** — ถ้าปริมาณการค้นหาของ FR-33 สูงมากจนกระทบประสิทธิภาพเมื่อ audit log สะสมมากขึ้นเรื่อยๆ โดยไม่มีการลบอัตโนมัติ (ตามข้อสมมติที่ [[architecture#7. ข้อสมมติ|architecture §7 ข้อ 6]] ระบุไว้) ให้ทบทวนกลยุทธ์การจัดทำดัชนี/แยก read replica ตามที่ [[architecture#8. ประเด็นรอตัดสินใจ|architecture §8]] เปิดไว้เป็นประเด็นเปิดอยู่แล้ว
7. **ทีมขยายจากคนเดียวเป็นหลายคน หรือทักษะทีมเปลี่ยน** — การเลือก Node.js/TypeScript ทั้ง client และ server อิงจากบริบท "ทีมคนเดียว ถนัด JS/TS" ถ้าทีมขยายและมีคนถนัดภาษาอื่นเข้ามาแทน ควรทบทวน Server-side Runtime ใหม่โดยเฉพาะถ้ามีความจำเป็นต้องใช้ Python ecosystem สำหรับ Server-side AI Analysis ในอนาคต
8. **`op-sqlite` หยุดการดูแลรักษา (unmaintained) หรือเข้ากันไม่ได้กับเวอร์ชัน React Native ที่เลือกใช้จริง** — เนื่องจากข้อมูลเปรียบเทียบ library ในหัวข้อ 3 อ้างอิงความรู้ถึงกลางปี 2026 เท่านั้น สถานะจริงอาจเปลี่ยนไปก่อนเริ่ม implementation จริง **ต้องตรวจสอบ commit ล่าสุด/issue ที่ค้าง/ความเข้ากันได้ก่อนติดตั้งเสมอ** ถ้าพบว่า `op-sqlite` ใช้ไม่ได้จริง ให้ทบทวนกลับไปยังทางเลือกที่เคยพิจารณาไว้ (`react-native-sqlite-storage` เป็นตัวสำรองที่ใกล้เคียงที่สุด)
9. **ความจำเป็นต้องย้ายจาก bare workflow ไป Expo ในภายหลัง** — ถ้าพบว่าภาระการดูแล native build เอง (ที่ bare RN ต้องทำ) สูงเกินกว่าที่ทีมคนเดียวจะรับไหว และมีเหตุผลจำเป็นต้องย้ายไป Expo (เช่น Expo รองรับ native module ที่ต้องการได้ดีขึ้นในอนาคต) **ต้องทบทวนทั้ง Field Client Framework และ Local Persistent Store library พร้อมกัน** เพราะ `op-sqlite` ผูกกับ bare workflow โดยตรง ไม่สามารถเปลี่ยนแค่ชั้นใดชั้นหนึ่งได้
10. **REST + Fastify + NFR-02 (multipart/resumable upload) หรือความต้องการเชื่อมระบบภายนอก (เพิ่มเข้ามา 2026-09-04)** — ถ้าพบว่า Fastify จัดการ multipart/stream สำหรับ resumable upload ไม่เสถียรพอในทางปฏิบัติ หรือถ้าในอนาคตมีความต้องการเชื่อมต่อระบบภายนอกที่ REST ตอบโจทย์ไม่ดีพอ (เช่นต้องการ real-time bidirectional หรือ schema ที่เข้มงวดกว่าแบบ gRPC ตามที่ [[architecture#2.1 ระบบภายนอกและจุดเชื่อมต่อ|architecture §2.1]] เปิดไว้เป็นไปได้) ให้ทบทวน Protocol/Web Framework ใหม่ (Express เป็นตัวเลือกสำรองที่เคยพิจารณาไว้สำหรับกรณีปัญหาความเสถียร ส่วน GraphQL/gRPC ยังไม่เคยถูกประเมินอย่างจริงจังในรอบนี้และต้องเปิดสัมภาษณ์ผู้ใช้ใหม่หากถึงจุดนั้น)

## เอกสารที่เกี่ยวข้อง

- [[backlog]] — FR/NFR ต้นทางทั้งหมดที่ใช้อ้างอิงในหัวข้อ 2-3
- [[architecture]] — ข้อจำกัดเชิงสถาปัตยกรรมที่ตัดสินไปแล้วก่อนชั้นนี้ (§6.1, §6.3, §6.4, §7, §8)
- [[api-spec]] — สัญญาการทำงานเชิง operation contract ที่ Protocol/Web Framework (REST over HTTP + Fastify) ต้องแมปด้วย (§16 ประเด็นรอตัดสินใจ ที่เคยเปิดประเด็น protocol ไว้)
- [[release-plan]] — ขอบเขต Phase 1 ที่กำหนดว่าชั้นใด "ต้องใช้" ในรอบนี้
- [[20260828-01-flood-damage-survey]] — spec ต้นทาง โดยเฉพาะหมวด 6 (ข้อสมมติ/ประเด็นค้างพิจารณา) ที่บล็อกหัวข้อ 4.1
- [[offline-sync]] — การออกแบบ sync/conflict resolution เชิง logical ที่ควรกลับไปตรวจว่ายัง implement ได้จริงบน `op-sqlite` ตามที่บันทึกไว้ในหัวข้อ 3 และ 5
