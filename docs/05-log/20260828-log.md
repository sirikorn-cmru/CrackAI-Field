### รหัส FR/NFR ที่เพิ่ม
เนื่องจากเป็น requirement แรกของโปรเจกต์ (ไม่มีรหัสเดิมมาก่อน) รหัสทั้งหมดต่อไปนี้เป็นรหัสใหม่ทั้งชุด (FR-01 ถึง FR-24, NFR-01 ถึง NFR-08):

- **FR-01 ถึง FR-04**: ข้อมูลทั่วไป/พิกัด GPS/ข้อมูลกายภาพอาคาร/อันตรายสภาพโดยรอบ
- **FR-05 ถึง FR-11**: การประเมินความเสียหายโครงสร้าง (ภายนอก, แยกตามวัสดุ, โครงหลังคา, ส่วนประกอบอาคาร, ระบบไฟฟ้า, สรุปผล 3 สี, การแสดงเกณฑ์อ้างอิงในแอป)
- **FR-12 ถึง FR-15**: ภาพถ่ายและ AI วิเคราะห์รอยร้าว (ถ่ายภาพผูกตำแหน่ง, AI ประเมินความกว้างรอยร้าว, การยืนยันผลโดยผู้สำรวจ (human-in-the-loop), การวาดภาพประกอบ)
- **FR-16 ถึง FR-20**: ผู้สำรวจ การรับรองผล และการมอบหมายงาน (ข้อมูลผู้สำรวจ/หัวหน้าผู้สำรวจ, เวลาสำรวจ, ลายมือชื่อดิจิทัล, การตรวจทาน, การมอบหมายงาน)
- **FR-21 ถึง FR-24**: การจัดการผู้ใช้/สิทธิ์ตามบทบาท, dashboard ภาพรวม, ส่งออกรายงาน, ค้นหา/กรองรายการ
- **NFR-01 ถึง NFR-08**: Availability/Offline Support, Performance/Reliability (sync ภาพขนาดใหญ่), Data Integrity (conflict resolution), Usability/Compatibility (มือถือ/แท็บเล็ต), Auditability, Accuracy, Scalability, Security

### สรุปคำถามที่ถามผู้ใช้และคำตอบที่ได้

ระหว่างงานนี้พบความไม่สอดคล้องสำคัญ: requirement ดิบที่ผู้ใช้พิมพ์มาระบุว่าเป็นเหตุการณ์ "น้ำท่วม" แต่เอกสารต้นทาง PDF ที่มีอยู่ในตอนแรก (`HandBook_CheckEarthQuake.pdf`, `Form_DPT_EarthEquake_Fill_in V1.pdf`) เป็นเรื่อง "แผ่นดินไหว" ล้วน จึงหยุดถามผู้ใช้ก่อนเขียนเอกสาร (ไม่มี AskUserQuestion ในเซสชันนี้ จึงตั้งคำถามผ่านข้อความรายงานกลับ ให้ผู้ประสาน/ผู้ใช้ตอบผ่านช่องทางของตน) คำถาม-คำตอบสรุปได้ดังนี้:

1. **Q1 — ระบบครอบคลุมภัยพิบัติแบบใด**: ผู้ใช้ยืนยันว่าเป็น **"อุทกภัย/น้ำท่วม"** ตามที่พิมพ์มาแต่แรก ไม่ใช่การพิมพ์ผิด และภายหลังผู้ใช้ส่งเอกสารต้นทางเพิ่ม `docs/01-requirements/00-source/Form_DPT_Flood_Survey.pdf` ซึ่งเป็นแบบฟอร์ม DPT ฉบับอุทกภัยตัวจริง ให้ใช้เป็นแหล่งความจริงหลักของโครงสร้างข้อมูล ส่วน PDF แผ่นดินไหว 2 ไฟล์เดิมใช้เป็นเอกสารประกอบ (โดยเฉพาะเกณฑ์ความกว้างรอยแตกร้าวเป็นหน่วยมิลลิเมตร เนื่องจากแบบฟอร์มอุทกภัยอ้างอิงเลขหน้าคู่มือชุดเดียวกัน) ไม่ต้องออกแบบเป็นระบบรองรับหลายภัยพิบัติในตอนนี้
2. **Q2 — ขอบเขตความสามารถ AI**: ผู้ใช้ยืนยันว่าระบบต้องมี AI วิเคราะห์รอยร้าวจากภาพถ่ายเพื่อช่วยวัด/จัดระดับความกว้างรอยแตก โดยต้อง**เสนอผลให้ผู้สำรวจยืนยันเสมอ** (human-in-the-loop ผู้สำรวจตัดสินใจสุดท้าย) → เขียนเป็นกลุ่ม FR-12 ถึง FR-15 แยกชุดของตัวเอง
3. **Q3 — อุปกรณ์และการทำงานออฟไลน์**: ผู้ใช้ยืนยันว่าใช้งานผ่านมือถือ/แท็บเล็ต และต้องรองรับการทำงาน**ออฟไลน์เต็มรูปแบบ** (กรอกครบทุกหมวดโดยไม่มีสัญญาณ แล้ว sync ภายหลัง รวมถึง sync ภาพขนาดใหญ่และจัดการ conflict) → เขียนเป็น NFR-01 ถึง NFR-03 (และ NFR-04 ด้าน mobile) ระดับความสำคัญ **สูง**
4. **Q4 — บทบาทผู้ใช้**: ผู้ใช้ยืนยัน 4 บทบาท: ผู้สำรวจภาคสนาม, หัวหน้าผู้สำรวจ, ผู้ดูแลระบบ, หน่วยงานส่วนกลาง/ผู้บริหาร → สะท้อนในหัวข้อ 3 ของเอกสาร spec และ FR-16 ถึง FR-22

นอกจากนี้ผู้ใช้ระบุว่า footer หน้า 5/5 ของ `Form_DPT_Flood_Survey.pdf` ยังพิมพ์คำว่า "แผ่นดินไหว" ค้างอยู่ (หน้า 1-4 เป็น "อุทกภัย" ถูกต้อง) เป็นข้อผิดพลาดตกค้างในเอกสารต้นฉบับของ DPT เอง ไม่นำมาตีความเป็นข้อกำหนดใดๆ

### เอกสารที่สร้าง

**`docs/02-design/feature-list.md`** — สร้างใหม่ทั้งไฟล์ จัดกลุ่ม FR/NFR ทั้ง 32 รายการเป็น 13 ฟีเจอร์ พร้อมตารางสรุปฟีเจอร์ต้นไฟล์ (คอลัมน์ # / ฟีเจอร์ / คำอธิบายสั้น / MoSCoW / รหัส FR-NFR / บทบาทผู้ใช้) และบรรทัด "ระดับความสำคัญ (MoSCoW): ..." ตรงกับตารางในทุกหัวข้อรายละเอียด:

1. บันทึกข้อมูลอาคารและสภาพแวดล้อม (FR-01–04, NFR-06) — Must have
2. ประเมินความเสียหายโครงสร้างและส่วนประกอบอาคารแยกตามหมวด (FR-05–09) — Must have
3. สรุปผลประเมินเป็น 3 ระดับสีพร้อมเกณฑ์อ้างอิงคู่มือ (FR-10, FR-11) — Must have
4. ถ่ายภาพและวิเคราะห์รอยร้าวด้วย AI (Human-in-the-loop) (FR-12–14, NFR-05) — Must have
5. วาดภาพประกอบเพิ่มเติม (FR-15) — Should have
6. บันทึกข้อมูลผู้สำรวจและระยะเวลาการสำรวจ (FR-16, FR-17) — Must have
7. ตรวจทานและรับรองผลสำรวจด้วยลายเซ็นดิจิทัล (FR-18, FR-19) — Must have
8. มอบหมายงานสำรวจให้ทีม (FR-20) — Should have
9. จัดการผู้ใช้และสิทธิ์การเข้าถึง (FR-21, NFR-08) — Must have
10. Dashboard ภาพรวมผลสำรวจ (FR-22) — Must have
11. ส่งออกรายงานผลการสำรวจ (FR-23) — Should have
12. ค้นหา/กรองรายการอาคารที่สำรวจแล้ว (FR-24) — Should have
13. การทำงานออฟไลน์และซิงค์ข้อมูลภาคสนาม (NFR-01, 02, 03, 04, 07) — Must have

ระดับ MoSCoW ทุกฟีเจอร์ map ตรงจากกฎ สูง→Must/กลาง→Should/ต่ำ→Could และใช้ระดับสูงสุดของรหัสที่ครอบคลุมเมื่อฟีเจอร์มีรหัสปนกันหลายระดับ ไม่มีฟีเจอร์ใดถูกกำหนดเป็น Won't have (ไม่พบเนื้อหาที่บ่งชี้ว่าควรเลื่อนออกจากขอบเขตทั้งหมด) รหัสทั้ง 32 รายการถูกครอบคลุมครบ ไม่มีตกหล่น

**`docs/02-design/user-journey.md`** — สร้างใหม่ทั้งไฟล์ มี 4 journey ตามบทบาทผู้ใช้ทั้ง 4 บทบาท แต่ละ journey มี Mermaid flowchart (`flowchart TD`) กำกับก่อนรายการขั้นตอนข้อความเสมอ ใช้ decision node สำหรับขั้นตอนตามเงื่อนไข (ดูเกณฑ์คู่มือ/มีรอยร้าวให้ AI วิเคราะห์/วาดภาพเพิ่มเติม/แก้ไขสิทธิ์ผู้ใช้/ส่งออกรายงาน) และตรวจสอบให้ node ในแผนภาพตรงกับรายการข้อความ 1:1 ทุก journey:

- Journey: ผู้สำรวจภาคสนามลงพื้นที่สำรวจอาคาร (16 ขั้นตอน, ครอบคลุมฟีเจอร์ 1–6, 13)
- Journey: หัวหน้าผู้สำรวจตรวจทานและรับรองผลสำรวจ (6 ขั้นตอน, ครอบคลุมฟีเจอร์ 7, 8, 12)
- Journey: ผู้ดูแลระบบจัดการผู้ใช้และสิทธิ์ (6 ขั้นตอน, ครอบคลุมฟีเจอร์ 9)
- Journey: หน่วยงานส่วนกลาง/ผู้บริหารติดตามภาพรวมผลสำรวจ (5 ขั้นตอน, ครอบคลุมฟีเจอร์ 10, 11, 12)

ฟีเจอร์ทั้ง 13 รายการจาก feature-list.md ถูกอ้างถึงในอย่างน้อย 1 journey ครบทุกรายการ

### รหัส FR/NFR ที่เพิ่ม
- **FR-25** — ยืนยันตัวตนผู้ใช้ (เข้าสู่ระบบ/ออกจากระบบ) — ระดับ **สูง**
- **FR-26** — บังคับสิทธิ์การเข้าถึงฟังก์ชัน/หน้าจอตามบทบาทหลังเข้าสู่ระบบ — ระดับ **สูง**
- **FR-27** — เข้าสู่ระบบและใช้งานแอปขณะไม่มีการเชื่อมต่ออินเทอร์เน็ต (offline login) — ระดับ **สูง** (สอดคล้องกับ NFR-01)
- **NFR-09** — Security (Offline Session Expiry): กำหนดให้ credential/session ที่แคชไว้สำหรับ FR-27 ต้องมีอายุจำกัดและบังคับยืนยันตัวตนใหม่เมื่อครบกำหนด/กลับมามีสัญญาณ

ทั้ง 4 รหัสไม่ซ้ำกับรหัสเดิม (ต่อจาก FR-24 และ NFR-08 ตามลำดับ)

### การทบทวน FR-21 / NFR-08 เดิม
- **FR-21** (จัดการผู้ใช้และสิทธิ์การเข้าถึงตามบทบาท) — คงระดับ "สูง" และเนื้อหาเดิมทั้งหมด เพิ่มเฉพาะประโยคชี้ไปยัง FR-25–FR-27 ว่าขอบเขตของ FR-21 คือการบริหารจัดการบัญชี/บทบาทโดยผู้ดูแลระบบเท่านั้น ไม่รวมกลไกยืนยันตัวตน/บังคับสิทธิ์ขณะใช้งานจริง เพื่อไม่ให้ทับซ้อนกับรหัสใหม่
- **NFR-08** (Security) — คงเนื้อหาเดิมทั้งหมด เพิ่มประโยคอ้างอิงไปยัง FR-25/FR-26 (กลไกบังคับใช้จริง) และ NFR-09 (กรณีออฟไลน์) เพื่อความชัดเจน ไม่เปลี่ยนความหมายเดิม

### สรุปคำถามที่ถามผู้ใช้และคำตอบที่ได้
ไม่มีการเรียกใช้ AskUserQuestion ในรอบนี้ (ทำงานภายใต้เงื่อนไข auto mode และข้อจำกัดที่ระบุห้ามหยุดงานหากเครื่องมือถามไม่พร้อมใช้งาน) ประเด็นที่ตัดสินใจเองและบันทึกเป็นข้อสมมติในหัวข้อ 6 ของ spec แทนการหยุดถาม:
1. จำนวน FR ที่แตกจากประเด็นนี้ — เลือกแตกเป็น 3 FR (ยืนยันตัวตน/บังคับสิทธิ์ตามบทบาท/เข้าสู่ระบบออฟไลน์) แทนที่จะรวมเป็น FR เดียว เพราะแต่ละอันมีเงื่อนไข acceptance ต่างกันชัดเจน (ออนไลน์ปกติ vs บังคับสิทธิ์ vs ออฟไลน์) และมี FR-26 คาบเกี่ยวกับ FR-21 เดิม จึงเพิ่มประโยคชี้ขอบเขตในทั้งสองจุดแทนการรวมหรือแก้ไข FR-21 ให้ครอบคลุมเพิ่ม
2. ระยะเวลาหมดอายุ credential ออฟไลน์ (NFR-09) — ไม่ระบุตัวเลขตายตัว บันทึกเป็นข้อสมมติค้างพิจารณาแทน
3. กลไกยืนยันตัวตนเฉพาะเจาะจง (FR-25) — ไม่ระบุ (username/password/PIN/biometric ฯลฯ) เนื่องจากยังไม่มี technology-stack.md

1. **node mermaid ↔ รายการข้อความ 1:1 ทั้ง 4 journey** — อ่านไฟล์ `user-journey.md` ทั้งไฟล์ซ้ำอีกครั้งเพื่อยืนยัน โดยเฉพาะ journey ผู้สำรวจภาคสนามที่เพิ่ง insert ขั้นตอนเข้าสู่ระบบเป็นขั้นตอนที่ 1 (17 ขั้นตอน, node A–Q): ตรวจแล้ว node ทุกตัวตรงกับข้อความตามลำดับ 1:1 ครบถ้วน ไม่มี node ตกหล่น/เกิน และ edge ของ decision node ทั้งหมด (F, J, M) ยังครบ 2 กิ่งและลิงก์ถูกต้อง — journey หัวหน้าผู้สำรวจ (7 ขั้นตอน, A–G), ผู้ดูแลระบบ (6 ขั้นตอน, A–F), หน่วยงานส่วนกลาง/ผู้บริหาร (5 ขั้นตอน, A–E) ตรวจแล้วตรงกันทั้งหมดเช่นกัน **ไม่พบความเพี้ยนของลำดับ node ที่กลัวไว้**
2. **เนื้อหาฟีเจอร์ 14 (ยืนยันตัวตนและเข้าสู่ระบบ)** — ตรวจกับข้อความจริงใน spec หัวข้อ 4.6 (FR-25/26/27) และ NFR-09 แล้วตรงกันครบ ไม่มีการตีความผิด
3. **เนื้อหาฟีเจอร์ที่มี FR-21/NFR-08** (ฟีเจอร์ 9 "จัดการผู้ใช้และสิทธิ์การเข้าถึง") — พบว่าคำอธิบายเดิมใช้ประโยค "เพื่อควบคุมว่าใครเข้าถึงข้อมูลส่วนใดของระบบได้บ้าง" ซึ่งเขียนขึ้นก่อนที่ spec รอบก่อนจะแก้ไข FR-21/NFR-08 ให้ระบุขอบเขตชัดเจนว่า FR-21 ครอบคลุมเฉพาะการบริหารจัดการบัญชี/บทบาท ส่วนกลไกบังคับใช้สิทธิ์จริงขณะใช้งาน (enforcement) ย้ายไปอยู่ที่ FR-25/FR-26 (ฟีเจอร์ 14) แล้ว คำอธิบายเดิมจึงคลุมเครือ อาจทำให้เข้าใจผิดว่าฟีเจอร์ 9 ครอบคลุม enforcement ด้วย **แก้ไขแล้ว**: ปรับคำอธิบายและหมายเหตุของฟีเจอร์ 9 ให้ระบุขอบเขตชัดเจนว่าเป็นการบริหารจัดการบัญชี/บทบาทเท่านั้น และชี้ไปยังฟีเจอร์ 14 สำหรับกลไกบังคับใช้จริง (ไม่เปลี่ยนรหัส FR/NFR, บทบาทผู้ใช้ หรือ MoSCoW ของฟีเจอร์นี้)
4. **หมายเหตุ MoSCoW ของฟีเจอร์ 14 เรื่อง NFR-09** — พบข้อความเดิมเขียนว่า "NFR-09 ไม่ระบุระดับความสำคัญแยกในหัวข้อ NFR ของ backlog แต่ผูกอยู่ใต้หัวข้อระดับสูง (MVP) เช่นกัน" ซึ่งชวนเข้าใจผิดว่า NFR-09 มีความกำกวมเรื่องระดับความสำคัญ ทั้งที่จริงแล้ว NFR-09 ถูกระบุไว้ชัดเจนในตาราง "ระดับความสำคัญ สูง (MVP)" ของ backlog เหมือนกับ FR-25/26/27 ทุกประการ (ไม่มีคอลัมน์ priority แยกในตารางเป็นรูปแบบมาตรฐานของ backlog ทั้งไฟล์อยู่แล้ว ไม่ใช่เรื่องเฉพาะของ NFR-09) **แก้ไขแล้ว**: ปรับข้อความหมายเหตุให้ชัดเจนตรงไปตรงมาว่าทั้ง 4 รหัสอยู่ในหมวดสูงเหมือนกันหมด ไม่มีข้อกำกวม
5. **การจัดสรรบทบาทต่อฟีเจอร์เทียบกับ journey ทั้ง 4** — ตรวจไล่ทีละฟีเจอร์ (1–14) เทียบกับบทบาท/ขั้นตอนที่ปรากฏจริงใน journey ทั้ง 4 เส้น พบว่าตรงกันครบทุกฟีเจอร์ (รวมถึงฟีเจอร์ 12 ที่มี 2 บทบาท และฟีเจอร์ 13/14 ที่มีบทบาทหลัก+รองที่ระบุไว้ชัดเจน) ไม่พบความไม่ตรงกัน

## ซิงก์ FR-28/FR-29 (เส้นทาง AI วิเคราะห์รอยร้าวไม่สำเร็จ + กรอกเอง) เข้า feature-list.md และ user-journey.md

### บริบท
`backlog.md` เพิ่มเป็น 38 รายการ (จาก 36) โดย FR-28 (ตรวจจับและแจ้งกรณี AI วิเคราะห์ภาพรอยร้าวไม่สำเร็จ พร้อมทางเลือกถ่ายภาพใหม่) และ FR-29 (กรอกระดับความเสียหายของรอยร้าวด้วยตนเองโดยไม่ต้องพึ่ง AI — เส้นทางปกติ ไม่ใช่ทางออกฉุกเฉิน) อยู่ในตาราง "ระดับความสำคัญ สูง (MVP)" ทั้งคู่ และอยู่ในหัวข้อ 4.3 เดียวกับ FR-12–FR-15 ของ spec (ผู้ประสานยืนยันรหัสปรากฏจริงแล้ว) `requirement-writer` ยังปรับถ้อยคำ FR-13/FR-14 เดิมเพิ่มประโยคชี้ขอบเขตไปยัง FR-28/FR-29 โดยไม่เปลี่ยนความหมายหลัก/ระดับความสำคัญ

### การตัดสินใจ: รวมเข้าฟีเจอร์ 4 เดิม (ไม่แยกฟีเจอร์ใหม่)
พิจารณาแล้วเลือก**รวม FR-28/FR-29 เข้าฟีเจอร์ 4 (ถ่ายภาพและวิเคราะห์รอยร้าวด้วย AI)** แทนการแยกฟีเจอร์ใหม่ เพราะ: (1) อยู่ในหัวข้อ 4.3 เดียวกับ FR-12–FR-14 ทุกประการ ไม่ใช่ความสามารถคนละเรื่อง, (2) เป็นเส้นทางเสริม/ทางเลือกในกระบวนการเดียวกัน (ถ่ายภาพ → ประเมินระดับความเสียหายของรอยร้าว ไม่ว่าจะผ่าน AI หรือกรอกเอง) เกิดขึ้นในหน้าจอ/ขั้นตอนต่อเนื่องเดียวกันจากมุมผู้ใช้จริง ไม่ใช่ฟีเจอร์ที่แยกเปิดใช้งานต่างหาก, (3) การแยกฟีเจอร์จะทำให้ผู้อ่านเข้าใจผิดว่าเป็นความสามารถอิสระจากฟีเจอร์ 4 ทั้งที่ FR-13/FR-14 เองก็เพิ่งถูกแก้ไขให้ระบุชัดว่า "ขอบเขตครอบคลุมเฉพาะกรณี AI สำเร็จ ส่วนกรณีไม่สำเร็จดู FR-28/FR-29" ซึ่งบ่งชี้ว่าเป็นกลุ่มเดียวกันโดยเจตนา

### เอกสารที่แก้ไข

**`docs/02-design/feature-list.md`**
- ปรับชื่อฟีเจอร์ 4 เป็น "ถ่ายภาพและประเมินรอยร้าวด้วย AI พร้อมทางเลือกกรอกเอง (Human-in-the-loop)" ในทั้งตารางสรุปและหัวข้อรายละเอียด พร้อมเพิ่ม FR-28, FR-29 เข้ารหัส FR/NFR ของฟีเจอร์นี้ และเขียนคำอธิบายใหม่ให้ครอบคลุมเส้นทาง AI สำเร็จ/ไม่สำเร็จ/กรอกเอง — MoSCoW ยังคง **Must have** เหมือนเดิม (FR-28, FR-29 อยู่ในหมวดสูงเช่นกัน ไม่กระทบระดับ)
- เพิ่มหมายเหตุอธิบายเหตุผลที่รวมเข้าฟีเจอร์เดิมแทนการแยกฟีเจอร์ใหม่
- อัปเดตหัวข้อ "หมายเหตุการจัดกลุ่ม": จำนวนรหัสรวมเปลี่ยนจาก 36 → **38 รายการ (FR-01–FR-29, NFR-01–NFR-09)** จำนวนฟีเจอร์**ยังคงเป็น 14 ฟีเจอร์เท่าเดิม** (ไม่มีฟีเจอร์ใหม่เกิดขึ้นรอบนี้) พร้อมบันทึกเหตุผลของการรวมไว้ด้วย

**`docs/02-design/user-journey.md`**
- Journey ผู้สำรวจภาคสนาม — แก้ไขทั้ง Mermaid และรายการข้อความให้ตรงกัน 1:1: แทรก decision node ใหม่ 3 จุด (มีรอยร้าวที่ต้องบันทึกระดับความเสียหายหรือไม่ / ต้องการให้ AI ช่วยวิเคราะห์ก่อนหรือไม่ / AI วิเคราะห์สำเร็จหรือไม่) และ action node ใหม่ 2 จุด (แจ้งสาเหตุ AI ไม่สำเร็จ+เสนอถ่ายใหม่ FR-28 / กรอกระดับความเสียหายด้วยตนเอง FR-29) พร้อม decision "ต้องการถ่ายภาพใหม่หรือไม่" ที่วนกลับไปยังขั้นตอนถ่ายภาพเดิมเมื่อเลือกถ่ายใหม่ — journey นี้ขยายจาก 17 เป็น **22 ขั้นตอน** (node A–V) ตรวจยืนยันแล้วว่า node ทุกตัวตรงกับข้อความ 1:1 ไม่มีตกหล่น/เกิน
- Journey อื่นอีก 3 เส้น (หัวหน้าผู้สำรวจ, ผู้ดูแลระบบ, หน่วยงานส่วนกลาง/ผู้บริหาร) **ไม่มีการแก้ไข** เนื่องจาก FR-28/FR-29 เกี่ยวข้องเฉพาะกระบวนการถ่ายภาพ/ประเมินรอยร้าวของผู้สำรวจภาคสนามเท่านั้น
- อัปเดตหัวข้อ "สรุปการครอบคลุมฟีเจอร์" เพิ่มย่อหน้าอธิบายการขยายฟีเจอร์ 4 และจำนวนขั้นตอนใหม่ของ journey ผู้สำรวจภาคสนาม

## NEEDS_NEW_REQUIREMENT

ระหว่างเขียน Acceptance Criteria ของ **FR-13 (วิเคราะห์ภาพถ่ายรอยร้าวด้วย AI)** ในฟีเจอร์ 4 ("ถ่ายภาพและวิเคราะห์รอยร้าวด้วย AI (Human-in-the-loop)") พบสถานการณ์ที่ไม่มี FR/NFR ใดใน backlog ระบุพฤติกรรมของระบบไว้เลย:

- **สถานการณ์ที่ยังไม่มีคำตอบ**: เมื่อผู้สำรวจสั่งให้ AI วิเคราะห์ภาพถ่ายรอยร้าว (ตาม FR-13) แต่ AI ไม่สามารถวิเคราะห์ภาพนั้นได้สำเร็จ ด้วยเหตุผลเช่น (1) ภาพเบลอ/แสงไม่เพียงพอ/มุมถ่ายไม่เหมาะสม จนคุณภาพภาพไม่พอให้ประมวลผล หรือ (2) ภาพนั้นไม่มีรอยร้าวปรากฏอยู่จริง (ผู้สำรวจถ่ายผิดตำแหน่ง/AI ตรวจไม่พบ) — ปัจจุบันทั้ง FR-13, FR-14 และ NFR-05 อธิบายเฉพาะกรณี AI วิเคราะห์สำเร็จแล้วเสนอผลตั้งต้นให้ผู้สำรวจยืนยัน/แก้ไขเท่านั้น ไม่มีข้อความใดใน spec/backlog/feature-list ที่ระบุว่าระบบควรแสดงผลอย่างไรเมื่อ AI วิเคราะห์ไม่สำเร็จ หรือผู้สำรวจควรมีทางเลือกอย่างไรต่อ (เช่น กรอกผลประเมินความกว้างรอยร้าวด้วยตนเองแทน ให้ถ่ายภาพใหม่ หรือข้ามการวิเคราะห์ AI ไปเลย)
- **เหตุผลที่ควรเป็น FR/NFR ใหม่แยกต่างหาก**: นี่ไม่ใช่ negative case ทั่วไปที่ตีความได้จากหลักการทั่วไป (เช่น required field validation) แต่เป็นพฤติกรรมเฉพาะของ AI pipeline ที่กระทบ workflow หลักของฟีเจอร์ที่มีความเสี่ยงสูงสุดของระบบนี้ (human-in-the-loop ของ AI ตามที่ระบุไว้ในบริบทงาน) หากไม่มี FR กำกับไว้ชัดเจน ทีมพัฒนาอาจเลือก fallback ไม่สอดคล้องกัน (เช่น บล็อกผู้สำรวจไม่ให้ทำงานต่อ ซึ่งขัดกับเป้าหมายการทำงานภาคสนามที่ต้องรวดเร็ว) จึงควรมี FR ใหม่ (หรือส่วนขยายของ FR-13/FR-14) ที่ระบุพฤติกรรม fallback ของระบบเมื่อ AI วิเคราะห์ภาพไม่สำเร็จ รวมถึงเส้นทางให้ผู้สำรวจกรอกผลประเมินด้วยตนเองแทนเพื่อไม่ให้งานสำรวจหน้างานสะดุด

### การตัดสินใจเรื่อง `client_generated_id` ของ entity ย่อย (ปิดช่องว่างข้อ 4 และ 5)
เลือก **เพิ่ม attribute ให้ entity ย่อยทั้ง 6 ตัว** (ไม่ใช่ตัดการอ้างอิงออกจาก api-spec 14.1) เพราะพบเหตุผลเชิงโครงสร้างที่จำเป็นเกินกว่าจะตัดออก: `DamagePhoto.linked_area_id` ต้องอ้างอิง `StructuralDamage`/`ComponentDamage`/`ExternalDamage` ตั้งแต่ตอนถ่ายภาพขณะยังออฟไลน์อยู่ (ก่อนซิงค์) จึงต้องมี id ที่เสถียรตั้งแต่สร้างบนอุปกรณ์ — แต่เพื่อไม่ให้ทับซ้อนกับช่องว่างเดิม **แยกขอบเขตชัดเจนเป็น 2 concept**: `client_generated_id` ของ entity ย่อยมีไว้เพื่อ **idempotent upsert + referential stability** เท่านั้น ส่วนการ**ตรวจจับความขัดแย้ง (conflict detection) ยังคงอยู่ที่ระดับ `SurveyedBuilding` (aggregate) เพียงจุดเดียว** ผ่าน `data_version`/`last_modified_at`/`last_modified_by_device_id` ของอาคารแม่ (การแก้ไข entity ย่อยใดๆ ทำให้ `data_version` ของอาคารแม่เพิ่มขึ้นเสมอ) — เหตุผล: ทีมสำรวจกรอกแบบฟอร์มทั้งชุดในช่วงเวลาเดียวกันบนอุปกรณ์เดียว ไม่มี use case ที่สองอุปกรณ์แก้ไข entity ย่อยคนละแถวของอาคารเดียวกันพร้อมกันโดยไม่แตะอาคารแม่ด้วย เขียนเหตุผลนี้ไว้ชัดเจนในทั้งสองไฟล์ (db-spec หัวข้อ 10 ข้อ 2-3, api-spec 14.1) ให้ nfr-review รอบหน้าตรวจสอบได้ว่าเพียงพอ

### ผลการปิดช่องว่าง 5 จุด
1. **ปิดแล้ว** — เพิ่ม operation 10.1 "ส่งแบบสำรวจเข้าสู่คิวตรวจทาน" ครอบคลุมทั้ง `ฉบับร่าง→รอตรวจทาน` และ `ส่งกลับแก้ไข→รอตรวจทาน` (ส่งซ้ำ)
2. **ปิดแล้ว** — เพิ่ม operation 2.4 "เปิดใช้งานบัญชีผู้ใช้คืน"
3. **ปิดแล้ว** — เพิ่ม operation 3.3 "เปลี่ยนสถานะงานมอบหมาย" (บังคับลำดับเดินหน้า มอบหมายแล้ว→กำลังดำเนินการ→เสร็จสิ้น)
4. **ปิดแล้ว** — เพิ่ม `client_generated_id` ให้ entity ย่อย 6 ตัวใน db-spec ให้ตรงกับที่ api-spec 14.1 อ้างอิงอยู่แล้วตั้งแต่รอบแรก
5. **ปิดแล้ว** — เขียนขอบเขตการตรวจจับความขัดแย้ง (aggregate-level ที่ `SurveyedBuilding`) ให้ชัดเจนในทั้งสองไฟล์ พร้อมเหตุผลประกอบ ให้ `nfr-review` ตัดสินได้ว่า NFR-03 รองรับครบหรือยัง
