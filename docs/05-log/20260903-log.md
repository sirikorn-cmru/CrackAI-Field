### บริบท

`/audit-pipeline` (ก่อนหน้านี้) ตรวจพบว่า NFR-05 กำหนดให้เก็บประวัติ "เพื่อการตรวจสอบย้อนหลัง" แต่ทั้งระบบไม่มีช่องทางอ่านเลย ผู้ใช้จึงเพิ่ม FR-32 (เรียกดูประวัติการแก้ไขผลประเมินรายอาคาร) และ FR-33 (ค้นหา/กรองประวัติทั่วทั้งระบบ) เป็น FR ใหม่ ระดับความสำคัญกลางทั้งคู่ เอกสารทุกชั้น (AC/TC, architecture, api-spec, db-spec, detailed-design, prototype) sync ครบแล้วก่อนหน้านี้ เหลือเพียงแผน phase/task ที่ยังไม่ได้จัด — `backlog.md` มี 43 รหัส (FR-01–FR-33, NFR-01–NFR-10) แต่ `release-plan.md`/`03-task/` เดิม (เขียนไว้ 2026-09-01) ครอบคลุมเพียง 41 รหัส

### แผนที่เสนอ (subagent วิเคราะห์)

เสนอให้ใส่ FR-32 และ FR-33 เข้า **Phase 4 เดิม** (ไม่สร้าง Phase 5 ใหม่) โดยให้เหตุผลหลัก:

1. Dependency ของ FR-32 (เหตุการณ์จาก FR-14/Phase 3, FR-18-19/Phase 2, FR-31/Phase 4, sync-conflict/Phase 1) ครบสมบูรณ์ที่สุดที่ปลาย Phase 4 เพราะ FR-31 (ชิ้นสุดท้ายของห่วงโซ่) อยู่ Phase 4 อยู่แล้ว
2. สิทธิ์การเข้าถึงของ FR-32/33 (หัวหน้าผู้สำรวจ/ผู้ดูแลระบบ/หน่วยงานส่วนกลาง) ตรงกับกลุ่มบทบาท back-office เดียวกับรหัสอื่นใน Phase 4 ทั้งหมด
3. FR-33 มีลักษณะเป็นเครื่องมือค้นหา/กรองแบบเดียวกับ FR-24 ที่มีอยู่แล้วใน Phase 4 เพียงเปลี่ยนขอบเขตข้อมูล

ทางเลือกที่พิจารณาแล้วไม่เลือก:
- **สร้าง Phase 5 ใหม่** — ปฏิเสธเพราะ Phase 5 จะต้องรอทั้ง Phase 3 และ Phase 4 มาบรรจบ ทำลายคุณสมบัติ "Phase 3/4 ทำขนานกันได้" ที่แผนเดิมระบุไว้ชัด กลายเป็นเพิ่มคอขวดเพื่อ 2 รหัสระดับกลางเท่านั้น เกินความจำเป็น
- **แยก FR-32 เข้า Phase 4 แล้วเลื่อน FR-33 ออก** — ไม่ได้เลือก (ผู้ใช้ยืนยันแนวทาง "Phase 4 ทั้งคู่" ตามที่เสนอ)

ระบุหมายเหตุเชิงลำดับไว้ในเอกสารด้วยว่า: หน้าประวัติของ FR-32 จะแสดงเหตุการณ์แก้ไขผล AI ได้ครบก็ต่อเมื่อ Phase 3 ทำเสร็จแล้วเช่นกัน จึงสนับสนุนคำแนะนำเดิมของแผนว่าควรทำ Phase 3 ก่อน Phase 4 เมื่อทรัพยากรจำกัด (ไม่ใช่ hard build gate — ไม่แก้ผัง Mermaid)
