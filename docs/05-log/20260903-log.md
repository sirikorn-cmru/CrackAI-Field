## `/sync-technology-stack` — สร้าง `technology-stack.md` ครั้งแรก ตัดสินใจครบ 5 ชั้นของ Phase 1 (ผ่าน subagent `technology-stack-writer`)

### บริบท
`technology-stack.md` ยังไม่มีไฟล์มาก่อน (ไม่เคยมี manifest/โค้ด/CI ใดๆ ในโปรเจกต์) — ขอบเขตรอบนี้จำกัดเฉพาะ 5 ชั้นที่ [[release-plan|Phase 1]] ต้องใช้ (Field Client Framework, Local Persistent Store, Server-side Runtime, Primary Data Store, Media/Object Storage) ไม่เร่งตัดสินชั้น runtime ของโมเดล AI เพราะ Phase 1 ไม่มีรหัสเกี่ยวกับ AI เลย (FR-21, FR-25, FR-26, FR-27, NFR-01–04, NFR-07–09)

### กระบวนการถามผู้ใช้
`AskUserQuestion` ใช้ไม่ได้ในเซสชัน subagent เหมือนเดิม — วิเคราะห์ตาราง NFR/FR บีบตัวเลือกแต่ละชั้นก่อน (ระบุว่า Field Client Framework ถูกบีบมากที่สุดจาก NFR-01/02/04/09 พร้อมกัน, Primary Data Store บีบปานกลางจาก NFR-03/07, Server-side Runtime บีบน้อยที่สุด) แล้วเสนอตัวเลือกอย่างน้อย 3 ทางต่อชั้นพร้อมข้อดี/ข้อเสีย/ตัวแนะนำ ส่งกลับให้ coordinator/เทรดหลักถามผู้ใช้แทนผ่าน `AskUserQuestion` 3 รอบ

### บริบทผู้ใช้ที่ได้จากการถาม
ทีมพัฒนาคนเดียว ถนัด JavaScript/TypeScript และ Python อุปกรณ์ภาคสนามเป้าหมาย Android เป็นหลัก (ยังไม่ยืนยันรุ่น) ยังไม่ได้คุยกับหน่วยงาน (กรมโยธาธิการและผังเมือง) เรื่อง hosting/data residency

### การตัดสินใจครบ 5 ชั้น

| ชั้น | เลือก | ตัวแนะนำเดิมที่ไม่ได้เลือก |
|---|---|---|
| Field Client Framework | React Native | Flutter (แนะนำเพราะ native ARM/ตอบ NFR-04 ตรงกว่า — ผู้ใช้เลือก RN เพราะทีมถนัด JS/TS อยู่แล้ว) |
| Local Persistent Store | SQLite ผ่าน library ของ React Native (ยังไม่เลือก library ตัวใดตัวหนึ่ง) | — |
| Server-side Runtime | Node.js / TypeScript | Python (แนะนำเผื่ออนาคตทำ Server-side AI — ผู้ใช้เลือก Node.js เพราะใช้ภาษาเดียวกับ client ได้) |
| Primary Data Store | MySQL / MariaDB | PostgreSQL (แนะนำเพราะตรงกับ db-spec entity-relationship มากกว่า — ผู้ใช้เลือก MySQL/MariaDB โดยรับทราบข้อเสีย) |
| Media/Object Storage | Local filesystem บนเซิร์ฟเวอร์ | S3-compatible object storage (แนะนำเพราะ resumable upload มาให้พร้อมใช้ตรง NFR-02 — ผู้ใช้เลือก local filesystem โดยรับทราบว่าต้องเขียน resumable upload เอง) |

ไม่มีเลขเวอร์ชันใดถูกระบุ (ผู้ใช้ไม่ได้ระบุ) ไม่มีชื่อ library/ORM/queue/framework เว็บฝั่งผู้ดูแลถูกเติมเข้าไปเอง

### ชั้นที่ยังไม่ตัดสินใจ (พร้อมเงื่อนไข)
1. **Runtime ของโมเดล AI + รูปแบบไฟล์โมเดล** — บล็อกโดยข้อสมมติ 2 และ 8 ในหมวด 6 ของ spec (ยังไม่มีโมเดล ไม่มีชุดข้อมูล) บล็อกเฉพาะ Phase 3 ไม่บล็อก Phase 1-2
2. **Hosting/deployment target** — รอคุยกับหน่วยงาน กระทบวิธี deploy ของ Server-side Runtime, Primary Data Store, Media/Object Storage (ไม่กระทบชื่อเทคโนโลยีที่เลือกไปแล้ว)
3. **Library เฉพาะตัวสำหรับ SQLite บน React Native** — ผู้ใช้เลือกแค่ระดับ "SQLite" ยังไม่เลือก library เจาะจง บล็อกการเริ่มเขียนโค้ดจริงของ Local Persistent Store

### เกณฑ์ทบทวนที่บันทึกไว้ (7 ข้อ ดูรายละเอียดเต็มในไฟล์)
React Native กับ NFR-04 (ต้องทดสอบอุปกรณ์จริงไม่ใช่ emulator), React Native กับ NFR-02 (background upload อาจต้องพึ่ง native module), React Native กับ AI on-device ตาม architecture §6.1 (ต้องทบทวนทั้งชั้นถ้า on-device inference ทำไม่ได้ดีพอ), Android-first แต่เลือก cross-platform (ทบทวนถ้ายืนยันไม่ต้องรองรับ iOS), local filesystem + hosting ที่ยังไม่ทราบ (อาจต้องรื้อโค้ดย้ายไป object storage), MySQL/MariaDB กับ FR-33 ปริมาณมาก (ทบทวนกลยุทธ์ดัชนี/read replica), ทีมขยายจากคนเดียว/ทักษะทีมเปลี่ยน (ทบทวน Server-side Runtime)

3. **§8 ประเด็นรอตัดสินใจ** — เขียนใหม่ทั้งหัวข้อ (รายละเอียดด้านล่าง)

### §8 — สิ่งที่ลบออก (ตัดสินใจแล้วจริง)
- "เทคโนโลยี/แพลตฟอร์มของ Field Client App (native / cross-platform) และกลไกเก็บข้อมูล/ไฟล์ในเครื่องแบบ persistent" — ลบทั้งข้อ (ปิดแล้ว: React Native + SQLite)
- "เทคโนโลยีของ Backend Service, Primary Data Store, และ Media/Object Storage" — ลบทั้งข้อ (ปิดแล้ว: Node.js/TypeScript, MySQL/MariaDB, Local filesystem)

### §8 — สิ่งที่คงไว้ (ยังไม่ตัดสินใจจริง) พร้อมเพิ่มลิงก์อ้างอิง
- รูปแบบ/โปรโตคอลการซิงค์ข้อมูลระหว่าง Field Client กับ Sync Service (FR-30/NFR-03) — คงเดิม ไม่มีคำตอบใน technology-stack.md
- Runtime ของโมเดล AI + รูปแบบไฟล์โมเดล — คงเดิม เพิ่มลิงก์ไปยัง `technology-stack.md` §4.1 และ §6.1 ของเอกสารนี้เอง
- กลไกยืนยันตัวตน/ออก session ที่เป็นรูปธรรม (NFR-09) — คงเดิม ระบุเพิ่มว่า framework/runtime หลักถูกเลือกแล้วแต่กลไก/library เฉพาะยังไม่ตัดสิน
- รูปแบบไฟล์ที่ใช้ส่งออกรายงาน (FR-23) — คงเดิม
- แนวทาง hosting/deployment (NFR-07 ในทางปฏิบัติ) — คงเดิม เพิ่มลิงก์ไปยัง `technology-stack.md` §4.2 พร้อมระบุชัดว่ากระทบวิธี deploy ของ Server-side Runtime/Primary Data Store/Media Storage ที่เลือกชื่อ stack ไปแล้ว แต่ไม่กระทบชื่อเทคโนโลยี
- รูปแบบการจัดทำดัชนี/กลยุทธ์การค้นหาสำหรับ FR-33 — คงเดิม เพิ่มลิงก์ไปยัง `technology-stack.md` §6 ข้อ 6

### §8 — สิ่งที่เพิ่มใหม่
- **Library เฉพาะตัวสำหรับ SQLite บน React Native** — ยังไม่มีข้อนี้ในเวอร์ชันเดิม (ผู้ใช้เลือกไว้เพียงระดับ "SQLite" ยังไม่เลือก library ตัวใดตัวหนึ่ง) เพิ่มเป็นรายการใหม่ พร้อมลิงก์ไปยัง `technology-stack.md` §4.3 และระบุว่าบล็อกเฉพาะการเริ่มเขียนโค้ดจริง ไม่บล็อกงานออกแบบระดับ logical

### จุดที่ตัดสินใจ**ไม่**ใส่ชื่อ stack และเพราะอะไร
- **§2 (ตาราง Logical Component) และ §3 (Component Diagram)** — ไม่เพิ่มชื่อ stack ใดๆ เข้าไป เพราะชื่อ component เชิงตรรกะ (Field Client App, Backend Service, Primary Data Store ฯลฯ) ยังสื่อความหมายได้ครบโดยไม่ต้องพึ่งชื่อจริง และ `technology-stack.md` มีเอกสารของตัวเองอยู่แล้วสำหรับรายละเอียดนี้ — การไล่ใส่ชื่อ framework ในทุก component จะทำให้เอกสารนี้ล้าสมัยเร็วขึ้นถ้า stack เปลี่ยนในอนาคต (เช่น React Native ถูกทบทวนใหม่ตามเกณฑ์ในหัวข้อ 6 ของ technology-stack.md) โดยไม่ได้เพิ่มความเข้าใจอย่างมีนัยสำคัญให้ผู้อ่านที่อ่าน architecture.md เพื่อดูภาพรวมเชิงโครงสร้าง
- **§4/§5/§5.5/§6.2-6.7/§7 (Data Flow, NFR mapping, cross-cutting, เหตุผลการตัดสินใจอื่น, ข้อสมมติ)** — ไม่แก้ไขเนื้อหาเหล่านี้เลย เพราะไม่มีข้อความใดในส่วนนี้ที่กลายเป็นเท็จหรือขัดแย้งจากการตัดสินใจ stack — ตรวจแล้วพบว่าการเลือก MySQL/MariaDB (relational) สอดคล้องกับสมมติฐานเดิมใน §6.5/NFR-03 (เก็บหลายเวอร์ชันที่ขัดแย้งในระเบียนเดียว, เปรียบเทียบ version/timestamp) และ §6.4 (แยก Primary Data Store กับ Media/Object Storage) พอดี ไม่มีความขัดแย้ง
- **§7 ข้อสมมติ** — ตรวจครบทั้ง 7 ข้อแล้วว่ามีข้อใดถูกตอบแล้วจากการตัดสินใจ stack หรือไม่ **ไม่พบข้อใดที่ตอบได้แล้ว** — ทุกข้อสมมติยังเป็นเรื่องระดับ business/spec (เกณฑ์ AI, ระยะเวลาหมดอายุ session เป็นตัวเลข, SLA, จำนวน/ขนาดภาพ, ระยะเก็บ audit trail, ขอบเขตทีม/อาคาร) ไม่ใช่เรื่องที่ tech stack ตอบได้ (แม้ NFR-09 ใน technology-stack.md จะยืนยันว่า React Native มี API เข้าถึง secure storage ระดับ OS ได้ แต่นั่นตอบแค่ "ทำได้ทางเทคนิคหรือไม่" ไม่ได้ตอบ "ตัวเลขอายุ session ควรเป็นเท่าไร" ที่เป็นข้อสมมติจริง) จึงไม่แก้ §7

### ตรวจย้อนกลับ: พบความขัดแย้งระหว่าง `architecture.md` กับ `technology-stack.md` หรือไม่
**ไม่พบ** — ตรวจครบทุกจุดที่ทั้งสองไฟล์อ้างถึงกัน (§6.4 แยก storage, NFR-03 versioning, NFR-07 queue/concurrent write, NFR-09 secure storage) การตัดสินใจ stack ทุกชั้นสอดคล้องกับข้อจำกัดที่ architecture ตัดสินไว้ก่อนหน้า ไม่มีจุดที่ต้องรายงานกลับให้แก้ฝ่ายใดฝ่ายหนึ่ง

### สรุปรายการ "สิ่งที่เปลี่ยน" ที่ต้องส่งต่อให้ชั้น api-spec/db-spec (ชั้นที่ 2/4 ของ `/sync-technical-spec`)
1. Primary Data Store ถูกตัดสินเป็น **relational (MySQL/MariaDB)** แล้ว — `api-spec.md`/`db-spec.md` ควรตรวจหัวข้อ "ประเด็นรอตัดสินใจ" ของตัวเองว่ามีข้อใดผูกกับชนิด database (relational vs document) ที่ตอนนี้ปิดได้แล้วหรือไม่ (ตามที่ `technology-stack.md` §5 ระบุไว้)
2. **Library เฉพาะตัวสำหรับ SQLite บน React Native ยังไม่ตัดสินใจ** — ถ้า `db-spec.md`/`api-spec.md` มีส่วนอ้างถึงกลไก local persistence ฝั่ง client ให้คงเป็น logical ต่อไป ยังอ้างชื่อ library เจาะจงไม่ได้

4. **Hosting/deployment ยังไม่ทราบ** — ไม่กระทบโครงสร้าง logical ของ api-spec/db-spec โดยตรง แต่เป็นบริบทที่ควรรู้ไว้เผื่อมีข้อจำกัดจาก data residency ในอนาคต
5. ไม่มีการเปลี่ยนแปลงใดใน Component/Data Flow/NFR Mapping ของ architecture.md เอง — ชั้น api-spec/db-spec จึงไม่จำเป็นต้องปรับโครงสร้าง entity/operation ใดๆ เพราะเหตุผลจากรอบนี้ (เป็นเพียงการอัปเดตหมายเหตุ/ประเด็นรอตัดสินใจ)

### บริบท
สืบเนื่องจากชั้นที่ 1/4 (`architecture-writer`) ด้านบน — รับรายการส่งต่อ 5 ข้อ ขอบเขตงานนี้แคบมาก: แก้เฉพาะข้อความที่กลายเป็นเท็จ 1 จุดต่อไฟล์ (หมายเหตุต้นเอกสารที่อ้างว่า `technology-stack.md` ยังไม่มีเนื้อหา) และทบทวนหัวข้อ "ประเด็นรอตัดสินใจ" ของทั้งสองไฟล์ **ห้ามแก้ operation/entity/attribute ใดๆ**

จุดสำคัญที่ต้องระวัง: การเลือก Server-side Runtime = Node.js/TypeScript **ไม่ใช่** การเลือก protocol/web framework — `api-spec.md` ต้องคง Operation Contract แบบไม่ผูก protocol ต่อไป ส่วน `db-spec.md` ประเด็น "SQL หรือ NoSQL" ปิดได้แล้วเพราะ Primary Data Store เป็น MySQL/MariaDB (relational) แต่ห้ามไล่แปลงชนิดข้อมูลเชิงตรรกะเป็น SQL type

### ผลตรวจ (รอบตรวจที่ 6 ของ `nfr-review.md`)

**เปลี่ยนจากรอบที่ 5**: มีเพียง **NFR-02 ตัวเดียว** ที่ลดระดับ (รองรับแล้ว → รองรับบางส่วน) จาก 10/10 รองรับแล้ว เหลือ **9 รองรับแล้ว (NFR-01, 03, 04, 05, 06, 07, 08, 09, 10) + 1 รองรับบางส่วน (NFR-02)**

**เหตุผลการลดระดับ NFR-02**: รอบตรวจก่อนหน้าปัดช่องว่างเรื่อง resumable/chunked upload ไว้เป็น "ประเด็นรอ `technology-stack.md` ตัดสินใจ ไม่ใช่ช่องว่างเชิง logical" โดยสมมติว่าถ้าเลือก object storage ความสามารถ resumable/multipart upload จะได้มาโดยอัตโนมัติ — สมมตินั้นพังลงเพราะผู้ใช้เลือก **local filesystem บนเซิร์ฟเวอร์** และ `technology-stack.md` บันทึกไว้เองว่า resumable upload "ต้องเขียนเอง ไม่ได้มาฟรี" ไล่ตรวจโมเดลข้อมูลจริงพบว่า `DamagePhoto`/`Sketch` มี `sync_status` เพียง 4 ค่า ไม่มี attribute ใดเก็บ byte offset/chunk ที่ส่งสำเร็จไปแล้ว และ `detailed-design/offline-sync.md` §3 (state diagram) เขียนว่า "ทำต่อได้ภายหลัง ไม่ต้องเริ่มใหม่ทั้งหมด" ทั้งที่ transition กลับไปที่ `ยังไม่ซิงค์` เท่านั้น (สถานะเดียวกับไฟล์ที่ไม่เคยส่งเลย) — ข้อความในเอกสารกับโมเดลข้อมูลจึงขัดกันเอง เป็นช่องว่างแบบเดียวกับที่เคยพบใน NFR-04/NFR-07 ("map ไว้ในตารางแต่ไม่มีกลไกจริงรองรับ") ไม่ใช่เพราะ local filesystem ด้อยกว่า object storage ที่เคยถูกแนะนำ (ผู้ใช้เลือกโดยรู้ข้อแลกเปลี่ยนแล้ว) แต่เพราะสมมติฐานที่เคยใช้ปัดช่องว่างนี้ไม่เป็นจริงอีกต่อไป — ยึดตามกฎที่กำชับมาว่า "ห้ามลดระดับเพียงเพราะ stack ต่างจากที่เคยแนะนำ ต้องมีเหตุผลเชิงเทคนิคที่ยืนได้"

**อีก 9 ตัวคงรองรับแล้ว** พร้อมข้อสังเกตความเสี่ยง implementation ที่ไม่บล็อกสถานะ 2 จุด (ทั้งคู่ `technology-stack.md` บันทึกไว้แล้วเองพร้อมเกณฑ์ทบทวน ไม่ใช่ช่องว่างเอกสารใหม่):
- **NFR-04**: React Native ยังตอบโจทย์ edge case เชิง logical ที่ออกแบบไว้ (ไม่ขึ้นกับ framework) แต่พบว่า `detailed-design/offline-sync.md` ออกแบบไว้แค่ "คิวทำงานต่อได้เมื่อ**เปิดแอปใหม่**" ซึ่งอ่อนกว่า "true background upload ขณะแอปปิดอยู่เบื้องหลัง" — ถ้าเจตนาจริงต้องการ background upload จะต้องมี native module เพิ่มตามที่ `technology-stack.md` §6 ข้อ 2 เตือนไว้แล้ว เป็นข้อสังเกตที่ต้องยืนยันเจตนากับผู้ใช้ ไม่ใช่สิ่งที่ nfr-reviewer ตัดสินใจแทนได้
- **NFR-07**: Node.js (เหมาะกับ I/O-bound concurrent) + local filesystem บนเซิร์ฟเวอร์เดียว หมายความว่าไม่มีทางขยายกำลังรับไฟล์ในแนวนอนได้โดยไม่รื้อสถาปัตยกรรมการเก็บไฟล์ — ความเสี่ยงนี้ `technology-stack.md` §6 ข้อ 5 บันทึกไว้แล้วพร้อมคำแนะนำ (เขียน abstraction layer แยกไว้แต่ต้น)

ยืนยันเพิ่มเติมว่า React Native เข้าถึง secure storage ระดับ OS (Android Keystore) ได้จริงผ่าน native module ที่มีอยู่แล้วในระบบนิเวศ (NFR-09), SQLite+MySQL/MariaDB ยังตอบโจทย์ offline-first และ versioning/conflict detection ตามที่ออกแบบไว้ (NFR-01/NFR-03), ส่วน NFR-05/06/08/10 เป็น business logic ที่ไม่ผูกกับ stack เฉพาะเจาะจง ไม่มีผลกระทบ

## `/sync-api-db` (ขอบเขตแคบ) — ปิดช่องว่าง NFR-02 (resumable upload) ที่ `nfr-reviewer` ลดระดับเป็น "รองรับบางส่วน" (ผ่าน subagent `api-db-writer`)

### บริบท
สืบเนื่องจากผลตรวจรอบที่ 6 ของ `nfr-review.md` ด้านบน — สมมติฐานเดิมที่ปัดเรื่อง resumable/chunked upload ไว้ว่า "รอ `technology-stack.md` ตัดสินใจ" (สมมติว่าเลือก object storage แล้วได้ resumable upload มาฟรี) พังลงเพราะผู้ใช้เลือก **local filesystem บนเซิร์ฟเวอร์** ซึ่ง `technology-stack.md` บันทึกไว้เองว่า resumable upload "ต้องเขียนเอง" ตรวจยืนยันข้อขัดแย้งที่ผู้เรียกใช้ระบุมาทั้ง 4 จุดแล้วตรงจริง: (1) `detailed-design/offline-sync.md` บรรทัด 24 (sequence diagram) อ้างว่า "รองรับทำต่อได้" (2) บรรทัด 76 (ตาราง edge case) อ้างแบบเดียวกัน (3) แต่บรรทัด 58 (state diagram) transition `กำลังซิงค์ --> ยังไม่ซิงค์` เมื่อไฟล์ส่งไม่สำเร็จบางส่วน คือกลับไปสถานะเริ่มต้นเดียวกับไฟล์ที่ไม่เคยส่งเลย (4) `db-spec.md` §6.1 `DamagePhoto` มี `sync_status` เพียง 4 ค่า ไม่มี attribute เก็บตำแหน่งที่ส่งสำเร็จ — ขอบเขตงานจำกัดเฉพาะ `db-spec.md`/`api-spec.md` เท่านั้น **ห้ามแตะ** `detailed-design/offline-sync.md` (คนละเจ้าของ) ให้รายงานกลับแทน

### การออกแบบ (ตอบคำถาม "ส่งสำเร็จไปเท่าไรแล้ว" + "อ้างอิงรอบการอัปโหลดใด")

**`db-spec.md` — เพิ่ม 4 attribute ใหม่ ให้ทั้ง 2 entity ที่เก็บไฟล์ (ตรวจแล้วไม่มี entity อื่นที่ต้องการความสามารถนี้ — `CertificationRecord.digital_signature_file` ไม่เข้าเงื่อนไขเพราะ operation ที่สร้างมัน (10.3) ต้องมีสัญญาณอินเทอร์เน็ตอยู่แล้ว ไม่ได้อยู่ในรายการ entity ที่ 14.1 ซิงค์แบบออฟไลน์):**

- **§6.1 `DamagePhoto`** และ **§6.3 `Sketch`** — เพิ่มต่อจาก `sync_status` เดิมทั้งคู่:
  - `upload_session_id` (ตัวระบุเฉพาะ, ไม่ (จำเป็นเมื่อ `sync_status = กำลังซิงค์`)) — รหัสรอบการอัปโหลดไฟล์นี้ปัจจุบัน ใช้แยกรอบที่กำลังส่งต่อจากรอบที่ต้องล้างแล้วเริ่มใหม่ — ตอบคำถาม "อ้างอิงรอบการอัปโหลดใด"
  - `total_file_size_bytes` (ตัวเลข, ใช่) — ขนาดไฟล์ทั้งหมดที่ทราบแล้วบนอุปกรณ์ก่อนเริ่มอัปโหลด เป็นตัวส่วนเทียบกับ `uploaded_bytes`
  - `uploaded_bytes` (ตัวเลข, ไม่ (จำเป็นเมื่อ `sync_status = กำลังซิงค์`)) — จำนวนไบต์ที่เซิร์ฟเวอร์ยืนยันว่าได้รับสำเร็จแล้วในรอบปัจจุบัน — ตอบคำถาม "ส่งสำเร็จไปเท่าไรแล้ว" และเป็นตำแหน่งกลับมาส่งต่อ
  - `last_chunk_received_at` (วันที่-เวลา, ไม่ (จำเป็นเมื่อ `sync_status = กำลังซิงค์`)) — เวลาที่เซิร์ฟเวอร์ได้รับส่วนไฟล์ล่าสุด ใช้ตรวจจับรอบที่ค้างนานเกินควร (stale)
  - ทุก attribute ที่จำเป็นแบบมีเงื่อนไขเขียนในรูปแบบ `ไม่ (จำเป็นเมื่อ X)` ตามรูปแบบที่ไฟล์ใช้อยู่แล้ว (เทียบเคียงกับ `AuditTrailEntry.related_surveyedbuilding_id` ที่มีอยู่เดิม) ไม่เขียน "ไม่" เฉยๆ

- **§10 กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล** — แทรกกฎใหม่เป็น **ข้อ 8** (เดิม: 1-7 คงที่, ข้อ 8 เดิม "AuditTrailEntry.related_surveyedbuilding_id ต้อง resolve" เลื่อนเป็นข้อ 9 — เป็นการเลื่อนเลขรายการในย่อหน้า ไม่ใช่เลขหัวข้อ จึงไม่กระทบ anchor ใดที่เอกสารอื่นอ้างอิง `db-spec#10. กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล`): กำหนดเงื่อนไขที่**ต้อง**ส่งต่อจากจุดค้าง (อ้าง `upload_session_id`/`uploaded_bytes` เดิม) เทียบกับเงื่อนไขที่**ต้อง**ล้างแล้วเริ่มใหม่จาก 0 — 2 กรณีเท่านั้น: (ก) `upload_session_id` ที่อุปกรณ์ถืออยู่ไม่ตรงกับที่เซิร์ฟเวอร์บันทึกไว้ (เช่น แอป/ที่เก็บข้อมูลถูกล้าง) หรือ (ข) `last_chunk_received_at` เก่ากว่าเกณฑ์ stale (ตัวเลขจริงยังไม่กำหนด — ไม่เดา) — และระบุว่า `sync_status = ซิงค์สำเร็จ` ได้ก็ต่อเมื่อ `uploaded_bytes = total_file_size_bytes` เท่านั้น

- **§11 ประเด็นรอตัดสินใจ** — เพิ่มบูลเลตใหม่ระบุว่าโครงสร้างข้อมูลปิดแล้ว แต่ตัวเลขเกณฑ์ stale timeout และขนาด chunk ต่อครั้งยังไม่กำหนด (ไม่เดาตัวเลข) รอ implementation ร่วมกับ `api-spec.md` §16

**`api-spec.md` §14.1 ซิงค์ข้อมูลแบบสำรวจที่ค้างจากอุปกรณ์ — ปรับ 3 ช่อง:**
- **Input**: เพิ่มว่าระเบียนที่มีไฟล์ (`DamagePhoto`/`Sketch`) ต้องส่ง `total_file_size_bytes`, `upload_session_id` (ถ้ามีจากรอบก่อน — ไม่ระบุถ้าเริ่มครั้งแรก) และเนื้อไฟล์ส่วนที่จะส่งนับจากตำแหน่งที่เซิร์ฟเวอร์เคยยืนยันไว้
- **Output**: เพิ่มว่าเซิร์ฟเวอร์**ต้อง**รายงานกลับ `upload_session_id` ปัจจุบัน + `uploaded_bytes` ล่าสุดเสมอสำหรับทุกรายการ `DamagePhoto`/`Sketch` เพื่อให้อุปกรณ์รู้ว่ารับไปถึงไหนก่อนส่งต่อรอบถัดไป
- **กฎทางธุรกิจ**: เพิ่มกฎว่าเซิร์ฟเวอร์ต้องอ้างอิง `uploaded_bytes`/`upload_session_id` ก่อนรับไฟล์ทุกครั้ง ไม่รับซ้ำส่วนที่มีอยู่แล้ว และระบุเงื่อนไขออก `upload_session_id` ใหม่ (อ้างอิงกฎข้อ 8 ใน db-spec §10) — ระบุชัดว่าขนาด chunk/เกณฑ์ stale เป็นประเด็นรอตัดสินใจ ห้ามเดาตัวเลข
- **กรณี error**: ปรับข้อความ "ไฟล์ภาพส่งไม่สำเร็จบางส่วน" ให้ระบุชัดว่าต้องส่งต่อจากตำแหน่ง `uploaded_bytes` เดิม ไม่ใช่เริ่มใหม่ทั้งหมด เว้นแต่เข้าเงื่อนไขล้างสถานะ

**§16 ประเด็นรอตัดสินใจ** — ปรับบูลเลตเรื่องไฟล์ภาพขนาดใหญ่: เพิ่มว่า **โมเดลข้อมูลระดับ logical ของสถานะอัปโหลดที่ค้างไว้ปิดแล้ว** (ลิงก์ไปยัง db-spec §6.1/§6.3/§10 ข้อ 8) แต่กลไก chunking จริง/เกณฑ์เวลา stale/การจัดคิวจริงยังไม่ปิด

### ตรวจสอบความสอดคล้องข้ามไฟล์ (บังคับ)
- field ทุกตัวที่ operation 14.1 อ้างถึงใหม่ (`total_file_size_bytes`, `upload_session_id`, `uploaded_bytes`) มี attribute รองรับใน `db-spec.md` §6.1/§6.3 ชื่อตรงกันทุกตัวอักษร
- ไม่มี HTTP method/path/protocol หลุดเข้าไปในข้อความที่แก้ (grep ยืนยัน "resumable upload", "upload_session_id" ไม่ปรากฏคำต้องห้าม)
- ไม่มีตัวเลขขนาด chunk/เกณฑ์เวลาถูกเดาทิ้งไว้ที่ใดเลยทั้งสองไฟล์ — ทุกจุดที่ยังไม่รู้ตัวเลขถูกส่งเข้า "ประเด็นรอตัดสินใจ" ทั้งหมด
- attribute ที่จำเป็นแบบมีเงื่อนไขทั้ง 3 ตัวใหม่เขียนแบบ `ไม่ (จำเป็นเมื่อ X)` ตรงรูปแบบเดิมของไฟล์ ไม่มีจุดใดเขียน "ไม่" เฉยๆ

### สิ่งที่ `detailed-design/offline-sync.md` ต้องปรับ (รายงานกลับ ไม่ได้แก้เอง — คนละเจ้าของ)
1. **State diagram (§3, บรรทัด 58)**: transition `กำลังซิงค์ --> ยังไม่ซิงค์ : ไฟล์ภาพส่งไม่สำเร็จบางส่วน/สัญญาณขาดหาย` ควรแก้เป็น **`กำลังซิงค์ --> กำลังซิงค์` (self-transition หรือหมายเหตุ "คงสถานะเดิม")** เมื่อสัญญาณขาดหายกลางคัน เพราะ `sync_status` ไม่ควรถอยกลับไป "ยังไม่ซิงค์" อีกต่อไป — ตำแหน่งที่ส่งสำเร็จแล้วถูกเก็บไว้ใน `uploaded_bytes`/`upload_session_id` ของ `DamagePhoto`/`Sketch` แล้ว (ตาม db-spec §10 ข้อ 8 ใหม่) การถอยไป "ยังไม่ซิงค์" จะสื่อความหมายผิดว่าต้องเริ่มนับจาก 0 ใหม่เสมอ ทั้งที่ควรเริ่มนับใหม่เฉพาะ 2 กรณี (upload_session_id ไม่ตรง/stale) เท่านั้น ควรเพิ่มหมายเหตุอ้างอิงเงื่อนไขนี้ในไดอะแกรมหรือคำอธิบายประกอบ
2. **ตาราง Edge Case (§5, บรรทัด 76)**: แถว "ไฟล์ภาพส่งไม่สำเร็จบางส่วน (สัญญาณขาดหาย)" ควรขยายคอลัมน์ "วิธีจัดการ" จาก "ต้องส่งต่อได้โดยไม่ต้องเริ่มใหม่ทั้งหมด (NFR-02)" เป็นระบุกลไกจริงที่ตอนนี้มีรองรับแล้ว: ส่งต่อจากตำแหน่ง `uploaded_bytes` ที่เซิร์ฟเวอร์ยืนยันล่าสุดของ `upload_session_id` เดิม พร้อมอ้างอิง [[db-spec#10. กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล|db-spec หัวข้อ 10 ข้อ 8]] และ [[api-spec#14.1 ซิงค์ข้อมูลแบบสำรวจที่ค้างจากอุปกรณ์|api-spec 14.1]] ที่ปรับแล้ว แทนคำอธิบายเชิงพฤติกรรมล้วนแบบเดิมที่ไม่มีกลไกจริงรองรับ
3. **Sequence diagram (§1, บรรทัด 24)**: ข้อความ "รองรับทำต่อได้เมื่อสัญญาณขาดหาย" ยังคงถูกต้องเชิงเจตนา ไม่จำเป็นต้องแก้ แต่ถ้าต้องการความชัดเจนขึ้น อาจเพิ่มหมายเหตุสั้นๆ อ้างอิง `upload_session_id`/`uploaded_bytes` ประกอบ (ไม่บังคับ เพราะเนื้อหาไม่ขัดแย้งของจริง)

## `/sync-detailed-design` (ขอบเขตแคบมาก: ไฟล์เดียว) — แก้ `offline-sync.md` ให้สอดคล้องกับ resumable upload ที่ `api-db-writer` เพิ่งปิดช่องว่าง (ผ่าน subagent `detailed-design-writer`)

### บริบท
สืบเนื่องจากหัวข้อ "สิ่งที่ `detailed-design/offline-sync.md` ต้องปรับ" ด้านบน — `api-db-writer` เพิ่ม 4 attribute (`upload_session_id`/`total_file_size_bytes`/`uploaded_bytes`/`last_chunk_received_at`) ให้ `db-spec.md` §6.1 `DamagePhoto`/§6.3 `Sketch`, เพิ่มกฎทางธุรกิจข้อ 8 ใน §10 (เงื่อนไขส่งต่อจากจุดค้าง vs ต้องเริ่มใหม่), และปรับ `api-spec.md` §14.1 ให้เซิร์ฟเวอร์รายงาน `upload_session_id`/`uploaded_bytes` กลับเสมอ — ไฟล์นี้ (`offline-sync.md`) เคยขัดแย้งกับตัวเอง: sequence diagram/edge case table อ้างว่ารองรับทำต่อได้ แต่ state diagram มี transition ถอยกลับ "ยังไม่ซิงค์" เมื่อไฟล์ส่งไม่สำเร็จบางส่วน ซึ่งขัดกับความหมายจริงของ resumable upload (ตำแหน่งที่ส่งสำเร็จถูกเก็บไว้แล้ว ไม่ควรนับใหม่จาก 0 เสมอไป)

### ตรวจยืนยันแหล่งความจริงก่อนแก้
อ่าน `db-spec.md` §6.1/§6.3 (4 attribute ใหม่ ครบตรงตามที่รายงาน) และ §10 ข้อ 8 (กฎทางธุรกิจ: ส่งต่อจาก `uploaded_bytes`/`upload_session_id` เดิมเสมอ **ห้าม**เริ่มนับใหม่จาก 0 เว้นแต่ (ก) `upload_session_id` ไม่ตรงกับที่เซิร์ฟเวอร์บันทึกไว้ หรือ (ข) `last_chunk_received_at` เก่ากว่าเกณฑ์ stale ที่ยังไม่กำหนดตัวเลข; `sync_status = ซิงค์สำเร็จ` ได้ก็ต่อเมื่อ `uploaded_bytes = total_file_size_bytes` เท่านั้น) และ `api-spec.md` §14.1 (Input/Output/กฎทางธุรกิจ/กรณี error ที่ปรับแล้วให้เซิร์ฟเวอร์รายงาน `upload_session_id`/`uploaded_bytes` กลับเสมอ) — ครบถ้วนตรงกับที่ผู้เรียกใช้สรุปมา ไม่มีช่องว่างเพิ่มเติมที่ต้องรายงานให้รัน `sync-api-db` ซ้ำ

### การแก้ไข (4 จุดหลัก + grep หาจุดเพิ่มเติม)
1. **State diagram (§3, เดิมบรรทัด 58)** — เปลี่ยน transition ถอยกลับ `กำลังซิงค์ --> ยังไม่ซิงค์` เป็น **2 self-loop บน `กำลังซิงค์`** แยกตามเงื่อนไขกฎข้อ 8: (ก) สัญญาณขาดหายแต่ `upload_session_id` ยังตรง+ไม่ stale → คงสถานะ `กำลังซิงค์` (ส่งต่อจาก `uploaded_bytes` เดิม) และ (ข) `upload_session_id` ไม่ตรง/รอบเดิม stale → ยังคงสถานะ `กำลังซิงค์` เดิม แต่ต้องออก `upload_session_id` ใหม่ + เริ่มนับ `uploaded_bytes` จาก 0 แล้วส่งไฟล์ใหม่ทั้งหมด (ไม่ถือเป็นการถอยไป "ยังไม่ซิงค์" เพราะยังอยู่ในรอบซิงค์เดียวกัน) — เพิ่มเติมยังปรับ transition `กำลังซิงค์ --> ซิงค์สำเร็จ` ให้ระบุเงื่อนไขจบของไฟล์ (`uploaded_bytes = total_file_size_bytes`) ตามกฎข้อ 8 ด้วย เพื่อไม่ให้ผู้อ่านเข้าใจว่า "บันทึกสำเร็จ" หมายถึงข้อมูลเชิงโครงสร้างอย่างเดียว
2. **ตาราง Edge Case (§5, เดิมบรรทัด 76)** — แยกเป็น **2 แถว** ตามเงื่อนไขเดียวกับ state diagram: แถวแรก (ส่งต่อได้) ระบุกลไกจริง "ส่งต่อจาก `uploaded_bytes` ของ `upload_session_id` เดิม" + ยืนยันว่า `sync_status` ไม่ถอยกลับ "ยังไม่ซิงค์"; แถวสอง (ต้องเริ่มใหม่) ระบุกลไกล้าง `upload_session_id`/`uploaded_bytes`/`last_chunk_received_at` แล้วออกรอบใหม่ แต่ `sync_status` ยังเป็น "กำลังซิงค์" เช่นเดิม — ทั้งสองแถวอ้างอิง [[db-spec#10. กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล|db-spec หัวข้อ 10 ข้อ 8]] และ [[api-spec#14. การทำงานออฟไลน์และซิงค์ข้อมูลภาคสนาม|api-spec 14.1]] ตามที่ระบุมา
3. **Sequence diagram (§1, เดิมบรรทัด 24)** — `api-db-writer` ระบุว่าไม่บังคับแก้ แต่ตัดสินใจปรับให้ชัดขึ้น: แก้ข้อความ arrow เป็น "บันทึกไฟล์ภาพ/ภาพวาด ต่อจาก `uploaded_bytes` ของ `upload_session_id` เดิม ... แล้วรายงาน `upload_session_id`/`uploaded_bytes` ล่าสุดกลับให้อุปกรณ์" และเพิ่ม `Note over Sync,Media` อธิบายเงื่อนไขออกรอบใหม่ (ให้สอดคล้องกับ state diagram/edge case ที่แก้ในจุด 1-2)
4. **grep หาจุดอื่นที่ยังไม่สอดคล้อง** — grep คำว่า "เริ่มใหม่", "ส่งต่อ", "resumable", "upload_session", "uploaded_bytes", "stale", "ทำต่อได้" ทั้งไฟล์ พบ 8 จุดตรงกับ 3 จุดที่แก้ข้างต้น + จุดอื่นที่ไม่เกี่ยวกับ resumable upload (บรรทัดเกี่ยวกับ manual conflict resolution/auto-merge ซึ่งเป็นคนละกลไก ไม่ต้องแก้) — **ไม่พบจุดตกค้างเพิ่มเติมนอกเหนือ 3 จุดที่ระบุมา**
5. เพิ่มเติมเล็กน้อยเพื่อความสอดคล้อง (นอกเหนือ 4 จุดที่ผู้เรียกใช้ระบุ): ตาราง Operation↔Entity (§2) แถว 14.1 — เติม 4 attribute ใหม่เข้าไปในวงเล็บอธิบาย `DamagePhoto`/`Sketch` และเพิ่มประโยคในคอลัมน์ "ลำดับ/เงื่อนไข" อ้างอิงกฎส่งต่อจากจุดค้าง เพื่อให้ตารางนี้ (ซึ่งเป็นสรุปภาพรวมของไฟล์) ไม่ตกหล่นความสามารถที่เพิ่งเพิ่มเข้ามา

### State diagram หลังแก้ (transition ทั้งหมด)
1. `[*] --> ยังไม่ซิงค์` : สร้าง/แก้ไขระเบียนบนอุปกรณ์ขณะออฟไลน์
2. `ยังไม่ซิงค์ --> กำลังซิงค์` : 14.1 เริ่มส่งข้อมูล/ไฟล์เมื่อกลับมามีสัญญาณ
3. `กำลังซิงค์ --> ซิงค์สำเร็จ` : 14.1 บันทึกสำเร็จ (ไม่พบความขัดแย้ง หรือ merge อัตโนมัติสำเร็จ — เพิ่มเงื่อนไข `uploaded_bytes = total_file_size_bytes` สำหรับ DamagePhoto/Sketch)
4. `กำลังซิงค์ --> มีความขัดแย้งรอแก้ไข` : 14.2 ตรวจพบ SurveyedBuilding ชุดเดียวกันถูกแก้ไขจากหลายอุปกรณ์ และ merge อัตโนมัติไม่ได้
5. **(ใหม่)** `กำลังซิงค์ --> กำลังซิงค์` : สัญญาณขาดหาย + `upload_session_id` ยังตรง/ไม่ stale → ส่งต่อจาก `uploaded_bytes` เดิม คงสถานะไว้ ไม่ถอยกลับ
6. **(ใหม่)** `กำลังซิงค์ --> กำลังซิงค์` : `upload_session_id` ไม่ตรง/รอบเดิม stale → ออกรอบใหม่ (`uploaded_bytes` เริ่มจาก 0) แต่ยังคงสถานะ `กำลังซิงค์` เดิม
7. `มีความขัดแย้งรอแก้ไข --> ซิงค์สำเร็จ` : 15.2 แก้ไขความขัดแย้งด้วยมือสำเร็จ
8. `ซิงค์สำเร็จ --> [*]`

(แทนที่ transition เดิม `กำลังซิงค์ --> ยังไม่ซิงค์` เพียงเส้นเดียวด้วย 2 self-loop ข้างต้น — **ไม่มี transition ใดถอยจาก `กำลังซิงค์` กลับไป `ยังไม่ซิงค์` อีกต่อไป** ตามที่ผู้เรียกใช้ชี้ปัญหาไว้)

### ตรวจสอบก่อนปิดงาน
- **Attribute/operation ที่ใช้ทั้งหมด** (`upload_session_id`, `total_file_size_bytes`, `uploaded_bytes`, `last_chunk_received_at`, operation 14.1) มีอยู่จริงใน `db-spec.md`/`api-spec.md` ที่อ่านมาก่อนแก้แล้วทุกตัว — ไม่ได้คิด attribute/operation ใหม่เอง
- **ไม่ได้เดาตัวเลข** ขนาด chunk หรือเกณฑ์ stale ที่ใดเลย — ทุกจุดที่พูดถึงเกณฑ์ stale เขียนกำกับว่า "ตัวเลขยังไม่ตัดสินใจ/เป็นประเด็นรอตัดสินใจ" เสมอ
- **ไม่มี HTTP method/path/protocol หรือ SQL type** หลุดเข้าไปในข้อความที่แก้ — grep คำว่า "GET/POST/PUT/PATCH/HTTP/VARCHAR/INT/JSON" ในเนื้อหาที่เพิ่ม ไม่พบ
- **Heading ไม่เปลี่ยน** — ยืนยันด้วยการอ่านไฟล์เต็มหลังแก้: `## 3. State Diagram: sync_status` และ `## 5. Edge Case และวิธีจัดการ` คงข้อความเดิมทุกตัวอักษร (ไฟล์อื่นที่อ้าง anchor เหล่านี้ยังใช้งานได้ปกติ)
- **Mermaid ยัง render ได้** — ทั้ง sequence diagram และ state diagram ใช้ syntax เดิมของไฟล์ (state name ไม่มีช่องว่าง, ไม่มีอักขระพิเศษที่ขัดกับ parser เช่น `:` ซ้อนในป้ายกำกับ, self-loop `A --> A : label` เป็น syntax มาตรฐานของ `stateDiagram-v2`)

### สิ่งที่ตรวจ
1. อ่าน `db-spec.md` §6.1 `DamagePhoto`/§6.3 `Sketch` จริง — ยืนยันมีครบ 4 attribute (`upload_session_id`, `total_file_size_bytes`, `uploaded_bytes`, `last_chunk_received_at`) เขียนเงื่อนไข "จำเป็น" ตรงรูปแบบเดียวกับฟิลด์มีเงื่อนไขอื่นในไฟล์ และ §10 ข้อ 8 มีกฎชัดเจนว่าเมื่อไรส่งต่อ/เมื่อไรเริ่มใหม่
2. อ่าน `api-spec.md` §14.1 จริง — ยืนยัน Input/Output/กฎทางธุรกิจ/กรณี error ทั้ง 4 ส่วนพูดเรื่อง resume สอดคล้องกันครบ เซิร์ฟเวอร์ต้องรายงาน `upload_session_id`/`uploaded_bytes` กลับเสมอ
3. **จุดตรวจเข้มที่สุด** — อ่าน `detailed-design/offline-sync.md` §3 state diagram จริง ยืนยันว่า transition `กำลังซิงค์ --> ยังไม่ซิงค์` ที่เคยขัดแย้งกับข้อความ "ทำต่อได้" **ถูกลบออกแล้วจริง** แทนที่ด้วย self-loop 2 เส้นบน `กำลังซิงค์` (ส่งต่อได้เมื่อ session ตรง+ไม่ stale / เริ่มรอบใหม่เมื่อ session ไม่ตรง/stale แต่ยังไม่ถอยกลับ "ยังไม่ซิงค์") — ตาราง edge case (§5) แยกเป็น 2 แถวตรงเงื่อนไขเดียวกัน และ sequence diagram/ตาราง operation↔entity (§1, §2) ระบุกลไกจริงตรงกันหมด ไม่พบข้อขัดแย้งระหว่างข้อความกับโมเดลข้อมูลอีกต่อไป
4. ประเมินว่าตัวเลข chunk size/เกณฑ์ stale ที่ยังไม่กำหนด ทำให้ต้องคงสถานะ "รองรับบางส่วน" หรือไม่ — สรุปว่า **ไม่ทำให้ต้องคงสถานะ** เพราะกลไกระดับ logical ครบสมบูรณ์แล้ว (attribute เก็บ progress, กฎ resume/reset, state model ไม่ขัดแย้ง, operation contract ระบุ resume ตรงๆ) ตัวเลขที่เหลือไม่กระทบทิศทาง/พฤติกรรมของกลไก เป็นพารามิเตอร์ระดับ implementation ล้วน ถูกบันทึกไว้ถูกที่แล้วใน `db-spec.md` §11/`api-spec.md` §16 พร้อมกำกับ "ห้ามเดาตัวเลข" — จัดหมวดเดียวกับ NFR-06/NFR-07 ที่เคยตัดสินไว้แล้วในรอบก่อนหน้า

### ผลตรวจ
**NFR-02 กลับเป็น "รองรับแล้ว"** — ทั้ง 3 ชั้นเอกสาร (`db-spec.md`, `api-spec.md`, `detailed-design/offline-sync.md`) สอดคล้องกันจริง ไม่ใช่แค่เพิ่ม attribute ผิวเผิน — บันทึกประวัติการขึ้น-ลงไว้ในตัวเอกสารด้วย (รอบที่ 5: รองรับแล้ว → รอบที่ 6: ลดเป็นรองรับบางส่วน → รอบที่ 7: กลับเป็นรองรับแล้ว) ไม่ลบทิ้งเหมือนไม่เคยเกิด

### บริบท

ผู้ใช้ตรวจ [[20260828-01-flood-damage-survey#6. ข้อสมมติ / ประเด็นค้างพิจารณา|หมวด 6]] แล้วพบว่าข้อสมมติ 5, 6, 7 ยังเปิดค้างอยู่ทั้งหมดโดยไม่มีคำตอบบันทึกไว้ที่ใดเลย จึงถามผู้ใช้ผ่าน `AskUserQuestion` ในเทรดหลัก (ไม่ได้ถามจากงานนี้เอง) แล้วส่งคำตอบมาให้ปิดข้อสมมติให้ตรงกับที่ตัดสินใจแล้ว งานนี้จำกัดเฉพาะการทำให้ข้อความ FR/NFR ที่เกี่ยวข้องเจาะจงขึ้นตามคำตอบ ไม่ใช่การเพิ่มความต้องการใหม่ — ห้ามเพิ่ม/ลบรหัส FR/NFR (ยอดต้องยัง 43 รหัสเท่าเดิม) และห้ามผูก tech stack ในข้อความ แม้ `technology-stack.md` จะตัดสินใจแล้วก็ตาม (spec เป็นเอกสารความต้องการ ไม่ใช่เอกสารเทคนิค)

### คำถาม-คำตอบที่ผู้ใช้ตอบไว้ในเทรดหลัก (สรุปรวบรวมไว้ตามที่ระบุ)

1. **ข้อสมมติ 7 — วิธียืนยันตัวตน (FR-25)**: เลือก "รหัสผ่านครั้งแรก + PIN ตอนกลับเข้า" — ล็อกอินครั้งแรกขณะมีสัญญาณด้วยรหัสผ่าน จากนั้นปลดล็อกขณะออฟไลน์ด้วย PIN เหตุผล: หน้างานสวมถุงมือ/มือเปียกกดรหัสผ่านยาวยาก PIN เร็วกว่ามาก และเข้ากันได้ดีกับ NFR-09 ที่จำกัดอายุ session (กระทบ FR-27 ด้วย)
2. **ข้อสมมติ 6 — อายุ session ที่แคชไว้ (NFR-09)**: เลือก "7 วัน" เหตุผล: ครอบคลุมภารกิจสำรวจหลังภัยพิบัติที่ต่อเนื่องหลายวันโดยไม่มีสัญญาณตามที่ spec ระบุไว้เอง ความเสี่ยงที่ยอมรับคือถ้าอุปกรณ์หายระหว่างทาง คนที่เก็บได้เข้าถึงข้อมูลที่ยังไม่ได้ซิงค์ได้นานสุด 7 วัน
3. **ข้อสมมติ 5 — จำนวนภาพถ่ายต่อบริเวณ (FR-12/NFR-02)**: เลือก "สูงสุด 5 ภาพต่อบริเวณ" เหตุผล: คุมปริมาณข้อมูลที่ต้องซิงค์ตาม NFR-02 และประมาณพื้นที่เก็บบนเครื่องได้ เพียงพอสำหรับถ่ายรอยร้าวหลายมุม — **ส่วนขนาด/ความละเอียดภาพยังไม่ตอบ** เพราะผูกกับ FR-13 (AI ประมาณความกว้างรอยร้าว) ซึ่งยังไม่มีโมเดลและเกณฑ์ยังยืมจากคู่มือแผ่นดินไหว (ข้อสมมติ 2 และ 8) จึงแยกปิดเฉพาะส่วนจำนวนภาพ ส่วนความละเอียดยังคงเปิดไว้

### การตัดสินใจ: แก้เอกสารเดิม ไม่สร้างใหม่

เลือกแก้ไข [[20260828-01-flood-damage-survey]] ที่มีอยู่แล้วโดยตรง (ไม่สร้างเอกสารใหม่ ไม่ย้ายไป `00-archived/`) เพราะนี่ไม่ใช่ requirement ใหม่ แต่เป็นการทำข้อสมมติที่เขียนไว้แล้วในหมวด 6 ของเอกสารเดิมให้เจาะจงขึ้นตามคำตอบที่ได้ — กระทบเฉพาะข้อความของ FR/NFR ที่มีอยู่แล้ว (FR-12, FR-25, FR-27, NFR-02, NFR-09) และหมวด 6 ของไฟล์เดียวกัน ไม่มีเนื้อหาใหม่มากพอที่จะแยกเป็นไฟล์ต่างหาก และไม่มีทิศทางใดเปลี่ยนจนของเดิมล้าสมัย

### การแก้ไขเอกสาร spec — `docs/01-requirements/01-spec/20260828-01-flood-damage-survey.md`

**หัวเอกสาร**: เพิ่มบรรทัด "ปรับปรุงล่าสุด: 2026-09-03" สรุปว่าปิดข้อสมมติข้อใดบ้าง

**FR-25** (เดิม: ไม่ผูกกลไกยืนยันตัวตนเฉพาะเจาะจง) → ใหม่: "ผู้ใช้ทุกบทบาทต้องเข้าสู่ระบบด้วยบัญชีของตนก่อนใช้งานฟังก์ชันใดๆ ของระบบ โดยการเข้าสู่ระบบครั้งแรก (ขณะอุปกรณ์มีการเชื่อมต่ออินเทอร์เน็ต) ต้องยืนยันตัวตนด้วยชื่อผู้ใช้และรหัสผ่าน จากนั้นตั้งรหัส PIN สำหรับใช้ปลดล็อกแอปเมื่อกลับเข้าใช้งานในภายหลังขณะไม่มีสัญญาณ (ดูเส้นทางเข้าสู่ระบบขณะออฟไลน์ใน FR-27) และสามารถออกจากระบบ (logout) ได้ทุกเมื่อ"

**FR-27** (เดิม: ยืนยันตัวตนจาก credential/session ที่แคชไว้ แบบไม่ระบุกลไก) → ใหม่: "ผู้สำรวจภาคสนามต้องสามารถเปิดใช้แอปได้แม้อุปกรณ์ไม่มีสัญญาณอินเทอร์เน็ต โดยปลดล็อกแอปด้วยรหัส PIN ที่ตั้งไว้ตอนเข้าสู่ระบบด้วยรหัสผ่านครั้งล่าสุดที่เชื่อมต่อสำเร็จ (ดู FR-25) โดยไม่ต้องติดต่อเซิร์ฟเวอร์ทุกครั้งที่เปิดแอป (สอดคล้องกับ NFR-01) เมื่อครบกำหนดอายุการใช้งานของ PIN/เซสชันที่แคชไว้ (NFR-09) หรือเมื่ออุปกรณ์กลับมามีสัญญาณ ผู้ใช้ต้องเข้าสู่ระบบใหม่ด้วยชื่อผู้ใช้และรหัสผ่านอีกครั้งตาม FR-25"

**NFR-09** (เดิม: "ต้องมีอายุการใช้งานจำกัด" ไม่ระบุตัวเลข) → ใหม่: ระบุ "ไม่เกิน 7 วัน นับจากการเข้าสู่ระบบด้วยชื่อผู้ใช้/รหัสผ่านครั้งล่าสุดที่เชื่อมต่อสำเร็จ" พร้อมบังคับเข้าสู่ระบบใหม่เมื่อครบกำหนดหรือกลับมามีสัญญาณ และหมายเหตุความเสี่ยงที่ยอมรับตามที่ผู้ใช้ให้เหตุผลไว้

**FR-12** (เดิม: "รองรับหลายภาพต่อหนึ่งบริเวณ" ไม่ระบุจำนวน) → ใหม่: เพิ่ม "สูงสุด 5 ภาพต่อบริเวณ" พร้อมหมายเหตุว่าขนาด/ความละเอียดยังไม่กำหนด (ส่วนที่ยังเปิดอยู่)

**NFR-02** (เดิม: กล่าวถึงประสิทธิภาพซิงค์ภาพทั่วไป ไม่ผูกกับจำนวนภาพ) → ใหม่: เพิ่มประโยคอ้างอิงกลับ FR-12 ว่าปริมาณภาพต่อการสำรวจถูกจำกัดด้วย 5 ภาพต่อบริเวณ ช่วยประมาณปริมาณข้อมูลที่ต้องซิงค์ พร้อมคงหมายเหตุว่าขนาด/ความละเอียดไฟล์ยังไม่กำหนด

**หมวด 6 (ข้อสมมติ)** — แก้ข้อ 5/6/7 ให้สะท้อนว่าปิดแล้ว **ไม่ลบข้อทิ้ง** (คงไว้เป็นบันทึกประวัติว่าเคยเป็นข้อสมมติและถูกปิดเมื่อใด/เพราะอะไร):
- ข้อ 5: ปิด**บางส่วน** (จำนวนภาพ = 5 ภาพ, วันที่ 2026-09-03) ส่วนขนาด/ความละเอียดยังเปิดไว้ชัดเจน อ้างอิงกลับไปยังข้อสมมติ 2/8 ที่ยังบล็อกอยู่
- ข้อ 6: ปิดครบ (7 วัน, วันที่ 2026-09-03)

## `/sync-technology-stack` — ปิด §4.3 (Library เฉพาะตัวสำหรับ SQLite บน React Native) ผู้ใช้เลือก `op-sqlite` บน bare React Native (ผ่าน subagent `tech-stack-writer`)

### บริบท
สืบเนื่องจากรอบก่อนหน้า (commit `def3eaf`) ที่บันทึกไว้ 5 ชั้นของ Phase 1 และทิ้ง §4.3 ไว้เป็น "ยังไม่ตัดสินใจ" เพราะผู้ใช้เลือกไว้เพียงระดับ "SQLite" ยังไม่เลือก library เจาะจง รอบนี้ผู้ใช้ตอบผ่าน `AskUserQuestion` ในเทรดหลักแล้ว (ไม่ต้องถามซ้ำ) — งานคือบันทึกผลการตัดสินใจที่เหลือลงไฟล์

### ตัวเลือกที่เคยเสนอเปรียบเทียบให้ผู้ใช้ (4 ทาง)
| ทางเลือก | จุดแข็ง | จุดอ่อน |
|---|---|---|
| **bare RN + `op-sqlite`** ← เลือก | JSI เร็วที่สุดในกลุ่ม, พัฒนาต่อเนื่อง, API สมัยใหม่, bare RN เปิดทางใส่ native module เอง | ตัวอย่าง/community น้อยกว่า, ต้องตั้งค่า native build เอง |
| bare RN + `react-native-sqlite-storage` | ตัวอย่างเยอะที่สุด | API เก่ากว่า, การดูแลเคยช้าเป็นช่วงๆ |
| Expo + `expo-sqlite` | ตั้งค่าง่ายที่สุด | เสี่ยงกับ NFR-02 (native module สำหรับ resumable upload ที่ managed workflow เข้าถึงได้จำกัด) |
| bare RN + WatermelonDB | มีชั้น sync มาให้ในตัว | ชนกับ sync/conflict resolution ที่ [[offline-sync]] ออกแบบเองไว้ละเอียดแล้ว |

ผู้ใช้เลือก **bare React Native + `op-sqlite`** — เหตุผล: ความเร็วสำคัญจริงเพราะ NFR-02 ต้องจัดการคิวซิงค์/ไฟล์ภาพจำนวนมากบนอุปกรณ์ Android ราคาประหยัดตาม NFR-04 และ bare RN เปิดทางให้เขียน native module เองได้ ซึ่ง NFR-02 (อัปโหลดเบื้องหลังต่อจากจุดค้าง) มักต้องใช้

### ข้อจำกัดเรื่องความรู้ล้าสมัยที่บันทึกไว้ในเอกสาร
ข้อมูลเปรียบเทียบ library ทั้ง 4 ตัวอ้างอิงความรู้ถึงกลางปี 2026 เท่านั้น — บันทึกไว้ใน §1, แถว Local Persistent Store ใน §3, และเพิ่มเป็นเกณฑ์ทบทวนข้อ 8 ใน §6 ว่าต้องตรวจ commit ล่าสุด/issue ที่ค้าง/ความเข้ากันได้กับเวอร์ชัน React Native ที่จะใช้จริงก่อนติดตั้งเสมอ

### การแก้ไขไฟล์
- **§1 สถานะการตัดสินใจ** — ปรับวันที่เป็น 2026-09-04, ระบุ Field Client Framework เป็น "bare React Native" ชัดเจน, ระบุ Local Persistent Store มี library แล้ว (`op-sqlite`), จำนวนที่ยังไม่ตัดสินใจลดจาก 3 เหลือ 2 รายการ (AI runtime, hosting) เพิ่มหมายเหตุความรู้ล้าสมัย
- **§3 การตัดสินใจรายชั้น** — ยังคง 5 แถวเท่าเดิม (ไม่เพิ่มแถวใหม่) แต่แก้เนื้อหา 2 แถว:
  - แถว **Field Client Framework**: เปลี่ยนจาก "React Native" เป็น "**bare React Native**" — เพิ่มเหตุผลใหม่ (NFR-02 + ต้องการผูก native module เต็มที่สำหรับ `op-sqlite`) และเพิ่มทางเลือกที่ไม่เลือกอีก 1 รายการ: **Expo (managed workflow)**
  - แถว **Local Persistent Store**: เปลี่ยนจาก "ยังไม่เลือก library" เป็น "**SQLite ผ่าน `op-sqlite`**" พร้อมเหตุผล (JSI เร็วที่สุด, พัฒนาต่อเนื่อง, เปิดทางเขียน native module เอง) และเพิ่มทางเลือกที่พิจารณาแล้วไม่เลือกอีก 3 รายการ: `react-native-sqlite-storage`, `expo-sqlite`, WatermelonDB (พร้อมเหตุผลแต่ละตัว รวมอ้างอิง [[offline-sync]] สำหรับกรณี WatermelonDB)
  - ไม่แตะแถว Server-side Runtime/Primary Data Store/Media-Object Storage และไม่ลบเหตุผลเดิมของ Field Client Framework/Local Persistent Store ที่มีอยู่แล้ว (เพิ่มเติมต่อท้าย)
- **§4 สิ่งที่ยังไม่ตัดสินใจ** — ลบหัวข้อ "4.3 Library เฉพาะตัวสำหรับ SQLite บน React Native" ออก แทนที่ด้วยหมายเหตุอ้างว่าย้ายไปบันทึกที่ §3 แล้ว เหลือ 4.1 (AI runtime) และ 4.2 (Hosting) เท่านั้น
- **§5 ผลกระทบต่อเอกสารชั้นอื่น** — เพิ่มรายการใหม่ชี้ไปที่ [[offline-sync]] (ควรกลับไปตรวจว่าออกแบบ queue/conflict resolution ยัง implement ได้จริงบน `op-sqlite` ล้วนๆ โดยไม่พึ่งชั้น sync สำเร็จรูป) และปรับข้อความ `nfr-review.md`/`release-plan.md`/`03-task/` ให้กล่าวถึง `op-sqlite`/bare workflow เพิ่มเติม
- **§6 เกณฑ์ทบทวน** — ปรับข้อ 1-4 เดิมให้ใช้คำ "bare React Native" ให้สอดคล้อง และเพิ่มเกณฑ์ใหม่ 2 ข้อ: (8) `op-sqlite` หยุดการดูแล/เข้ากันไม่ได้กับเวอร์ชัน RN ที่ใช้จริง → ทบทวนกลับไปที่ `react-native-sqlite-storage`, (9) ถ้าจำเป็นต้องย้ายจาก bare workflow ไป Expo ในอนาคต → ต้องทบทวน Field Client Framework และ Local Persistent Store library พร้อมกันเพราะผูกกันโดยตรง
- **เอกสารที่เกี่ยวข้อง** — เพิ่ม [[offline-sync]] เข้ารายการ

### กติกาที่ยึดตามคำสั่ง
ไม่เดาเวอร์ชันของ `op-sqlite`/React Native (ผู้ใช้ไม่ได้ระบุ) ไม่เติมไลบรารี/เครื่องมือประกอบอื่นที่ผู้ใช้ไม่ได้เลือก (ไม่มี ORM/migration tool/state library ใดถูกเพิ่ม) ไม่ลบเหตุผลการตัดสินใจเดิมของชั้นใดเลย

  5. รอสัญญาณเพื่อเข้าสู่ระบบใหม่ (FR-27, NFR-09) — กรณี PIN หมดอายุแล้วแต่ยังไม่มีสัญญาณ (วนกลับไปขั้นตอนที่ 2 เมื่อมีสัญญาณ)
  6. บังคับสิทธิ์ตามบทบาท (FR-26)
  ทำให้ journey นี้ขยายจาก 22 เป็น **27 ขั้นตอน** (เลข 2-22 เดิมเลื่อนเป็น 7-27 ทั้งหมด รวมถึงเลขอ้างอิงขั้นตอนภายในข้อความ เช่น "ไปขั้นตอนที่ X" ที่ต้องปรับตามทุกจุด) — แก้ mermaid diagram คู่กันในการแก้ไขเดียวกัน (node A เดิมแยกเป็น A1-A6 ส่วน B เป็นต้นไปคงเดิม)
- **3 journey ที่เหลือ** (หัวหน้าผู้สำรวจ, ผู้ดูแลระบบ, หน่วยงานส่วนกลาง/ผู้บริหาร) **ตัดสินใจคงขั้นตอนเข้าสู่ระบบเป็น 1 ขั้นตอนเดียว** (ไม่แตก decision node) เพราะ 3 บทบาทนี้ไม่มีฉากทำงานออฟไลน์ปรากฏใน journey ของตนเลยตาม spec (ทำงานในบริบทที่มีสัญญาณเสมอ) — ปรับเพียงข้อความให้ระบุกลไกที่เจาะจงขึ้น ("เข้าสู่ระบบด้วยชื่อผู้ใช้และรหัสผ่าน" แทน "เข้าสู่ระบบด้วยบัญชีผู้ใช้ของตน") ทั้ง node และข้อความขั้นตอนที่ 1 ของทั้ง 3 journey โดยไม่เปลี่ยนจำนวนขั้นตอน — บันทึกเหตุผล/ทางเลือกที่พิจารณาไว้เป็นข้อสมมติใหม่ข้อ 3 ท้ายไฟล์ (เผื่อผู้ใช้เห็นว่าทั้ง 4 บทบาทควรเห็นขั้นตอนตั้ง PIN ตอนเข้าสู่ระบบครั้งแรกเหมือนกันหมดตามที่ FR-25 เขียนไว้ว่า "ผู้ใช้ทุกบทบาท")
- **หมดอายุ 7 วัน (NFR-09) ตัดสินใจให้ปรากฏเป็น decision node ชัดเจน** (ขั้นตอนที่ 3 ข้างต้น) ตามที่ผู้เรียกใช้ระบุว่าเป็นเหตุการณ์จริงที่ผู้สำรวจเจอกลางภารกิจหลายวัน — ไม่ได้ซ่อนไว้เบื้องหลัง FR-27 เหมือนเดิมอีกต่อไป พร้อมปรับข้อความในหัวข้อ "สรุปการครอบคลุมฟีเจอร์" (ย่อหน้าฟีเจอร์ 14) ให้ตรงกับการเปลี่ยนแปลงนี้ (ลบข้อความเดิมที่บอกว่า NFR-09 "ไม่ได้ปรากฏเป็น node แยก" ซึ่งไม่จริงอีกต่อไป) และปรับตัวเลขขั้นตอนรวมของ journey ผู้สำรวจภาคสนามจาก 22 เป็น 27 ในย่อหน้าฟีเจอร์ 4

### ตรวจสอบความสอดคล้อง mermaid ↔ ข้อความหลังแก้ไข
- Journey ผู้สำรวจภาคสนาม: นับ node ในแผนภาพ (A1-A6, B-V) = 27 node ตรงกับ 27 ขั้นตอนข้อความ 1:1 ทุกจุด รวม label/รหัส FR ในวงเล็บของแต่ละ node ตรงกับข้อความกำกับ — decision node ใหม่ทั้ง 2 จุด (ตรวจสัญญาณ, ตรวจอายุ PIN) ใช้ `{"..."}` พร้อม 2 กิ่งเงื่อนไขครบ (`-->|มีสัญญาณ|`/`-->|ไม่มีสัญญาณ|`, `-->|ยังไม่ครบกำหนด|`/`-->|ครบกำหนดแล้ว|`) ตามรูปแบบเดิมของไฟล์
- 3 journey ที่เหลือ: ไม่มีการเปลี่ยนโครงสร้าง node/edge ใดๆ (แก้เฉพาะข้อความ label ของ node A และขั้นตอนที่ 1) — ตรวจซ้ำว่าจำนวน node/ขั้นตอนยังตรงกัน 1:1 เหมือนเดิมทุกจุด (12/12, 13/13, 9/9 ตามลำดับ)

สถานะที่ตรวจก่อนเริ่ม: `01-spec/` มี 1 ไฟล์ ([[20260828-01-flood-damage-survey]]) — `backlog.md` มี 43 รหัส (FR-01–FR-33, NFR-01–NFR-10) ยืนยันด้วย grep `FR-\d+`/`NFR-\d+` ทั้งไฟล์ spec และ backlog ก่อนตัดสินใจว่ารหัสถัดไปที่ไม่ซ้ำคือ **NFR-11**

### แนวทางสร้างเอกสาร (ก/ข/ค) และการตัดสินใจ
เลือก **(ก) เพิ่มแถวใหม่ต่อท้ายตาราง NFR ในเอกสารเดิม** (ไม่สร้างไฟล์ใหม่ ไม่แทนที่เอกสารเดิม) เพราะ: (1) เป็นเรื่องเดียวกันกับ NFR-08/NFR-09 ที่มีอยู่แล้วในหัวข้อ 5 ของเอกสารเดียวกัน การแยกไฟล์จะทำให้ผู้อ่านต้องสลับไฟล์เพื่อเข้าใจกลไกความปลอดภัยชุดเดียวกัน, (2) ไม่กระทบ anchor เดิมเลยเพราะไม่มีการแก้ไข heading ใดๆ เพียงเพิ่มแถวท้ายตารางที่มีอยู่, (3) สอดคล้องกับรูปแบบที่เอกสารนี้เคยทำมาแล้วหลายครั้ง (เช่น NFR-10 ที่เพิ่มเข้ามาทีหลังในลักษณะเดียวกัน) — ไม่ต้องถามผู้ใช้เพิ่มเพราะขอบเขตชัดเจนมากอยู่แล้วว่าเป็น NFR เดี่ยวเสริมของ NFR-09 ไม่ใช่หัวข้อใหม่ที่ควรแยก

### ประเด็นที่ต้องตัดสินใจเองและผลการตัดสินใจ

**1) จำนวนครั้งที่ยอมให้กรอกผิด** — ยังไม่มีตัวเลขจากผู้ใช้ **ตัดสินใจ: ไม่เขียนตัวเลขตายตัวในข้อความ NFR-11** เพราะการเดาตัวเลขแล้วเขียนเป็นข้อกำหนดจริงเสี่ยงทำให้ผู้อ่าน/ผู้ออกแบบต่อ (`architecture-writer`, `detailed-design-writer`) เข้าใจผิดว่าเป็นค่าที่ยืนยันแล้วเหมือน NFR-09 (7 วัน) หรือ FR-12 (5 ภาพ) ซึ่งทั้งสองมีร่องรอยการยืนยันจากผู้ใช้ชัดเจนในหัวข้อ 6 ทางเลือกที่ใช้คือเขียนเป็น**ช่วงที่สมเหตุสมผลพร้อมระบุว่ารอยืนยัน** (5-10 ครั้ง ตามแนวปฏิบัติทั่วไปของกลไกป้องกันการเดารหัส PIN สั้นบนอุปกรณ์มือถือ) และบันทึกเป็นข้อสมมติใหม่ **ข้อ 11** ในหัวข้อ 6 ของ spec ควบคู่กัน (ทำทั้งสองอย่างพร้อมกันแทนที่จะเลือกอย่างใดอย่างหนึ่ง) เพราะข้อความในตาราง NFR ต้องอ่านเข้าใจได้ทันทีว่ามีเงื่อนไขอยู่ ในขณะที่หัวข้อ 6 ให้พื้นที่อธิบายเหตุผล/ที่มาของช่วงตัวเลขที่เสนอได้ครบถ้วนกว่า

**2) ผลของการล้าง credential ต่อข้อมูลที่ยังไม่ซิงค์** — จุดอันตรายที่สุดตามที่ระบุมา **ตัดสินใจ: เขียนรวมอยู่ใน NFR-11 เดียวกัน ไม่แยกเป็นอีกข้อ** เพราะเป็นเงื่อนไข/ขอบเขตของกลไกเดียวกัน (การล้าง credential) ไม่ใช่คุณลักษณะเชิงคุณภาพอีกด้านหนึ่ง แยกออกไปจะเสี่ยงเกิดปัญหาแบบเดียวกับที่เคยเกิดกับ NFR-05/FR-32-33 (กำหนดพฤติกรรมไว้จุดหนึ่งแต่ไม่มีอะไรบังคับให้คนอ่านอีกจุดเห็นเงื่อนไขคู่กัน) จึงระบุไว้ในประโยคเดียวกับที่สั่งให้ล้าง credential ว่า **"ขอบเขตของการล้างครอบคลุมเฉพาะ credential/PIN/เซสชันที่แคชไว้สำหรับยืนยันตัวตนเท่านั้น ข้อมูลแบบสำรวจที่บันทึกไว้ในเครื่องแต่ยังไม่ได้ซิงค์ขึ้นเซิร์ฟเวอร์ต้องไม่ถูกลบหรือสูญหายจากการล้าง credential นี้โดยเด็ดขาด"** พร้อมอ้างอิงกลับ NFR-01 (offline-first) เพื่อผูกเหตุผลว่าทำไมข้อมูลนี้ห้ามหาย (เก็บได้ครั้งเดียวหน้างานจริง)

**3) ควรอยู่หัวข้อใด** — **ตัดสินใจ: หัวข้อ 5 (Non-Functional Requirements) เป็นหลัก พร้อมเพิ่ม cross-reference สั้นๆ ในแถว FR-27 ของหัวข้อ 4.6** เพราะ NFR-11 เป็นคุณลักษณะเชิงความปลอดภัย (เหมือน NFR-08/NFR-09) ไม่ใช่ความสามารถเชิงฟังก์ชันใหม่ที่ผู้ใช้กระทำเอง (ผู้ใช้ไม่ได้ "สั่ง" ให้ระบบล็อก — ระบบบังคับพฤติกรรมนี้เองเมื่อเงื่อนไขเป็นจริง) จึงไม่เข้าเกณฑ์เป็น FR ใหม่ในหัวข้อ 4.6 เหมือนที่เคยแยก FR-25/26/27 ออกจาก NFR-08 มาก่อน (เหตุผลตอนนั้นคือ "การเข้าสู่ระบบเป็นสิ่งที่ผู้ใช้กระทำ" ซึ่งตรงข้ามกับกรณีนี้) แต่เพิ่มประโยคอ้างอิงสั้นในแถว FR-27 เพื่อให้คนอ่านเส้นทางออฟไลน์เห็นเงื่อนไขนี้ทันทีโดยไม่ต้องไล่หาเอง

**4) ความสัมพันธ์กับ NFR-08/NFR-09** — **ตัดสินใจ**: เขียนความสัมพันธ์แบบ 3 เส้าไว้ในข้อความ NFR-11 เอง (อ้างอิงกลับทั้ง NFR-08 และ NFR-09 พร้อมอธิบายบทบาทต่างกันของแต่ละข้อ: NFR-08 = จำกัดสิทธิ์ตามบทบาทเป็นฐาน, NFR-09 = จำกัดกรอบเวลาที่ PIN ใช้ได้เหลือ 7 วัน, NFR-11 = จำกัดจำนวนครั้งที่เดาได้ภายในกรอบเวลานั้น) และ**เพิ่มประโยคอ้างอิงกลับจาก NFR-09 มาที่ NFR-11** (ต่อท้ายข้อความเดิมของ NFR-09 โดยไม่ลบ/แก้เนื้อหาเดิม) เพื่อให้คนอ่าน NFR-09 ก่อนก็เห็นว่ามีมาตรการเสริมอยู่ ไม่ต้องพึ่งการไล่อ่านจาก NFR-11 ทางเดียว — ไม่แก้ NFR-08 เพิ่มเติมเพื่อจำกัดขอบเขตการแก้ไขให้น้อยที่สุดเท่าที่จำเป็น (NFR-08 เดิมอ้างอิง NFR-09 อยู่แล้วซึ่งเป็นห่วงโซ่ที่เพียงพอ)

## `/sync-feature-journey` — จัด NFR-11 (PIN Attempt Lockout) เข้าฟีเจอร์ 14 เดิม ปรับ mermaid diagram journey ผู้สำรวจภาคสนาม (ผ่าน subagent `feature-journey-writer`)

### สถานะก่อนเริ่มงาน
`backlog.md` มี **44 รหัส** (FR-01–FR-33, NFR-01–NFR-11 — เพิ่ม NFR-11 ใหม่จากรอบ `requirement-writer` ก่อนหน้าในวันเดียวกัน) ส่วน `feature-list.md` (17 ฟีเจอร์/43 รหัส) และ `user-journey.md` (4 journey/27 ขั้นตอนใน journey ผู้สำรวจภาคสนาม) ยังไม่รู้จัก NFR-11 — ตารางสรุป MoSCoW เดิมของทั้ง 17 ฟีเจอร์ตรงกับหัวข้อรายละเอียดครบถ้วนอยู่แล้วก่อนเริ่ม (ไม่มีส่วนต่างอื่นนอกเหนือ NFR-11 ที่ขาดหาย) และทุก journey เดิมมี mermaid diagram ตรงกับข้อความ 100% อยู่แล้วก่อนเริ่มงานนี้เช่นกัน

### อ่านของจริงก่อนตัดสินใจ (ตามที่กำชับ)
เปิด `20260828-01-flood-damage-survey.md` หัวข้อ 4.6 และ 5 อ่านข้อความเต็มของ NFR-11 พบว่า: (1) ผูกตรงกับ FR-27 (ปลดล็อกออฟไลน์ด้วย PIN) และ NFR-09 (อายุ session 7 วัน) โดยตรง อยู่ในหัวข้อ/บทบาทเดียวกันกับฟีเจอร์ 14 ทุกประการ ไม่มีความกำกวมว่าควรอยู่ฟีเจอร์อื่น จึงไม่ต้องใช้ `AskUserQuestion`, (2) ระบุเงื่อนไขห้ามลบข้อมูลสำรวจที่ยังไม่ซิงค์ไว้ชัดเจน (อ้าง NFR-01), (3) จำนวนครั้งยังเป็นข้อสมมติเปิด (ช่วง 5-10 ครั้ง ข้อสมมติหมวด 6 ข้อ 11)

### การแก้ไข `feature-list.md`
- **ตารางสรุปฟีเจอร์** แถวที่ 14: เพิ่ม NFR-11 เข้าคอลัมน์รหัส FR/NFR (`FR-25, FR-26, FR-27, NFR-09, NFR-11`), ปรับคำอธิบายสั้นให้กล่าวถึงกลไกล้าง credential เมื่อกรอก PIN ผิดครบจำนวน, ปรับคอลัมน์บทบาทผู้ใช้ให้รวม NFR-11 ในกลุ่ม "เฉพาะผู้สำรวจภาคสนาม" — MoSCoW คงเป็น **Must have** เดิม (NFR-11 อยู่หมวดสูงเช่นเดียวกับรหัสอื่นในฟีเจอร์นี้ ไม่กระทบระดับสูงสุดที่มีอยู่แล้ว)
- **หัวข้อ 14 รายละเอียด**: ต่อท้ายคำอธิบายด้วยย่อหน้ากลไก PIN Attempt Lockout (เงื่อนไข ผลลัพธ์ ข้อยกเว้นเรื่องข้อมูลที่ยังไม่ซิงค์ต้องไม่ถูกลบ), เพิ่ม NFR-11 ในบรรทัด "รหัส FR/NFR" (พร้อม wikilink `[[20260828-01-flood-damage-survey#5. Non-Functional Requirements|NFR-11]]`), ปรับบรรทัด "บทบาทผู้ใช้" และปรับ/ต่อท้ายบรรทัด "หมายเหตุ" ให้ระบุที่มาของ NFR-11 และยืนยันว่ายังเป็น Must have — **ตารางสรุปกับหัวข้อรายละเอียดตรงกัน 100% หลังแก้**
- **หมายเหตุการจัดกลุ่มท้ายไฟล์**: แก้ตัวเลขรวมจาก "43 รายการ" เป็น "**44 รายการ**" (NFR-01–NFR-11) และเพิ่ม bullet ใหม่บันทึกที่มา/เหตุผลที่ NFR-11 เข้าฟีเจอร์ 14 (ไม่ใช่ฟีเจอร์ใหม่) — ยังคง **17 ฟีเจอร์** เท่าเดิม

### การแก้ไข `user-journey.md`
พิจารณาแล้วว่า **ต้องเพิ่มขั้นตอน** ใน journey ผู้สำรวจภาคสนามเท่านั้น (บทบาทเดียวที่มีเส้นทางปลดล็อกออฟไลน์ด้วย PIN — อีก 3 journey ทำงานในบริบทที่มีสัญญาณเสมอ ไม่เกี่ยวข้องกับ NFR-11) เพราะเป็นเหตุการณ์ที่ผู้สำรวจเจอได้จริงกลางพื้นที่ไม่มีสัญญาณและผลลัพธ์รุนแรง (ต้องรอสัญญาณกลับเข้าระบบใหม่) — แทรกเป็น **decision node คู่ใหม่ต่อจากขั้นตอน "ปลดล็อกแอปด้วย PIN" (FR-27)**:
- Mermaid: เพิ่ม node `A4a{"กรอก PIN ผิดติดต่อกันครบจำนวนครั้งสูงสุดที่กำหนดหรือไม่? (NFR-11)"}` และ `A4b["ระบบล้าง credential/PIN ที่แคชไว้ทันที โดยไม่ลบข้อมูลแบบสำรวจที่ยังไม่ซิงค์ แล้วรอสัญญาณเพื่อเข้าสู่ระบบใหม่ด้วยรหัสผ่าน (NFR-11)"]` พร้อมปรับ edge: `A4-->A4a`, `A4a-->|ครบ|A4b`, `A4a-->|ยังไม่ครบ|A6`, `A4b-->|มีสัญญาณแล้ว|A2` (แทนที่ edge เดิม `A4-->A6`)
- ข้อความขั้นตอน: แทรกเป็นขั้นตอนที่ 5-6 ใหม่ (decision + action) แล้วเลื่อนเลขขั้นตอนเดิมทั้งหมดตั้งแต่ขั้นตอนที่ 5 (PIN หมดอายุ) เป็นต้นไป **+2** ทุกขั้นตอน พร้อมแก้ทุกจุดที่อ้าง "ไปขั้นตอนที่ N"/"กลับไปขั้นตอนที่ N" ให้ตรงกับเลขใหม่ (รวมจุดอ้างอิงในขั้นตอน 2, 3, 4, 11(เดิม)/13(ใหม่), 15(เดิม)/17(ใหม่), 16(เดิม)/18(ใหม่), 18(เดิม)/20(ใหม่), 19(เดิม)/21(ใหม่), 21(เดิม)/23(ใหม่), 22(เดิม)/24(ใหม่), 23(เดิม)/25(ใหม่))
- **ขั้นตอนเปลี่ยนจาก 27 เป็น 29 ขั้นตอน** (เพิ่ม 2 ขั้นตอนใหม่พอดี ไม่มีการเพิ่ม/ลดขั้นตอนอื่นใด)
- ปรับย่อหน้าสรุปท้ายไฟล์ 2 จุด (ย่อหน้าฟีเจอร์ 14 และย่อหน้าสรุปจำนวนขั้นตอนรวมท้ายฟีเจอร์ 4) ให้ระบุที่มาของ decision node คู่ใหม่และตัวเลข 29 ขั้นตอน — journey อีก 3 บทบาท (หัวหน้าผู้สำรวจ, ผู้ดูแลระบบ, หน่วยงานส่วนกลาง/ผู้บริหาร) **ไม่ต้องแก้ไข** เพราะขั้นตอนเข้าสู่ระบบยังคงเป็น 1 ขั้นตอนเดียว (FR-25, FR-26) ไม่มีเส้นทางออฟไลน์ให้ NFR-11 เกี่ยวข้อง

### ตรวจยืนยันหลังแก้ไข
- Node ในแผนภาพ mermaid ของ journey ผู้สำรวจภาคสนาม (29 node: A1-A6, A4a, A4b, B-V) ตรงกับรายการขั้นตอนข้อความ 29 ข้อ แบบ 1:1 ครบทุกจุด ไม่มี node ไร้ขั้นตอนคู่กันหรือขั้นตอนไร้ node คู่กัน

1. **NFR-11 ต้องการฟิลด์/metadata สำหรับนับจำนวนครั้งที่กรอก PIN ผิดติดต่อกันบนอุปกรณ์** (เช่น failed attempt counter, timestamp ของความพยายามล่าสุด) — เป็นข้อมูลที่อยู่**ฝั่ง Field Client เท่านั้น** (ไม่ผ่าน sync ขึ้นเซิร์ฟเวอร์ เพราะเป็นกลไกออฟไลน์ล้วน) db-spec ควรพิจารณาว่าจำเป็นต้องมี entity/field ฝั่ง local schema สำหรับเรื่องนี้หรือไม่ (ไม่กระทบ schema ฝั่ง Primary Data Store เพราะไม่ sync)
2. **การล้าง credential ตาม NFR-11 ต้องเป็นการลบเฉพาะ credential/PIN/session ไม่แตะข้อมูลแบบสำรวจ** (สถาปัตยกรรม §6.8) — ถ้า db-spec เคยออกแบบ local schema (ฝั่งอุปกรณ์) แบบปนกันระหว่าง credential กับข้อมูลสำรวจในตารางเดียว ควรทบทวนแยกเป็นคนละส่วนของ schema
3. **api-spec**: ไม่มี operation ใหม่ฝั่งเซิร์ฟเวอร์เกิดจาก NFR-11 โดยตรง เพราะกลไกทำงานบนอุปกรณ์ล้วนขณะออฟไลน์ — จุดเดียวที่อาจเกี่ยวข้องคือ endpoint เข้าสู่ระบบด้วยรหัสผ่านเดิม (FR-25) ที่ผู้ใช้ต้องเรียกซ้ำหลัง lockout ซึ่งมี operation รองรับอยู่แล้ว ไม่ต้องเพิ่มใหม่ (ควรยืนยันซ้ำใน `/sync-technical-spec` ขั้นถัดไป)
4. **§8 ปิดหัวข้อ "Library เฉพาะตัวสำหรับ SQLite บน React Native" แล้ว** — ถ้า api-spec/db-spec เคยมีประเด็นรอตัดสินใจที่ผูกกับเรื่องนี้ (ไม่คาดว่ามี เพราะเป็นเรื่อง client-side implementation ล้วน) ให้ตรวจสอบซ้ำเช่นกัน

## `/sync-technical-spec` — ชั้นที่ 2/4: ปรับ `api-spec.md`/`db-spec.md` ให้รองรับ NFR-11 (PIN Attempt Lockout) (ผ่าน subagent `api-db-writer`)

### บริบท
รับช่วงต่อจาก `architecture-writer` (ชั้นที่ 1/4 ด้านบน) ตามรายการ "สิ่งที่เปลี่ยน" ที่ส่งมา 4 ข้อ — อ่าน `db-spec.md`/`api-spec.md` ทั้งฉบับ (18 entity / 40 operation เดิม) เทียบกับ `architecture.md` §5/§5.5/§6.8 และ backlog/feature-list/user-journey/spec ต้นทางส่วน FR-25/FR-27/NFR-09/NFR-11 ก่อนแก้

### จุดค้นพบสำคัญระหว่างตรวจ (นอกเหนือจากที่ระบุมา)
- **`Session` entity เดิมไม่มี attribute ใดรองรับ PIN เลย** (มีแค่ `is_offline_cached` เป็น boolean ธง) ทั้งที่ FR-25/FR-27/NFR-11 อ้างถึง "PIN" เป็นความลับคนละตัวจาก `credential_secret` (รหัสผ่าน) มาตั้งแต่ก่อนรอบนี้ — เป็นช่องว่างที่ทำให้ NFR-11 (ตัวนับ PIN ผิด) ไม่มีที่เก็บค่าได้เลยถ้าไม่แก้ จึงถือเป็นส่วนหนึ่งของงาน NFR-11 นี้ ไม่ใช่การขยายขอบเขตเกินคำขอ
- operation เดิม 1.3 ("เข้าสู่ระบบด้วย credential ที่แคชไว้ขณะออฟไลน์") ใช้ field ชื่อ `credential_secret` ทั้งที่ตามเจตนาจริง (feature-list ฟีเจอร์ 14, user-journey A4/A4a) ต้องเป็น PIN — แก้ไขให้ตรงกับความเป็นจริงของ business flow ไปพร้อมกัน
- ยืนยันว่า **credential/PIN/session (กลุ่ม User/Session) แยกจากข้อมูลสำรวจ (กลุ่ม SurveyedBuilding และ entity ย่อย) อยู่แล้วตั้งแต่ระดับ entity group** (db-spec หัวข้อ 1-2 กับหัวข้อ 4-8 เป็นคนละกลุ่มเดิมทีอยู่แล้ว) — สอดคล้องกับ architecture §6.8 โดยไม่ต้องปรับโครงสร้างกลุ่ม entity ใหม่

### สิ่งที่แก้ใน `db-spec.md`
1. **§2.2 Session** — เพิ่ม `NFR-11` เข้าบรรทัดรองรับ, เพิ่ม attribute ใหม่ 2 ตัว: `cached_pin_secret` (ข้อความ, ไม่ (จำเป็นเมื่อ `is_offline_cached = true`)) และ `failed_pin_attempt_count` (ตัวเลข, ไม่ (จำเป็นเมื่อ `is_offline_cached = true`)) พร้อมหมายเหตุกำกับก่อนตารางว่าทั้งสอง attribute อยู่ในพื้นที่จัดเก็บเดียวกับ session ที่แคชไว้ ซึ่งแยกจากข้อมูลแบบสำรวจตาม architecture §6.8 และ `failed_pin_attempt_count` **ไม่ถูกซิงค์ขึ้นเซิร์ฟเวอร์เลย** — ปรับคำอธิบาย `status` ให้ระบุว่าค่า "ถูกเพิกถอน" ครอบคลุมทั้งกรณีปิดบัญชี (2.3) และกรณี lockout (NFR-11) โดยไม่เพิ่มค่า enum ใหม่ (คุมความเสี่ยง enum ไม่ตรงกันข้ามไฟล์)
2. **§10 กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล** — เพิ่มเป็น **ข้อ 10 ต่อท้าย** (ไม่แทรกกลาง ไม่ชนกับเลขอ้างอิงเดิมที่มีบั๊ก off-by-one อยู่ก่อนแล้วระหว่างข้อ 8/ข้อ 9 ที่ตารางไฟล์แนบอ้างผิดเป็น "ข้อ 9" ทั้งที่ควรเป็น "ข้อ 8" — **พบแล้วแต่ไม่แก้ เพราะเป็นบั๊กเดิมที่ไม่เกี่ยวกับ NFR-11 และอยู่นอกขอบเขตงานนี้ รายงานไว้ด้านล่าง**) อธิบายกลไกนับ/รีเซ็ต/ล้าง `failed_pin_attempt_count`+`cached_pin_secret` ครบวงจร อ้างอิง api-spec 1.1/1.3 และ architecture §6.8
3. **§11 ประเด็นรอตัดสินใจ** — ขยาย bullet เข้ารหัสเดิมให้ครอบคลุม `cached_pin_secret`, เพิ่ม bullet ใหม่เรื่องจำนวนครั้งสูงสุดของ PIN lockout (อ้างข้อสมมติข้อ 11 ของ spec ช่วง 5-10 ครั้ง) ระบุชัดว่าเป็นประเด็นนโยบาย ไม่ใช่ tech stack และ **ห้ามเดาตัวเลข**
4. **ไม่แก้ ER Diagram (§9)** — Session ไม่เคยมี attribute box ในแผนภาพเดิม (เหมือน Assignment/SurveyParticipant/ฯลฯ ที่ไม่มี box เช่นกัน) การเพิ่ม attribute จึงไม่กระทบ diagram ตามรูปแบบเดิมของเอกสาร ไม่มีความสัมพันธ์ใหม่ระหว่าง entity

### สิ่งที่แก้ใน `api-spec.md`
1. **1.1 เข้าสู่ระบบ** — เพิ่ม input ไม่บังคับ `cached_pin_secret` (จำเป็นเมื่อผู้เรียกเป็นผู้สำรวจภาคสนาม เพื่อตั้ง/เปลี่ยน PIN สำหรับรอบออฟไลน์ถัดไป — ปิดช่องว่างเดิมที่ FR-25 ไม่เคยมี operation รองรับการตั้ง PIN เลย), output เพิ่ม `failed_pin_attempt_count = 0`, กฎทางธุรกิจเพิ่มเรื่องแยกเก็บ PIN จาก credential_secret และการรีเซ็ตตัวนับทุกครั้งที่ login สำเร็จ
2. **1.3 เข้าสู่ระบบด้วย credential ที่แคชไว้ขณะออฟไลน์** — เปลี่ยน input จาก `credential_secret` เป็น `cached_pin_secret` ให้ตรงกับ business flow จริง, แตก output เป็น 3 กรณี (ถูก/ผิดยังไม่ครบ/ผิดครบ lockout) ระบุผลต่อ `Session.failed_pin_attempt_count`/`cached_pin_secret`/`status` ชัดเจน, กฎทางธุรกิจ+กรณี error เพิ่มเรื่อง NFR-11 lockout พร้อมย้ำ "ห้ามเดาตัวเลข" จำนวนครั้งสูงสุด และย้ำว่าการล้างนี้ไม่แตะข้อมูลแบบสำรวจ/คิวรอซิงค์เลย, เพิ่ม `NFR-11` เข้ารหัส FR/NFR ที่รองรับ
3. **1.4 ต่ออายุ/ยืนยันตัวตนใหม่เมื่อกลับมามีสัญญาณ** — เพิ่มกรณี error ใหม่: `Session.status = ถูกเพิกถอน` จาก lockout ต้องปฏิเสธและบังคับกลับไป 1.1 เท่านั้น
4. **§16 ประเด็นรอตัดสินใจ** — เพิ่ม bullet เรื่องจำนวนครั้งสูงสุดของ PIN lockout (ชี้ไป db-spec §11 คู่กัน) และยืนยันชัดเจนว่า **NFR-11 ไม่ต้องการ server-side operation ใหม่** (ข้อ 3 ที่ architecture-writer ขอให้ยืนยัน — **ยืนยันแล้วว่าจริง**) เพราะกลไกทั้งหมดฝังอยู่ใน business rule ของ 1.3 ที่มีอยู่แล้ว

### ตรวจความสอดคล้องข้ามไฟล์ (ข้อ 6 ตามขั้นตอนบังคับ)
- `cached_pin_secret`, `failed_pin_attempt_count` — ชื่อ/ชนิดตรงกันทั้งสองไฟล์ (ข้อความ/ตัวเลข)
- `Session.status = ถูกเพิกถอน` — ใช้ enum เดิมที่มีอยู่แล้ว ไม่เพิ่มค่าใหม่ จึงไม่มีความเสี่ยง enum ไม่ตรงกัน

2. **Sequence Diagram (§1)** — เดิมมีเพียง 1 เส้นทางสำหรับ 1.3 ("สร้าง Session ใหม่" เฉยๆ) แก้เป็น `alt` 3 กรณีตามที่ `api-spec` 1.3 กำหนด: PIN ถูก (รีเซ็ตตัวนับ) / PIN ผิดยังไม่ครบ (+1 ตัวนับ, ไม่แตะข้อมูลสำรวจ) / PIN ผิดครบ lockout (ล้าง `cached_pin_secret`+ตัวนับ, ตั้ง `status=ถูกเพิกถอน`, ย้ำไม่แตะ `SurveyedBuilding`/entity ย่อย/คิวรอซิงค์) — เพิ่มขั้นตอนตั้ง/บันทึก `cached_pin_secret` ใน 1.1 ด้วย และปรับ 1.4 ให้ระบุกรณี error ใหม่ (session ถูกเพิกถอนจาก lockout)
3. **ตาราง Operation ↔ Entity (§2)** — ปรับแถว 1.1 (ระบุ `failed_pin_attempt_count=0` เสมอ + บันทึก `cached_pin_secret` ถ้ามี), 1.3 (เปลี่ยนจาก "สร้าง" เป็น "แก้ไข" พร้อมแตก 3 กรณีผลลัพธ์ในคอลัมน์เงื่อนไข), 1.4 (เพิ่มเงื่อนไข session ถูกเพิกถอนจาก lockout ต้องปฏิเสธ)
4. **State Diagram (§3)** — เพิ่ม transition ใหม่ `ใช้งานอยู่ --> ถูกเพิกถอน` จาก lockout (แยกจาก transition เดิมที่มาจากปิดบัญชีผู้ใช้ 2.3), ปรับ transition `ใช้งานอยู่ --> ใช้งานอยู่` ให้ครอบคลุมกรณี PIN ถูกต้องด้วย (ไม่ใช่แค่ 1.4 ต่ออายุ), เพิ่มหมายเหตุอธิบายว่ากรณี PIN ผิดยังไม่ครบไม่ทำให้ `status` เปลี่ยน (มีแค่ตัวนับเพิ่ม ไม่ใช่ transition สถานะ)
5. **ตาราง Edge Case (§4)** — เพิ่ม 5 แถวใหม่ตามที่ถูกขอให้ครอบคลุม: (ก) PIN ผิดยังไม่ครบ (ข) PIN ผิดครบ lockout — ระบุชัดเจนว่า "สิ่งที่ถูกลบ" (เฉพาะ credential/PIN/session) กับ "สิ่งที่ห้ามลบเด็ดขาด" (ข้อมูลแบบสำรวจ+คิวรอซิงค์ทุกรายการ) แยกกันในคอลัมน์เดียวเพื่อไม่ให้อ่านพลาด (ค) ครบจำนวนครั้งขณะยังไม่มีสัญญาณ — อธิบายว่าผู้ใช้ทำอะไรได้/ไม่ได้บ้าง (ง) ตัวนับรีเซ็ตเมื่อใด — ระบุ 2 เงื่อนไขเท่านั้น (ปลดล็อกสำเร็จ/login รหัสผ่านสำเร็จใหม่) (จ) session ถูกเพิกถอนจาก lockout แล้วกลับมามีสัญญาณ — ต้องปฏิเสธ 1.4 เสมอ
6. **เอกสารที่เกี่ยวข้อง** — เพิ่มลิงก์ `architecture#6.8` และหมายเหตุยืนยันว่า `offline-sync.md` ไม่กระทบกันแม้เกิด lockout

### สิ่งที่ยังไม่ครอบคลุมในรอบนี้
- ไม่ได้แตะ `nfr-review.md` — เป็นหน้าที่ของ `/sync-technical-spec` ชั้นที่ 4/4 ถัดไป (ตรวจอย่างเดียวโดย `nfr-reviewer`) ควรตรวจว่า NFR-11 ถูกจัดสถานะ "รองรับแล้ว" ในเอกสารนั้นหรือยัง
- จำนวนครั้งสูงสุดของ PIN lockout ยังไม่ยืนยันจากผู้ใช้ (คงข้อสมมติช่วง 5-10 ครั้ง) — ทุกจุดที่แก้ในไฟล์นี้เขียนแบบไม่ผูกตัวเลขตายตัวตามที่กำชับ ไม่มีจุดใดหลุดตัวเลข
- บั๊ก off-by-one ของ `db-spec.md` §10 ข้อ 8/9 ที่ `api-db-writer` รายงานไว้ก่อนหน้า (ไม่เกี่ยวกับ NFR-11) — ยังไม่ถูกแก้ เพราะอยู่นอกขอบเขตงานนี้ (แก้ได้เฉพาะ `detailed-design/`) ยังคงต้องรอรอบ `/sync-api-db` ถัดไป
- ไม่ได้ตรวจ/แก้ไขไฟล์อื่นนอกเหนือ `detailed-design/authentication-login.md` และ log นี้ ตามขอบเขตที่กำหนด
