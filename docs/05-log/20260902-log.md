   - **แต่ก่อนที่ prototype จะสร้างหน้าจอนี้ได้ ต้นตอต้องได้รับการแก้ที่ชั้นบนกว่าก่อน**: ตรวจ `feature-list.md` และ `user-journey.md` แล้วพบว่า**ไม่มีฟีเจอร์หรือขั้นตอน journey ใดเลยที่พูดถึง "ผู้ดูแลระบบเปิดดูประวัติ/audit trail ของอาคารรายตัว"** — ฟีเจอร์ 9 (จัดการผู้ใช้และสิทธิ์) พูดถึงเฉพาะบัญชีผู้ใช้ ฟีเจอร์ 15 (Manual Conflict Resolution) พูดถึงเฉพาะช่วงที่ระเบียนยังขัดแย้งอยู่ ไม่มีฟีเจอร์ใดครอบคลุม "ดูประวัติเหตุการณ์ทั้งหมดของอาคารหลังจากนั้น" เลย ตรวจ `api-spec.md` เพิ่มเติมก็พบว่ามีแต่ operation ที่**สร้าง** `AuditTrailEntry` (14.1, 14.2, 7.3, 3.2/3.3, 6.4/6.5, 15.1) แต่**ไม่มี operation ใดสำหรับดึง/แสดง (`GET`) `AuditTrailEntry` เลยสักตัว**
   - ช่องว่างนี้จึงเกิดจาก **ชั้นเทคนิค+ทดสอบสมมติว่ามีความสามารถ "ดูประวัติ" อยู่แล้ว แต่ไม่มีฟีเจอร์/journey/API ใดนิยามความสามารถนี้ไว้จริงในชั้นต้นทาง** ไม่ใช่ความผิดของ prototype โดยตรง — ส่งสัญญาณ `NEEDS_FEATURE_JOURNEY_SYNC` ให้ตัดสินใจก่อนว่าจะเพิ่มเป็นฟีเจอร์ใหม่ (แล้วค่อยไล่ให้ `sync-technical-spec` เพิ่ม API + `build-prototype` เพิ่มหน้าจอ) หรือจะปรับ TC-13-08/09 ให้ตรวจสอบผ่านช่องทางอื่นที่ไม่ใช่ UI (เช่น เชิงเทคนิคเท่านั้น) แทน — **ไม่ใช่การตัดสินใจที่ prototype-auditor ควรทำเอง**

2. **NFR-05 AC-4 + TC-15-11 (ปฏิเสธการบันทึกประวัติของมนุษย์ที่ไม่ระบุผู้กระทำ — regression guard)** — อ่านขั้นตอนของ TC-15-11 แล้วพบว่าโจทย์ระบุไว้ตรงๆ ว่าเป็นการ "จำลองการเรียกบันทึกผลการแก้ไขความขัดแย้งโดยไม่มีค่าผู้กระทำ (เช่น ผ่านช่องทางที่ไม่ผ่านหน้าจอปกติ หรือ session ที่ไม่ยืนยันตัวตนผู้กระทำ)" **นี่คือ TC เชิงเทคนิค/backend-validation ที่ตั้งใจจะข้าม UI ปกติอยู่แล้วโดยตัวโจทย์เอง** — ต้นแบบ HTML คงที่ (mock, ไม่มี backend จริง) จึงไม่มีทางแสดงพฤติกรรมนี้ได้อยู่แล้วโดยธรรมชาติของเครื่องมือ **ไม่ใช่ช่องว่างของ prototype** — ตรวจ `conflict-detail.html` เพิ่มเติมพบว่าทุกจุดที่มนุษย์เป็นผู้กระทำ (ปุ่ม "ใช้เวอร์ชันนี้ทั้งหมด" ทั้งสองคอลัมน์, ปุ่ม "บันทึกผลลัพธ์และปลดสถานะขัดแย้ง") แสดงชื่อผู้แก้ไขของแต่ละเวอร์ชันไว้ชัดเจนอยู่แล้ว (`แก้ไขโดย: สมชาย ใจดี` / `วิภา สายชล`) สอดคล้องกับหลักการ "การกระทำของมนุษย์ต้องระบุผู้กระทำ" ในเชิงภาพที่ตรวจได้จากการอ่านโค้ด
   - จุดสังเกตเล็กน้อย (ไม่ใช่ข้อผิดพลาด ไม่ต้องส่งสัญญาณ): `lead-review-detail.html` มี dialog ลงลายมือชื่อ (FR-18) ที่ระบุ "หัวหน้าผู้ลงนาม: (บัญชีปัจจุบัน)" ชัดเจน แต่ dialog "ส่งกลับให้แก้ไข" (FR-19) ในหน้าเดียวกันไม่ได้ระบุข้อความคล้ายกัน — ทั้งสองกรณีเป็นการกระทำของมนุษย์ตาม AC-4 เช่นกัน (ผู้กระทำ = บัญชีที่ login อยู่โดยปริยาย) ความไม่สม่ำเสมอนี้เป็นระดับ cosmetic/ข้อความเท่านั้น ไม่กระทบตรรกะ จึงไม่ยกเป็นสัญญาณอย่างเป็นทางการ แต่บันทึกไว้เผื่อ `prototype-writer` สนใจแก้ตอน rebuild รอบหน้า
   - เช่นเดียวกัน `admin-users.html` (FR-21, การจัดการบัญชี) ไม่มีข้อความ "ดำเนินการโดย (บัญชีปัจจุบัน)" ใน dialog ปิดใช้งานบัญชีทั้ง 3 ใบ — cosmetic เช่นกัน ไม่ส่งสัญญาณแยก

### ทิศทางที่ 2 — prototype ถูกแก้แล้วเอกสารยังไม่ตาม
ไม่พบพฤติกรรม/หน้าจอ/ปุ่มใหม่ใน HTML ที่ไม่มีรหัส FR/NFR ใดรองรับ (ตรวจตารางไฟล์↔ตารางแล้วครบ 1:1) และไม่พบ token สี/ขนาดใหม่ที่ไม่มีใน `DESIGN.md` รองรับในรอบนี้ — เนื้อหาของ `prototype.md` เองก็ระบุครบทุกจุดที่เพิ่ม token ใหม่ (`--state-progress-*`, `--state-account-*`) ว่าอ้างอิง DESIGN.md §2.4/§3.8 UX-14 ไว้แล้วในรอบก่อนหน้า **ไม่พบส่วนต่างทิศทางนี้ในรอบนี้**

### สรุปสถานะ prototype
**ยังไม่ up to date อย่างสมบูรณ์** — พบช่องว่าง 1 จุดจริง (ไม่ใช่การหาเรื่อง): ไม่มีหน้าจอ audit-trail สำหรับผู้ดูแลระบบตามที่ TC-13-08/TC-13-09 (ทั้งคู่ระดับสูง) คาดหวัง แต่ช่องว่างนี้**แก้ที่ prototype โดยตรงไม่ได้** เพราะต้นตออยู่ที่ feature-list.md/user-journey.md/api-spec.md ที่ไม่เคยนิยามความสามารถนี้ไว้เลย ส่วน TC-15-11 ยืนยันแล้วว่า**ไม่ใช่ช่องว่างของ prototype** เพราะเป็น backend-only test case ตามที่ระบุไว้ในตัวโจทย์เอง

**อะไร**: `feature-list.md` และ `user-journey.md` ไม่มีฟีเจอร์/ขั้นตอน journey ใดที่ครอบคลุม **"ผู้ดูแลระบบ (หรือบทบาทที่มีสิทธิ์) เปิดดูประวัติ/audit trail ของอาคารรายตัว"** — ทั้งที่ `test-cases/offline-sync.md` (TC-13-08, TC-13-09 ที่เพิ่งเพิ่มโดย `test-writer` ในรอบนี้) กำหนดขั้นตอนทดสอบที่อ้างอิงถึงหน้าจอนี้ตรงๆ ว่า "เข้าสู่ระบบด้วยบัญชีที่มีสิทธิ์ดูประวัติ (ผู้ดูแลระบบ) แล้วเปิดดูประวัติ (audit trail) ของอาคารนั้น"

- **FR-33** ค้นหา/กรองประวัติการแก้ไขทั่วทั้งระบบ (ระดับ กลาง) — สิทธิ์: ผู้ดูแลระบบ, หน่วยงานส่วนกลาง/ผู้บริหาร เท่านั้น (ขอบเขตกว้างกว่าทีมที่หัวหน้าผู้สำรวจรับผิดชอบ)
- ไม่มีรหัสใดถูกแก้ไข/ลบ — NFR-05 คงเนื้อหาเดิมทั้งหมด เพิ่มเฉพาะ wikilink cross-reference ต่อท้าย

### เหตุผลที่แยกเป็น 2 FR (ไม่ใช่ 1 หรือมากกว่า)
แยกตามขอบเขตและกลุ่มผู้ใช้ที่ต่างกันชัดเจน: FR-32 คือการไล่ดูประวัติของระเบียนเดียว (operational, ใช้เวลาตรวจทาน/มีข้อโต้แย้งเฉพาะจุด) ส่วน FR-33 คือการค้นหาข้ามระบบเพื่อการกำกับดูแลระดับหน่วยงาน (oversight) — รูปแบบเดียวกับที่เอกสารนี้เคยแยก FR-30/FR-31 ในหัวข้อ 4.7 มาก่อน ไม่แตกเกินความจำเป็นเพราะทั้งสองอ้างอิงข้อมูลประวัติชุดเดียวกันจาก NFR-05

### ทำไมจึงเลือกหัวข้อ 4.8 (สร้างหัวข้อใหม่) แทนที่จะใส่ในหัวข้อ 4.5 เดิม
หัวข้อ 4.5 "การจัดการผู้ใช้ สิทธิ์ และภาพรวมผลสำรวจ" เป็นกลุ่มฟังก์ชันบริหาร/ภาพรวม (FR-21–FR-24) ในขณะที่ audit trail เป็นความสามารถเชิง accountability ที่ผูกตรงกับ NFR-05 และเชื่อมโยงทั้ง FR-14 (หมวด 4.3) และ FR-31 (หมวด 4.7) ข้ามหลายหัวข้อ การแยกเป็นหัวข้อ 4.8 ใหม่ทำให้เห็นที่มา (คำอธิบายช่องว่างที่ `prototype-auditor` พบ) และขอบเขตชัดเจนกว่า สอดคล้องกับ pattern ที่เอกสารนี้ใช้มาแล้วสำหรับ 4.6/4.7

ตรวจ `db-spec.md`/`api-spec.md` เดิมแล้วพบว่า**ความสัมพันธ์นี้มีอยู่แล้วจริง** ผ่าน `SurveyParticipant` (junction entity ระหว่าง `SurveyedBuilding` และ `User` ที่มี `role_in_team = หัวหน้าผู้สำรวจ`) ซึ่งเป็น pattern ที่ operation 3 ตัวที่มีอยู่แล้วใช้ scoping แบบเดียวกันนี้อยู่ก่อนแล้ว ([[api-spec#10.3 ลงลายมือชื่อดิจิทัลรับรองผล|10.3]], [[api-spec#13.1 ค้นหา/กรองรายการอาคารที่สำรวจแล้ว|13.1]], [[api-spec#15.1 แสดงรายการระเบียนที่มีความขัดแย้งของข้อมูลรอการแก้ไขด้วยมือ|15.1]]) — จึง**ไม่ต้องเพิ่ม entity/ความสัมพันธ์ใหม่**สำหรับ ownership-scoping ของ FR-32 ใช้ pattern เดิมนี้ต่อได้เลย ไม่ใช่ต้องอาศัย `Assignment`/`AssignmentMember` (FR-20) ตามที่ architecture ตั้งข้อสมมติไว้ (ข้อสมมตินั้นคลาดเคลื่อนเล็กน้อย แต่ไม่กระทบผลลัพธ์เพราะกลไก scoping ที่ต้องการมีอยู่แล้วผ่านเส้นทางอื่น) — จุดนี้ **ไม่เข้าเงื่อนไขที่ต้องถามผู้ใช้** เพราะเป็นการยืนยัน pattern ที่ถูกใช้ซ้ำแล้ว 3 ครั้งในเอกสารเดิม ไม่ใช่การตีความใหม่ที่กำกวม

### ประเด็น polymorphic ที่ผู้เรียกใช้เตือนไว้ — การตัดสินใจ
`AuditTrailEntry.related_entity_id` เป็น polymorphic (อ้างอิงได้ทั้ง `SurveyedBuilding`, `StructuralDamage`, `ComponentDamage`, `ExternalDamage`, `User`, `SyncConflict`) และ spec (feature-list ฟีเจอร์ 16) ระบุชัดว่า FR-32 ต้อง "ครอบคลุมทั้งกรณีผู้สำรวจแก้ไขผลที่ AI เสนอ (เกิดที่ `StructuralDamage`/`ComponentDamage`) และกรณีแก้ไขความขัดแย้งด้วยมือ (เกิดที่ `SyncConflict`)" — **ไม่ใช่ประเด็นกำกวมที่ต้องถามผู้ใช้** (สเปกฟันธงแล้วว่าต้องครอบคลุม) แต่เป็นโจทย์เชิงโครงสร้างข้อมูลว่าจะ "ทำอย่างไร" ให้ query รายอาคารได้ครบ **ตัดสินใจ**: เพิ่ม attribute ใหม่ `related_surveyedbuilding_id` (อ้างอิงถึง `SurveyedBuilding`, ไม่บังคับ/nullable เมื่อ `related_entity_name = User`) เข้า `AuditTrailEntry` เป็นค่าที่ resolve ไว้ล่วงหน้าตอนสร้างระเบียนเสมอ (กฎใหม่ในหัวข้อ 10 ข้อ 8 ของ db-spec) แทนการให้ operation อ่านต้อง join ตามชนิด entity ทีละแบบทุกครั้ง — ทำให้ทั้ง FR-32 (ดึงประวัติอาคารครบทุกเหตุการณ์รวม entity ย่อย) และ FR-33 (กรองตามพื้นที่/จังหวัด) ทำได้ตรงไปตรงมา ไม่ต้องเพิ่ม component ใหม่ตามที่ architecture §6.7 กำหนดไว้แล้ว

### สิ่งที่ยังไม่ครอบคลุมในรอบนี้
- ไม่ได้ตรวจสอบ/แก้ไข anchor ที่ชี้ออกจากไฟล์อื่น (เช่น `test-cases/*.md`, `acceptance-criteria.md`) เข้ามาที่ `detailed-design/*.md` เพราะอยู่นอกขอบเขตไฟล์ที่ agent นี้เขียนได้ — ถ้าพบว่ามี ต้องส่งสัญญาณให้ `test-writer` แก้เอง (ยังไม่ได้ตรวจสอบว่ามีหรือไม่ในรอบนี้)
- ไม่ได้ยืนยัน/เพิ่มค่า retention policy ของ `AuditTrailEntry` (ยังคงเป็นประเด็นรอตัดสินใจใน `db-spec.md` §11 ตามเดิม) — ระบุไว้ในหัวข้อ "ประเด็นที่ยังไม่ตัดสินใจ" ของทั้งสองไฟล์ใหม่แล้วเพื่อไม่ให้ผู้อ่านเข้าใจผิดว่าเป็นเรื่องตัดสินใจแล้ว
- ไม่ได้ตรวจสอบเนื้อหาของไฟล์ `detailed-design/*.md` อื่นๆ ที่ไม่เกี่ยวกับ anchor (เช่น ความถูกต้องของ sequence diagram เดิม) ซ้ำอีกครั้ง เพราะอยู่นอกขอบเขตงานที่ผู้เรียกใช้ระบุมา (เฉพาะฟีเจอร์ 16/17 + แก้ anchor เท่านั้น)
