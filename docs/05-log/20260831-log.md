รับสัญญาณ `## NEEDS_DESIGN_SYSTEM` จาก `/audit-prototype` รอบก่อนหน้า (ดู entry ด้านบน): token `--state-pending-*`/`--state-synced-*` ซึ่ง `DESIGN.md` หัวข้อ 2.4 นิยามไว้เฉพาะ "สถานะการซิงค์ข้อมูล" (NFR-01/02) ถูก `lead-assign.html`, `field-my-tasks.html` (ผ่าน class `.badge.pending`/`.badge.synced`, `.sync-indicator.*`) และ `lead-review-list.html` นำไปใช้สื่อความหมาย "สถานะความคืบหน้าของงาน/การตรวจทาน" (FR-19/20) และ `.wizard-step.done` ในหน้าจอวิซาร์ดสำรวจ 4 หน้านำไปใช้สื่อ "ขั้นตอนที่ทำเสร็จแล้ว" — เป็น semantic drift ที่ไม่ใช่ข้อผิดพลาดของ prototype แต่เป็นช่องว่างของ design system งานนี้**แก้เฉพาะ `DESIGN.md`** ไม่แตะไฟล์ prototype ตามหน้าที่เจ้าของไฟล์

**หมายเหตุข้อจำกัดเซสชัน**: เซสชันนี้ไม่มีเครื่องมือ `AskUserQuestion` ให้ใช้งาน (ไม่อยู่ในชุดเครื่องมือที่ได้รับ) จึงไม่ได้สัมภาษณ์ผู้ใช้ตามขั้นตอนปกติของ `design-system-writer` — เลือกแนวทางที่เห็นว่าเหมาะสมที่สุดเองพร้อมเหตุผลกำกับ ให้ผู้เรียกใช้ (agent ที่เรียกงานนี้) นำไปยืนยันกับผู้ใช้จริงแทน

### แนวทางที่พิจารณาและเหตุผลที่เลือก
พิจารณา 3 แนวทาง:
1. **เพิ่มกลุ่ม token ใหม่ `--state-progress-*` แยกจากสถานะซิงค์โดยสิ้นเชิง (เลือกแนวทางนี้)** — ข้อดี: ตัดการเชื่อมโยงเชิงความหมายระหว่าง "สถานะซิงค์" กับ "สถานะความคืบหน้าของงาน" อย่างถาวร ป้องกันปัญหาที่ระบุไว้ในสัญญาณต้นทาง (เปลี่ยนสีสถานะซิงค์แล้วสีสถานะงานเปลี่ยนตามโดยไม่ตั้งใจ) และตรงกับหลักการที่ `DESIGN.md` ใช้อยู่แล้วกับ conflict/ai token (แยก token ตามความหมายแม้จะมีสถานะ "ไม่เสร็จ/เสร็จแล้ว" คล้ายกัน) ข้อเสีย: เพิ่มจำนวน token ในเอกสาร ต้องระวังไม่ให้ผู้ใช้สับสนว่าทำไมสีซ้ำกับกลุ่มเดิม (แก้ด้วยหมายเหตุกำกับชัดเจนในเอกสาร)
2. ขยายนิยาม token เดิมให้ครอบคลุมทั้งสองความหมาย — ไม่เลือก เพราะเป็นสาเหตุของปัญหาเดิม (ทำให้ token เดียวรับผิดชอบสองโดเมนที่ไม่เกี่ยวข้องกัน สถานะซิงค์คือ NFR-01/02 ส่วนสถานะความคืบหน้างานคือ FR-19/20 การเปลี่ยนแปลงในโดเมนหนึ่งจะกระทบอีกโดเมนเสมอ)
3. คงนิยามเดิม ผลักให้ `build-prototype` แก้การใช้งานผิดแทน — ไม่เลือก เพราะ prototype มีความต้องการใช้สีสถานะ "ยังไม่เสร็จ/เสร็จแล้ว" จริงตาม FR-19/20 การไม่ให้ token รองรับความหมายนี้เลยจะทำให้ prototype ไม่มีทางเลือกอื่นนอกจากยืมของกลุ่มอื่นซ้ำอีก (ปัญหาเดิมจะเกิดซ้ำกับ token กลุ่มอื่นแทน)

**การตัดสินใจเรื่องค่าสี**: ให้ `--state-progress-todo-*` ใช้ค่าเดียวกับ `--state-pending-*` (`#5C5346`/`#EFEBE4`) และ `--state-progress-done-*` ใช้ค่าเดียวกับ `--state-synced-*` (`#41564A`/`#E9EEEA`) ทุกตัวอักษร — จงใจให้ค่าซ้ำเพื่อไม่ต้องคำนวณคอนทราสต์ใหม่ (ค่านี้ผ่าน AAA ≥7:1 ตามที่ยืนยันไว้แล้วในหัวข้อ 2.3 ของเอกสาร) แต่แยกชื่อ token เพื่อตัดการเชื่อมโยงเชิงความหมาย บันทึกไว้ชัดเจนในหัวข้อ "สิ่งที่ยังไม่ตัดสินใจ" ว่าถ้าในอนาคตพบเคสจริงที่สถานะซิงค์และสถานะความคืบหน้าของงานปรากฏพร้อมกันในหน้าเดียวจนผู้ใช้แยกไม่ออก ต้องกลับมาแยกค่าสีให้ต่างกันจริง

### ส่วนที่แก้ใน `docs/02-design/DESIGN.md`
1. **หัวข้อ 2.4** — เพิ่มคำเตือนชัดเจนว่า `--state-pending-*`/`--state-synced-*` ใช้ได้เฉพาะสถานะซิงค์ (NFR-01/02) เท่านั้น และเพิ่มตารางใหม่ "สถานะความคืบหน้าของงาน/การตรวจทาน" พร้อม token `--state-progress-todo-fg/-bg` และ `--state-progress-done-fg/-bg` ระบุ FR-19/20 กำกับ พร้อมหมายเหตุอธิบายเหตุผลที่ค่าสีซ้ำกับกลุ่มเดิม
2. **หัวข้อ 3.8 (ป้ายสถานะ)** — เพิ่มตารางช่วยตัดสินใจ "ป้ายนี้สื่อเรื่องอะไร → ใช้ token กลุ่มใด" ครอบคลุมทั้ง 5 กลุ่ม (severity, sync, conflict, ai, progress) พร้อมตัวอย่างหน้าจอจริงที่เกี่ยวข้อง เพื่อป้องกัน semantic drift ซ้ำในอนาคต
3. **หัวข้อ 4 (UX Guidelines)** — เพิ่ม `UX-14 แยก token ตามความหมาย ห้ามข้ามกลุ่มความหมาย` เป็นกติกาบังคับใหม่
4. **หัวข้อ 5 (สิ่งที่ยังไม่ตัดสินใจ)** — เพิ่มบันทึกว่าค่าสีของ `--state-progress-*` ซ้ำกับ `--state-pending-*`/`--state-synced-*` โดยตั้งใจ และเงื่อนไขที่ต้องกลับมาแยกค่าสีจริงในอนาคต

### คู่สีที่ต้องคำนวณคอนทราสต์ยืนยันเพิ่มเติม
**ไม่มี** — ค่าสีของ `--state-progress-todo-*`/`--state-progress-done-*` เป็นค่าเดียวกับ `--state-pending-*`/`--state-synced-*` ที่มีอยู่แล้วในเอกสาร (ระบุไว้ว่าผ่าน AAA ≥7:1 ทั้งบนพื้น `--surface-page` และบนพื้น `-bg` ของตัวเองแล้วในหัวข้อ 2.3) จึงไม่มีค่าสีใหม่ที่ต้องคำนวณซ้ำ — คงยึดกติกาเดิมว่าไม่มีการอ้างตัวเลขคอนทราสต์ที่ไม่ได้ตรวจสอบ

### ผลกระทบต่อ Prototype
มี — `lead-assign.html`, `field-my-tasks.html`, `lead-review-list.html` และหน้าจอวิซาร์ดสำรวจ 4 หน้าที่ใช้ `.wizard-step.done` **ยังใช้ token `--state-pending-*`/`--state-synced-*` เดิมอยู่** ต้องเปลี่ยนไปอ้างอิง `--state-progress-todo-*`/`--state-progress-done-*` แทน เพื่อให้สอดคล้องกับนิยามใหม่ — งานนี้ไม่ได้แก้ไฟล์ prototype (นอกเหนือขอบเขตหน้าที่) จึงต้องส่งต่อให้ `/build-prototype` หรือ `prototype-writer` ดำเนินการแก้ไขในรอบถัดไป

### สิ่งที่ยังไม่ตัดสินใจ (เพิ่มจากรอบนี้)
- ถ้าสถานะซิงค์และสถานะความคืบหน้าของงานต้องแสดงพร้อมกันในหน้าเดียวจนแยกไม่ออก ต้องแยกค่าสีจริงในรอบถัดไป (ยังไม่มีเคสยืนยัน)
- ทุกรายการเดิมในหัวข้อ 5 ของ `DESIGN.md` (ไอคอน, high-visibility mode, dark mode, โลโก้, ค่าเชิงเทคนิค) ยังคงค้างอยู่เหมือนเดิม ไม่มีการเปลี่ยนแปลงในรอบนี้

### การตัดสินใจเรื่อง `lead-review-detail.html` (ประเด็นที่ `prototype-writer` แจ้งค้างไว้)

**การตัดสินใจ**: นี่คือช่องว่างของตาราง §3.8 เอง ไม่ใช่ prototype ใช้ token ผิด — เพราะ `prototype-writer` ทำถูกต้องตามตัวอักษรของ DESIGN.md ที่มีอยู่ (ไม่ระบุไฟล์นี้ไว้ จึงไม่แตะ) แต่คำนิยามของหมวดหมู่เองครอบคลุมความหมายนี้อยู่แล้ว → ส่งสัญญาณ **`NEEDS_DESIGN_SYSTEM`** ให้ `design-system-writer` เพิ่ม `lead-review-detail.html` เข้าคอลัมน์ตัวอย่างของ §3.8 (และ/หรือระบุกติกาทั่วไปแทนการแจกแจงชื่อไฟล์ เพื่อกันปัญหาซ้ำในอนาคต) — **ไม่ส่ง `NEEDS_PROTOTYPE_REBUILD` ในจุดนี้** เพราะค่าสีของ token ทั้งสองกลุ่มเท่ากันทุกตัวอักษร (ไม่มีบั๊กที่เห็นบนจอจริง) และการแก้ prototype ให้ใช้ token ใหม่ควรเกิด**หลัง**จาก DESIGN.md ยืนยันการจัดกลุ่มก่อนเสมอ (หลักการ single source of truth) เมื่อ DESIGN.md แก้แล้ว จะต้องมี `NEEDS_PROTOTYPE_REBUILD` ตามมาอีกจุดหนึ่งเพื่อสลับคลาสใน `lead-review-detail.html` บรรทัดเดียว

### สัญญาณที่ส่งต่อให้ผู้เรียกใช้
- `## NEEDS_DESIGN_SYSTEM` — `DESIGN.md` §3.8 (บรรทัด 306) ตารางตัวอย่างของหมวด "ความคืบหน้าของงาน/การตรวจทาน" ยังไม่ระบุ `lead-review-detail.html` ทั้งที่นิยามหมวดหมู่ (บรรทัด 116-118) ครอบคลุมความหมายนี้อยู่แล้ว และหน้านี้แสดงสถานะเดียวกันของระเบียนเดียวกันกับ `lead-review-list.html` ที่ถูกจัดอยู่ในหมวดนี้แล้ว (ต่างกันแค่มุมมองรายการ/รายละเอียด) — ขอให้พิจารณาเพิ่มชื่อไฟล์นี้ในตาราง หรือปรับคำอธิบายให้เป็นกติกาทั่วไปแทนการแจกแจงชื่อไฟล์เจาะจง เพื่อกันปัญหาลักษณะนี้ซ้ำในอนาคต
- `## NEEDS_PROTOTYPE_REBUILD` — `conflict-list.html` ยังไม่มีสถานะ "ไม่มีระเบียนรอแก้ไข" ตามที่ `acceptance-criteria.md` FR-30 AC-3 และ `test-cases/manual-conflict-resolution.md` TC-15-03 กำหนด (แนะนำรูปแบบเดียวกับ empty-state ที่เพิ่งเพิ่มใน `lead-assign.html`/`building-search.html`) — **หมายเหตุ**: เมื่อ `NEEDS_DESIGN_SYSTEM` ข้างต้นถูกปิดแล้ว จะมี `NEEDS_PROTOTYPE_REBUILD` ตามมาอีกจุดหนึ่งเพื่อสลับคลาส badge ใน `lead-review-detail.html` จาก `.badge.pending` เป็น `.badge.task-todo`
- ไม่มี `NEEDS_NEW_REQUIREMENT` (ไม่พบพฤติกรรมใหม่ในรอบนี้ที่ไม่มีรหัส FR/NFR รองรับ)
- ไม่มี `NEEDS_FEATURE_JOURNEY_SYNC` (ไม่พบฟีเจอร์/journey ใหม่ที่ยังไม่ครอบคลุมในรอบนี้)
- ไม่มี `NEEDS_TEST_PLAN_SYNC` (AC/TC ของทุกจุดที่ตรวจมีอยู่ครบแล้ว เพียงแต่ prototype ยังไม่แสดงหน้าจอตาม ซึ่งจัดเป็น `NEEDS_PROTOTYPE_REBUILD`)

### สถานะหลังงานนี้
สัญญาณจาก audit รอบ 2 ปิดครบทั้ง 3 จุดจริงตามขอบเขตที่สั่ง (2 empty state ของ FR-20/FR-23 + token migration ของ 3 ไฟล์) ไม่มีจุดค้าง ไม่พบ regression ใหม่จากการแก้ล่าสุด แต่พบส่วนต่างใหม่ 2 จุด: (1) ช่องว่าง classification ของ `DESIGN.md` §3.8 ที่ไม่ครอบคลุม `lead-review-detail.html` ทั้งที่ควรอยู่ในหมวดเดียวกับ `lead-review-list.html` และ (2) `conflict-list.html` ยังขาด empty state ตาม FR-30 AC-3/TC-15-03 — ทั้งสองจุดเป็นส่วนต่างที่เพิ่งถูกค้นพบในรอบนี้ ไม่ใช่จุดที่เคยถูกปิดแล้วแล้วกลับมาใหม่ ไม่มีการแก้ไขไฟล์ใดในโฟลเดอร์ prototype หรือเอกสารชั้นอื่นในรอบนี้

### บริบท
รับสัญญาณ `## NEEDS_DESIGN_SYSTEM` จาก entry `prototype-auditor` รอบ 3 ด้านบน: ตารางช่วยเลือกกลุ่ม token ในหัวข้อ 3.8 (คอลัมน์ "ตัวอย่าง" ของแถว "ความคืบหน้าของงาน/การตรวจทาน") ระบุไฟล์ไว้เพียง `lead-assign`, `field-my-tasks`, `lead-review-list` + จุดบอกขั้นตอนวิซาร์ด แต่ `lead-review-detail.html` มี badge "รอตรวจทาน" สื่อสถานะเดียวกันของระเบียนเดียวกัน (FR-19) กับคอลัมน์สถานะใน `lead-review-list.html` เพียงต่างมุมมอง (รายการ/รายละเอียด) auditor ยืนยันว่านิยามหมวดหมู่ในหัวข้อ 2.4 ครอบคลุมความหมายนี้อยู่แล้ว ช่องว่างอยู่ที่ตารางตัวอย่างใน §3.8 เท่านั้น งานนี้เล็กมาก **แก้เฉพาะจุดใน `DESIGN.md`** ไม่แตะไฟล์ prototype (เป็นหน้าที่ของ `prototype-writer` ในรอบถัดไปที่จะสลับคลาส badge ใน `lead-review-detail.html`)

**หมายเหตุข้อจำกัดเซสชัน**: ไม่มีเครื่องมือ `AskUserQuestion` ในเซสชันนี้ และงานชัดเจนพอที่จะตัดสินเองได้ตามคำสั่งของผู้เรียก จึงไม่ได้สัมภาษณ์ผู้ใช้เพิ่มเติม — อ่านเฉพาะหัวข้อ 2.4 และ 3.8 ของ `DESIGN.md` เท่านั้น (ไม่ได้อ่านทั้งไฟล์) ตามคำเตือนเรื่อง session limit

### สิ่งที่แก้ใน `docs/02-design/DESIGN.md` (หัวข้อ 3.8 เท่านั้น)
1. **เติมชื่อไฟล์ `lead-review-detail`** เข้าคอลัมน์ "ตัวอย่าง" ของแถว "ความคืบหน้าของงาน/การตรวจทาน" พร้อมวงเล็บอธิบายเหตุผลสั้นๆ ว่า badge "รอตรวจทาน" ในไฟล์นี้คือระเบียนเดียวกับคอลัมน์สถานะใน `lead-review-list.html` แค่มุมมองรายละเอียด
2. **เพิ่มย่อหน้ากติกาป้องกันปัญหาซ้ำต่อท้ายตาราง** ระบุชัดว่ารายชื่อไฟล์ในคอลัมน์ "ตัวอย่าง" เป็นเพียงตัวอย่างประกอบ **ไม่ใช่รายการปิด (non-exhaustive)** เพราะตารางนี้จะล้าสมัยทุกครั้งที่ prototype เพิ่มหน้าจอใหม่โดยธรรมชาติ — เกณฑ์ตัดสินที่แท้จริงคือ **ความหมายที่ป้ายนั้นสื่อ** ไม่ใช่ว่าไฟล์ถูกระบุไว้ในตารางหรือไม่ ถ้าพบป้ายในไฟล์ที่ไม่ถูกระบุแต่สื่อความหมายเดียวกับแถวใดในตาราง (เช่น ระเบียน/สถานะเดียวกันที่แสดงต่างมุมมอง) ให้จัดเข้ากลุ่ม token เดิมของแถวนั้นได้ทันทีโดยไม่ต้องรอแก้ตารางนี้ก่อน แล้วค่อยเพิ่มชื่อไฟล์เข้ามาเป็นตัวอย่างเพิ่มเติมภายหลังเพื่อความครบถ้วนของเอกสาร

**เหตุผลที่เลือกวิธีนี้แทนแนวทางอื่น**: พิจารณาแล้วว่าการลบคอลัมน์ "ตัวอย่าง" ออกทั้งหมดจะทำให้เอกสารเป็นนามธรรมเกินไปจนผู้เขียน prototype รอบแรกนึกภาพไม่ออกว่าแต่ละหมวดหมู่ใช้กับหน้าจอลักษณะใด (ตัวอย่างยังมีประโยชน์เชิงการสื่อสาร) จึงเลือกคงตัวอย่างไว้แต่ **ประกาศชัดเจนว่าไม่ใช่รายการปิด** แทน — วิธีนี้แก้ต้นตอของปัญหาจริง (คนอ่านตีความ "ไม่อยู่ในตาราง = ไม่เข้าเกณฑ์" ทั้งที่นิยามหมวดหมู่ครอบคลุมอยู่แล้ว) โดยไม่ต้องแลกกับการสูญเสียตัวอย่างที่เป็นประโยชน์

## design-system-writer: ปิดสัญญาณ `NEEDS_DESIGN_SYSTEM` จาก `/audit-prototype` รอบ 5 — เพิ่มกลุ่ม token สถานะบัญชีผู้ใช้ (โดเมนที่สาม) + เสริม UX-14

### บริบท
รับสัญญาณ `## NEEDS_DESIGN_SYSTEM` จากผู้เรียก (สรุปผล `/audit-prototype` รอบ 5): `admin-users.html` ใช้ `.badge.synced` สื่อ "ใช้งานอยู่" และ `.badge.offline` สื่อ "ปิดใช้งานแล้ว" ซึ่งเป็นสถานะบัญชีผู้ใช้ (FR-21, NFR-08) — คนละโดเมนกับสถานะซิงค์ (NFR-01/02) โดยสิ้นเชิง เป็น semantic drift โดเมนที่สามที่พบ ต่อจากกรณีสถานะความคืบหน้าของงาน (entry ก่อนหน้าของวันนี้) งานนี้**แก้เฉพาะ `DESIGN.md`** ไม่แตะ `admin-users.html` (เป็นหน้าที่ `prototype-writer` ในรอบถัดไป) ไม่มี `AskUserQuestion` ในเซสชันนี้ ตัดสินใจเองตามที่ผู้เรียกอนุญาต — อ่านเฉพาะหัวข้อ 2.1, 2.4, 3.8 และ UX-14 เท่านั้นตามคำเตือนเรื่อง session limit

### Token ใหม่
| Token | ค่า | ใช้เมื่อ |
|---|---|---|
| `--state-account-active-fg` / `-bg` | `#41564A` / `#E9EEEA` | บัญชีใช้งานได้ตามปกติ (FR-21) |
| `--state-account-inactive-fg` / `-bg` | `#5C5346` / `#EFEBE4` | บัญชีถูกปิดใช้งานแล้ว เข้าสู่ระบบไม่ได้ (FR-21, NFR-08) |

### เหตุผลที่เลือกค่านี้ (ชั่งน้ำหนักตามที่ผู้เรียกแนะนำให้พิจารณา)
- **ไม่ใช้ `--text-disabled`/`--surface-muted`**: สอง token นี้ออกแบบมาสำหรับองค์ประกอบ UI ที่ปิดใช้งานเชิงโต้ตอบและมีคอนทราสต์ต่ำโดยตั้งใจ ตามกติกาหัวข้อ 2.1 ที่ห้ามใช้ `--text-disabled` กับ "ข้อมูลที่ผู้ใช้ต้องอ่าน" — แต่สถานะบัญชีในหน้าผู้ดูแลระบบเป็นข้อมูลที่ผู้ดูแลต้องอ่านและตัดสินใจต่อจริง (เช่น จะเปิดบัญชีคืนหรือไม่) ตรงกับข้อกังวลที่ผู้เรียกชี้ไว้เป๊ะ จึงต้องผ่านเกณฑ์คอนทราสต์เดียวกับข้อความสำคัญอื่น
- **ไม่ใช้ `--state-offline-*`**: "ปิดใช้งานแล้ว" ไม่เกี่ยวกับการเชื่อมต่อเครือข่ายเลย การยืมสีออฟไลน์จะทำให้ผู้ดูแลระบบสับสนว่าบัญชีนี้ "ยังไม่ได้ซิงค์"
- **เลือกใช้ค่าเดียวกับ `--state-progress-done-*`/`--state-progress-todo-*` ทุกตัวอักษร (ต่อยอดแนวทางรอบก่อน)**: ไม่ต้องคำนวณคอนทราสต์ใหม่ (ผ่าน AAA ≥7:1 ยืนยันแล้วในหัวข้อ 2.3) และจับคู่ความหมายที่ใกล้เคียงกัน ("ใช้งานอยู่" ≈ สถานะบวก/ปกติ เหมือน "เสร็จแล้ว", "ปิดใช้งานแล้ว" ≈ สถานะเป็นกลาง-ลบเล็กน้อย เหมือน "ยังไม่เริ่ม") แต่แยกชื่อ token เพื่อตัดการเชื่อมโยงเชิงความหมายระหว่างสามโดเมนอย่างเด็ดขาด บันทึกเงื่อนไขไว้ว่าถ้าสถานะบัญชีต้องแสดงพร้อมสถานะซิงค์/ความคืบหน้างานในหน้าเดียวจนแยกไม่ออก ต้องกลับมาแยกค่าสีจริงในรอบถัดไป (ยังไม่พบเคสจริง)

### คู่สีที่ต้องคำนวณคอนทราสต์ยืนยัน
**ไม่มีค่าสีใหม่** — `--state-account-active-*`/`--state-account-inactive-*` ใช้ค่าเดียวกับ `--state-progress-done-*`/`--state-progress-todo-*` ทุกตัวอักษร ซึ่งเป็นค่าเดียวกับ `--state-synced-*`/`--state-pending-*` เดิมที่ยืนยันผ่าน AAA ≥7:1 แล้วในหัวข้อ 2.3 ของเอกสาร (ทั้งบนพื้น `--surface-page` และบนพื้น `-bg` ของตัวเอง) จึงไม่มีคู่สีใหม่ที่ต้องให้ผู้เรียกคำนวณคอนทราสต์เพิ่ม

### ส่วนที่แก้ใน `docs/02-design/DESIGN.md`
1. **หัวข้อ 2.4** — เพิ่มกลุ่มใหม่ "สถานะบัญชีผู้ใช้ (Account Status)" ต่อท้ายกลุ่มความคืบหน้าของงาน พร้อม token ทั้งสองคู่ และหมายเหตุอธิบายเหตุผล 3 ข้อข้างต้น (ทำไมไม่ใช้ text-disabled, ทำไมไม่ใช้ state-offline, ทำไมค่าสีซ้ำ)

3. **UX-14** — (ก) เติม "สถานะบัญชีผู้ใช้" เข้ารายการโดเมนสถานะที่ต้องไม่ปนกัน (ข) เพิ่มย่อหน้าใหม่ระบุขั้นตอนบังคับเมื่อพบโดเมนสถานะใหม่ที่ยังไม่มี token: ห้ามยืมกลุ่มเดิมแม้ชื่อจะฟังดูใช้ได้ ให้หยุดแล้วส่งสัญญาณผ่าน `/sync-design-system` ก่อนใช้งานจริงเสมอ พร้อมอ้างอิงว่ารูปแบบนี้เกิดซ้ำมาแล้ว 3 ครั้งเพื่อให้เห็นน้ำหนักของปัญหา — เลือกเสริมเข้า UX-14 เดิมแทนการตั้งกติกาใหม่ (UX-15) เพราะเป็นเนื้อหาเดียวกัน (การแยก token ตามความหมาย) เพียงต้องระบุขั้นตอนปฏิบัติที่เป็นรูปธรรมกว่าเดิม ไม่ใช่หลักการใหม่

### ผลกระทบต่อ Prototype

### บริบท
ผู้เรียกระบุ scope เจาะจง: ตรวจ 9 ไฟล์ที่ไม่เคยถูกไล่ตรวจละเอียดเทียบ AC/test case ทุกข้อมาก่อน ([[../02-design/01-prototypes/20260830-01-v1/conflict-detail|conflict-detail.html]], `field-survey-building.html`, `field-survey-damage.html`, `field-survey-photo-ai.html`, `field-survey-summary.html`, `field-survey-sketch.html`, `admin-users.html`, `field-sync-status.html`, `field-my-tasks.html`) โดยระบุลำดับความสำคัญมาให้ชัดเจน และสั่งชัดว่า "ตรวจลึก 5 ไฟล์มีค่ากว่าตรวจตื้น 9 ไฟล์" พร้อมเบาะแสจาก script สแกน git ของผู้เรียกว่าทั้ง 9 ไฟล์มี `empty-state`/`banner danger`/`field-error` เท่ากับ 0 จุดทุกไฟล์ (ใช้ชี้เป้า ไม่ใช่ข้อสรุป) งานนี้เป็นงานตรวจอย่างเดียว **ไม่แก้ไฟล์ใดในโฟลเดอร์ prototype**

**หมายเหตุข้อจำกัดเซสชัน**: ผู้เรียกแจ้งว่าเซสชันนี้ชน API session limit มาแล้ว 5 ครั้ง จึงจำกัดการอ่านเฉพาะไฟล์ในขอบเขต + AC/test case เฉพาะฟีเจอร์ที่เกี่ยวข้อง ไม่อ่าน `feature-list.md`/`user-journey.md`/`backlog.md` ฉบับเต็ม (เปิดเฉพาะส่วน mermaid/ขั้นตอนของ journey ผู้สำรวจภาคสนามที่เกี่ยวกับ decision node F/J) — ยึดหลัก "ตรวจลึกดีกว่าตรวจตื้น" ตรวจจริง **5/9 ไฟล์** ตามลำดับในตารางของผู้เรียก แล้วหยุดรายงานผลกลับก่อนไล่ต่อ 4 ไฟล์ที่เหลือ
