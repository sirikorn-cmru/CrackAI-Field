# Audit Prototype

Skill นี้ตรวจความสอดคล้องระหว่าง **Prototype** กับ **เอกสารทุกชั้น** และทำให้กลับมาตรงกัน

```
01-spec/ → backlog.md → feature-list.md → user-journey.md
                              ↓                    ↓
        acceptance-criteria.md → test-cases/ → test-plan.md
                              ↓
                    01-prototypes/{version}/   ←  DESIGN.md
```

**ต่างจาก skill อื่นในโปรเจกต์ตรงที่ prototype เป็นได้ทั้งปลายทางและต้นทางของการเปลี่ยนแปลง:**

- **ทิศทางไล่ลง** — เอกสารถูกแก้ prototype ยังเป็นของเก่า → ต้องสร้าง/แก้ prototype ให้ตาม
- **ทิศทางย้อนขึ้น** — มีคนแก้ prototype โดยตรง (เพิ่มหน้าจอ เปลี่ยน flow) แล้วเอกสารยังไม่รู้เรื่อง
  → ต้องอัปเดตเอกสารชั้นที่เกี่ยวข้องให้ตาม **ไม่ใช่ลบสิ่งที่ทำใน prototype ทิ้ง**

การแก้ prototype โดยตรงมักเกิดจากการค้นพบระหว่างออกแบบที่ถูกต้องกว่าเอกสารเดิม
**ห้ามถือว่า prototype ผิดโดยอัตโนมัติ**

## กฎการถามผู้ใช้ (ใช้กับทุกคำถามใน workflow นี้)

ทุกครั้งที่ใช้ `AskUserQuestion` **ต้องเสนออย่างน้อย 3 ตัวเลือก/แนวทาง** แต่ละตัวเลือกระบุ
**ข้อดีและข้อเสีย** ใน `description` และ **ระบุตัวเลือกที่แนะนำ** เป็นตัวเลือกแรก ต่อท้าย label
ด้วย "(แนะนำ)" พร้อมเหตุผลที่อิงบริบทจริง

## ขอบเขตงาน (scope) — ระบุเจาะจงได้

ค่าเริ่มต้นคือตรวจ prototype **เวอร์ชันล่าสุด** เทียบกับ **เอกสารทุกชั้น** แต่ระบุเจาะจงได้:
**เวอร์ชันที่ต้องการตรวจ** · **ชั้นเอกสารที่ต้องการเทียบ** · **ตามบทบาท/journey/ฟีเจอร์/รหัส FR**
· **เฉพาะไฟล์ที่เพิ่งถูกแก้**

- ระบุมาชัดแล้ว → ส่งต่อใน prompt ตรงๆ **ห้ามถามซ้ำ** · ไม่ระบุ → ใช้ค่าเริ่มต้น ไม่ต้องถาม
- กำกวมว่าหมายถึงระดับใด → ถามก่อน โดยสร้างตัวเลือกจากเวอร์ชัน/ฟีเจอร์ที่มีอยู่จริง
- **scope ถูกจำกัดเมื่อใด ต้องรายงานเสมอว่าอะไรยังไม่ถูกตรวจ**

## เมื่อถูกเรียกใช้

1. **หาวันที่ปัจจุบัน** (`YYYYMMDD`) — subagent ไม่มี Bash ต้องส่งให้ใน prompt เสมอ

2. **ตรวจว่า prototype ถูกแก้ไขไปแล้วหรือไม่ (ทำเองด้วย Bash — subagent ทำไม่ได้)**
   นี่คือขั้นตอนที่ทำให้ทิศทางย้อนขึ้นตรวจได้จริง:
   - `git log -1 --format=%cd -- docs/02-design/01-prototypes/` และ
     `git log -1 --format=%cd -- docs/02-design/feature-list.md docs/01-requirements/backlog.md`
     เทียบกันว่าฝั่งใดถูกแก้ล่าสุดกว่า
   - `git status --short -- docs/02-design/01-prototypes/` ดูว่ามีไฟล์ที่แก้แล้วยังไม่ commit
   - `git diff --stat HEAD~5 -- docs/02-design/01-prototypes/` (หรือช่วงที่เหมาะสม) ดูว่าไฟล์ใด
     ในโฟลเดอร์ prototype ถูกแก้ล่าสุด
   - **ส่งรายชื่อไฟล์ที่เพิ่งถูกแก้เข้า prompt ของ subagent** เพื่อให้เน้นอ่านไฟล์เหล่านั้นก่อน
     — subagent อ่าน HTML ทุกไฟล์ไม่ไหว การชี้เป้าให้จึงสำคัญ
   - ถ้า git บอกว่า prototype ไม่เคยถูกแก้เลยหลังสร้าง ให้แจ้ง subagent ว่าน่าจะเป็นทิศทางไล่ลง
     อย่างเดียว **แต่ห้ามสั่งให้ข้ามการตรวจทิศทางย้อนขึ้น** เพราะไฟล์อาจถูกแก้นอก git

3. **ส่งต่อให้ subagent `prototype-auditor`**: เรียกผ่าน Agent tool
   (`subagent_type: prototype-auditor`, `run_in_background: false`) โดย prompt ต้องมี:
   วันที่ปัจจุบัน · scope ที่ตกลง · **ผลการตรวจ git จากข้อ 2** · บริบทว่านี่คือ session
   สนทนากับผู้ใช้จริง

4. **ตรวจสอบผลลัพธ์**: **ยืนยันว่า subagent ไม่ได้แก้ไฟล์ใดในโฟลเดอร์ prototype**
   (`git status --short -- docs/02-design/01-prototypes/` ต้องไม่มีไฟล์เปลี่ยนเพิ่มจากข้อ 2)
   ถ้าพบว่าแก้ **ถือว่าผิดกฎร้ายแรง หยุดและแจ้งผู้ใช้ทันที** — agent นี้ต้อง report-only 100%
   จากนั้นสุ่มตรวจข้อค้นพบ 1-2 จุดด้วยตัวเองก่อนเชื่อรายงาน

4.5. **ตรวจการตอบสนองของปุ่มด้วยเบราว์เซอร์จริง (บังคับ — ทำเองในเทรดหลัก subagent ทำไม่ได้)**

   `prototype-auditor` ตรวจได้แค่ว่า **"หน้าจอมีไหม ครอบคลุม AC ไหม"** และการอ่านโค้ดยืนยันได้แค่ว่า
   `onclick` **ที่มีอยู่**เขียนถูก — **บอกไม่ได้ว่าปุ่มไหนไม่มี handler ทั้งที่ควรมี** ช่องว่างนี้เคยทำให้
   ปุ่ม 4 จุดที่กดแล้วเงียบหลุดผ่าน audit มา **5 รอบ** รวมถึงปุ่มที่เป็นเส้นทางกู้คืนซึ่ง FR กำหนดไว้ตรงๆ

   a. **เปิดเซิร์ฟเวอร์** ด้วย preview tool ตาม `.claude/launch.json` — **ห้ามเปิดด้วย `file://`**
      เพราะ CSS แบบ path สัมพัทธ์จะไม่โหลดและทำให้สรุปผิดว่าสไตล์พัง ถ้ายังไม่มี `launch.json`
      ให้สร้าง config เสิร์ฟโฟลเดอร์ prototype แบบ static
   b. **ไล่ทุกหน้าจอในโฟลเดอร์** (ไม่ใช่เฉพาะหน้าที่เพิ่งแก้) รันสคริปต์ตรวจในหน้า โดยหา:
      - **ปุ่มไร้ handler**: `<button>` ที่ไม่มีทั้ง `onclick` และไม่ได้ `disabled` และไม่ได้อยู่ใน
        `<a href>` — นี่คือของจริงที่ต้องรายงาน
      - **handler ที่กดแล้วไม่เกิดอะไร**: เรียก handler ทุกตัวแล้วเทียบสถานะ `display` ของทุก
        element ที่มี `id` ก่อน/หลัง ถ้าไม่เปลี่ยนเลยและไม่ได้ยิง alert ให้ตั้งข้อสงสัย
      - **ดัก `alert`**: แทนที่ `window.alert` ด้วยตัวเก็บข้อความ มิฉะนั้น alert จะบล็อกการทดสอบ
      - **console error** และ **ลิงก์ภายในที่ตอบไม่ใช่ 200**
   c. **ยกเว้นสิ่งเหล่านี้ ไม่ใช่บั๊ก** (เคยเป็น false positive มาแล้ว):
      - `<summary>` ใน `<details>` — กดได้เองโดยไม่ต้องมี `onclick`
      - ปุ่ม `disabled` ที่ตั้งใจปิดตามสถานะ (เช่น ยังไม่ได้กรอกค่า)
      - ปุ่มที่ห่อด้วย `<a href>` อยู่แล้ว
   d. **ล้าง cache ก่อนสรุปเสมอ** — เบราว์เซอร์ cache ไฟล์ static ไว้ **เคยทำให้อ่านได้ว่าปุ่มยังไม่มี
      `onclick` ทั้งที่ไฟล์บนดิสก์แก้แล้ว** ถ้าผลที่เห็นขัดกับไฟล์จริง **ให้เชื่อไฟล์บนดิสก์ก่อน**
      แล้วโหลดใหม่พร้อม query string กันแคช อย่าเพิ่งสรุปว่า agent ไม่ได้แก้
   e. **เมื่อสลับสถานะ ต้องตรวจว่าไปสถานะที่ถูกต้อง ไม่ใช่แค่ "เปลี่ยนอะไรก็ได้"** — เทียบชื่อ
      element ที่เปิด/ปิดจริงกับสิ่งที่ปุ่มนั้นควรทำตาม AC/detailed-design
   f. **ข้อค้นพบจากข้อนี้ให้รวมเข้า `## NEEDS_PROTOTYPE_REBUILD` ในข้อ 5** พร้อมระบุไฟล์+บรรทัด
      และ**เสนอวิธีแก้ที่ตรงกับธรรมเนียมที่ prototype นั้นใช้อยู่แล้ว** (เช่น ถ้าไฟล์ชุดนั้นใช้
      `alert('… (สาธิต)')` กับการกระทำที่จำลองไม่ได้ ก็ให้ใช้แบบเดียวกัน ไม่ใช่คิดรูปแบบใหม่) —
      **ถ้ามีสถานะที่มีอยู่แล้วซึ่งแทนผลลัพธ์ของปุ่มนั้นได้ ให้เสนอสลับไปสถานะนั้นก่อนเสมอ**
      เพราะสาธิตเส้นทางกู้คืนได้จริง มีค่ากว่า alert
   g. **หลัง `build-prototype` แก้เสร็จ ต้องกลับมารันข้อนี้ซ้ำเฉพาะจุดที่แก้** — รายงานของ
      `prototype-writer` บอกได้แค่ว่ามัน*ตั้งใจ*แก้อะไร ไม่ได้ยืนยันว่ากดแล้วทำงาน

5. **จัดการสัญญาณตามลำดับ — ห้ามสลับ** เพราะแต่ละชั้นยึดชั้นก่อนหน้าเป็นแหล่งความจริง:

   | ลำดับ | สัญญาณ | ส่งต่อไปยัง |
   |---|---|---|
   | 1 | `## NEEDS_NEW_REQUIREMENT` | subagent `requirement-writer` (Agent tool) |
   | 2 | `## NEEDS_FEATURE_JOURNEY_SYNC` | `skill: sync-feature-journey` (Skill tool) |
   | 3 | `## NEEDS_TEST_PLAN_SYNC` | `skill: sync-test-plan` (Skill tool) |
   | 4 | `## NEEDS_DESIGN_SYSTEM` | `skill: sync-design-system` (Skill tool) |
   | 5 | `## NEEDS_PROTOTYPE_REBUILD` | `skill: build-prototype` (Skill tool) |

   - ส่งเนื้อหาใต้แต่ละหัวข้อแบบ **verbatim** ต่อไปด้วย เพื่อไม่ให้ชั้นปลายทางตรวจซ้ำทั้งหมด
   - **ถ้ามีสัญญาณข้อ 1** ให้ถือว่าชั้น 2-5 ล้าสมัยโดยปริยาย ต้องทำต่อทุกข้อแม้ไม่มีสัญญาณของมัน
   - **ข้อ 5 (`build-prototype`) ต้องเป็นข้อสุดท้ายเสมอ** และ **ห้ามรันเองอัตโนมัติ** —
     ต้องถามผู้ใช้ก่อนด้วย `AskUserQuestion` เพราะการสร้าง/แก้ prototype ต้องยืนยัน scope
     และเลือกระหว่างเวอร์ชันใหม่/แก้ของเดิมกับผู้ใช้เสมอ (`build-prototype` จะถามเองอีกที)
   - **ป้องกัน infinite loop**: ทำข้อ 5 ทั้งชุดซ้ำได้อีกไม่เกิน **1 รอบ** ถ้ารอบสองยังพบสัญญาณ
     ให้หยุดแล้วรายงานผู้ใช้ตรงๆ

6. **ตรวจสอบผลลัพธ์หลัง chain**: สุ่มอ่านเอกสารที่ถูกแก้จริงอย่างน้อย 1-2 จุดต่อชั้นที่ chain ไป
   **ห้ามเชื่อรายงานของ skill/subagent 100% โดยไม่ตรวจเอง**

7. **สรุปให้ผู้ใช้ทราบ**:
   - เวอร์ชัน prototype ที่ตรวจ และผลการตรวจ git ว่า prototype หรือเอกสารถูกแก้ล่าสุดกว่ากัน
   - **ส่วนต่างแยกตามทิศทาง** (เอกสารนำ / prototype นำ) ให้ชัด อย่ารวมกัน
   - เอกสารชั้นใดถูกอัปเดตบ้างจากการ chain พร้อมรหัส FR/NFR ใหม่ที่เกิดขึ้น (ถ้ามี)
   - **สิ่งที่ยังไม่ถูกตรวจ/ยังไม่ถูกแก้ในรอบนี้** พร้อมคำสั่งที่ควรรันต่อ
   - **ผลการตรวจปุ่มด้วยเบราว์เซอร์จากข้อ 4.5**: จำนวนหน้าจอที่ตรวจ · จำนวน control ทั้งหมด ·
     จำนวน handler ที่เรียกจริง · ปุ่มไร้ handler ที่พบและแก้แล้ว/ยังไม่แก้ · console error ·
     ลิงก์ที่ตอบไม่ใช่ 200 — **และแยกให้ชัดว่าอันไหนเป็น false positive ที่ตรวจแล้วไม่ใช่บั๊ก**
   - **ระบุขอบเขตของการตรวจด้วยเบราว์เซอร์ให้ตรงความจริง** — ข้อ 4.5 ยืนยันได้ว่า *ปุ่มตอบสนอง
     และสลับไปสถานะที่ถูก* แต่**ยังไม่ได้ยืนยันเรื่องการแสดงผลเชิงสายตา** (คอนทราสต์จริงบนจอ,
     ข้อความล้น, การแสดงผลบนจอขนาดต่างๆ) ถ้ายังไม่ได้ตรวจส่วนนี้ ต้องบอกตรงๆ อย่าปล่อยให้เข้าใจ
     ว่า "เปิดเบราว์เซอร์แล้ว = ตรวจครบทุกอย่างแล้ว"

## ข้อควรระวัง

- ห้ามข้ามการเรียก subagent แล้ววิเคราะห์เองตรงๆ ในเทรดหลัก — `prototype-auditor` คือแหล่ง
  ความจริงเดียวของกฎการเทียบ prototype กับเอกสาร
- **`prototype-auditor` เป็น report-only 100%** เขียนได้เฉพาะ log ของวันนั้น หากผลลัพธ์พูดถึง
  การแก้ไขไฟล์อื่นใด ให้หยุดและแจ้งผู้ใช้ทันที
- **ห้ามแก้ prototype เพื่อให้กลับไปตรงกับเอกสารเดิม โดยไม่ถามผู้ใช้** — สิ่งที่อยู่ใน prototype
  อาจเป็นการตัดสินใจเชิงออกแบบที่ตั้งใจ การลบทิ้งคือการทำลายงาน
- **ห้ามแก้เอกสารเพื่อกลบสิ่งที่พบใน prototype** เช่นกัน — ถ้า prototype มีพฤติกรรมที่ไม่มี FR
  รองรับ ทางที่ถูกคือเพิ่ม FR ผ่าน `requirement-writer` ไม่ใช่ลบพฤติกรรมนั้นออกจาก prototype
- ไฟล์ในชั้นต่างๆ ต้องแก้ผ่าน agent เจ้าของเท่านั้น: `feature-list.md`/`user-journey.md` ผ่าน
  `sync-feature-journey` · `docs/03-testing/**` ผ่าน `sync-test-plan` · `DESIGN.md` ผ่าน
  `sync-design-system` · `01-prototypes/` ผ่าน `build-prototype` · `backlog.md`/`01-spec/`
  ผ่าน `requirement-writer`
- skill นี้ **ไม่รวม**เอกสารเชิงเทคนิคใน `02-technical/` — ถ้าต้องการตรวจครบทั้งสายงาน
  ให้แนะนำ `/audit-pipeline` แทน
- ถ้า subagent รายงานว่ายังไม่เคยมี prototype เลย ให้แจ้งผู้ใช้พร้อมแนะนำ `/build-prototype`
  **แต่ห้ามรันเองอัตโนมัติ** (ดูข้อ 5)
- **ห้ามข้ามข้อ 4.5 แม้ `prototype-auditor` จะรายงานว่า up to date ทุกอย่าง** — สองอย่างนี้ตรวจคนละ
  เรื่องกัน: subagent ตรวจ *ความสอดคล้องกับเอกสาร* ส่วนข้อ 4.5 ตรวจ *ปุ่มตอบสนองไหม* prototype
  ที่ตรงกับเอกสารครบ 100% ยังมีปุ่มที่กดแล้วเงียบได้ และเคยเป็นแบบนั้นจริงมาแล้ว
- **ห้ามรันข้อ 4.5 ใน subagent** — subagent ไม่มีเครื่องมือเบราว์เซอร์ ต้องทำในเทรดหลักเท่านั้น
- **อย่าเชื่อสิ่งที่เบราว์เซอร์แสดงทันทีเมื่อมันขัดกับไฟล์บนดิสก์** — cache ของไฟล์ static เคยทำให้
  สรุปผิดว่า agent ไม่ได้แก้ไฟล์ ทั้งที่แก้แล้ว ตรวจไฟล์จริงก่อนเสมอแล้วค่อยโหลดใหม่แบบกันแคช
