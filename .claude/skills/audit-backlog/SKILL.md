# Audit Backlog

Skill นี้เป็น workflow มาตรฐานสำหรับตรวจสอบความสอดคล้อง ("up to date") ของเอกสาร**ช่วงต้น
สายงานทั้ง 4 ชั้น** และทำให้ทุกชั้นกลับมาตรงกันในคำสั่งเดียว:

```
01-spec/  →  backlog.md  →  feature-list.md  →  user-journey.md
 (ชั้น 1)      (ชั้น 2)         (ชั้น 3)            (ชั้น 4)
```

ชั้นซ้ายคือแหล่งความจริงของชั้นขวาเสมอ **การแก้ไขที่ชั้นใดชั้นหนึ่งจึงต้องไล่ลงไปให้ครบทุกชั้น
ที่อยู่ถัดจากนั้น** ไม่ใช่แก้เฉพาะจุดที่ถูกแตะ — skill นี้จัดการการไล่ลงให้อัตโนมัติผ่านการ
auto-chain ในข้อ 5-6 พร้อมบันทึก log ตามกฎใน `CLAUDE.md`

ความไม่สอดคล้องมีได้ 2 ทิศทาง และจัดการต่างกัน:
- **ไล่ลง (ปกติ)** — ชั้นต้นทางเปลี่ยน ชั้นปลายทางยังไม่ตาม → แก้ที่ชั้นปลายทางให้ตาม
- **ย้อนขึ้น** — ชั้นปลายทางมีพฤติกรรม/ความต้องการที่ไม่มีรหัส FR/NFR รองรับ → **ห้ามแก้ที่ชั้น
  ปลายทางให้กลบปัญหา** ต้องย้อนกลับไปเพิ่มที่ spec ผ่าน `requirement-writer` แล้วไล่ลงมาใหม่

## เมื่อถูกเรียกใช้

1. **หาวันที่ปัจจุบัน**: ใช้ค่าวันที่ปัจจุบันที่มีอยู่ในบริบทของคุณ (รูปแบบ `YYYYMMDD`)
   เพื่อส่งต่อให้ subagent ใช้ตั้งชื่อ/ต่อท้ายไฟล์ log ของวันนี้ — subagent ไม่มีเครื่องมือ Bash
   จึงหาวันที่เองไม่ได้ ต้องส่งมาให้ใน prompt เสมอ

2. **ส่งต่อให้ subagent `backlog-auditor`**: เรียกผ่าน Agent tool
   (`subagent_type: backlog-auditor`, รันแบบ foreground คือ `run_in_background: false`
   เพราะอาจต้องถามผู้ใช้แบบโต้ตอบผ่าน AskUserQuestion กรณีเจอรายการกำพร้าใน backlog)
   โดย prompt ที่ส่งต้องมี:
   - วันที่ปัจจุบัน (YYYYMMDD) สำหรับใช้กับไฟล์ log
   - บริบทว่านี่คือ session สนทนากับผู้ใช้จริง คำถามที่ subagent ถามจะไปถึงผู้ใช้ทันที
     ไม่ใช่ mock/สมมติคำตอบเอง และถ้า AskUserQuestion ใช้ไม่ได้ **ห้ามหยุดงาน** ให้เลือก
     พฤติกรรมที่ปลอดภัยที่สุดแล้วรายงานกลับมา
   - คำสั่งชัดเจนว่าให้ตรวจ **ครบทั้ง 4 ชั้น** ไม่ใช่แค่ spec ↔ backlog
   - ถ้าผู้ใช้ระบุเจาะจงมาว่าต้องการตรวจสอบเฉพาะไฟล์ spec ใดไฟล์หนึ่ง ให้ระบุ path นั้นไปด้วย
     ไม่เช่นนั้นให้ตรวจสอบทุกไฟล์ใน `01-spec/`

3. **รอผลลัพธ์**: เพราะรันแบบ foreground เทิร์นนี้จะได้รับผลลัพธ์ก่อนตอบผู้ใช้ต่อ
   ระหว่างที่ subagent ถามคำถามผู้ใช้ (กรณีเจอรายการกำพร้า) ให้ปล่อยให้ subagent จัดการเอง
   อย่าตอบแทนผู้ใช้

4. **ตรวจสอบผลลัพธ์ชั้น 1→2 ก่อนไปต่อ**: สุ่มตรวจสอบเองอย่างน้อย 1-2 จุด (เช่น เปิดอ่าน
   `backlog.md` จริงว่ามีการแก้ไขตรงตามที่รายงานหรือไม่ และรหัสที่อ้างว่าเพิ่มมีอยู่จริง)
   เนื่องจากเคยมีกรณี subagent ในโปรเจกต์นี้รายงานผลไม่ตรงกับสิ่งที่ทำจริง (เช่น อ้าง path ผิด)
   **ห้ามเชื่อรายงานของ subagent 100% โดยไม่ตรวจเอง** ถ้า subagent รายงานปัญหาเชิงโครงสร้าง
   ที่ทำให้ตรวจต่อไม่ได้ ให้หยุดทันทีและรายงานผู้ใช้ ไม่ต้อง auto-chain ต่อ

5. **Auto-chain กรณีพบ `## NEEDS_NEW_REQUIREMENT` (ความไม่สอดคล้องแบบย้อนขึ้นต้นน้ำ)**:
   ทำข้อนี้**ก่อน**ข้อ 6 เสมอ เพราะ FR/NFR ใหม่จะเปลี่ยน backlog ซึ่งเป็นต้นทางของชั้น 3/4
   a. แจ้งผู้ใช้สั้นๆ ว่าเจอความต้องการที่ยังไม่มีรหัสรองรับ กำลังส่งต่อให้ `requirement-writer`
      เขียนเป็น FR/NFR ให้อัตโนมัติ (ไม่ต้องถามผู้ใช้ก่อนว่าจะส่งต่อหรือไม่ — เป็นพฤติกรรม
      มาตรฐานของ skill นี้ เหมือน `sync-feature-journey` และ `sync-test-plan`)
   b. เรียก subagent `requirement-writer` ผ่าน Agent tool (`run_in_background: false`) โดย prompt
      ต้องมี: เนื้อหาทั้งหมดใต้หัวข้อ `## NEEDS_NEW_REQUIREMENT` แบบ verbatim (ไม่สรุปย่อเอง),
      วันที่ปัจจุบัน (YYYYMMDD), บริบทว่าเนื้อหานี้ค้นพบระหว่างตรวจสอบความสอดคล้องของเอกสาร
      ไม่ใช่ผู้ใช้พิมพ์มาตรงๆ, และบริบทว่านี่คือ session สนทนากับผู้ใช้จริง
   c. รอผลลัพธ์ แล้วสุ่มตรวจสอบเองอย่างน้อย 1 จุด (เปิดอ่าน `backlog.md` ว่ามีรหัส FR/NFR ใหม่
      ปรากฏจริงตามที่รายงาน) ก่อนไปข้อ 6
   d. หลังจากนี้ให้ถือว่าชั้น 3/4 ล้าสมัยแน่นอน ต้องทำข้อ 6 ต่อเสมอ แม้รายงานเดิมจะไม่มีหัวข้อ
      `## NEEDS_FEATURE_JOURNEY_SYNC` ก็ตาม

6. **Auto-chain กรณีพบ `## NEEDS_FEATURE_JOURNEY_SYNC` (ไล่ลงชั้น 3/4)**:
   - **ถ้าไม่มีหัวข้อนี้ และไม่ได้ทำข้อ 5**: แปลว่าทั้ง 4 ชั้นสอดคล้องกันอยู่แล้ว ข้ามไปข้อ 8
   - **ถ้ามีหัวข้อนี้ หรือเพิ่งทำข้อ 5 ไป**: เรียกผ่าน **Skill tool** ด้วย `skill: sync-feature-journey`
     (ไม่ใช่เรียก subagent `feature-journey-writer` ตรงๆ) เพราะ skill นั้นมี logic auto-chain
     และการตรวจสอบผลลัพธ์ของตัวเองอยู่แล้ว ส่งเนื้อหาใต้หัวข้อ `## NEEDS_FEATURE_JOURNEY_SYNC`
     แบบ verbatim ต่อไปด้วย เพื่อให้ชั้นนั้นไม่ต้องตรวจซ้ำทั้งหมด

7. **ตรวจสอบผลลัพธ์ชั้น 3/4**: สุ่มอ่าน `feature-list.md`/`user-journey.md` จริงอย่างน้อย 1-2 จุด
   ว่ารหัสที่เพิ่ง sync ปรากฏจริง, ระดับ MoSCoW ในตารางสรุปต้นไฟล์ตรงกับหัวข้อรายละเอียดของฟีเจอร์
   เดียวกัน, และทุก journey ยังมี mermaid block กำกับครบ
   - **ป้องกัน infinite loop**: ทำข้อ 5-6 ซ้ำได้อีกไม่เกิน **1 รอบเท่านั้น** (รวมแล้วเรียก
     `backlog-auditor` ได้สูงสุด 2 ครั้งต่อ 1 คำขอผู้ใช้) ถ้าหลังรอบที่สองยังพบสัญญาณค้างอีก
     ให้หยุด auto-chain แล้วรายงานผู้ใช้ตรงๆ ว่ายังมีส่วนต่างค้างอยู่ ให้ผู้ใช้ตรวจสอบเองก่อน
     สั่งต่อ อย่าวนไม่รู้จบ

8. **สรุปให้ผู้ใช้ทราบ** โดยแยกตามชั้นให้ชัด:
   - **spec ↔ backlog**: up to date อยู่แล้วหรือแก้ไขอะไรไปบ้าง
   - **backlog ↔ feature-list**: up to date อยู่แล้วหรือแก้ไขอะไรไปบ้าง (รวมระดับ MoSCoW
     ที่ถูกปรับให้ตรงกับระดับความสำคัญใน backlog)
   - **feature-list ↔ user-journey**: up to date อยู่แล้วหรือแก้ไขอะไรไปบ้าง
   - **ความต้องการใหม่ที่ถูก auto-chain ไป `requirement-writer` ให้เอง (ถ้ามี)** พร้อมรหัส
     FR/NFR ใหม่ที่ได้และเอกสาร spec ที่ถูกแก้ไข
   - รายการกำพร้าที่ยังรอผู้ใช้ตัดสินใจ (ถ้ามี)
   - ปัญหาเชิงโครงสร้างอื่นที่ subagent รายงาน (เช่น รหัสซ้ำใน spec เอง)
   - **ถ้าชั้นปลายทางถัดจากนี้ (เอกสารทดสอบ / prototype / เอกสารเชิงเทคนิค) มีเนื้อหาอยู่แล้ว
     และชั้น 2-4 เพิ่งถูกแก้ในรอบนี้** ให้แจ้งผู้ใช้ว่าเอกสารเหล่านั้นอาจล้าสมัยตามไปด้วย
     พร้อมแนะนำให้รัน `/audit-pipeline` ต่อ — **แต่ห้ามรันเองอัตโนมัติ** เพราะอยู่นอกขอบเขต
     ของ skill นี้

## ข้อควรระวัง

- ห้ามข้ามการเรียก subagent แล้วแก้ `backlog.md` เองตรงๆ ในเทรดหลัก — subagent คือแหล่งความจริง
  เดียวของกฎการเทียบรหัส FR/NFR ระหว่างชั้นต่างๆ
- **Subagent `backlog-auditor` แก้ได้เฉพาะ `backlog.md` และไฟล์ log ของวันนั้นเท่านั้น**
  ถ้าผลลัพธ์ที่ได้กลับมาพูดถึงการแก้ไข `feature-list.md`, `user-journey.md`, หรือไฟล์ใน
  `01-spec/` ให้หยุดและแจ้งผู้ใช้ทันที อย่าดำเนินการต่อ เพราะแปลว่ามีบางอย่างผิดปกติ —
  สองไฟล์ในชั้น 3/4 ต้องถูกแก้ผ่าน `sync-feature-journey` เท่านั้น เพื่อไม่ให้มี agent สองตัว
  เป็นเจ้าของไฟล์เดียวกัน
- การ auto-chain ไป `requirement-writer`/`sync-feature-journey` (ข้อ 5-6) เป็นข้อยกเว้นเดียว
  ที่ skill นี้เรียก subagent/skill อื่นนอกเหนือจาก `backlog-auditor` — ต้องเรียกก็ต่อเมื่อพบ
  หัวข้อสัญญาณตรงตัวในรายงานเท่านั้น (หรือกรณีข้อ 5d) ห้ามเดาเองจากเนื้อหาอื่นว่าเข้าเงื่อนไขหรือไม่
- ห้ามวน auto-chain เกิน 1 รอบเด็ดขาด (ดูข้อ 7) เพื่อป้องกัน infinite loop
- ถ้า subagent รายงานว่าหาโฟลเดอร์ `docs/` หรือโครงสร้างที่คาดไว้ไม่เจอ อย่าให้ subagent ลองสร้าง/
  ย้าย/เดาชื่อโฟลเดอร์เอง ให้ผู้ใช้เข้ามาตรวจสอบโครงสร้างจริงก่อน
- กรณี `feature-list.md`/`user-journey.md` **ยังไม่เคยถูกสร้าง** ไม่ถือเป็นข้อผิดพลาด ให้ถือเป็น
  ส่วนต่างปกติที่ต้อง auto-chain ไป `sync-feature-journey` เพื่อสร้างขึ้นมาให้ครบ
- skill นี้ครอบคลุมถึงชั้น `user-journey.md` เท่านั้น **ไม่รวม**เอกสารทดสอบ, prototype, และ
  เอกสารเชิงเทคนิค — ถ้าผู้ใช้ต้องการตรวจครบทั้งสายงานตั้งแต่ spec ถึงปลายทาง ให้แนะนำ
  `/audit-pipeline` แทน
