# Sync Technology Stack

Skill นี้ทำให้ `docs/02-design/02-technical/technology-stack.md` บันทึก**การตัดสินใจเรื่อง
technical stack** พร้อมเหตุผลและทางเลือกที่ไม่เลือก

**เอกสารนี้ต่างจากเอกสารอื่นทุกไฟล์ในโปรเจกต์ 2 ข้อ:**

1. **derive จาก FR/NFR แบบ mechanical ไม่ได้** — NFR บีบตัวเลือกให้แคบลงได้ แต่ตัดสินแทนไม่ได้
   เพราะขึ้นกับทีมที่จะพัฒนาจริง งบประมาณ อุปกรณ์ที่หน่วยงานใช้ และการยอมรับความเสี่ยง
   **ต้องสัมภาษณ์ผู้ใช้เสมอ**
2. **เมื่อถูกตัดสินใจแล้วจะเปลี่ยนกติกาของเอกสารทุกชั้น** — ทุกชั้นเขียนไว้ว่า "ไม่ผูก tech stack
   จนกว่า `technology-stack.md` จะถูกตัดสินใจ" การเขียนไฟล์นี้จึงต้องตามด้วยการทบทวนชั้นล่าง

## กฎการถามผู้ใช้ (ใช้กับทุกคำถามใน workflow นี้)

ทุกครั้งที่ใช้ `AskUserQuestion` — ทั้งที่ skill นี้ถามเองและที่ subagent ถาม — **ต้องเสนอ
อย่างน้อย 3 ตัวเลือก** แต่ละตัวระบุ **ข้อดีและข้อเสีย** และ **ตัวเลือกแรกคือตัวที่แนะนำ**
ต่อท้าย label ด้วย "(แนะนำ)" พร้อมเหตุผลที่**อ้างรหัส NFR/FR จริงของโปรเจกต์นี้**

## ขอบเขตงาน (scope) — ระบุเจาะจงได้

ค่าเริ่มต้นคือตัดสินใจทุกชั้นที่จำเป็นต่อการเริ่มพัฒนา แต่ผู้ใช้ระบุเจาะจงได้:
**เฉพาะชั้นใดชั้นหนึ่ง** (เช่นเฉพาะฝั่งเซิร์ฟเวอร์) · **เฉพาะที่จำเป็นต่อ phase แรก** ·
**บันทึกทิศทางที่ตัดสินไปแล้วโดยยังไม่ลงรายละเอียด**

- ระบุมาชัดแล้ว → ส่งต่อใน prompt ตรงๆ **ห้ามถามซ้ำ**
- ไม่ระบุ → **แนะนำให้จำกัดที่ "ชั้นที่จำเป็นต่อ phase แรกตาม `release-plan.md`" ก่อน**
  เพราะการบังคับตัดสินใจชั้นที่ยังไม่ต้องใช้ มักตัดสินโดยไม่มีข้อมูลพอ
- **scope ถูกจำกัดเมื่อใด ต้องรายงานเสมอว่าชั้นใดยังไม่ถูกตัดสินใจ และมันบล็อก phase ใด**

## เมื่อถูกเรียกใช้

1. **หาวันที่ปัจจุบัน** (`YYYYMMDD`) — subagent ไม่มี Bash ต้องส่งให้ใน prompt เสมอ

2. **สำรวจสถานะจริงก่อนเรียก subagent (ทำเองด้วย Bash)** แล้วส่งไปใน prompt เพื่อไม่ให้
   subagent เสียเวลาสำรวจซ้ำและไม่ให้เดาตัวเลขผิด:
   - `technology-stack.md` มีไฟล์แล้วหรือยัง / มีเนื้อหาชั้นใดแล้วบ้าง
   - จำนวนรหัสใน `backlog.md` · phase แรกใน `release-plan.md` ต้องใช้ชั้นใดบ้าง
   - **มีโครงสร้างซอร์สโค้ด/manifest/CI อยู่แล้วหรือยัง** — ถ้ามีแล้ว แปลว่าบางอย่างถูกเลือกไป
     แล้วโดยพฤตินัย ต้องบันทึกให้ตรงความจริง ไม่ใช่ทำเหมือนยังไม่เคยเลือก
   - ไฟล์ log ของวันนี้มีอยู่แล้วหรือยัง (ถ้ามีต้องสั่งให้ append ห้ามเขียนทับ)

3. **ส่งต่อให้ subagent `tech-stack-writer`**: เรียกผ่าน Agent tool
   (`subagent_type: tech-stack-writer`, `run_in_background: false` เพราะต้องสัมภาษณ์ผู้ใช้)
   โดย prompt ต้องมี: วันที่ · scope · ผลสำรวจจากข้อ 2 · บริบทว่านี่คือ session สนทนากับผู้ใช้จริง
   · **ย้ำทางถอย**: ถ้า `AskUserQuestion` ใช้ไม่ได้ **ห้ามเดา ห้ามเขียนไฟล์** ให้ส่งทางเลือก
   ทั้งหมดกลับมาให้ skill ถามผู้ใช้แทน

4. **รอผลลัพธ์**: ปล่อยให้ subagent สัมภาษณ์เอง **อย่าตอบแทนผู้ใช้** ถ้า subagent ส่งทางเลือก
   กลับมาเพราะถามเองไม่ได้ ให้ skill ถามผู้ใช้ตามรูปแบบข้างบน แล้วส่งคำตอบกลับไปให้เขียนต่อ

5. **ตรวจสอบผลลัพธ์ก่อนรายงาน** — อ่านไฟล์จริง ตรวจครบทุกข้อ:
   - **ไม่มี technology ใดถูกเขียนลงไฟล์โดยที่ผู้ใช้ไม่ได้เลือกจริง** — เทียบกับคำตอบที่ผู้ใช้ให้
     ทีละข้อ **ถ้าพบว่ามีของแถมที่ผู้ใช้ไม่ได้เลือก ถือว่าผิดกฎร้ายแรง** หยุดและแจ้งผู้ใช้
   - **ไม่มีเลขเวอร์ชันเจาะจงที่ผู้ใช้ไม่ได้ระบุ**
   - **หัวข้อบังคับครบ**: สถานะการตัดสินใจ · ข้อจำกัดที่บีบตัวเลือก · การตัดสินใจรายชั้นพร้อม
     คอลัมน์ทางเลือกที่ไม่เลือก · สิ่งที่ยังไม่ตัดสินใจพร้อมเงื่อนไขที่ต้องมีก่อน ·
     ผลกระทบต่อเอกสารชั้นอื่น · เกณฑ์ที่จะทำให้ต้องทบทวนใหม่
   - **ทุกการตัดสินใจอ้างรหัส NFR/FR จริง** ไม่ใช่เหตุผลลอยๆ — สุ่มตรวจว่ารหัสที่อ้างมีจริงใน
     `backlog.md` และเนื้อหาตรงกับที่อ้าง
   - **ไม่ขัดกับสิ่งที่ `architecture.md` ตัดสินไปแล้ว** — ถ้าขัด ให้หยุดและแจ้งผู้ใช้
     **ห้ามให้ skill นี้แก้ `architecture.md` เอง**
   - anchor ของ `[[wikilink]]` ตรง heading จริง

6. **ส่งต่อให้ชั้นล่างทบทวน (เฉพาะเมื่อพบ `## NEEDS_TECHNICAL_SPEC_REVISIT`)**:
   a. แจ้งผู้ใช้สั้นๆ ว่า stack ถูกตัดสินใจแล้ว กำลังส่งให้เอกสารเชิงเทคนิคทบทวน
   b. เรียก `skill: sync-technical-spec` (Skill tool) โดยส่งเนื้อหาใต้หัวข้อสัญญาณแบบ
      **verbatim** พร้อมระบุชัดว่า **`technology-stack.md` มีเนื้อหาแล้ว** เพื่อให้ทุกชั้นรู้ว่า
      กติกาเปลี่ยนแล้ว — อ้างอิงชื่อ stack จริงได้ในจุดที่เหมาะสม และต้องอัปเดตหัวข้อ
      "ประเด็นรอตัดสินใจ" ของตัวเองให้สะท้อนสิ่งที่ปิดไปแล้ว
   c. **ป้องกัน infinite loop**: ทำซ้ำได้อีกไม่เกิน **1 รอบ**
   d. **ถ้าผู้ใช้จำกัด scope ไว้และยังมีชั้นที่ไม่ตัดสินใจ ให้บอกชั้นล่างด้วยว่าชั้นใดยังไม่ตัดสิน**
      เพื่อไม่ให้มันเผลอเขียนผูก stack ในส่วนที่ยังไม่มีคำตอบ

7. **สรุปให้ผู้ใช้ทราบ**:
   - ตัดสินใจชั้นใดบ้าง เลือกอะไร และ**ทางเลือกที่ไม่เลือกพร้อมเหตุผล**
   - **ชั้นที่ยังไม่ตัดสินใจ พร้อมเงื่อนไขที่ต้องมีก่อน และมันบล็อก phase ใด**
   - เอกสารชั้นใดถูกทบทวนตามในข้อ 6
   - **สิ่งที่ต้องทำต่อก่อนเริ่มเขียนโค้ดจริง** เช่นข้อสมมติใน spec ที่ยังค้างและกระทบ phase แรก
     หรือการอัปเดต `CLAUDE.md` ให้มีคำสั่ง build/lint/test เมื่อมีโครงสร้างโปรเจกต์จริงแล้ว

## ข้อควรระวัง

- ห้ามข้ามการเรียก subagent แล้วเขียน `technology-stack.md` เองตรงๆ ในเทรดหลัก
- **ห้ามยก skill นี้ไปเป็น subagent** — ต้องสัมภาษณ์ผู้ใช้ และ subagent ในโปรเจกต์นี้ถามผู้ใช้
  ไม่ได้จริง (ดู `CLAUDE.md`)
- Subagent แก้ได้เฉพาะ `technology-stack.md` และ log ของวันนั้น หากผลลัพธ์พูดถึงการแก้ไฟล์อื่น
  **โดยเฉพาะ `architecture.md`/`api-spec.md`/`db-spec.md`** ให้หยุดและแจ้งผู้ใช้ทันที
- **ถ้า subagent เขียนชื่อ technology ที่ผู้ใช้ไม่ได้เลือกลงไฟล์ ให้ถือว่าผิดกฎร้ายแรง** —
  เอกสารนี้เป็นบันทึกการตัดสินใจ ไม่ใช่ข้อเสนอ สิ่งที่เขียนลงไปจะถูกใช้เป็นข้อผูกมัดจริง
- **อย่าเร่งให้ตัดสินใจชั้นที่ยังไม่มีข้อมูลพอ** — การบันทึกว่า "ยังไม่ตัดสินใจ เพราะรอ X"
  มีค่ามากกว่าการเดาแล้วต้องรื้อทีหลัง ให้ระบุเงื่อนไขที่ต้องมีก่อนแทน
- ถ้าผู้ใช้ขอ stack ที่ขัดกับ NFR อย่างชัดเจน (เช่นเลือกสิ่งที่ทำงานออฟไลน์ไม่ได้ทั้งที่ NFR
  บังคับ offline-first) **ให้ทักท้วงพร้อมเหตุผลและเสนอทางออก** แต่ถ้าผู้ใช้ยืนยันหลังรับทราบแล้ว
  ให้ทำตามและ**บันทึกข้อกังวลไว้ในเอกสาร** เพื่อให้คนอ่านภายหลังรู้ว่าเคยมีการทักท้วง
- เมื่อโปรเจกต์มีโครงสร้างซอร์สโค้ดจริงแล้ว ให้แนะนำผู้ใช้อัปเดต `CLAUDE.md` ให้มีคำสั่ง
  build/lint/test — **แต่ห้ามแก้ `CLAUDE.md` เองจาก skill นี้**
