# Build Prototype

Skill นี้เป็น workflow มาตรฐานสำหรับสร้าง/ปรับปรุง Clickable HTML Prototype ภายใต้
`docs/02-design/01-prototypes/` จากแหล่งความจริงปัจจุบันทั้งสาย (spec → `backlog.md` →
`feature-list.md`/`user-journey.md`) โดยยึด `DESIGN.md` เป็นแหล่งความจริงของภาพ ตามกฎใน
`CLAUDE.md`

## กฎการถามผู้ใช้ (ใช้กับทุกคำถามใน workflow นี้ ไม่มีข้อยกเว้น)

ทุกครั้งที่ใช้ `AskUserQuestion` — ทั้งที่ skill นี้ถามเองและที่ subagent ถาม — **ต้องเสนอ
อย่างน้อย 3 ตัวเลือก/แนวทาง** แต่ละตัวเลือกระบุ **ข้อดีและข้อเสีย** ไว้ใน `description`
และ **ระบุตัวเลือกที่แนะนำ** เป็นตัวเลือกแรก ต่อท้าย label ด้วย "(แนะนำ)" พร้อมเหตุผลที่อิง
บริบทจริงของคำขอ ไม่ใช่ค่าเริ่มต้นตายตัว

ถ้าจุดใดไม่ชัดเจนจนตัดสินใจต่อไม่ได้ **ให้ถามเสมอ อย่าเดา**

## เมื่อถูกเรียกใช้

1. **หาวันที่ปัจจุบัน**: ใช้ค่าวันที่ปัจจุบันที่มีอยู่ในบริบทของคุณ (รูปแบบ `YYYYMMDD`)
   เพื่อส่งต่อให้ subagent ใช้ตั้งชื่อโฟลเดอร์เวอร์ชัน/log ของวันนี้ — subagent ไม่มีเครื่องมือ
   Bash จึงหาวันที่เองไม่ได้ ต้องส่งมาให้ใน prompt เสมอ

2. **ตรวจ `DESIGN.md` ก่อนทุกอย่าง (gate)**: อ่าน `docs/02-design/DESIGN.md`
   - **ถ้ายังไม่มีไฟล์ หรือมีแต่ขาดหัวข้อหลัก** (Brand Identity, Design Token — สี/ตัวอักษร/
     ระยะห่าง, UI Component, UX Guideline) → **ห้ามเรียก `prototype-writer` เด็ดขาด**
     ให้แจ้งผู้ใช้สั้นๆ ว่ายังสร้าง prototype ไม่ได้เพราะยังไม่มีระบบออกแบบให้ยึด แล้ว
     **เรียก `sync-design-system` ผ่าน Skill tool ต่อทันที** (skill นั้นจะสัมภาษณ์ผู้ใช้เรื่อง
     โทนสี สไตล์ และโลโก้/ภาพอ้างอิงเอง) เมื่อ `DESIGN.md` พร้อมแล้วจึงกลับมาทำข้อ 3 ต่อ
     — **ไม่ต้องถามผู้ใช้ก่อนว่าจะสร้าง `DESIGN.md` ไหม** เพราะไม่มีทางเลือกอื่นที่ทำให้งานเดินต่อได้
     ถ้าผู้ใช้ปฏิเสธระหว่างการสัมภาษณ์ ให้หยุด workflow แล้วรายงานตรงๆ ว่าทำต่อไม่ได้และเพราะอะไร
   - **ถ้ามีครบ** → ไปข้อ 3

3. **ตกลงขอบเขต (scope) กับผู้ใช้**: ค่าเริ่มต้นคือครอบคลุมทุก journey ใน `user-journey.md`
   แต่ผู้ใช้ระบุเจาะจงได้หลายระดับ — **ทั้งระบบ** · **ตามบทบาทผู้ใช้** · **ตาม journey** ·
   **ตามฟีเจอร์** · **ตามรหัส FR/NFR** · **ตามระดับ MoSCoW** (เช่น เฉพาะ Must have)
   - ถ้าผู้ใช้ระบุ scope มาชัดเจนแล้วในคำขอ → ใช้ตามนั้น **ห้ามถามซ้ำ**
   - ถ้าไม่ได้ระบุ หรือระบุมาแบบกำกวมว่าหมายถึงระดับใด → ใช้ `AskUserQuestion` ถาม โดย
     **สร้างตัวเลือกจากเนื้อหาจริงใน `feature-list.md`/`user-journey.md`** (ชื่อ journey/ฟีเจอร์
     จริง จำนวนหน้าจอโดยประมาณ) ไม่ใช่ตัวเลือกลอยๆ — ปกติควรแนะนำให้เริ่มจากกลุ่ม **Must have**
     ก่อนถ้ายังไม่เคยมี prototype เลย เพราะได้เส้นทางหลักครบเร็วและรีวิวได้จริงก่อนลงทุนกับ
     ส่วนที่ยังไม่แน่นอน

4. **ตัดสินเรื่องโฟลเดอร์เวอร์ชัน**: Glob ดูโฟลเดอร์ `docs/02-design/01-prototypes/*`
   - **ยังไม่มีเวอร์ชันใดเลย** → ข้ามคำถามนี้ เตรียมสร้างเวอร์ชันแรก (`{YYYYMMDD}-01-v1`)
   - **มีเวอร์ชันก่อนหน้าอยู่แล้ว** → **ต้องถามผู้ใช้ทุกครั้ง ห้ามสันนิษฐานเอง** ด้วย
     `AskUserQuestion` โดยเสนอ 3 ตัวเลือกพร้อมข้อดี-ข้อเสีย:

     | ตัวเลือก | ข้อดี | ข้อเสีย |
     |---|---|---|
     | **(ก) สร้างเวอร์ชันใหม่** (บอกชื่อโฟลเดอร์ถัดไปที่คำนวณได้) | เก็บของเดิมไว้เทียบ/ย้อนกลับได้ เหมาะกับการรื้อโครงสร้างหรือเปลี่ยนทิศทางออกแบบ | ต้องสร้างหน้าจอ shared ซ้ำ กินพื้นที่ และมีหลายเวอร์ชันให้ต้องดูแล |
     | **(ข) แก้ไขเวอร์ชันล่าสุดในที่เดิม** | ต่อเนื่อง ไม่ต้องทำหน้าจอ shared ซ้ำ เหมาะกับการเพิ่ม/ปรับฟีเจอร์ทีละน้อย | ทับของเดิม ย้อนกลับได้เฉพาะผ่าน git |
     | **(ค) แก้ไขเวอร์ชันอื่นที่ไม่ใช่ล่าสุด** (ให้ผู้ใช้ระบุ) | ใช้เมื่อต้องแก้เวอร์ชันที่กำลังถูกรีวิวอยู่ | เสี่ยงทำให้หลายเวอร์ชันไม่สอดคล้องกัน |

     **การเลือกตัวเลือกที่แนะนำต้องอิงบริบทของคำขอจริง ไม่ใช่ตายตัว**:
     - คำขอสื่อถึงการ **เพิ่ม/ปรับฟีเจอร์ในของเดิม** → แนะนำ **(ข)**
     - คำขอสื่อถึงการ **รื้อโครงสร้าง เปลี่ยนทิศทางออกแบบ หรือ `DESIGN.md` เพิ่งเปลี่ยน
       token หลัก** → แนะนำ **(ก)** เพราะของเดิมจะไม่สอดคล้องกับระบบออกแบบใหม่ทั้งชุด
     - **มี requirement ใหม่เข้ามาจำนวนมาก** จนหน้าจอเดิมครอบคลุมไม่ถึงครึ่ง → แนะนำ **(ก)**
     - ระบุเหตุผลที่แนะนำให้ผู้ใช้เห็นเสมอ ไม่ใช่แค่ติดป้าย "(แนะนำ)" เฉยๆ

5. **ส่งต่อให้ subagent `prototype-writer`**: เรียกผ่าน Agent tool
   (`subagent_type: prototype-writer`, รันแบบ foreground คือ `run_in_background: false`
   เพราะ subagent ต้องเสนอแผน scope ให้ผู้ใช้ยืนยันแบบโต้ตอบผ่าน `AskUserQuestion` เสมอ
   ก่อนเขียนไฟล์จริง) โดย prompt ที่ส่งต้องมี:
   - วันที่ปัจจุบัน (YYYYMMDD)
   - โฟลเดอร์เป้าหมายเต็ม (path) และระบุชัดว่าเป็น "เวอร์ชันใหม่ทั้งหมด" หรือ "แก้ไขเวอร์ชันเดิม"
     ตามที่ตัดสินใจในข้อ 4
   - **ขอบเขตที่ตกลงในข้อ 3 แบบเจาะจง** (ระบุเป็นชื่อ journey/ฟีเจอร์/รหัส FR จริง ไม่ใช่คำกว้างๆ)
   - ยืนยันว่า `DESIGN.md` ผ่าน gate ในข้อ 2 แล้ว
   - บริบทว่านี่คือ session สนทนากับผู้ใช้จริง คำถามที่ subagent ถาม (รวมถึงการขอยืนยันแผน
     scope) จะไปถึงผู้ใช้ทันที ไม่ใช่ mock/สมมติคำตอบเอง

6. **รอผลลัพธ์**: ปล่อยให้ subagent เสนอแผนและถามคำถามเอง **อย่ายืนยัน/ตอบแทนผู้ใช้**

7. **จัดการสัญญาณ `## NEEDS_DESIGN_SYSTEM`**: ถ้า subagent รายงานหัวข้อนี้กลับมา (แปลว่า
   `DESIGN.md` ขาดบางอย่างที่ตรวจไม่พบในข้อ 2) ให้เรียก `sync-design-system` ต่อเพื่อเติมส่วน
   ที่ขาด แล้วเรียก `prototype-writer` อีกรอบด้วย prompt เดิม
   **ป้องกัน infinite loop: ทำได้ไม่เกิน 1 รอบ** ถ้ารอบที่สองยังพบสัญญาณอีก ให้หยุดแล้วรายงาน
   ผู้ใช้ตรงๆ ว่ายังขาดอะไร ให้ผู้ใช้ตัดสินใจเองก่อนสั่งต่อ

8. **ตรวจสอบผลลัพธ์ก่อนรายงาน**: สุ่มตรวจเองอย่างน้อย 1-2 จุด — เปิดโฟลเดอร์เวอร์ชันจริงว่ามี
   ไฟล์ตามที่รายงาน เปิดอ่าน 1-2 หน้าจอตรวจว่าอ้างอิง `style.css` ถูกต้อง ลิงก์ระหว่างหน้าไม่ตาย
   และ **ค่าสี/ขนาดที่ใช้ตรงกับ token ใน `DESIGN.md` จริง ไม่มีค่าดิบที่คิดขึ้นเอง**
   **ห้ามเชื่อรายงานของ subagent 100% โดยไม่ตรวจเอง**
   - subagent ไม่มีเครื่องมือเบราว์เซอร์ จึงยังไม่มีการเปิดดูจริง — เสนอผู้ใช้ได้ว่าจะเปิดตรวจ
     ด้วยเบราว์เซอร์ในเทรดหลักต่อหรือไม่ (ไม่ใช่ default บังคับ)

9. **สรุปให้ผู้ใช้ทราบ**:
   - สร้างเวอร์ชันใหม่หรือแก้เวอร์ชันเดิม โฟลเดอร์ไหน (path เต็ม) และเหตุผลที่เลือกแบบนั้น
   - ขอบเขตที่ตกลงไว้ และ **สิ่งที่ยังไม่ถูกสร้างในรอบนี้** พร้อมรหัส FR ที่เกี่ยวข้อง
   - ไฟล์ใดถูกสร้าง/แก้ไขบ้าง พร้อม journey/FR ที่ครอบคลุม
   - `DESIGN.md` ถูกสร้าง/เติมระหว่างทางหรือไม่ (ถ้ามีการ chain ไป `sync-design-system`)
   - จุดที่ถาม/รอผู้ใช้ตัดสินใจระหว่างทาง และปัญหาเชิงโครงสร้างที่ subagent รายงาน

## ข้อควรระวัง

- ห้ามข้ามการเรียก subagent แล้วเขียนไฟล์ HTML เองตรงๆ ในเทรดหลัก — subagent คือแหล่ง
  ความจริงเดียวของกฎการแปลง feature/journey เป็นหน้าจอตาม `DESIGN.md`
- **Subagent ต้องเสนอแผน scope ให้ผู้ใช้ยืนยันก่อนเขียนไฟล์ HTML จริงเสมอ** ถ้าผลลัพธ์แสดงว่า
  subagent เขียนไฟล์โดยไม่มีการขอยืนยันแผนก่อนเลย ให้ถือว่าผิดกฎ หยุดและแจ้งผู้ใช้ทันที
- **ต้องถามเรื่องโฟลเดอร์เวอร์ชันทุกครั้งที่มีเวอร์ชันเดิมอยู่แล้ว** แม้ผู้ใช้จะเคยตอบไปแล้วในรอบก่อน
  เพราะบริบทของแต่ละรอบต่างกัน
- Subagent นี้ตั้งใจไม่มีเครื่องมือ Bash และห้ามแตะไฟล์ใดๆ นอกจากภายในโฟลเดอร์เวอร์ชัน
  prototype เป้าหมายเดียว กับไฟล์ log ของวันนั้น หากผลลัพธ์พูดถึงการแก้ไขไฟล์อื่น (โดยเฉพาะ
  `backlog.md`, `feature-list.md`, `user-journey.md`, `DESIGN.md`, หรือไฟล์ใน `01-spec/`)
  ให้หยุดและแจ้งผู้ใช้ทันที — **`DESIGN.md` ต้องแก้ผ่าน `sync-design-system` เท่านั้น**
  เพื่อไม่ให้มี agent สองตัวเป็นเจ้าของไฟล์เดียวกัน
- ถ้า subagent รายงานว่า `feature-list.md`/`user-journey.md` ไม่ตรงกับ `backlog.md` หรือ
  `backlog.md` ไม่ตรงกับ spec — ให้แจ้งผู้ใช้ตามที่ subagent แนะนำ (รัน `/sync-feature-journey`
  หรือ `/audit-backlog` ก่อน) อย่าฝืนสร้าง prototype ต่อในสถานะที่ไม่พร้อม
- ถ้า subagent รายงานว่าหาโฟลเดอร์ `docs/02-design/` หรือโครงสร้างที่คาดไว้ไม่เจอ อย่าให้
  subagent ลองสร้าง/ย้าย/เดาชื่อโฟลเดอร์เอง ให้ผู้ใช้เข้ามาตรวจสอบโครงสร้างจริงก่อน
