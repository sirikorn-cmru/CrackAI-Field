# Sync API & DB Spec

Skill นี้เป็น workflow มาตรฐานสำหรับสร้าง/ปรับปรุง `api-spec.md` และ `db-spec.md` เชิง
conceptual ให้สอดคล้อง ("up to date") กับ `architecture.md`/`feature-list.md` ถ้าไม่สอดคล้อง
ให้ปรับปรุงทั้งสองไฟล์พร้อมกัน (operation contract + logical ER model) แบบ**ไม่ผูกมัดกับ
technical stack** พร้อมบันทึก log ตามกฎใน `CLAUDE.md`

**เขียนสองไฟล์นี้คู่กันเสมอ** เพราะ field ที่ operation ใช้ต้องตรงกับ attribute ใน entity จริง
แยกทำคนละรอบคือสาเหตุที่ข้อมูลสองฝั่งหลุดจากกัน

## เมื่อถูกเรียกใช้

1. **หาวันที่ปัจจุบัน**: รูปแบบ `YYYYMMDD` เพื่อส่งต่อให้ subagent

2. **รับขอบเขตจากผู้ใช้ (ถ้ามีการระบุ)**: ผู้ใช้ระบุขอบเขตเจาะจงได้ เช่น เฉพาะฟีเจอร์ใดฟีเจอร์
   หนึ่ง, เฉพาะกลุ่ม entity, หรือเฉพาะ operation ที่เกี่ยวกับ FR บางรหัส — ถ้าไม่ระบุ ให้ถือว่า
   ครอบคลุมทั้งระบบ **ถ้าขอบเขตถูกจำกัด ต้องรายงานท้ายงานเสมอว่าอะไรยังไม่ถูกครอบคลุมในรอบนี้**

3. **ส่งต่อให้ subagent `api-db-writer`**: เรียกผ่าน Agent tool
   (`subagent_type: api-db-writer`, `run_in_background: false` เพราะอาจต้องถามผู้ใช้แบบโต้ตอบ)
   โดย prompt ต้องมี:
   - วันที่ปัจจุบัน (YYYYMMDD)
   - ขอบเขตที่ผู้ใช้ระบุ (ถ้ามี)
   - บริบทว่านี่คือ session สนทนากับผู้ใช้จริง คำถามที่ subagent ถามจะไปถึงผู้ใช้ทันที
   - **ย้ำกฎการถาม**: ถ้าพบประเด็นที่ตัดสินแทนผู้ใช้ไม่ได้ (เช่น เก็บ snapshot หรืออ้างค่าปัจจุบัน,
     cardinality ที่ตีความได้หลายแบบ, ลบจริงหรือทำเครื่องหมายยกเลิก) ต้องถามผ่าน
     `AskUserQuestion` โดยเสนออย่างน้อย 3 แนวทาง แต่ละแนวทางระบุข้อดี/ข้อเสีย และตัวเลือกแรก
     คือตัวที่แนะนำ ต่อท้าย label ด้วย `(แนะนำ)` — **ถ้า `AskUserQuestion` ใช้ไม่ได้ในเซสชันนั้น
     ห้ามเดาเอง ให้รายงานทางเลือกทั้งหมดกลับมาโดยยังไม่เขียนส่วนที่ต้องตัดสินใจ** แล้ว skill
     จะถามผู้ใช้แทน

4. **รอผลลัพธ์**: ปล่อยให้ subagent จัดการคำถามผู้ใช้เอง **อย่ายืนยัน/ตอบแทนผู้ใช้** ถ้า subagent
   ส่งทางเลือกกลับมาเพราะถามเองไม่ได้ ให้ skill ถามผู้ใช้ตามรูปแบบในข้อ 3 แล้วส่งคำตอบกลับไป

5. **ตรวจจับสัญญาณ "ต้องการ requirement ใหม่"**: อ่านรายงานทั้งหมด
   - **ไม่มีหัวข้อ `## NEEDS_NEW_REQUIREMENT`**: ข้ามไปข้อ 7
   - **มีหัวข้อนี้**: ทำข้อ 6 ก่อน แล้วค่อยไปข้อ 7

6. **Auto-chain ไป `requirement-writer` (เฉพาะเมื่อมีสัญญาณ)**:
   a. แจ้งผู้ใช้สั้นๆ ว่ากำลังส่งต่อให้ `requirement-writer` อัตโนมัติ (ไม่ต้องถามก่อน)
   b. เรียก subagent `requirement-writer` โดย prompt มีเนื้อหาใต้หัวข้อสัญญาณแบบ verbatim +
      วันที่ + บริบท session จริง
   c. รอผลลัพธ์ สุ่มตรวจ `backlog.md` อย่างน้อย 1 จุด
   d. เรียก `sync-feature-journey` ต่อ (Skill tool) ให้ feature-list/journey สะท้อนรหัสใหม่ก่อน
      แล้วเรียก `sync-architecture` ต่อ (Skill tool) ให้ architecture ครอบคลุมรหัสใหม่ด้วย
      (เพราะ api-spec/db-spec ต้องอ้างอิง component จาก architecture เสมอ) แล้วจึงเรียก
      subagent `api-db-writer` อีกรอบ
   e. **ป้องกัน infinite loop**: ทำซ้ำได้อีกไม่เกิน 1 รอบ

7. **ตรวจสอบผลลัพธ์ก่อนรายงาน** — อ่านไฟล์จริง ตรวจครบทุกข้อต่อไปนี้:
   - **`db-spec.md` มี ER Diagram เป็น Mermaid `erDiagram` จริง** และ entity ในไดอะแกรมตรงกับ
     entity ที่มีตารางรายละเอียดในไฟล์ — **นับเทียบกันจริง** ไดอะแกรมที่ไม่ตรงกับตารางทำให้เข้าใจ
     ผิดหนักกว่าไม่มีไดอะแกรม
   - **หัวข้อบังคับของ `db-spec.md` ครบ**: ชนิดข้อมูลเชิงตรรกะ · ภาพรวมกลุ่ม entity ·
     รายละเอียด entity รายตัว · ER Diagram · กฎทางธุรกิจที่กระทบโครงสร้างข้อมูล ·
     ตารางความครอบคลุมฟีเจอร์/FR ↔ entity · ประเด็นรอตัดสินใจ
   - **หัวข้อบังคับของ `api-spec.md` ครบ**: ภาพรวมและกติกาการอ่าน · operation จัดกลุ่มตามฟีเจอร์
     โดยแต่ละตัวมีครบ 7 ช่อง (ชื่อ · ผู้เรียกได้ · input · output · กฎทางธุรกิจ · error · รหัส
     FR/NFR) · ตารางความครอบคลุม FR ↔ operation · ประเด็นรอตัดสินใจ
   - **ตารางความครอบคลุมมีครบทุก FR ใน `backlog.md`** — นับเทียบกันจริง FR ที่ไม่ต้องมี operation
     ต้องมีแถวพร้อมเหตุผล ไม่ใช่หายไปเฉยๆ
   - **ไม่มี HTTP method/path, protocol (REST/GraphQL/gRPC), SQL type, ชื่อ database engine
     หรือชื่อ technology ใดๆ หลุดเข้าไป** (ถ้า `technology-stack.md` ยังว่างเปล่า)
   - **field sync กันข้ามสองไฟล์**: สุ่มตรวจอย่างน้อย 2 จุดว่า field ที่ operation รับ/คืน มี
     attribute รองรับจริงใน `db-spec.md` และค่า enum ที่ปรากฏทั้งสองไฟล์มีครบเท่ากัน
   - **attribute ที่จำเป็นแบบมีเงื่อนไขเขียนถูกรูปแบบ**: ต้องเป็น `ไม่ (จำเป็นเมื่อ <เงื่อนไข>)`
     ในคอลัมน์ "จำเป็น" **ห้ามเป็น `ไม่` เฉยๆ แล้วอธิบายเงื่อนไขไว้ในคอลัมน์คำอธิบาย** — เคยเกิด
     ข้อผิดพลาดจริงจากจุดนี้จนทำให้ NFR ด้าน auditability ถูกลดระดับมาแล้ว
   - anchor ของ `[[wikilink]]` หลัง `#` ตรงกับ heading จริงทุกตัวอักษร

8. **สรุปให้ผู้ใช้ทราบ**: up to date หรือไม่ก่อนตรวจ, ส่วนที่แก้ไขในทั้งสองไฟล์, จำนวน
   operation/entity หลังแก้, คำถามที่ถามผู้ใช้และคำตอบ (ถ้ามี), ความต้องการใหม่ที่ auto-chain
   ไปให้ (ถ้ามี), **และสิ่งที่ยังไม่ถูกครอบคลุมในรอบนี้**

## ข้อควรระวัง

- ห้ามข้ามการเรียก subagent แล้วเขียนไฟล์เองตรงๆ ในเทรดหลัก
- Subagent ห้ามแตะไฟล์ใดๆ นอกจาก `api-spec.md`, `db-spec.md`, และไฟล์ log — หากผลลัพธ์พูดถึง
  การแก้ไข `architecture.md`/`feature-list.md`/`technology-stack.md`/`detailed-design/`/
  `nfr-review.md` ให้หยุดและแจ้งผู้ใช้ทันที
- **ถ้าผลลัพธ์ระบุ HTTP method/path, protocol, SQL type, หรือชื่อ database engine ใดๆ ทั้งที่
  `technology-stack.md` ยังว่างเปล่า ให้ถือว่าผิดกฎ** หยุดและแจ้งผู้ใช้ทันที
- **ถ้า subagent ตัดสินใจประเด็นที่ควรถามผู้ใช้เองโดยไม่ถาม ให้ถือว่าผิดกฎ** — จุดที่ต้องระวัง
  เป็นพิเศษคือการเลือกระหว่างเก็บค่า ณ เวลานั้นกับอ้างค่าปัจจุบัน และการเลือก cardinality
  เพราะทั้งสองอย่างย้อนแก้ทีหลังแทบไม่ได้เมื่อมีข้อมูลจริงแล้ว
- **ถ้า subagent เรียงเลขหัวข้อใหม่ทั้งไฟล์ ให้ตรวจ inbound anchor ทันที** — `detailed-design/`
  และ `nfr-review.md` อ้าง anchor ของสองไฟล์นี้อยู่ และ subagent แก้ไฟล์เหล่านั้นไม่ได้
- **ถ้าเอกสารที่ได้มีข้อความอธิบายข้อจำกัดของรอบการทำงานปนอยู่** (เช่น "ไม่ได้อ่านไฟล์นั้นเพราะ
  ประหยัดเวลา/session") ให้ส่งกลับไปให้ subagent แก้
- ห้ามวน auto-chain เกิน 1 รอบเด็ดขาด
- ถ้า subagent รายงานว่า `architecture.md` ยังว่างเปล่า/ไม่ครอบคลุม ให้แจ้งผู้ใช้ให้รัน
  `sync-architecture` ก่อน อย่าฝืนทำต่อ
