# Sync Design System

Skill นี้เป็น workflow มาตรฐานสำหรับสร้าง/ปรับปรุง `docs/02-design/DESIGN.md` ตามกฎใน
`CLAUDE.md` ซึ่งเป็นแหล่งอ้างอิงเดียวของระบบออกแบบเชิงภาพที่ทุก Prototype ต้องยึดถือ

**เอกสารนี้ต่างจากเอกสารชั้นอื่นในโปรเจกต์ตรงที่ derive จาก FR/NFR แบบ mechanical ไม่ได้** —
โทนสีและบุคลิกของแบรนด์เป็นการตัดสินใจของเจ้าของผลิตภัณฑ์ workflow นี้จึงมีขั้นตอนสัมภาษณ์ผู้ใช้
เป็นแกนกลาง ไม่ใช่การเทียบส่วนต่างระหว่างเอกสารเหมือน skill อื่น

## เมื่อถูกเรียกใช้

1. **หาวันที่ปัจจุบัน**: รูปแบบ `YYYYMMDD` เพื่อส่งต่อให้ subagent ใช้กับไฟล์ log ของวันนี้ —
   subagent ไม่มีเครื่องมือ Bash จึงหาวันที่เองไม่ได้ ต้องส่งมาให้ใน prompt เสมอ

2. **ตรวจสถานะไฟล์ก่อนเรียก subagent**: อ่านว่ามี `docs/02-design/DESIGN.md` อยู่แล้วหรือไม่
   และถ้ามี มีหัวข้อใดครบ/ขาดบ้าง แล้วส่งข้อมูลนี้ไปใน prompt เพื่อไม่ให้ subagent เสียเวลาสำรวจซ้ำ
   - **ยังไม่มีไฟล์** → เป็นการสร้างใหม่ทั้งหมด subagent ต้องสัมภาษณ์ผู้ใช้ครบทุกหัวข้อ
   - **มีแล้วแต่ขาดบางส่วน** → เป็นการเติมเฉพาะจุด **ห้ามให้ subagent เขียนทับทั้งไฟล์**
     ระบุให้ชัดใน prompt ว่าขาดอะไรและต้องคงอะไรไว้

3. **รวบรวมสิ่งที่ผู้ใช้ระบุมาแล้ว**: ถ้าผู้ใช้บอกโทนสี สไตล์ หรือแนบไฟล์โลโก้/ภาพอ้างอิงมาใน
   คำขอ **ให้ส่งต่อไปใน prompt ทั้งหมดแบบ verbatim พร้อม path ของไฟล์ภาพ** เพื่อไม่ให้ subagent
   ถามซ้ำในสิ่งที่ผู้ใช้ตอบไปแล้ว — การถามซ้ำสร้างความรำคาญและทำให้ผู้ใช้เสียความเชื่อมั่นใน workflow

4. **ส่งต่อให้ subagent `design-system-writer`**: เรียกผ่าน Agent tool
   (`subagent_type: design-system-writer`, รันแบบ foreground คือ `run_in_background: false`
   เพราะ subagent ต้องสัมภาษณ์ผู้ใช้และขอยืนยันแผนผ่าน `AskUserQuestion` ก่อนเขียนไฟล์จริง)
   โดย prompt ต้องมี:
   - วันที่ปัจจุบัน (YYYYMMDD)
   - สถานะไฟล์จากข้อ 2 (สร้างใหม่ / เติมเฉพาะจุดอะไรบ้าง)
   - สิ่งที่ผู้ใช้ระบุมาแล้วจากข้อ 3 (โทนสี/สไตล์/path ของภาพ)
   - บริบทว่านี่คือ session สนทนากับผู้ใช้จริง คำถามที่ subagent ถามจะไปถึงผู้ใช้ทันที
     ไม่ใช่ mock/สมมติคำตอบเอง

5. **รอผลลัพธ์**: ปล่อยให้ subagent สัมภาษณ์และขอยืนยันแผนเอง **อย่าตอบแทนผู้ใช้**

6. **คำนวณคอนทราสต์ยืนยันด้วยตัวเอง (บังคับ — subagent ทำเองไม่ได้)**:
   subagent ไม่มีเครื่องมือคำนวณ จึงเขียนได้เพียง "เป้าหมายที่ต้องผ่าน" เท่านั้น
   **ผู้เรียกใช้ skill นี้ต้องคำนวณอัตราส่วนคอนทราสต์จริงตามสูตร WCAG ของทุกคู่สีที่ subagent
   รายงานมา** แล้วเทียบกับเป้าหมายที่เอกสารประกาศไว้
   - ถ้ามีค่าใด **ไม่ผ่าน** → **แก้ค่าสีให้ผ่าน อย่าแก้ตัวเลขเป้าหมายให้ต่ำลงเพื่อให้ผ่าน**
     เพราะเป้าหมายมาจากข้อจำกัดการใช้งานจริง ไม่ใช่ตัวเลขที่ตั้งไว้ลอยๆ
   - อัปเดตค่าที่คำนวณได้จริงลงในเอกสารแทนคำว่า "ต้องผ่าน ≥ X" เพื่อให้คนอ่านรอบหน้าตรวจสอบได้
   - รายงานให้ผู้ใช้ทราบทุกจุดที่ต้องแก้ **อย่าเงียบ** เพราะเป็นสัญญาณว่าจานสีที่เลือกไว้
     มีข้อจำกัดที่ผู้ใช้ควรรู้

7. **ตรวจสอบผลลัพธ์ก่อนรายงาน**: สุ่มอ่าน `DESIGN.md` จริงอย่างน้อย 1-2 จุด ตรวจว่ามีครบทั้ง
   4 หัวข้อหลัก (Brand Identity & CI, Design Tokens, UI Components & Patterns, UX Guidelines
   & Rules) ทุก token มีค่าจริงและคำอธิบาย "ใช้เมื่อไร" และไม่มีชื่อ framework/library หลุดเข้าไป
   **ห้ามเชื่อรายงานของ subagent 100% โดยไม่ตรวจเอง**

8. **สรุปให้ผู้ใช้ทราบ**:
   - สร้างใหม่หรือเติมส่วนใด (path เต็ม) และมีหัวข้ออะไรบ้าง
   - โทนสี/สไตล์ที่ผู้ใช้เลือก และตัวเลือกอื่นที่ถูกเสนอไป
   - **ผลการคำนวณคอนทราสต์ และค่าสีที่ต้องแก้เพราะไม่ผ่าน (ถ้ามี)**
   - สิ่งที่ยังไม่ตัดสินใจ (เช่น ชุดไอคอน โลโก้) และควรกลับมาเติมเมื่อใด
   - **ถ้ามี Prototype อยู่แล้วใน `01-prototypes/` และ `DESIGN.md` เพิ่งถูกแก้ในรอบนี้**
     ให้แจ้งว่า Prototype เดิมอาจไม่ตรงกับ token ใหม่แล้ว พร้อมแนะนำให้รัน `/build-prototype`
     ต่อ — **แต่ห้ามรันเองอัตโนมัติ** เพราะการสร้าง prototype ต้องยืนยัน scope กับผู้ใช้ก่อนเสมอ

## ข้อควรระวัง

- ห้ามข้ามการเรียก subagent แล้วเขียน `DESIGN.md` เองตรงๆ ในเทรดหลัก — subagent คือแหล่ง
  ความจริงเดียวของกฎการสัมภาษณ์และโครงสร้างเอกสาร
- **Subagent ต้องสัมภาษณ์ผู้ใช้และขอยืนยันแผนก่อนเขียนไฟล์จริงเสมอ** ถ้าผลลัพธ์แสดงว่า subagent
  เขียนไฟล์โดยกำหนดโทนสีเองโดยไม่ถามเลย ให้ถือว่าผิดกฎ หยุดและแจ้งผู้ใช้ทันที
- **ทุกคำถามที่ถามผู้ใช้ต้องมีอย่างน้อย 3 ตัวเลือก พร้อมข้อดี-ข้อเสียของแต่ละตัวเลือก และระบุ
  ตัวเลือกที่แนะนำพร้อมเหตุผล** — ใช้กับทั้ง subagent และคำถามที่ skill นี้ถามเอง
- Subagent แก้ได้เฉพาะ `DESIGN.md` และ log ของวันนั้น หากผลลัพธ์พูดถึงการแก้ไขไฟล์อื่น
  (โดยเฉพาะ `feature-list.md`, `user-journey.md`, `backlog.md`, ไฟล์ใน `01-prototypes/`)
  ให้หยุดและแจ้งผู้ใช้ทันที
- **ห้ามให้ subagent ประดิษฐ์โลโก้หรือชื่อแบรนด์ขึ้นเอง** ถ้าผู้ใช้ยังไม่มี ให้บันทึกไว้ในหัวข้อ
  "สิ่งที่ยังไม่ตัดสินใจ"
- ถ้าผู้ใช้ขอสไตล์ที่ขัดกับข้อจำกัดด้านความปลอดภัย/การอ่านออกของผลิตภัณฑ์ (เช่น อยากได้สีจาง
  ทั้งระบบ ทั้งที่ผู้ใช้งานจริงอ่านหน้าจอกลางแดด) ให้ทักท้วงพร้อมเหตุผลและเสนอทางออกที่ได้ทั้ง
  สองอย่าง แต่ถ้าผู้ใช้ยืนยันหลังรับทราบแล้ว ให้ทำตามและบันทึกข้อกังวลไว้ในเอกสาร
- ถ้า subagent รายงานว่าหาโฟลเดอร์ `docs/02-design/` ไม่เจอ อย่าให้ subagent สร้าง/เดาชื่อ
  โฟลเดอร์เอง ให้ผู้ใช้เข้ามาตรวจสอบโครงสร้างจริงก่อน
