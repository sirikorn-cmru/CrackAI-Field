# Sync Technical Spec (Orchestrator)

Skill นี้รันเอกสารเชิงเทคนิคทั้ง 4 ชั้นต่อเนื่องในคำสั่งเดียว ตามลำดับ:
`architecture.md` → `api-spec.md`/`db-spec.md` → `detailed-design/` → `nfr-review.md`
ทั้งหมดเขียนแบบ**ไม่ผูกมัดกับ technical stack** (logical/conceptual) จนกว่า
`technology-stack.md` จะถูกตัดสินใจ

**รันตามลำดับชั้นเสมอ ไม่ใช่รันขนาน** เพราะแต่ละชั้นต้องใช้ผลลัพธ์ที่อัปเดตล่าสุดของชั้นก่อนหน้า
เป็นแหล่งความจริง

ชั้น `nfr-review.md` เป็นชั้นเดียวที่ **ตรวจสอบและรายงานเท่านั้น ไม่แก้เอกสารที่ตรวจ** (agent
`nfr-reviewer` เป็น report-only) — แต่ **skill นี้มีหน้าที่ปิดช่องว่างที่มันพบให้ต่อ** ตามข้อ 11
ไม่ใช่รายงานทิ้งไว้ให้ผู้ใช้ไปสั่งเอง

**Orchestrator ต้องอยู่ในเทรดหลัก ห้ามยกไปเป็น subagent** — ทุกชั้นอาจต้องถามผู้ใช้ผ่าน
`AskUserQuestion` และ subagent ในโปรเจกต์นี้ถามผู้ใช้ไม่ได้ ถ้ายก orchestrator ไปอยู่ใน subagent
ทั้งสายจะเดาแทนผู้ใช้ทันที ซึ่งขัดกฎการถามใน `CLAUDE.md`

## เมื่อถูกเรียกใช้

1. **หาวันที่ปัจจุบัน**: รูปแบบ `YYYYMMDD` เพื่อส่งต่อให้ทุกชั้น

2. **รับขอบเขตจากผู้ใช้ (ถ้ามีการระบุ)**: ผู้ใช้จำกัดขอบเขตได้ เช่น เฉพาะฟีเจอร์ใดฟีเจอร์หนึ่ง
   หรือเฉพาะ FR บางรหัส — ถ้าไม่ระบุ ให้ถือว่าครอบคลุมทั้งระบบ **ส่งขอบเขตเดียวกันนี้ต่อให้ทุกชั้น**
   และ**ถ้าขอบเขตถูกจำกัด ต้องรายงานท้ายงานว่าอะไรยังไม่ถูกครอบคลุม**

3. **สำรวจสถานะจริงก่อนเริ่ม (ทำครั้งเดียว ใช้ได้ทั้ง 4 ชั้น)**: ตรวจด้วยเครื่องมือในเทรดหลัก
   ว่า `technology-stack.md` มีไฟล์หรือยัง, จำนวนรหัสใน `backlog.md`, จำนวนฟีเจอร์ใน
   `feature-list.md`, จำนวน journey ใน `user-journey.md`, จำนวน operation/entity ปัจจุบัน,
   จำนวนไฟล์ใน `detailed-design/` และไฟล์ log ของวันนี้มีอยู่แล้วหรือยัง (ถ้ามีแล้วต้องสั่งให้
   append ห้ามเขียนทับ) — **ส่งข้อมูลชุดนี้ไปกับ prompt ของทุกชั้น** เพื่อไม่ให้แต่ละชั้นเสียเวลา
   สำรวจซ้ำและไม่ให้เดาตัวเลขผิด

### ชั้นที่ 1 — architecture

4. เรียกผ่าน **Skill tool** ด้วย `skill: sync-architecture` (ไม่เรียก subagent
   `architecture-writer` ตรงๆ เพราะ skill นั้นมี auto-chain ไป `requirement-writer` ในตัว)
   รอผลลัพธ์ก่อนไปขั้นตอนถัดไปเสมอ

5. **ตรวจผลชั้นที่ 1 และสรุป "สิ่งที่เปลี่ยน"**: อ่าน `architecture.md` จริงอย่างน้อย 1 จุด
   แล้ว**บันทึกเป็นรายการสิ่งที่เปลี่ยนในชั้นนี้** (component ใหม่/ที่หายไป, data flow ที่แก้,
   ข้อผูกมัดใหม่ที่กระทบชั้นล่าง เช่น สิ่งที่ต้องบันทึกเป็นประวัติ หรือสถานะที่ต้องกันไม่ให้ไหลเข้า
   รายงาน) ถ้าไม่มีอะไรเปลี่ยน ให้บันทึกว่า "up to date ไม่มีส่วนต่าง" ถ้าพบปัญหาเชิงโครงสร้างที่
   ทำให้ตรวจต่อไม่ได้ **ให้หยุดทันทีและรายงานผู้ใช้**

### ชั้นที่ 2 — API + DB spec

6. เรียกผ่าน Skill tool ด้วย `skill: sync-api-db` **ต้องรอชั้นที่ 1 เสร็จก่อนเสมอ**
   **ส่งรายการสิ่งที่เปลี่ยนจากข้อ 5 ไปด้วยเสมอ** พร้อมชี้จุดที่น่าจะกระทบ api/db เป็นพิเศษ —
   ชั้นล่างจะได้ตรวจตรงจุดแทนการไล่อ่านใหม่ทั้งหมด

7. **ตรวจผลชั้นที่ 2 และสรุป "สิ่งที่เปลี่ยน"**: อ่าน `api-spec.md`/`db-spec.md` จริงอย่างน้อย
   1 จุด บันทึก operation/entity/attribute/ค่า enum ที่เพิ่ม-ลบ-แก้ และผลข้างเคียงใหม่ที่
   operation ระบุว่าต้องเกิด

### ชั้นที่ 3 — Detailed Design

8. เรียกผ่าน Skill tool ด้วย `skill: sync-detailed-design` **ต้องรอชั้นที่ 2 เสร็จก่อนเสมอ**
   **ส่งรายการสิ่งที่เปลี่ยนจากข้อ 7 ไปด้วยเสมอ** พร้อมระบุว่าไฟล์ใดใน `detailed-design/`
   น่าจะกระทบ เพื่อให้ชั้นนี้ไม่ต้องเปิดอ่านครบทุกไฟล์โดยไม่จำเป็น

9. **ตรวจผลชั้นที่ 3**: อ่านไฟล์ที่ถูกแก้จริงอย่างน้อย 1 จุด

### ชั้นที่ 4 — NFR Review (report-only)

10. เรียก subagent `nfr-reviewer` ผ่าน Agent tool (`run_in_background: false`) **ต้องรอชั้นที่ 3
    เสร็จก่อนเสมอ** **ส่งรายการสิ่งที่เปลี่ยนของทั้ง 3 ชั้นไปด้วย** และระบุจุดที่ควรตรวจเป็นพิเศษ
    ตามสิ่งที่เปลี่ยน — ถ้าผลลัพธ์แสดงว่ามันแก้/สร้างไฟล์ใดๆ นอกจาก `nfr-review.md`/log
    **ให้ถือว่าผิดกฎ หยุดและแจ้งผู้ใช้ทันที**

### ปิดช่องว่างที่ชั้นที่ 4 พบ (หัวใจของการทำงานต่อเนื่อง)

11. **ถ้า `nfr-review.md` รายงาน NFR ที่ "รองรับบางส่วน" หรือ "ยังไม่รองรับ"** และช่องว่างนั้นชี้ชัด
    ว่าต้องแก้ที่ชั้นใด **ให้ปิดต่อทันทีโดยไม่ต้องถามผู้ใช้ก่อน** — แจ้งผู้ใช้สั้นๆ ว่ากำลังปิด
    ช่องว่างอะไร แล้ว:
    a. เรียก skill ของชั้นที่เกี่ยวข้องซ้ำ (`sync-architecture` / `sync-api-db` /
       `sync-detailed-design`) โดย prompt **ต้องระบุขอบเขตแคบเฉพาะช่องว่างนั้น** และกำชับว่า
       ห้ามแก้เรื่องอื่น ห้ามจัดรูปแบบใหม่
    b. เรียก `nfr-reviewer` อีกครั้ง **โดยจำกัดขอบเขตให้ตรวจซ้ำเฉพาะ NFR ที่เพิ่งแก้** พร้อมสั่ง
       ให้เก็บประวัติการขึ้น-ลงสถานะไว้ในเอกสาร ไม่ใช่ลบทิ้งเหมือนไม่เคยเกิด (ห้ามให้มันตรวจ NFR
       ข้ออื่นใหม่ทั้งหมด เปลืองโดยไม่จำเป็นและเสี่ยงแก้ผลที่ถูกอยู่แล้ว)
    c. **ป้องกัน infinite loop: ทำซ้ำได้อีกไม่เกิน 1 รอบ** ถ้ายังปิดไม่ได้ ให้หยุดและรายงานผู้ใช้
       ตรงๆ ว่าเหลือช่องว่างอะไรและทำไมปิดไม่ได้ในรอบเดียว
    d. **ข้อยกเว้นที่ต้องถามผู้ใช้ก่อน**: ถ้าการปิดช่องว่างต้องตัดสินใจเชิงออกแบบที่ตัดสินแทนไม่ได้
       (เช่น ต้องเลือกระหว่างสองแนวทางที่แลกกันคนละอย่าง) ให้ถามผู้ใช้ตามกฎ ≥3 แนวทางพร้อม
       ข้อดี/ข้อเสีย ตัวแรกแนะนำ ก่อนสั่งชั้นล่างแก้

12. **ถ้าช่องว่างที่พบเกิดจากการแก้ในรอบนี้เอง (regression)** ให้ระบุไว้ชัดเจนในรายงานว่าเป็น
    regression ของรอบนี้ ไม่ใช่ของเก่า — ข้อมูลนี้สำคัญต่อการเชื่อถือผลลัพธ์ของ pipeline

13. **สรุปผลรวมทั้งสายเป็นรายงานเดียว** แยกตามชั้น: architecture · api-spec/db-spec ·
    detailed design · nfr-review (จำนวน NFR ที่รองรับแล้ว/บางส่วน/ยังไม่รองรับ) พร้อม:
    - สิ่งที่เปลี่ยนจริงในแต่ละชั้น และชั้นใดที่ "up to date ไม่ต้องแก้"
    - ช่องว่างที่ปิดไปแล้วในข้อ 11 และช่องว่างที่ยังเหลือ (ถ้ามี) พร้อมคำแนะนำว่าควรรันอะไรต่อ
    - **สิ่งที่ยังไม่ถูกครอบคลุม** — โดยเฉพาะสายงานอื่นที่อาจต้องตามด้วย (เช่น ถ้าค่า enum หรือ
      กฎ validation เปลี่ยน เอกสารทดสอบใน `03-testing/` อาจต้องตาม ให้แนะนำ `/sync-test-plan`)

## ข้อควรระวัง

- **ต้องรันทั้ง 4 ชั้นตามลำดับเสมอ ห้ามรันขนาน ห้ามข้ามชั้น** แม้ผู้ใช้จะถามถึงแค่ปัญหาชั้นปลาย
  (เช่น "NFR ตัวนี้รองรับหรือยัง") — ชั้นที่ไม่มีอะไรเปลี่ยนจะจบเร็วเองอยู่แล้ว
- **ถ้าชั้นใดเพิ่งถูก sync ไปในเซสชันเดียวกันและไม่มีอะไรเปลี่ยนตั้งแต่นั้น** ยังต้องรันชั้นนั้น
  แต่ให้ระบุในprompt ว่าเป็นการ**ตรวจยืนยัน** และห้ามเขียนซ้ำ/จัดรูปแบบใหม่โดยไม่มีส่วนต่างจริง
- ห้ามข้ามการเรียก skill/subagent แล้วแก้ไฟล์เองตรงๆ ในเทรดหลักไม่ว่าชั้นใด
- แต่ละ skill ย่อยมี loop guard auto-chain ไป `requirement-writer` ของตัวเองอยู่แล้ว ไม่ต้องทำซ้ำ
  ในชั้นนี้ — loop guard ในข้อ 11 เป็นคนละตัวและนับแยก
- ถ้า skill/subagent ตัวใดรายงานปัญหาเชิงโครงสร้าง ให้หยุด pipeline ทันที ไม่ไปชั้นถัดไป แล้ว
  รายงานปัญหานั้นให้ผู้ใช้ก่อนเสมอ
- ทุกเอกสารในสายนี้ต้อง**ไม่ระบุชื่อ technology/framework/database engine/HTTP method/SQL type
  ใดๆ** จนกว่า `technology-stack.md` จะถูกตัดสินใจแล้วจริง ถ้าพบหลุดเข้าไปในรายงานของ subagent ใด
  ให้ถือว่าผิดกฎ หยุดและแจ้งผู้ใช้ทันที
- **สายนี้ยาวและเคยถูกตัดกลางคันจาก API error มาแล้ว** — หลังจบแต่ละชั้น ให้สรุปสั้นๆ ให้ผู้ใช้เห็น
  ว่าชั้นนั้นได้อะไร ก่อนเริ่มชั้นถัดไป เพื่อให้งานที่ทำไปแล้วไม่หายไปพร้อมกับ context ถ้าถูกตัด
  และถ้าอยู่ในสภาพแวดล้อมที่ commit ได้ ให้ commit เป็นจุดตรวจก่อนเริ่มชั้นที่ยาวที่สุด
